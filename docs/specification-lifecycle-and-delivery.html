Specification Lifecycle & Delivery

The governance contract for a specification, from creation through delivery. Arke governs the specification; git delivers the code. The specification's markdown is the single source of truth for its governed state — so every transition is a gated operation, and git is an optional accelerator, never a prerequisite.

1 · The one principle

The markdown is the source of truth. Everything else is a projection.

Every feature is exactly one specification.md, authored on its branch, reviewed, and approved. Tickets, board cards, tests, and tracking are generated from that file — never edited beside it.

Corollary — the load-bearing rule

A specification's governed state lives in one place: the status: field of its frontmatter. The delivery board, the audit trail, and every downstream artifact are read-only projections of that field plus live session / CI state. A card moves because a governed operation ran and passed its gate — never because a person dragged pixels, and never because a client wrote a column.

Two consequences follow, and they are the whole reason this document exists:

  • State changes must be authoritative. Whoever can write status: controls delivery. That write must therefore be gated — a completed review, a well-formed document, a non-author human — not a free edit.
  • The projection must be faithful. One specification is one unit of work and therefore one card. Anything that mints extra cards (e.g. a harness session appearing as its own row) is a projection defect, not new work.
2 · Two tracks

Arke governs the specification; git delivers the code

The lifecycle is two linked but separable tracks. Keeping them separate is what makes the system usable with or without a configured git host.

Track 1 — Governance

Owned by Arke

draft → in-review → approved → delivered, persisted in the frontmatter status: and moved only by gated coordinator ops. This is the WHAT — the agreed change. It works with zero git configuration.

Track 2 — Delivery

Tracked through git

Once a spec is approved, git + agent activity is the live telemetry of turning it into code: agent implementing → branch in PR → PR merged. The board projects this; it never invents spec status.

The handshake The merge is the single git event permitted to write back into governance: it flips approved → delivered and flattens the deltas. Everything from approved up to that merge is read-only projection — git does not dribble into the frontmatter at every push.

Graceful degradation. "Agent implementing" is Arke-native (the coordinator's own harness session) and is visible with no git host at all. Only "branch in PR" and "PR merged" genuinely need git — and host-less, delivered is reached by a local branch merge the coordinator performs instead of a PR merge. Nothing goes dark.

4 · Two vocabularies — do not conflate them

Spec status (4) vs. board columns (7)

The single most common confusion — and a direct cause of the board looking "broken" — is treating board columns as if they were spec statuses. They are not.

A · Spec status — authored, governed, four values

draft
Being authored on its branch.
in-review
Complete enough to critique; a panel has run.
approved
Agreed by a non-author human. A stable resting state — the backlog.
delivered
Terminal. Code merged to the mainline; deltas flattened into current truth.

These live in status:. They move only through gated ops (triggered by a human or a webhook — §5), never by hand. Note delivered means landed on the mainline as current truth, not "deployed to production" — deployment, if ever modelled, is a separate axis.

B · Board columns — a live projection, seven lanes

The board combines spec status with live session state and CI / PR state to place a card. Three of its columns are not spec statuses at all — they describe what the harness is doing to an approved spec:

Implementinga task session is running against an approved specno — session-derived

Rule Column precedence is computed per card: an open human gate wins → else a running / finished delivery session → else the spec's status. One specification yields exactly one card that walks these lanes. Sessions fold into that card; they are never cards of their own.
5 · The unifying rule

One op, two triggers

A card moves only when a governed transition op runs and passes its gate. The op writes status: (single write path). The trigger can be a git-host webhook or a human — neither bypasses the gate.

Trigger A — automated

When a git host is configured, PR / review / merge webhooks fire the same ops automatically. Branch protection and CI harden the gates. This is the target steady state.

Trigger B — human

A person invokes the transition from the board or cockpit (§8). Same op, same gate. Used when no host is configured, and always available as an override.

Why this matters Because both triggers call the same op, adopting a git host later requires no rework — the manual path and the automated path were always the same gated write. The git host is an accelerator layered on an Arke-native governance core, not a dependency.
6 · The flow, end to end

Create → author → review → approve → (later) deliver

Reading the diagram. The top lane is governed — the four values that live in the markdown and move only through gated ops. approved is a home, not a doorway: a spec rests there in the backlog until someone explicitly chooses to deliver it. The bottom lane is the delivery effort — started on demand, on any branch, whenever — projecting implementing / diff review over the still-approved spec. The dashed reopen edge is the reversibility rule.

7 · The gates

What SHALL be true at each transition

Each transition names a legitimate trigger and the preconditions that MUST hold. The gate is identical whether the trigger is a human or a webhook. Anything else is rejected with a named error and logged to the audit trace.

Non-normative edits do not regress. — (automatic, reversible)

The review-panel gate, precisely

  • At least two reviewers, resolving to pairwise-distinct concrete models — two roles on the same model is rejected.
  • Reviewers are read-only (edit: deny, bash: deny), grounded in source, and blind to each other.
  • "Complete" = panel.complete {status:"complete"} plus human adjudication (accept / dismiss / send-back). One reviewer erroring does not abort; all erroring yields a failed panel that does not satisfy the gate.
  • Gate state is reconstructed from the durable trace on restart — not in-memory only.
8 · Host-optional & safe manual moves

Letting the human move the board — without breaking the gate

When no git host is configured, or as a deliberate override, a human moves a card. A manual move is not a raw status: write — it is the human acting as the trigger for the same gated op a webhook would fire.

  1. The drag dispatches the op, not the column. Dropping a card into the next lane calls the transition op (e.g. approve), which runs its full gate. Fail the gate → the move is rejected with the reason. The projection stays read-only; the human only triggered a governed write.
  2. Only legal adjacent transitions are offered — you may drop into the next valid lane, never an arbitrary jump.
  3. Confirmation shows the write — "This sets status: approved and commits to spec/x, attributed to you." Deliberate, not accidental.
  4. Every manual move is a first-class audit event — spec.status { reason:"manual", actor, from → to }. The difference between manual and webhook-driven is always visible in the trace.
  5. Host-independent gates still fire — the review panel and well-formedness checks apply whether the trigger is a human or a webhook.
The one honest trade-off — the "second human" Only one gate genuinely needs an identity system: approver ≠ owner. Today that identity comes from the git host. Host-less, Arke shows a governance-level badge on the board and behaves in one of two modes: team (an in-app approver identity distinct from the owner is required) or solo (self-approval is permitted but explicitly flagged and audited — "approved by owner, no independent reviewer"). No one should mistake solo-mode assurance for host-enforced assurance.
9 · Delivery is explicit

Approve now, deliver later — on any branch

Approval agrees the WHAT. It must not dictate the WHEN. So:

  • The Approved lane is the backlog. Approved-but-unbuilt specs live in the library (merged to main at approval), browsable and prioritisable — a real backlog, not cards stranded on rotting feature branches.
  • A spec is identified by spec_id, not its branch. That is exactly what lets delivery happen later, off main, on a fresh branch — its own, or one you name to bundle with other work.
  • Deltas stay tagged as "pending delivery" on an approved-but-undelivered spec, and flatten only at delivered. This keeps current truth honest: the library shows the spec is agreed, but not that the capability is built, until it is.
  • Roll-up: one branch, one PR, one completion. Parallel task worktrees roll back into the single delivery branch; the one feature → main merge is the unambiguous "spec delivered" signal.
Edge to name later A spec can rest at approved indefinitely. If a spec is decided against rather than pending, a future superseded / withdrawn terminal will keep the backlog free of zombies. Out of scope for now — approved cleanly covers "waiting."
10 · Invariants & restrictions

The things that SHALL NOT happen

  • No ungoverned state changes. status is written only by a gated op. A hand-edited status: that bypasses the coordinator is a divergence, surfaced as a warning — never honoured as a transition.
  • No raw column writes. The board column is a read-only projection; a drag triggers a gated op, it never sets a column. No column field is ever written from the client.
  • No self-approval. The approver's identity SHALL NOT equal the spec's owner — enforced at the coordinator and (host mode) at branch protection; flagged-and-audited in solo mode.
  • One specification per active branch. The branch guard ties every approval to HEAD == branch; delivery runs on one branch that merges once.
  • One specification → one card. Harness sessions fold into their spec's card; a session is never a top-level card.
  • Single write path. All writes to docs/specifications/ flow through the coordinator / harness adapter. The client renders a read-only preview and never holds a separate authoritative copy.
  • No advance out of draft for a malformed spec. Required anatomy (SHALL statements, WHEN/THEN scenarios, mandated sections) must be present before promotion.
  • Git is optional. No governed transition may require a git host to exist — the host only automates and hardens what Arke can already do.
11 · Deltas & flatten-on-deliver

How a spec versions itself

While a change is in flight, each affected requirement carries a delta tag, e.g. delta: ADDED (feat/x). The vocabulary is closed:

TagMeaningOn deliver (flatten)
ADDEDNew requirement.Drop the tag; it becomes current truth.
MODIFIEDChanged behaviour — write the full updated requirement, not a diff.Drop the tag.
REMOVEDGoing away — keep a tombstone.Cut the body; leave a ## Removed tombstone with Reason + Migration.
RENAMEDName-only change; note FROM/TO.Apply in place.

Flatten runs at delivered (the merge handshake), is idempotent (flatten-started / -complete trace markers), appends one Change-history line, and never invents content. Per-capability "current truth" is a generated, read-only roll-up — never authored by hand — and reflects delivered capabilities, not merely approved ones.

12 · Conformance & current gaps

Where the implementation must be tightened

The contract above is largely already specified. This section is the honest delta between it and today's code — the work this document authorises. The broken delivery board (raw ses_… ids showing as duplicate cards) is the visible symptom of the first two rows.

RuleTodayGap & where it livesFix direction
One spec → one card broken Cards are minted per session: session.status calls ensureCard(sessionId,…), so a real harness session (ses_…) becomes its own card next to the spec card. The design assumed sessionId === specId, which only holds in the mock. read-model.ts:87 · live.ts:196 Fold sessions into the spec's card via specId; never emit a session-keyed top-level card.
Faithful session↔spec linkage broken The link is the session title with a raw-id fallback: specId: s.title ?? s.id. When the title doesn't encode the spec id, the card's id, title and specId are all the same raw ses_… string. normalize.ts:135 Resolve specId from the active spec, not the title; an unlinkable session is attached-or-dead-lettered, never its own spec.
Delivery is explicit (no auto fan-out) coupled Reaching approved currently triggers fanOut immediately, so "approve now, deliver later" is impossible and the Approved lane can't act as a backlog. project-context.ts:712 Decouple: approved rests. Add an explicit Deliver op that records a delivery branch and starts fan-out.
One gated door to in-review two doors The strict path approveDraft enforces panel + branch guard. But spec.promote flips draft → in-review after only checking status === "draft" — no review, no authority, no validation. project-context.ts:763 vs 1148 Route all promotion through the gated path; remove or gate spec.promote.
Well-formedness before promotion missing Nothing validates required anatomy before promotion. parseSpecDoc marks sections present:false but no gate reads it. spec.ts (SPEC_ANATOMY) Add a promotion precondition rejecting a malformed spec (spec.malformed) with the reason surfaced in the cockpit.
delivered terminal + flatten rename The terminal state is currently merged, coupling governance vocabulary to a git verb. spec.ts (SpecStatus) · spec-lifecycle.ts Rename the enum merged → delivered; keep flatten at the merge handshake; update the column + webhook map.
Manual moves + governance level missing No human-triggered transition path or governance-level badge; the board assumes webhooks it may never receive if no host is configured. board-session-diff-permission.tsx Add gated manual-move ops (dispatch the op, not the column) + a host-configured / solo / team badge.
Self-approval / branch guard / material-change enforced Fail-closed self-approval, branch-mismatch rejection, normative-hash regression already hold. spec-lifecycle.ts Keep; add tests that pin each gate.
Bottom line The lifecycle is well-specified but has a handful of implementation holes — the session→card projection, the ungated spec.promote door, no well-formedness gate, delivery coupled to approval, and no host-optional manual path. Closing them is what makes "the markdown drives the state" safe to rely on — and fixes the board at the same time, because the board is only ever a mirror.
