# HTML specifications alongside markdown — a format-dispatched spec pipeline

## Why

Arke's specification pipeline assumes markdown everywhere: sections are split on `##` headings, requirements
on `### Requirement:`, scenarios on `#### Scenario:`, and the file discovery filters `*.md`. Some teams
author specifications as **HTML** — richer inline formatting, embedded diagrams/tables, or an existing HTML
docs toolchain. Today such a file is invisible to Arke (the `.md` filter drops it) and unparseable (the
heading regexes don't match HTML tags). This specification makes the pipeline **format-aware**: a spec may be
authored as `.md` or `.html`, and every stage — discovery, parsing, the well-formedness gate, the lifecycle
writes, and the cockpit preview — handles both. The specification stays the single source of truth (rule 1);
only its serialisation format is new.

The design is deliberately **minimal-fork**: the mapped pipeline shows that the YAML frontmatter, the
normative text-checks (SHALL/MUST, WHEN/THEN), the delta/capability tokens, `normativeHash`, `parseLinkage`,
and `parseCapabilities` are already format-agnostic. Only *section/requirement discovery*, the *blank
template*, the *lifecycle body-edits* (change-history append, delta-flatten), and the *client renderer* are
markdown-specific. So this spec adds an HTML parse path for exactly those, sharing everything else.

## What changes

- ADDED spec-format — a specification's **format** is detected from its file extension (`.md`/`.markdown` →
  `markdown`; `.html`/`.htm` → `html`); a single spec is one format. `parseSpecDoc` becomes
  format-dispatched: it extracts the same logical sections/requirements from either serialisation, so every
  downstream consumer (well-formedness gate, `normativeHash`, the cockpit preview, the library) is unchanged
  in shape.
- ADDED spec-format — an HTML spec carries its YAML frontmatter in a **leading HTML comment**
  (`<!--arke … -->`), keeping the file valid, browser-renderable HTML while the same YAML parser reads it.
- MODIFIED authoring-cockpit — spec discovery includes `.html` files at every discovery site (library,
  grounding, the docs watcher, the OKF bundle predicate); the cockpit preview renders an HTML spec through a
  **new sanitising HTML renderer** and a markdown spec through the Markdown renderer; the raw view is
  unchanged for both. `spec.create` accepts an optional `format` (default `markdown`) and writes the matching
  blank template; `spec.deliver` on an HTML spec is refused with a typed error in v1 (delivery task-parsing is
  markdown-coupled — a bounded follow-up).
- MODIFIED spec-lifecycle — the body-editing lifecycle writes (`setFrontmatterStatus`, `setFrontmatterField`,
  `appendChangeHistory`, `flattenDeltaTags`) are format-dispatched so status advances, change-history lines,
  and merge-time delta flattening work on an HTML spec exactly as on a markdown one. *(breaking: no — every
  existing markdown spec parses and lifecycles byte-identically; the markdown path is untouched.)*

## Requirements

### Requirement: A specification's format is detected and every parse dispatches on it
`capability: spec-format` · `delta: ADDED (feat/spec-036-html-specifications)`

The system SHALL determine a specification's **format** from its filename extension — `.md`/`.markdown` →
`markdown`, `.html`/`.htm` → `html` — and `parseSpecDoc` SHALL dispatch on it, returning the SAME
`ParsedSpecDoc` shape (frontmatter, requirements, anatomy sections) regardless of format, so no downstream
consumer changes. A file with an unrecognised extension SHALL be treated as `markdown` (the safe default,
preserving today's behaviour). Format detection SHALL be a pure function of the filename, never of content
sniffing, so it is stable and cheap on the discovery hot path.

#### Scenario: A markdown spec parses exactly as before
- **WHEN** `parseSpecDoc` is given the text of a `.md` spec
- **THEN** it returns the identical frontmatter, requirements, and sections it returns today
- **AND** no markdown-path behaviour changes

#### Scenario: An HTML spec parses into the same logical shape
- **WHEN** `parseSpecDoc` is given the text of a `.html` spec with the equivalent content
- **THEN** it returns the same anatomy sections (Why, Requirements, Design, …) and the same requirement list
  (title, capability, delta) as the markdown equivalent would

#### Scenario: An unknown extension defaults to markdown
- **WHEN** a spec file has neither a markdown nor an html extension
- **THEN** it is parsed as markdown (no regression for any existing file)

### Requirement: An HTML spec carries YAML frontmatter in a leading comment
`capability: spec-format` · `delta: ADDED (feat/spec-036-html-specifications)`

An HTML specification SHALL carry its frontmatter as a `---`-fenced YAML block inside a **leading HTML
comment** at the head of the file (`<!--arke\n---\n…\n---\n-->`), so the file remains valid, directly
browser-renderable HTML while the SAME YAML frontmatter parser reads it.

The frontmatter parser SHALL detect the leading comment **from the content itself** — recognising a leading
`<!--arke` … `-->` block whether or not a `format` argument is supplied — and extract the fenced YAML from it,
then parse it with the existing flat-scalar + `parseLinkage` nested logic (no separate YAML implementation).
Content-based extraction is deliberate: many read-side callers (`normativeHash`, the OKF index generators, the
client preview) pass only text, not a filename, so a `format`-argument-only design would make every un-threaded
caller **silently mis-parse an HTML file as empty markdown** rather than fail loudly. `frontmatterInner` (the
second `---` gate used by `parseLinkage`) SHALL be forked the same way. A markdown spec's leading `---` fence
is unchanged, and CRLF handling (the Windows `autocrlf` fix already in the markdown scanner) SHALL apply to the
comment-wrapped YAML too. Frontmatter-field writes (`setFrontmatterStatus`, `setFrontmatterField`) SHALL edit
the YAML in place within the comment for an HTML spec, and within the `---` fence for a markdown spec.

#### Scenario: HTML frontmatter is read from the leading comment
- **WHEN** an HTML spec begins with a leading `<!--arke … --- … --- … -->` comment
- **THEN** its `spec_id`, `status`, `branch`, `owner`, `capabilities`, and `ripples`/`canonical` linkage parse
  exactly as a markdown spec's frontmatter does

#### Scenario: A status advance rewrites the HTML frontmatter comment, not the body
- **WHEN** an HTML spec is approved and its status is advanced to `in-review`
- **THEN** only the `status:` line inside the leading comment changes
- **AND** the HTML body is untouched and the file remains valid HTML

### Requirement: HTML section and requirement discovery mirrors the markdown anatomy
`capability: spec-format` · `delta: ADDED (feat/spec-036-html-specifications)`

For an HTML spec, section discovery SHALL find the anatomy sections by `<h2>` headings, requirements by an
`<h3>` heading whose text begins `Requirement:`, and scenarios by an `<h4>` heading whose text begins
`Scenario:` — the direct structural analogue of the markdown `##`/`### Requirement:`/`#### Scenario:` split —
producing the same `ParsedSection`/`ParsedRequirement` values. A requirement's `capability:` and `delta:`
tokens SHALL be read from the **tag-stripped text** of its block using the existing token logic (no backticks
required), so metadata authored as `<code>` or plain text both parse. Heading matching SHALL be:
tag-name case-insensitive (`<H2>` matches); attribute-tolerant (`<h3 id="x">` matches); tolerant of a heading
that spans lines and of inline tags inside it (`<h3>Requirement: <code>foo</code></h3>` yields the title
`Requirement: foo` — the title is itself tag-stripped and trimmed); and it SHALL NOT treat a heading-like
string inside a `<pre>`/`<code>` block or an HTML comment as a real section boundary.

#### Scenario: HTML headings map to the anatomy
- **WHEN** an HTML spec has `<h2>Requirements</h2>` followed by `<h3>Requirement: A thing</h3>`
- **THEN** the Requirements section is present and the requirement `A thing` is parsed with its capability and
  delta, identically to `## Requirements` / `### Requirement: A thing` in markdown

#### Scenario: Requirement metadata parses from tag-stripped text
- **WHEN** an HTML requirement block contains `capability: x · delta: ADDED (branch)` as text or inside a
  `<code>`/`<p>` element
- **THEN** its capability is `x` and its delta kind is `ADDED`

### Requirement: The well-formedness gate is format-agnostic once sections are extracted
`capability: spec-lifecycle` · `delta: MODIFIED (feat/spec-036-html-specifications)`

`validateWellFormed` SHALL operate on the format-dispatched `parseSpecDoc` output plus the **tag-stripped
text** of the Requirements section, so its three checks are unchanged in meaning for both formats: (a) a
non-empty Requirements section, (b) at least one SHALL/MUST statement, (c) at least one scenario containing
both a WHEN and a THEN. For an HTML spec the SHALL/MUST and WHEN/THEN word-checks SHALL run against text with
HTML tags removed, so inline markup (`The system <em>SHALL</em> …`) does not defeat the word-boundary match,
and scenarios SHALL be located by the `<h4>Scenario:` split.

Because the well-formedness gate is a **governance control**, `stripTags` SHALL NOT be a naive `<[^>]+>`
removal — it SHALL first drop the **text content** of `<script>`, `<style>`, and `<!-- comment -->` regions,
then decode a minimal HTML-entity set, and only then run the word-checks. Otherwise a draft could smuggle a
passing token in non-rendered content (e.g. `<script>const WHEN, THEN…</script>`) and clear the gate without a
visible scenario. The gate's error shape (`spec.malformed { missing }`) is unchanged.

#### Scenario: A well-formed HTML draft promotes
- **WHEN** an HTML draft has a Requirements section, a SHALL/MUST statement, and a WHEN/THEN scenario
- **THEN** `validateWellFormed` passes and promotion proceeds exactly as for a markdown draft

#### Scenario: A malformed HTML draft is rejected with the same error
- **WHEN** an HTML draft has requirements but no WHEN/THEN scenario
- **THEN** promotion is rejected with `spec.malformed` whose `missing` includes "scenarios"

#### Scenario: A token hidden in non-rendered content does not satisfy the gate
- **WHEN** an HTML draft's only WHEN/THEN tokens appear inside a `<script>` or `<!-- comment -->`, not in a
  visible `<h4>Scenario:` block
- **THEN** the gate treats it as missing scenarios and rejects it — the smuggled token does not count

### Requirement: Discovery, creation, and lifecycle body-edits handle both formats
`capability: authoring-cockpit` · `delta: MODIFIED (feat/spec-036-html-specifications)`

**Discovery** SHALL include `.html`/`.htm` files alongside `.md`/`.markdown` (still excluding the template and
generated `index.md`) at EVERY discovery site — not only `findSpecFile`/`specLibrary`/`isSpecFile`, but also
the grounding walk (`collectGroundingDocs`, `collectSpecIndexDigest`), the OKF bundle predicate
(`isBundleDoc`), and the **docs watcher** suffix test (`startDocsWatcher`, which today only reacts to `.md`,
so an HTML spec save would otherwise never regenerate the index or invalidate grounding). The grounding digest
helpers that read markdown structure (`firstH1`/`firstMeaningfulParagraph`) SHALL operate on the
format-dispatched parse (or tag-stripped text) so an HTML spec contributes real grounding, not an empty/`⚠`
entry.

**Creation.** `spec.create` SHALL accept an optional `format` (default `markdown`) and write the matching
blank template — a markdown skeleton or an HTML skeleton (leading-comment frontmatter + the equivalent
`<h2>`/`<h3>` structure). Two specs SHALL NOT share a number+slug across ANY spec extension: creation SHALL
reject when a `docs/specifications/<nnn>.<slug>.{md,markdown,html,htm}` already exists (not just the exact
extension being written), and `renameSpec`'s target-existence check SHALL widen the same way.

**Lifecycle body-edits.** `appendChangeHistory` and `flattenDeltaTags` SHALL be format-dispatched: for an HTML
spec they append a change-history entry under `<h2>Change history</h2>` (as an `<li>` in that section's list,
creating the section + list if absent) and flatten delta tokens within `<h3>Requirement:` blocks (idempotent;
a REMOVED requirement's tombstone lands under `<h2>Removed</h2>`, created if absent; the tombstone-dedup and
CRLF-strip logic of the markdown path carry over). `normativeHash` needs no change (it consumes the dispatched
`parseSpecDoc` output).

**Delivery.** `parseTasks` (which drives single-session delivery off `## Tasks` + `- [ ]` checkboxes) is
markdown-structural, so for v1 `spec.deliver` on an HTML spec SHALL be **refused with a typed error**
(`spec.deliver-unsupported-format`) guiding the author, rather than silently dispatching a delivery that would
parse zero tasks and never complete. HTML delivery (an HTML task/checkbox convention + a format-aware
implementer prompt) is a named follow-up. Authoring through approval is fully supported for HTML.

#### Scenario: The library lists an HTML spec
- **WHEN** `docs/specifications/` contains `042.thing.html`
- **THEN** it appears in the spec library with its frontmatter-derived status, title, and capabilities

#### Scenario: Creating an HTML spec writes the HTML skeleton on a fresh branch
- **WHEN** `spec.create { format: "html" }` runs
- **THEN** a `docs/specifications/<nnn>.<slug>.html` file is written from the HTML template with
  leading-comment frontmatter, on a new feature branch, and the cockpit opens on it

#### Scenario: Approval and change-history work on an HTML spec
- **WHEN** an HTML spec is approved
- **THEN** its status advances via the frontmatter comment and a change-history entry is appended under
  `<h2>Change history</h2>` (the section + list created if absent) — the same lifecycle as a markdown spec

#### Scenario: A cross-format number/slug collision is rejected at creation
- **WHEN** `spec.create` would write `042.thing.html` but `042.thing.md` already exists
- **THEN** creation is rejected — no two specs share a number+slug across extensions

#### Scenario: Delivering an HTML spec is refused with guidance in v1
- **WHEN** `spec.deliver` targets an HTML spec
- **THEN** it is refused with a typed `spec.deliver-unsupported-format` error naming HTML delivery as
  unsupported in v1, rather than dispatching a delivery that parses zero tasks

### Requirement: The cockpit preview renders each format natively, through a sanitising HTML renderer
`capability: authoring-cockpit` · `delta: MODIFIED (feat/spec-036-html-specifications)`

The cockpit's live preview SHALL render an HTML spec's section bodies through a **sanitising HTML renderer**
and a markdown spec's through the existing Markdown renderer, dispatched on the active spec's format; the
section/requirement outline (driven by the format-dispatched `parseSpecDoc`) is identical for both. The
**raw view** SHALL show the file text verbatim for both formats.

The sanitising HTML renderer is **NEW work — not reuse**: the current SPEC-032 `Markdown` component
(`packages/client/src/ds.tsx`) is `react-markdown` + `remark-gfm` with **no `rehype-raw`**, so today it
*drops* raw HTML rather than rendering it. This spec SHALL add a sanitised path — either `rehype-raw` +
`rehype-sanitize` (with a locked schema) on the `Markdown` component, or a dedicated `SafeHtml` component
(DOMPurify → `dangerouslySetInnerHTML`). It SHALL enforce an explicit allow-list: a bounded set of structural
tags (headings, paragraphs, lists, tables, `code`/`pre`, `em`/`strong`, `a`, `blockquote`), safe attributes
only, and URL schemes restricted to `http`/`https`/`mailto` (reusing the client's existing `safeHref` rule).
No active content — `<script>`, inline event handlers, `javascript:`/`data:` URLs, or external resource loads
— SHALL survive sanitisation or execute in the preview (NFR-1/5).

#### Scenario: An HTML spec renders as formatted, sanitised HTML in the preview
- **WHEN** the cockpit shows an HTML spec's Requirements section
- **THEN** the section renders as sanitised formatted HTML (headings, lists, tables intact), and the
  requirement outline matches the markdown equivalent's

#### Scenario: Active content is stripped, not executed
- **WHEN** an HTML spec's body contains a `<script>`, an `onclick=` handler, or a `javascript:` link
- **THEN** the preview renders the visible content with all active content removed, executing nothing

## Design

### Architectural decision

Introduce a `SpecFormat = "markdown" | "html"` detected purely from the filename, and make `parseSpecDoc` (and
the body-editing lifecycle writers) **dispatch** on it while everything downstream keeps operating on the
existing `ParsedSpecDoc`/`ParsedRequirement`/`ParsedSection` shapes. The mapped pipeline shows the fork is
small: only section/requirement *discovery*, the *blank template*, the *body edits* (change-history append,
delta flatten), and the *client renderer* are markdown-specific. Everything else — YAML frontmatter,
`parseLinkage`, `parseCapabilities`, `deltaKindOf`, the SHALL/MUST + WHEN/THEN word-checks, `normativeHash`
(which consumes parsed section text) — is reused unchanged. HTML frontmatter lives in a leading comment so the
file is browser-valid and the same YAML parser reads it.

### Target architecture

- **`packages/contracts/src/spec-doc.ts`** (the fork point):
  - `specFormatOf(filename): SpecFormat` — pure extension detection.
  - `parseSpecDoc(md, format?)` — auto-detects when `format` is omitted (defaults markdown); dispatches to
    `splitSectionsMd`/`splitSectionsHtml` and `parseRequirementsMd`/`parseRequirementsHtml`. The HTML variants
    are tag-based (`<h2>`, `<h3>…Requirement:`, `<h4>…Scenario:`, tag-name-case-insensitive, attribute- and
    inline-tag-tolerant, ignoring heading-like text inside `<pre>`/`<code>`/comments) and produce identical
    values; a hardened `stripTags(html): string` (drops `<script>`/`<style>`/comment CONTENT, decodes a
    minimal entity set) feeds the shared token + SHALL/MUST/WHEN/THEN logic and the requirement-title cleanup.
  - `parseFrontmatter(text)` + `frontmatterInner(text)` — **content-detect** a leading `<!--arke … -->` block
    (no `format` arg needed) and extract the fenced YAML, then reuse the existing flat scalar scan + `parseLinkage`;
    CRLF handling carries over.
  - `setFrontmatterStatus`/`setFrontmatterField`/`appendChangeHistory` — format-dispatched body edits (HTML
    change-history as an `<li>` under `<h2>Change history</h2>`, section+list created if absent).
  - `validateWellFormed(text, format?)` — dispatches section extraction, runs the same three checks on the
    hardened tag-stripped text.
  - `renderBlankSpecHtml(...)` — the HTML skeleton (leading-comment frontmatter + `<h2>`/`<h3>` structure)
    beside the existing markdown `renderBlankSpec`.
- **`packages/coordinator/src/spec-lifecycle.ts`**: `flattenDeltaTags(text, branch, date, format?)` + the
  delta-token strip dispatched by format (HTML tombstone under `<h2>Removed</h2>`); `normativeHash` unchanged.
- **`packages/coordinator/src/project-context.ts`**: extend `.html` discovery at **every** site —
  `findSpecFile`, `specLibrary`, `collectGroundingDocs`, `collectSpecIndexDigest`, and the `startDocsWatcher`
  suffix test — plus `isBundleDoc` in `okf-index.ts`; `createSpec(rawTitle, format?)` writes the matching
  template + extension with a cross-extension collision guard (and `renameSpec`'s target check widened);
  `spec.deliver` refuses an HTML spec with a typed error (v1). Read-side call sites need no format threading
  because frontmatter is content-detected and `parseSpecDoc` gets the format from the (available) filename.
- **`packages/client/src/screens/cockpit.tsx`** + **`ds.tsx`**: add a **sanitising HTML renderer** (new —
  `rehype-raw` + `rehype-sanitize` on `Markdown`, or a dedicated `SafeHtml` via DOMPurify, allow-list per the
  preview requirement); the preview dispatches on the active spec's format (via `file.path` → `specFormatOf`),
  markdown → the existing renderer; raw view unchanged.

### Interfaces and contracts

- `SpecFormat` + `specFormatOf` added to `@arke/contracts`.
- `parseSpecDoc` / `parseFrontmatter` / `validateWellFormed` / `appendChangeHistory` / `setFrontmatterStatus`
  gain an optional trailing `format?: SpecFormat` (back-compatible — omitted defaults to markdown, so no
  existing call breaks).
- `spec.create` op accepts `{ title?, format?: "markdown" | "html" }`.

### Cross-cutting

- **Security (NFR-1/5):** HTML spec bodies are **sanitised** before rendering (the SPEC-032 renderer strips
  active content); no script/handler/external-load executes in the preview. Frontmatter never contains
  resolved secrets (unchanged).
- **Determinism / lifecycle:** the markdown path is byte-for-byte unchanged (the format defaults to markdown
  when unspecified), so every existing spec parses, gates, and lifecycles identically — the new code is purely
  additive.
- **Design template:** the format toggle + HTML preview follow the `arke-design` skill
  (`.claude/skills/arke-design/`); the HTML blank template mirrors `specification.template.md`'s anatomy.

### Testing
- **Unit (contracts):** `specFormatOf` extension mapping; `parseSpecDoc` on an HTML spec yields the same
  sections/requirements as the markdown equivalent; HTML frontmatter (leading comment) parses incl.
  `ripples`/`canonical`; `validateWellFormed` on HTML (well-formed passes; missing scenario → `spec.malformed`;
  SHALL inside `<em>` still detected); `appendChangeHistory`/`setFrontmatterStatus` edit the right region of an
  HTML file; `flattenDeltaTags` on HTML requirement blocks (idempotent; REMOVED tombstone). Every existing
  markdown test stays green (defaults).
- **Integration (coordinator):** an HTML spec is discovered in the library; `spec.create { format: "html" }`
  writes the skeleton + branch; approveDraft advances an HTML spec's status via the comment and appends a
  change-history line under `<h2>Change history</h2>`; a cross-format collision at creation is rejected.
- **Manual:** author an HTML spec in the cockpit; the preview renders sanitised HTML with a working outline; a
  `<script>` in the body executes nothing; the raw view shows the file verbatim.

### Definition of done
A spec can be authored as `.md` or `.html`; both are discovered, parsed into the same anatomy, gated by the
same well-formedness rules, lifecycled (status, change-history, delta-flatten) identically, and rendered
natively (HTML sanitised) in the cockpit; the markdown path is byte-for-byte unchanged and every existing test
passes; `typecheck` + `build` green; a non-author reviewer has signed off.

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Format is detected from the file **extension**, not content sniffing | Cheap + stable on the discovery hot path; a spec is unambiguously one format; no heuristic mis-detection |
| 2 | `parseSpecDoc` **dispatches** and returns the same shape; downstream is unchanged | The mapped pipeline shows only discovery/template/body-edit/renderer are markdown-specific — everything else already operates on parsed text, so the fork is minimal and low-risk |
| 3 | HTML frontmatter lives in a **leading HTML comment**, **content-detected** (not by a `format` arg) | Keeps the file valid, browser-renderable HTML AND reuses the existing YAML + `parseLinkage` parser; content-detection means read-side callers that pass only text (`normativeHash`, the index generators, the preview) can't SILENTLY mis-parse an HTML file as empty markdown — the sharp edge of the "defaults to markdown" mechanism |
| 4 | The normative checks run on **hardened tag-stripped text** (script/style/comment content dropped, entities decoded) | The word-boundary checks are already format-agnostic; a naive strip would let a `<script>`-hidden token bypass the governance gate, so stripping must remove non-rendered content first |
| 5 | HTML section/requirement discovery uses **tag regex** (`<h2>`/`<h3>`/`<h4>`), not a DOM library | `@arke/contracts` is browser-safe and dependency-light; a focused tag scan mirrors the markdown heading regexes — with explicit guards for attributes, case, inline tags in titles, and heading-like text in `<pre>`/comments |
| 6 | The markdown path defaults when `format` is omitted | Purely additive for compilation — but combined with content-detected frontmatter (Decision 3), a missed call site degrades gracefully rather than silently corrupting |
| 7 | HTML bodies are **sanitised** before preview via a **NEW** renderer (rehype-raw+sanitize / SafeHtml) | The cited SPEC-032 `Markdown` component drops raw HTML (no rehype-raw), so a sanitising renderer is new work, not reuse; a spec body must never execute active markup in the client (NFR-1/5) |
| 8 | HTML **delivery** is refused in v1 (typed error), not silently attempted | `parseTasks` is markdown-structural (`## Tasks` + `- [ ]`); an HTML spec would parse zero tasks and never complete. Authoring→approval is fully supported; HTML delivery is a bounded follow-up |

## Open questions
- Should the cockpit offer a **live format conversion** (markdown ⇄ HTML) for an existing spec, or is choosing
  the format at creation enough? v1: choose at creation; conversion is a later affordance.
- Should the HTML metadata (`capability:`/`delta:`) have a **structured element convention** (e.g.
  `<p class="meta">`) recommended in the template, even though the parser reads tag-stripped text either way?
  v1: recommend a `<p class="meta">…</p>` in the template for readability; the parser stays lenient.
- Do generated **downstream artefacts / pointer stubs** (SPEC-013/030) need an HTML variant, or do they stay
  markdown regardless of the source spec's format? v1: generated artefacts stay markdown (they are Arke's own
  deterministic output, not authored); revisit if HTML round-tripping is wanted.
