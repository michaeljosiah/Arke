# Codex harness adapter — a second leaf, proving the neutral seam over JSON-RPC

## Why

Arke's whole architecture rests on one claim: the `HarnessAdapter` interface is the seam, and **no single
harness is load-bearing**. Today only OpenCode proves it, and OpenCode is an HTTP-server + SSE backend —
so the adapter code has never been exercised against a fundamentally different integration model. The
named risk (PRD §17) is *"the adapter leaks OpenCode-specific assumptions."* A **second leaf adapter for
OpenAI's Codex** retires that risk directly: Codex integrates over **JSON-RPC 2.0 on stdio** (a spawned
`codex app-server`), not HTTP/SSE — a genuinely different transport, session model, and approval
mechanism. If Arke's orchestration drives Codex through the same `HarnessAdapter` the coordinator already
targets, the seam is proven, not merely asserted. (This is a *leaf* adapter — a direct single-harness
integration, distinct from the Omnigent *meta-harness* substrate spike, ADR-0002.)

## What changes

- ADDED harness-integration — a **`@arke/adapter-codex`** package implementing `HarnessAdapter` over the
  **`codex app-server`** JSON-RPC 2.0/stdio protocol: `initialize` handshake, `thread/start` (session),
  `turn/start` (a turn), streaming `item/*` notifications, and the server→client `item/*/requestApproval`
  round-trip. It advertises **events, permissions, diff, todos, models** and degrades honestly on the
  rest. (breaking: no — a new optional package, selected only when a project's harness `driver` is `codex`.)
- ADDED harness-integration — a **pure `normalize()`** translating Codex `ThreadEvent`/`item` shapes into
  Arke `DomainEvent`s (table-tested), mirroring the OpenCode adapter's `normalize.ts`.
- MODIFIED harness-integration — the coordinator's harness selection (`server.ts` `connectHarness` /
  `buildContextDeps`) gains a **`codex` driver branch** and stops rejecting the already-mapped `codex`
  scheme as *"not runnable in this build yet."*

**Depends on:** SPEC-002 (the `HarnessAdapter` contract + the OpenCode reference), SPEC-016/018/019
(harness lifecycle, per-project managed runners, driver/config resolution).

## Requirements

### Requirement: Codex is driven over the app-server JSON-RPC protocol, not `codex exec`
`capability: harness-integration` · `delta: ADDED (feat/spec-034-codex-adapter)`

The adapter SHALL integrate Codex through **`codex app-server`** (a long-lived process, JSON-RPC 2.0 over
stdio), NOT by spawning `codex exec` per turn. The reason is normative, not incidental: `codex exec` runs
under a **fixed pre-set approval policy and hard-fails** on any approval it cannot auto-satisfy — it emits
no answerable approval event — so it cannot support Arke's *propose · decide · execute* gate. The
app-server is the only Codex surface that issues **server→client approval requests** the host answers, so
it is the only surface on which the `permissions` capability can be honestly implemented. The adapter
SHALL perform the `initialize`/`initialized` handshake once, start a Codex **thread** per Arke session
(`thread/start`), and start a **turn** per prompt (`turn/start`), reading streaming notifications from the
single process and fanning them into one `streamEvents()` channel.

#### Scenario: A prompt starts a Codex turn on the session's thread
- **WHEN** the coordinator sends a prompt for an Arke session mapped to Codex thread `T`
- **THEN** the adapter issues a `turn/start` JSON-RPC request naming thread `T`, the prompt, and (when the
  agent pins one) the model and working directory

#### Scenario: Exec's fixed-policy limitation is documented, not silently worked around
- **WHEN** an operator asks why the adapter spawns a server rather than `codex exec`
- **THEN** the spec and code record that `codex exec` cannot round-trip approvals (it fails on them), so
  the app-server is required for the permission gate

### Requirement: Codex notifications normalise to canonical domain events
`capability: harness-integration` · `delta: ADDED (feat/spec-034-codex-adapter)`

A **pure, side-effect-free `normalize()`** SHALL translate Codex app-server notifications into Arke
`DomainEvent`s, restamping `seq`/`ts` to 0 (the coordinator re-stamps) and returning an array (possibly
empty for structural frames). At minimum: `turn/started` → `session.status running`; an `agent_message`
item (or its streaming `delta`) → `message.updated` / `message.part`; a `plan_update` item →
`todo.updated`; `turn/completed` → `session.status idle` + `turn.quiescent`; `turn/failed`/`error` →
`session.status error`. Unmapped frames are ignored, never errored. The adapter SHALL validate every
event at the boundary (`DomainEvent.safeParse`) before emitting it.

#### Scenario: An assistant message becomes a message.updated
- **WHEN** the app-server emits an `item.completed` with `item.type: "agent_message"` carrying `text`
- **THEN** `normalize()` yields a `message.updated` for that session with the text, `isStreaming: false`

#### Scenario: A completed turn goes idle and signals quiescence
- **WHEN** a `turn.completed` notification arrives
- **THEN** `normalize()` yields `session.status idle` and a `turn.quiescent` receipt for the turn

#### Scenario: A plan update becomes a todo list
- **WHEN** the app-server emits a `plan_update`/`todo_list` item
- **THEN** `normalize()` yields a `todo.updated` event whose items mirror the plan steps + done state

### Requirement: A Codex approval request routes through the human gate
`capability: harness-integration` · `delta: ADDED (feat/spec-034-codex-adapter)`

When the app-server sends a server-initiated `item/commandExecution/requestApproval`,
`item/fileChange/requestApproval`, or `item/permissions/requestApproval`, the adapter SHALL emit a
`permission.asked` domain event (carrying the request's title/detail) and hold the JSON-RPC request open.
`respondToPermission(decision)` SHALL reply to that exact JSON-RPC request id with the mapped decision —
`reject → "decline"`, `once/always → "accept"` — and confirm via a `permission.replied` event. A decision
for an unknown/stale permission id SHALL return `stale`, never a false success.

#### Scenario: An approval is proposed, decided, and executed
- **WHEN** Codex requests approval to run a command and the human chooses `once`
- **THEN** the adapter had emitted `permission.asked`, replies `accept` to the pending JSON-RPC id, and
  emits `permission.replied` — Codex then proceeds

#### Scenario: A rejected approval declines the action
- **WHEN** the human chooses `reject`
- **THEN** the adapter replies `decline` and Codex does not perform the action

### Requirement: The adapter advertises only what Codex delivers; the model list is config-driven
`capability: harness-integration` · `delta: ADDED (feat/spec-034-codex-adapter)`

`capabilities()` SHALL advertise `events`, `permissions`, `diff`, and `todos` and — because Codex
**cannot enumerate its model catalog** (OpenAI closed that request; only per-run `--model` selection
exists) — `models` SHALL be served from a **config-driven / known list**, never a live query. `getDiff`
SHALL derive a `DiffSummary` from the session's working directory via git (the reliable on-disk truth),
independent of whether `file_change` items were observed. The board/cockpit degrade to whatever
`capabilities()` reports.

#### Scenario: listModels returns the configured catalog
- **WHEN** the coordinator calls `listModels()`
- **THEN** the adapter returns the configured/known Codex model set (e.g. the `gpt-5.*` family), each as
  `{ id, provider: "openai" }`, with no attempt to query a catalog Codex does not expose

## Design

### Architectural decision

Integrate via **`codex app-server`** (JSON-RPC 2.0/stdio), not `codex exec`, because only the app-server
issues answerable approval requests — the precondition for the `permissions` gate (and it also gives
streaming deltas, `thread/resume`, and `thread/fork`). The adapter mirrors the OpenCode adapter's shape —
a thin `HarnessAdapter` over a transport module plus a pure `normalize()` — so the seam is exercised by a
transport that shares no code or assumptions with OpenCode's HTTP/SSE.

### Target architecture (`packages/adapter-codex/`)

- **`app-server.ts`** — spawns `codex app-server`, frames JSON-RPC 2.0 over stdio, does the
  `initialize`/`initialized` handshake, exposes `request(method, params)` (id-correlated responses),
  a notification stream, and a hook for **server→client requests** (the approval round-trip: the server
  sends a request the client must answer with a result).
- **`normalize.ts`** — pure `normalize(frame, sessionId, identity, harness, state) → DomainEvent[]`
  (table-tested), mirroring `adapter-opencode/normalize.ts`.
- **`session-map.ts`** — Arke `sessionId` ↔ Codex `thread_id` + working directory + spec identity.
- **`permissions.ts`** — pending approval requests by permission id → the JSON-RPC id to reply to.
- **`models.ts`** — the config-driven Codex model catalog (no enumeration API).
- **`config.ts`** — `CodexConfig` (binary path, cwd/root, sandbox + approval policy defaults, model list,
  host-side auth reference — never an inline credential, NFR-1).
- **`capabilities.ts`** — the advertised `Capability` set.
- **`index.ts`** — `CodexAdapter implements HarnessAdapter` + an `EventChannel` (multi-producer /
  single-consumer, as in the Omnigent adapter).

### Coordinator wiring

`server.ts` `SCHEME_DRIVER` already maps `codex → codex`. `buildContextDeps` gains a driver branch
(`config.driver === "codex" → new CodexAdapter(loadCodexConfig(...))`); `connectHarness` widens its
runnable-driver check from *opencode-only* to a whitelist including `codex`.

### Cross-cutting

- **Security / NFR-1:** Codex auth is host-side (`codex login` → `~/.codex/auth.json`, or
  `OPENAI_API_KEY`); the adapter never carries a credential on the wire or to the client. cwd is
  root-confined (per session, supports the SPEC-028 delivery worktree via the thread's working directory).
- **Verification honesty (see DoD):** Codex is not installed in the authoring/CI environment and requires
  OpenAI auth, so the adapter is built to the **documented** app-server protocol and tested against a
  **fake JSON-RPC app-server stub** (mirroring the OpenCode adapter's stub-server tests) plus pure
  `normalize()` table tests. A **live-Codex smoke test is a DoD follow-up**, run where Codex is authed —
  this spec does not claim a live end-to-end it cannot perform here.
- **Known Codex limits carried into the design:** no model enumeration (config-driven list); `--json`
  exec-mode has a documented MCP-active bug (irrelevant — we use the app-server); the exact stdio framing
  is built to the app-server docs and flagged for the smoke test to confirm.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Integrate via `codex app-server` (JSON-RPC/stdio), NOT `codex exec` | Only the app-server issues answerable approval requests; `exec` runs a fixed policy and hard-fails on approvals, so it cannot support the propose·decide·execute gate |
| 2 | A pure `normalize()` mirrors the OpenCode adapter | Keeps the transport-specific mapping table-testable and the `HarnessAdapter` impl thin; proves the seam without leaking OpenCode assumptions |
| 3 | `models` queries `model/list`, config catalog as fallback | REVISED after live verification: the Codex *CLI* can't enumerate, but the *app-server* exposes `model/list` (returned 7 real models live) — so `listModels` queries it and falls back to the config-driven/known list when unavailable |
| 4 | `getDiff` derives from git in the session cwd | The on-disk git state is the reliable diff truth and is transport-independent; `file_change` items are advisory |
| 5 | Fixture/stub-tested now; live-Codex smoke deferred | Codex isn't installed and needs OpenAI auth in this environment; building to the documented protocol + a protocol-faithful stub is honest and valuable, with the live smoke a clearly-scoped follow-up |
| 6 | A LEAF adapter, distinct from the Omnigent meta-harness (ADR-0002) | Codex is a direct single-harness integration; Omnigent is the substrate one level up — different roles, both validate the seam |
