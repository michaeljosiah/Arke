# Project reference library — directly-citable business-context entries with durable spec links

## Why

Business context is already **stored** and **ambiently injected** into authoring ([SPEC-027](027.okf-grounding-layer.md)): typed grounding documents under `docs/` frame every draft in the background. But grounding today is *whole-document and ambient* — the author cannot **deliberately cite a specific, granular fact** ("our pricing tiers", "the SOC-2 constraint", "north-star = weekly active teams") and have the specification **durably record that it rests on that fact**. So there is no link from a requirement back to the business truth that justified it, and — as [`business-context.md`](../business-context.md) itself names — *"grounding drifts"*: when a fact later changes, nothing knows which specs relied on it. This specification adds a **reference library**: granular, addressable entries the author can cite on purpose during authoring, a durable citation recorded on the spec, and a reverse index so a change to a fact can flag the specs that depend on it. It **builds on** SPEC-027's grounding layer; it does not replace the ambient digest.

## What changes

- ADDED reference-library — foundational grounding becomes **addressable at entry granularity**: a reference entry is a grounding-typed OKF document *or* a stably-anchored section within one, each with a **stable reference id**, built on SPEC-027's tree (no new store, same two-tier split).
- ADDED reference-library — the author can **directly cite** an entry during authoring (cockpit pick/@-mention), which pulls the entry's **full body** into the session as foreground context — distinct from SPEC-027's ambient background digest.
- ADDED reference-library — a cited reference is **recorded durably** in the spec's `references:` frontmatter, so the spec records which business facts it rests on.
- ADDED reference-library — the coordinator maintains a **reverse index** (entry id → citing specs) and **flags citing specs as grounding-stale** when a referenced entry materially changes — a propose-only signal, never an auto-edit — reusing SPEC-039's drift-signal discipline and resolution vocabulary.
- ADDED reference-library — references to **local-tier** (`.arke/grounding/`, sensitive) entries are allowed but recorded `tier: local` and never copied into the committed spec, preserving the leak-safety wager.

**Depends on:** SPEC-027 (grounding layer — this composes on it), SPEC-026 (OKF convention + generated indexes), SPEC-020 (authoring grounding + uploads), SPEC-006 (authoring cockpit), SPEC-008/024 (lifecycle — the stale flag rides the same board/trace discipline), SPEC-039 (drift-signal + resolution vocabulary reused), SPEC-015 (audit trace). **Relates to:** SPEC-030 (ripple — the reverse index is an analogous linkage).

## Requirements

### Requirement: Foundational grounding is addressable at entry granularity with a stable id
`capability: reference-library` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

A **reference entry** SHALL be either a grounding-typed OKF document (SPEC-027's `product-overview` / `business-context` / `domain-glossary` / `architecture` / `convention`) or a **stably-anchored section** within one (a heading with a slug, or an explicit `{#id}` anchor), and SHALL carry a **reference id** unique within the project. The reference library is the set of such entries; it SHALL build on SPEC-027's grounding tree — **no new store** — and inherit its two-tier split (committed `docs/` vs. local `.arke/grounding/`). A reference id SHALL be **stable across edits to the entry's body**: it is derived from the anchor/slug (or an explicit id), not from the entry's prose, so a wording change does not break existing citations. Renaming an anchor SHALL be detectable (an explicit id survives a heading rename; a slug rename is surfaced, not silently orphaned). Anchor and slug machinery is **new parser work this spec ADDS**: nothing in the codebase computes heading slugs or parses `{#id}` anchors today, and grounding documents are parsed only to type/title/first-paragraph — entry-level enumeration of a grounding document's sections is added here.

#### Scenario: A section becomes an addressable entry
- **WHEN** a `business-context.md` section has a heading slug or `{#id}` anchor
- **THEN** it is available as a reference entry with a stable id, without moving it to a new store

#### Scenario: An entry id survives a body edit
- **WHEN** a referenced entry's prose is edited but its anchor/id is unchanged
- **THEN** existing citations to it still resolve

#### Scenario: A local-tier entry is addressable but private
- **WHEN** an entry lives under `.arke/grounding/`
- **THEN** it is addressable as a reference entry with `tier: local` and is never auto-copied into the tracked tree

### Requirement: The author can directly cite an entry during authoring, pulling its full body into context
`capability: authoring-cockpit` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

In the authoring cockpit (SPEC-006/020), the author SHALL be able to reference a project entry **by id** — a picker or `@`-mention over the reference library — and doing so SHALL (a) inject that entry's **full body** into the authoring session as clearly-labelled **foreground** context (beyond SPEC-027's ambient truncated digest summary) and (b) record the citation on the working draft. This is an **explicit, per-draft** act, distinct from ambient grounding: the author chooses which facts this spec rests on, and only cited entries get their full body pulled in. Foreground bodies SHALL be **budgeted** — a per-entry and a total foreground cap (env-overridable, following the existing `ARKE_GROUNDING_*` pattern): cited context rides the per-turn `specContext` injection, and an unbounded body (local uploads may be megabytes) must not blow the prompt. The picker SHALL list committed and (locally) local-tier entries, showing each entry's id, title, type, and tier.

#### Scenario: Citing an entry injects its full body
- **WHEN** the author cites a reference entry while authoring
- **THEN** that entry's full body is injected into the session as foreground context, labelled distinctly from the ambient grounding digest

#### Scenario: Only cited entries are pulled in full
- **WHEN** a draft cites two of the library's entries
- **THEN** only those two entries' full bodies are foreground context; the rest remain ambient digest only

#### Scenario: The picker shows tier
- **WHEN** the author opens the reference picker
- **THEN** each entry shows its id, title, type, and whether it is committed or local-tier

### Requirement: A cited reference is recorded durably on the spec
`capability: reference-library` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

Each citation SHALL be recorded in the specification's `references:` frontmatter as an entry `{ id, title, tier }` — deterministic and machine-readable — so the spec durably records which business facts it rests on. The `references:` list is **enduring contract metadata**, not an in-flight delta: it SHALL survive flatten/merge (SPEC-024) and remain on the delivered spec. Requirement text MAY additionally carry inline `[[ref:<id>]]` markers pointing at an entry, but the frontmatter list is the **authoritative** link. Storage round-trips safely today — frontmatter rewrites are line-by-line and preserve unknown keys, and delta-flatten never touches frontmatter — but the flat frontmatter parser cannot *read* a nested list, so this spec ADDS a dedicated `parseLinkage`-style walker for `references:` (the SPEC-030 precedent); new code SHALL tolerate both coexisting spec-id conventions (`spec_id`/`specId`). A citation to an entry that no longer resolves SHALL be surfaced (a dangling-reference warning), never silently dropped.

#### Scenario: A citation lands in frontmatter
- **WHEN** the author cites entry `pricing-tiers`
- **THEN** the spec's `references:` frontmatter gains `{ id: "pricing-tiers", title, tier }`

#### Scenario: References survive delivery
- **WHEN** a spec that cites entries reaches `delivered` and its deltas flatten
- **THEN** its `references:` list is intact on the delivered spec

#### Scenario: A dangling reference is surfaced
- **WHEN** a cited entry's id no longer resolves in the library
- **THEN** a dangling-reference warning is surfaced on the spec rather than the citation being silently removed

### Requirement: The library maintains a reverse index of entry → citing specs
`capability: reference-library` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

The coordinator SHALL maintain a deterministic projection mapping each reference id → the set of specs that cite it, derived from every spec's `references:` frontmatter. This reverse index SHALL be regenerated on the same signals that rebuild the OKF indexes (SPEC-026) and be queryable (which specs depend on this fact?). It is a **projection**, never hand-edited, consistent with the OKF generated-index discipline.

#### Scenario: Citing updates the reverse index
- **WHEN** a spec cites entry `north-star-metric`
- **THEN** the reverse index lists that spec under `north-star-metric`

#### Scenario: The reverse index answers "what depends on this fact?"
- **WHEN** the reverse index is queried for an entry id
- **THEN** it returns every spec whose `references:` frontmatter cites that id

---

### Requirement: A material change to a cited entry flags the specs that reference it
`capability: reference-library` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

When a reference entry's body **materially changes** (not a whitespace/typo edit), the coordinator SHALL flag **every spec that cites it** as **grounding-stale** — a **propose-only** signal surfaced on the board and the trace (`reference.entry-changed { id, citingSpecs[] }` / `spec.grounding-stale { specId, entryId }`), mirroring SPEC-039's drift-signal discipline. The change detector is an analog of the **existing** `checkCanonicalEdits` → `cascadeRippleStaleness` pattern (the docs watcher re-hashing canonical documents and cascading staleness flags, SPEC-030); SPEC-008's `normativeHash` itself does **not** transfer — it hashes a spec's Requirements+Design sections, which grounding prose lacks — so this spec ADDS an entry-scoped content hash over the anchored section body. **Local-tier caveat:** the docs watcher covers `docs/` only; a `.arke/grounding/` entry changed out-of-band is re-hashed only on upload or project open — until the watcher is extended to the local tier (an explicit follow-up), local-entry staleness detection is declared best-effort, not silently assumed. The detector SHALL **NOT** auto-edit any spec. Resolution is a human decision sharing SPEC-039's triad: **ratify** (the spec still holds against the new fact — clear the flag, in place, no lifecycle reset), **correct** (the spec must change — the human amends it through the normal authoring/lifecycle path), or **accept** (a recorded, reasoned tolerance). This directly attacks the "grounding drifts" problem: a business fact can no longer change without the specs that depend on it knowing.

#### Scenario: A changed fact flags its dependents
- **WHEN** a cited reference entry's body materially changes
- **THEN** every spec that cites it is flagged `grounding-stale` on the board and the change is traced
- **AND** no spec is auto-edited

#### Scenario: A cosmetic edit does not flag
- **WHEN** a referenced entry changes only in whitespace or a typo (no entry-hash change after normalisation)
- **THEN** no `grounding-stale` flag is raised

#### Scenario: Ratifying a stale flag clears it without a reset
- **WHEN** a human resolves a `grounding-stale` flag as "ratify — the spec still holds"
- **THEN** the flag clears in place and the spec's lifecycle status is unchanged

---

### Requirement: References to local-tier entries are allowed but never leak into the committed spec
`capability: reference-library` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

A citation MAY target a `.arke/grounding/` local-tier entry; the reference SHALL be recorded with `tier: local` and the spec SHALL note that the referenced body resolves **only in the local environment** (it is not in the tracked tree). The system SHALL NOT copy a local entry's body into the committed specification — the durable citation is the id and title, not the sensitive body. A reviewer-checklist note (as SPEC-027 established for grounding commits) SHALL cover the case where an author is tempted to paste a local fact's body inline; the two-tier leak-safety wager stays intact.

#### Scenario: A local reference records id, not body
- **WHEN** an author cites a local-tier entry
- **THEN** the spec's `references:` records `{ id, title, tier: "local" }` and the sensitive body is not written into the committed spec

#### Scenario: A local reference is marked as local-only
- **WHEN** a spec citing a local entry is opened on another machine without that local tier
- **THEN** the citation resolves to a local-only marker (id + title), not a broken body, and is surfaced as unresolved-locally rather than dangling

## Design

### Architectural decision

The reference library is a **thin addressability + citation layer over SPEC-027's existing grounding tree**, not a new knowledge store. Three additions compose on top of ambient grounding: (1) **addressability** — a stable id per grounding doc/section; (2) **explicit citation** — a foreground channel that pulls a cited entry's full body into authoring and records the link in `references:` frontmatter; (3) a **reverse index + material-change flag** that reuses SPEC-039's propose-only drift discipline and resolution vocabulary, applied to *business facts* instead of *code*. This keeps one grounding tree, one two-tier split, and one drift-signal pattern — the library is the *foreground, cited* half of the grounding SPEC-027 made *background, ambient*.

### Target architecture

- **Contracts** (`packages/contracts`): a `ReferenceEntry { id, title, type, tier, path, anchor? }` shape; the spec `references: { id, title, tier }[]` frontmatter (extend `parseFrontmatter`/spec-doc); events `reference.entry-changed`, `spec.grounding-stale`, `spec.reference-dangling`. Zod-first, validated at the boundary.
- **Coordinator** (`packages/coordinator`): a **reference resolver** that enumerates entries over the SPEC-027 grounding tree (docs + local tier) and computes stable ids from anchors (ADDED slug/anchor parsing); a **reverse-index projection** (entry id → citing specs) following the established derived-projection machinery (`okf-index.ts` renderers + `regenerateBundleIndex` + the `fs.watch` docs watcher, with the generated banner + `type: index` frontmatter so it self-excludes from grounding and the watcher); a **material-change detector** on entry bodies (ADDED entry-scoped hash, `checkCanonicalEdits`-style cascade) that emits `grounding-stale` for citing specs; budgeted foreground-body injection into the authoring `specContext` for cited entries (alongside SPEC-027's ambient digest). Reuses SPEC-039's signal-fold + resolution ops where possible.
- **Client** (`packages/client`): a cockpit reference **picker / `@`-mention** over the library; a **References panel** on the spec showing cited entries (with tier badges); a `grounding-stale` badge + the ratify/correct/accept resolution affordance (shared with SPEC-039's drift UI). Thin realisation layer.
- **CLI** (SPEC-017): `arke reference list` / `arke reference deps <id>` for the reverse index.

### Data model

- `ReferenceEntry` — `{ id, title, type, tier: "committed" | "local", path, anchor? }`, enumerated (not persisted) over the grounding tree.
- Spec frontmatter — `references: { id, title, tier }[]`, durable contract metadata (survives flatten).
- **Reverse-index projection** — `{ [entryId]: specId[] }`, generated like the OKF indexes (SPEC-026), never hand-edited.
- Trace events (SPEC-015): `reference.cited`, `reference.entry-changed`, `spec.grounding-stale`, `spec.reference-dangling`.

### Interfaces and contracts

- New (authoring) op: cite/uncite an entry on the working draft (updates `references:` + injects/removes the foreground body).
- New op: resolve a `grounding-stale` flag (`ratify | correct | accept`) — the same triad as SPEC-039's `conformance.resolve`, one shape shared rather than a parallel one.
- Frontmatter: `references: [{ id, title, tier }]`; optional inline `[[ref:<id>]]` markers (frontmatter is authoritative).
- Reverse index: a generated projection + `arke reference deps <id>`.

### Cross-cutting

- **Design template:** the reference picker, References panel, tier badges, and `grounding-stale` affordance follow the `arke-design` skill (`.claude/skills/arke-design/`) — teal accent (SPEC-033) for the stale-attention state; the resolution affordance reuses SPEC-039's drift UI so the two feel like one pattern.
- **Security / leak-safety (the wager):** the two-tier split is inherited from SPEC-027; a local-tier citation records id+title only, never the sensitive body; the reviewer-checklist note extends to inline-pasting temptation. All resolution is host-side and traced.
- **Determinism:** the reverse index and stale-flagging are deterministic projections (SPEC-014/026 discipline), not agent behaviour — a fact changing flags dependents mechanically, not by an LLM's judgement.
- **Observability:** citation counts, most-cited entries, and grounding-stale rate flow to the SPEC-015 trace/span path (OTLP-exportable in design; no exporter exists yet) — surfacing which business facts are load-bearing across the corpus.

### Testing
- **Unit (addressability):** an anchored section resolves to a stable id; the id survives a body edit; a local-tier entry resolves with `tier: local`.
- **Unit (citation):** citing injects the full body as foreground context distinct from the ambient digest; only cited entries are pulled in full; the citation lands in `references:` and survives flatten.
- **Unit (reverse index):** citing updates the index; querying an id returns all citing specs.
- **Unit (staleness):** a material entry change flags citing specs `grounding-stale` and traces; a cosmetic edit does not; ratify clears the flag in place with no lifecycle change.
- **Unit (leak-safety):** a local citation records id+title only, never the body; an unresolved-locally citation surfaces as local-only, not dangling.
- **Integration:** author a spec, cite two business facts (one committed, one local) → `references:` records both with tiers, bodies injected foreground → deliver → references intact → materially edit one cited fact → the citing spec is flagged `grounding-stale` → ratify clears it with no reset. Host and host-less.

### Definition of done
Grounding is addressable at entry granularity with stable ids over SPEC-027's tree (no new store); the author can directly cite an entry to pull its full body foreground and the citation is recorded durably in `references:` (surviving flatten); a reverse index answers "what depends on this fact?"; a material change to a cited entry flags citing specs `grounding-stale` propose-only (cosmetic edits do not), resolvable via ratify/correct/accept with ratify clearing in place; local-tier references never leak a body; suite green; a non-author reviewer has signed off; SPEC-027 in place (grounding dependency).

## Open questions
- **Anchor stability vs. authoring ergonomics:** should entries require an explicit `{#id}` (robust to renames but more authoring ceremony), or default to heading-slugs (zero ceremony but a rename orphans citations, surfaced as dangling)? (Lean: slug by default with an optional explicit id for facts expected to be widely cited.)
- **Cite-time vs. review-time enforcement:** should a spec be allowed to reach `approved` with a dangling reference, or is a resolvable `references:` list a well-formedness gate (SPEC-024)? (Lean: warn at author-time, block at promotion only if configured — avoid over-gating early drafts.)
- **Auto-suggest citations:** should the spec-author agent *propose* which library entries a draft should cite (grounded, but the human confirms), rather than the author hunting the picker? (Natural fit, but keep it propose-only; defer to a follow-up.)
- **Granularity of "material change":** ✅ RESOLVED (defensive review, 2026-07-20) — it does not transfer: `normativeHash` covers a spec's Requirements+Design sections only. The detector adds an entry-scoped hash over the anchored section body, following the existing `checkCanonicalEdits` → `cascadeRippleStaleness` watcher/cascade pattern (SPEC-030).
- **Cross-repo facts:** when a fact is shared across repos (SPEC-030 territory), does the reverse index span repos? (Defer; single-repo for v1.)
