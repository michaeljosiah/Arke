# Project overview dashboard, live git/PR status & desktop chrome cleanup

## Why

Today, opening a project drops straight into the specification library — there is no single screen that answers "what needs me right now, and what are the agents doing?" This specification adds a **Project overview** dashboard as the landing screen: triage of what's waiting on a human, situational awareness of the pipeline, running sessions, and record-sync health, plus — the piece that makes it genuinely useful for a Product Engineer — **live repository state**: which spec branches are ahead/behind, which have uncommitted changes, what each branch's diff looks like, and whether a pull request is open. The coordinator has no ahead/behind, dirty-tree, diff-stat, or PR-status query capability today (it does already shell out to git for cloning, committing, merging, and branch probing — see Decision #1, corrected from an earlier draft that claimed otherwise). This specification adds the coordinator-side capability to compute repo/PR status, wires the whole dashboard into the real client against live store data, and removes the non-functional macOS traffic-light bar (`ChromeBar`) that serves no purpose in this build (this is a browser-first client; the separate Electron desktop app, [SPEC-022](022.electron-desktop-app.md), has its own native OS chrome and is unaffected).

## What changes

- ADDED client-shell — a new **Overview** screen (`view: 'dashboard'`), the landing view for a project whose setup is already complete (a freshly-scaffolded/greenfield project continues to land on the authoring cockpit, unchanged — see Requirement "Opening a project lands on the Overview").
- ADDED git-status — the coordinator computes live git branch status (ahead/behind the default branch, working-tree dirty count, diff line/file stats) and GitHub PR status per specification branch, via new read-only `git`/`gh` queries scoped to the project root, and republishes it as new `repo.status`/`repo.identity` domain events, seeded into the connection snapshot so a freshly-connected client isn't blank.
- MODIFIED client-shell — opening a `method-ready` project routes to `dashboard` instead of `library`, from every call site that lands a project (picker, recents, clone/create, and the desktop menu bridge — not only the one this spec's first draft named); the Specifications nav item remains, unchanged, as its own destination.
- REMOVED client-shell — the desktop window-chrome bar (traffic lights + centred wordmark) is deleted from the shell entirely; the `chrome` store field, its Settings toggle, and every remaining reference to it are removed. *(breaking: removes a user-visible Settings control.)*

## Requirements

### Requirement: A single Overview screen surfaces what needs a human and what agents are doing
`capability: dashboard` · `delta: ADDED (feat/spec-025-overview-dashboard)`

The system SHALL provide an `Overview` screen, routed as `view: 'dashboard'`, composed from the live store — `cards`, `specs`, `projections`, `events`, `project`, `repo`, `gitBranches` (`packages/client/src/store.ts`) — with no hardcoded or demo values. The screen SHALL render, top to bottom: a **triage** panel ("Waiting on you") aggregating every open human gate, every card in `review`, every card in `diff`, and every projection with `health !== 'ok'`; a **repository** panel (see the next requirement); a **sessions in flight** panel listing cards in `authoring` or `implementing`; a **record sync** panel summarising `projections` by `system`; a **pipeline** panel summarising `specs` grouped by `status`; and a **recent activity** rail sourced from the live `events` feed, filtered to governance-relevant kinds (`permission.*`, `diff.finalized`, `spec.status`, `projection.write`) — not from `audit`, which today is fetched per-spec on demand (`live.ts`'s `fetchAuditRecords(specId)`) and has no project-wide live feed (Decision #7). `notifs` is excluded from this list: it is never populated outside demo/mock data (no `applyEvent`/`applySnapshot` case in `live.ts` sets it), so it carries no live signal for this screen. When a project has no specs and no cards, the screen SHALL render an empty state instead of empty panels.

#### Scenario: Nothing needs a decision
- **WHEN** no card has an open human gate, no card is in `review` or `diff`, and no projection has `health !== 'ok'`
- **THEN** the "Waiting on you" panel shows a calm confirmation state (a positive status dot and "Nothing needs a decision — the harness is working."), not an empty list with no explanation

#### Scenario: A permission gate surfaces in triage
- **WHEN** a card has `needsHuman: true`
- **THEN** the triage panel lists it with a "Decide" action that populates `store.permission` from that card's open gate — the same mechanism a live `permission.asked` event uses (`live.ts`'s handling around line 250) — so the existing `PermissionOverlay` (rendered at `root.tsx:106`) opens exactly as it does from the delivery board
- **AND** selecting a diff-ready card's "Review diff" action resolves navigation via the shared helper in the next-but-one requirement ("Repository row navigation reuses the board's session picker")

#### Scenario: New project, nothing authored yet
- **WHEN** a project has zero specs and zero cards
- **THEN** the Overview screen shows an empty state directing the user to author a first specification
- **AND** no panel renders with misleading zero/blank content

### Requirement: A repository panel shows live branch, diff and PR status per specification
`capability: dashboard` · `delta: ADDED (feat/spec-025-overview-dashboard)`

The Overview screen SHALL include a **Repository** panel bound to the live store's `repo` (project identity) and `gitBranches` (per-spec branch status) fields. The panel header SHALL show the repository name, default branch, and current `HEAD` short SHA. Each row SHALL show: the branch name and its owning `specId`; ahead/behind counts relative to the default branch, or a degraded notice if unavailable; the working-tree dirty-file count, rendered as **"—" (not `0`)** when the branch is not the one currently checked out in the project root at query time, since dirty state is only known for the checked-out branch; added/removed diff line counts and file count relative to the default branch, or a degraded notice if unavailable; and a pull-request badge (`open` / `draft` / none / unknown) with its number when known. No numeric field SHALL ever be fabricated: a field the coordinator could not compute is rendered as a degraded notice, never a guessed `0` or `null`-as-if-verified (see the next requirement's data model for how "verified none" and "unknown" are distinguished).

#### Scenario: Ahead/behind and diff stats render for every branch, checked out or not
- **WHEN** a specification's branch has 2 commits ahead and 0 behind the default branch, with a diff of +41/−6 across 5 files
- **THEN** the repository panel row shows those exact ahead/behind and diff numbers, regardless of whether that branch is currently checked out

#### Scenario: Dirty count is honest about what is actually known
- **WHEN** the project root currently has `spec/payment-retry` checked out (queried fresh via `gitHeadBranch()` at computation time, not cached) with 1 uncommitted file, and a different row is `spec/rate-limits` (not checked out)
- **THEN** the `spec/payment-retry` row shows a dirty count of `1`
- **AND** the `spec/rate-limits` row shows "—" for dirty, never a fabricated `0`

#### Scenario: A row degrades gracefully when git/PR data could not be computed
- **WHEN** the coordinator's most recent computation for a branch's ahead/behind or diff failed (e.g. no upstream, or — for PR status — `gh` is not installed or the project's GitHub integration is not configured)
- **THEN** that row shows a clear "status unavailable" notice for the affected field(s) only
- **AND** no other row or field is affected

`capability: dashboard` · `delta: ADDED (feat/spec-025-overview-dashboard)`

#### Scenario: Multi-session row opens the existing picker
- **WHEN** a user selects a repository-panel row whose spec has more than one active/done session
- **THEN** the existing session-picker overlay opens, listing those sessions, exactly as it does from the board

### Requirement: The coordinator computes and republishes git and GitHub PR status per specification
`capability: git-status` · `delta: ADDED (feat/spec-025-overview-dashboard)`

`ProjectContext` (`packages/coordinator/src/project-context.ts`) already shells out to git for cloning, committing, merging, and branch probing (`gitAvailable`, `gitHeadBranch`, `gitDefaultBranch`, `gitCommit`, `gitMerge`, `gitCloneAsync`, all built on a shared bounded-timeout `gitOpts()`/`GIT_TIMEOUT_MS` convention at `project-context.ts:2588–2718`). This requirement extends that same convention — reusing `gitAvailable`, `gitHeadBranch`, and `gitDefaultBranch` rather than re-deriving a second, divergent notion of "default branch" — with a new read-only **status** capability, in a new co-located module `packages/coordinator/src/git-status.ts` that imports the existing helpers and matches their `gitOpts()`/timeout convention (exporting it from `project-context.ts` if not already exported, rather than duplicating it). The new module SHALL expose: `gitAheadBehind(root, defaultBranch, branch)` and `gitDiffStat(root, defaultBranch, branch)`, computed against **remote-tracking refs** (`origin/<default>`, `origin/<branch>`) when an `origin` remote exists, falling back to comparing directly against the **local** default-branch tip (via the existing `gitDefaultBranch()`) when there is no `origin` — the common case for a host-less, local-only project (SPEC-024's governance model); `gitDirtyCount(root)`, computed via `git status --porcelain` against **whichever branch `gitHeadBranch(root)` reports at query time** (not a cached assumption — the coordinator's own operations, such as a local merge, change what is checked out between queries); and `githubPrStatus(branch)`, which — **only when the project's GitHub integration is configured** (reusing the existing `hostConfigured()` check, so an unauthenticated/host-less project never attempts a `gh` call on a timer) — queries `gh pr view <branch> --json number,state,isDraft` for **both** the PR number and its open/draft state. `SpecLibraryRecord.prNumber` (SPEC-008's webhook-tracked field) is used only as a **display fallback** when `gh` itself is unavailable or the integration isn't configured, since that field is coordinator in-memory state populated only by a webhook and does not survive a coordinator restart on its own. Every command SHALL be read-only (no `git push`, `git commit`, `gh pr create/merge`, or any mutating call), run with a bounded timeout, scoped to the project's own validated root, and never require or handle a permission gate (they change nothing and, for `gh`, are gated behind integration configuration rather than a human approval). A failure (missing `git`/`gh` binary, command timeout, no upstream, integration not configured) for one field on one branch SHALL be caught, traced with a reason (NFR-7), and SHALL NOT crash the context or block any other branch's or field's result.

The coordinator SHALL emit the result as a new `repo.status` domain event, one per specification branch, and a `repo.identity` event once per project (re-emitted if `HEAD` or the remote changes). Both SHALL be added to the `DomainEvent` discriminated union (`packages/contracts/src/events.ts`) and folded by `read-model.ts`'s `apply()`, which has no default fold today — an unhandled event type is silently dropped. Recomputation SHALL be triggered by: (1) `project.open`; (2) a bounded background refresh (no more than once per 60 seconds) while the project is open; (3) immediately, for the affected branch only, after a `diff.finalized` event or a `session.status` transition to a **terminal** state (`done`, `error`, `interrupted`) for a session belonging to that specification — `diff.finalized` carries only `sessionId` (`events.ts:171-177`), so the coordinator SHALL resolve the owning `specId` via the same session-ownership graph SPEC-023 already established, and per-branch recomputation SHALL be debounced (coalesced) rather than fired once per raw event, since `session.status` transitions are frequent during fan-out; and (4) an explicit client-issued `repo.status.refresh` op (optionally scoped to one `specId`).

#### Scenario: Repo status recomputes after a diff finalizes
- **WHEN** a `diff.finalized` event is recorded for a session belonging to `SPEC-014`
- **THEN** the coordinator resolves `SPEC-014` via the session-ownership graph and recomputes/re-emits `repo.status` for that branch only, not the whole project

#### Scenario: A busy fan-out does not spawn a git/gh storm
- **WHEN** ten `session.status` transitions to `running` fire in quick succession for tasks belonging to the same specification
- **THEN** none of them trigger a recompute (only terminal transitions do), and any terminal transitions that do arrive in the same short window are coalesced into a single recompute for that branch

#### Scenario: PR status is not attempted without a configured GitHub integration
- **WHEN** a project has no GitHub integration configured (`hostConfigured()` is false)
- **THEN** every branch's PR field is marked degraded/unknown rather than attempting (and silently failing) a `gh` call on every refresh
- **AND** ahead/behind, dirty count, and diff stats — which need no credentials — are still computed and published normally

#### Scenario: A client-requested refresh is scoped and read-only
- **WHEN** a client sends `repo.status.refresh` for a single `specId`
- **THEN** only that specification's branch is recomputed and re-published
- **AND** no git or GitHub mutating command is ever issued by this capability

### Requirement: A newly-connected client sees repository status immediately, not after the next refresh
`capability: git-status` · `delta: ADDED (feat/spec-025-overview-dashboard)`

`ProjectContext.snapshotPayload()` (`project-context.ts:286-301`) today sends `cards`, `projectState`, and related fields but nothing about repository status. Because `repo.status`/`repo.identity` are coordinator-emitted events folded live into the read model, a client that connects **after** those events already fired would otherwise see nothing until the next ≤60s background refresh. The snapshot payload SHALL include the read model's current `repoStatusBySpec`/`repoIdentity` state, and the client's `applySnapshot()` (`live.ts`) SHALL set `store.gitBranches`/`store.repo` from it on connect.

#### Scenario: Reconnecting client sees repo status without waiting
- **WHEN** a client connects to a project whose repo status was already computed before the connection
- **THEN** the snapshot alone (not a subsequent refresh) populates `store.repo` and `store.gitBranches`

#### Scenario: Specifications nav still works

- **THEN** the client navigates to the existing library view unchanged

## Design

### Architectural decision

The Overview is a projection screen, like the delivery board, for the panels backed by `cards`/`specs`/`projections`/`events` — all already real in `packages/client/src/store.ts`/`live.ts`. Repository/PR status is genuinely new, but it extends an **existing** git capability rather than starting from zero: `project-context.ts` already shells out to git (clone, commit, merge, branch-probe) through a shared bounded-timeout convention, and the new status queries reuse that convention and those existing helpers instead of re-deriving a parallel, weaker one. `ProjectContext` remains the sole owner of a project's filesystem root (SPEC-018); the new git/`gh` queries run through it, not through the harness adapter (adapter-opencode has no git awareness and should not gain any). The chrome-bar removal is a pure deletion, and this draft corrects two grounding errors from the original: the "no git shell-out beyond clone" claim was false (git-status queries are new; git shell-out itself is not), and the original Design section's citation of a "Project overview dashboard" / "`repository` layout" already present in the committed `arke-design` skill could not be substantiated — that layout was designed for this specification and is being vendored into the skill as part of it (see Cross-cutting and Decision #2), not retrofitted from a pre-existing template.

### Target architecture

- **New screen** `packages/client/src/screens/overview.tsx`, registered in `SCREENS.dashboard` and `CRUMBS.dashboard = ['Overview']` in `packages/client/src/root.tsx`. Built as separate, independently testable panels — `Triage`, `Repository`, `Sessions`, `SyncHealth`, `Pipeline`, `Activity` — rather than one monolithic component, so each panel's data-source claim can be checked on its own.
- **Sidebar** (`packages/client/src/shell.tsx`): add a new **`Home`** nav group (a name distinct from the existing bottom `Project` group at `shell.tsx:44`, which owns Agent roster/Harnesses/Settings and is unchanged) positioned first, containing a single `{ id: 'dashboard', name: 'gauge', label: 'Overview' }` item (the `gauge` icon already exists in `icons.tsx:62`).
- **Routing helper**: one function (e.g. `routeOpenedProject(projectState)`) called from `picker-init-library.tsx`'s `enter()`, the recents/open path, the clone/create path, and `desktop.ts`'s `open-project` handler — returning `'dashboard'` for a `method-ready` project and `'init'` otherwise — replacing four independent `view: 'library'` assignments.
- **Shared UI**: the screen composes from existing `Page`, `SectionHead`, and `Empty` (`packages/client/src/utils.tsx`) and existing `Button`, `Badge`, `StatusDot` (`packages/client/src/ds.tsx`) — no new design-system primitives needed.
- **Shared navigation helper**: extract `board-session-diff-permission.tsx`'s local `openCard(c)` into an exported helper, used by both the board and the Overview's repository panel, so session-picker behaviour for multi-session cards is identical in both places.
- **Chrome removal**: delete `ChromeBar` and every read/render/destructure of `chrome` listed in the corresponding Requirement above.
- **New coordinator module** `packages/coordinator/src/git-status.ts`: `gitAheadBehind`, `gitDiffStat`, `gitDirtyCount`, `githubPrStatus` — importing `gitAvailable`/`gitHeadBranch`/`gitDefaultBranch` from `project-context.ts` and reusing its `gitOpts()`/`GIT_TIMEOUT_MS` convention (exported from there if not already).
- **`ProjectContext` extension** (`project-context.ts`): a `refreshRepoStatus(specId?: string)` method that calls `git-status.ts` per branch (from the spec library's existing `branch` field), stores the result, and emits `repo.status`/`repo.identity` through the same `emit()` path other domain events already use. Trigger wiring (`project.open`, the 60s timer, the debounced post-terminal-event hook, and the explicit op) is a **separate** task from the method itself, since the post-event hook needs its own session→spec resolution and debounce logic.
- **Snapshot seeding**: `snapshotPayload()` gains the read model's `repoStatusBySpec`/`repoIdentity`; `applySnapshot()` in `live.ts` sets `store.gitBranches`/`store.repo` from it.
- **Read model** (`packages/coordinator/src/read-model.ts`, mirrored in `packages/client/src/live.ts`): a new `repoStatusBySpec: Map<specId, RepoStatus>` and `repoIdentity: RepoIdentity | null`, folded from `repo.status`/`repo.identity` events, exposed to the client as `store.gitBranches` (array) and `store.repo`.
- **New op** `repo.status.refresh` (optional `specId`): a new `case` in `ProjectContext.dispatch()`'s existing switch (`project-context.ts:1869`, alongside `case "diff.refresh"` at `:2054`) — `server.ts` needs no change, since it already routes every op to `activeCtx(conn).dispatch(op, msg.args)` (`server.ts:601`) generically. A client-side wrapper `refreshRepoStatusLive(specId?)` in `live.ts`, modelled on the existing `refreshDiffLive` `governed(...)` pattern, is the caller for a manual refresh and for retrying a degraded row.
- **Design vendoring**: the Overview/Repository layout is added to `.claude/skills/arke-design/app/` as `screens_dashboard.jsx`, alongside the existing `screens_{board,cockpit,config,gov,review,spec}.jsx`, so the design this specification describes has a citable, versioned source going forward (see Cross-cutting).

### Data model

The Overview screen reads (read-only, no writes) `cards`, `specs`, `projections`, `events` (unchanged shapes) plus two new store fields populated from the coordinator. Every git-derived numeric field is nullable, paired with an explicit `degraded` reason — there is no field that is simultaneously "must be a number" and "must not be fabricated on failure":

```
RepoIdentity { name: string; remote: string; default: string; head: string }
// "default" reuses the existing gitDefaultBranch() convention (local refs/heads/{main,master} probe),
// not a separate git symbolic-ref notion. `lastMerge`-style display text, if wanted, should read the
// specs list's most recently `delivered` entry (SPEC-024 renamed `merged` → `delivered`) — deferred to
// the client if needed rather than modelled here, to avoid re-deriving status logic in two places.

RepoStatus (one per specification branch, → client `gitBranches[]`) {
  specId: string; branch: string;
  ahead: number | null; behind: number | null;        // vs default; null = not computed (see degraded)
  dirty: number | null;                                // null = not the checked-out branch, OR not computed
  added: number | null; removed: number | null; files: number | null;  // git diff --stat vs default
  pr: { number: number | null; status: 'open' | 'draft' | null } | null;
  // pr === null means "verified: no PR is linked" (no degraded entry for 'pr').
  // pr !== null with a null number/status, OR a `degraded` entry for field 'pr', means "unknown" —
  // never collapse "unknown" into "none".
  degraded?: { field: 'ahead' | 'behind' | 'dirty' | 'diff' | 'pr'; reason: string }[];
}
```

### Interfaces and contracts

- New wire events in `packages/contracts/src/events.ts`: `RepoIdentityEvent { type: "repo.identity", ...RepoIdentity }` and `RepoStatusEvent { type: "repo.status", ...RepoStatus }`, added to the `DomainEvent` discriminated union (`events.ts:453-461` and onward) and to `read-model.ts`'s `apply()` switch, which currently has no default fold for an unrecognised type.
- New client-invocable op `repo.status.refresh` (`{ specId?: string }`), handled as a new `case` inside `ProjectContext.dispatch()` (not a `server.ts` change — `server.ts` already forwards every op generically).
- `snapshotPayload()`/`applySnapshot()` gain the repo-status fields (see the corresponding Requirement above).
- No changes to existing ops or events; `SpecLibraryRecord.prNumber` (SPEC-008) is read, never written, by this capability, and used only as a fallback display value when `gh` itself can't be queried.

### Cross-cutting
- **Design template:** the Overview/Repository screen is vendored into the `arke-design` skill as `.claude/skills/arke-design/app/screens_dashboard.jsx` as part of this specification's own scope (see Target architecture and Decision #2) — it is a **new** screen this spec introduces, not a pre-existing template screen being reused. Once vendored, it follows the skill's shadcn-neutral tokens, Geist, and Lucide iconography exactly like the other prototype screens.
- **Security (NFR-1):** git-status commands are read-only and scoped to the project's already-validated root; `gh`-dependent PR status additionally requires the project's GitHub integration to be configured (reusing `hostConfigured()`) before it is ever attempted, so an unconfigured/host-less project makes no outbound authenticated network call on a timer.
- **Observability (NFR-7):** a failed git/`gh` call, or a call skipped because the integration isn't configured, is traced with its reason, matching the existing dead-letter pattern in `adapter-opencode`, rather than silently defaulting to a fabricated value.
- **Accessibility:** triage and repository-panel row actions are real buttons/rows with visible focus states, matching the board's existing permission/diff controls.

### Testing
- **Unit (git-status):** ahead/behind and diff-stat computed correctly against remote-tracking refs when `origin` exists, and against the local default-branch tip when it doesn't; dirty count reflects `gitHeadBranch()` queried fresh, not cached, and is `null` for any branch that isn't the current HEAD; a missing `git`/`gh` binary, a command timeout, or an unconfigured GitHub integration is caught and reported as a degraded field, never a thrown error or a fabricated `0`. Test doubles inject the command runner rather than shelling out for real.
- **Unit (read model):** `repo.status`/`repo.identity` events fold into `repoStatusBySpec`/`repoIdentity`; the `DomainEvent` union accepts both new types.
- **Unit (`ProjectContext` triggers):** a `diff.finalized` for one spec resolves the correct `specId` via the session-ownership graph and re-triggers refresh for that spec only; a burst of terminal `session.status` transitions for the same spec within the debounce window produces exactly one recompute; `project.open` and the `repo.status.refresh` op each trigger correctly. (Trigger tests live here, not in the read model, since they are side effects on `ProjectContext`, not pure folds.)
- **Unit (client dashboard):** triage aggregation covers all four sources (gate, review, diff, projection-unhealthy) and produces the calm empty state when none apply; pipeline counts match `specs` grouped by `status`; the repository panel renders ahead/behind/diff/PR per row and shows "—" for dirty on non-checked-out branches, and a degraded notice (not a fabricated value) when a field is unavailable.
- **Component:** opening a ready project renders the Overview screen from every routing call site (picker, recents, clone/create, desktop bridge), not the library; a freshly-scaffolded project still lands on the cockpit; clicking "Specifications" still reaches the library; a triage "Decide" action opens the same permission overlay the board uses; a repository row opens directly for a single session and opens the picker for multiple sessions; no `ChromeBar` node renders in any store state. (This requires adding minimal DOM-rendering test infrastructure to `packages/client` — see Decision #8 — since today's Node-test-runner setup has none.)
- **Integration:** a mock project root with two branches (one with an `origin` and one without) produces correct ahead/behind/diff for both via their respective code paths; a project with no GitHub integration configured produces a degraded PR field on every branch, never a `gh` call attempt.
- **Regression:** Settings screen renders with no "Window chrome" row; a repo-wide search finds no remaining `chrome`/`ChromeBar` reference under `packages/client/src`.

### Definition of done
Opening a `method-ready` project from any entry point lands on a real-data Overview screen, including live git branch/PR status computed host-side and seeded via the connection snapshot; the traffic-light chrome bar, its Settings toggle, and every reference to it are fully removed; a missing `git`/`gh` binary or unconfigured GitHub integration degrades gracefully per-field rather than crashing or fabricating data; existing board/library/settings behaviour is unaffected; suite green; a non-author reviewer has signed off.

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Corrected: git shell-out already exists (clone/commit/merge/branch-probe in `project-context.ts`); this spec adds **status/read queries** (ahead-behind, diff-stat, dirty, PR), reusing the existing helpers and timeout convention rather than modelling on `workspace.ts` | Both review-panel passes (Claude Opus 4.8 and GPT-5.5) independently found the original draft's "no git-shell-out beyond clone" claim false and traced it to `project-context.ts:2588-2718`; extending the real pattern avoids a second, weaker git layer |
| 2 | The Overview/Repository layout is a new screen designed for this spec, vendored into `arke-design` as part of it — not a pre-existing template screen | Both reviewers independently grepped the entire `arke-design` skill for "Project overview," "dashboard," "repository layout," and the cited asset id and found zero matches; the original citation was unverifiable. Vendoring the actual layout (rather than re-citing a nonexistent source) makes it citable going forward |
| 3 | Ahead/behind and diff stats use remote-tracking refs when `origin` exists, falling back to the local default-branch tip when it doesn't | The coordinator manages one checked-out branch per project root (no worktree-per-branch model, SPEC-018), and SPEC-024's host-less/solo governance mode means many projects have no `origin` at all — a remote-tracking-only design would degrade every branch on exactly the projects the product already supports |
| 4 | Dirty working-tree count is `null` (rendered "—"), computed against whichever branch `gitHeadBranch()` reports **at query time**, for any branch that isn't currently checked out | Uncommitted-change state is genuinely undefined for a branch that isn't checked out, and the coordinator's own operations (local merges, approvals) change what's checked out between queries — a cached assumption would attribute dirty state to the wrong row |
| 5 | `gh pr view` is the primary source for **both** PR number and state when the GitHub integration is configured; `SpecLibraryRecord.prNumber` (SPEC-008's webhook field) is a **display fallback** only when `gh` can't be queried | The original draft had this backwards — `prNumber` is coordinator in-memory state that doesn't survive a restart on its own, so treating it as authoritative and `gh` as merely confirming "state" left the common case (webhook never fired, or coordinator restarted) with no PR number at all |
| 6 | `gh` calls are gated behind the project's GitHub integration being configured (`hostConfigured()`), not attempted unconditionally on every refresh | An unconfigured/host-less project should not make a repeated, silently-failing authenticated network call every ≤60 seconds; non-credentialed git queries (ahead/behind, dirty, diff) have no such gate since they need no credentials |
| 7 | The "recent activity" rail sources from the live `events` feed (filtered to governance-relevant kinds), not from `audit` | `audit` has no project-wide live feed today — `fetchAuditRecords(specId)` is per-spec, on-demand. Building a new project-wide audit query was out of scope for this spec; `events` is already live and sufficient for "what just happened" |
| 8 | Minimal DOM-rendering test infrastructure is added to `packages/client` as part of this spec's own task list, rather than deferred to a separate infra spec | `packages/client` has no jsdom/testing-library today, and this spec is the first to need component-level rendering tests (Overview panels, chrome-bar removal). The addition is small and unblocks the Testing section as written rather than leaving it aspirational |
| 9 | Chrome-bar removal is an outright deletion, not a default-off toggle, and is scoped to every reference (including `shell.tsx:184` and `tweaks.tsx:33`, missed in the first draft) | The bar is non-functional in this build and the user asked for it gone, not hidden; a partial deletion would leave dead selectors referencing a removed store field |

## Open questions
- Should the coordinator eventually manage a git worktree per specification branch so working-tree dirty state can be reported for *every* branch, not just the one currently checked out? Decision #4 is the honest answer for now; a worktree-per-branch model would be a larger follow-on capability.
- Should the ≤60s background refresh pause entirely when the Overview screen isn't the active view, to cut idle `git`/`gh` calls further than the integration-configured gate already does?
- Does `gh` need to be an explicitly probed/reported host dependency (alongside the existing harness probes in SPEC-005/016), so a missing `gh` shows up as a setup issue rather than only as a degraded dashboard row?
- Should this spec ship as three separate PRs in dependency order (chrome removal, which is independent and trivial; the git-status coordinator capability; then the Overview UI, which consumes both), even though it remains one specification? The three pieces have different risk and rollback profiles.
