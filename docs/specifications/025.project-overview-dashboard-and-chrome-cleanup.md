# Project overview dashboard, live git/PR status & desktop chrome cleanup

## Why

Today, opening a project drops straight into the specification library — there is no single screen that answers "what needs me right now, and what are the agents doing?" A design template (`Arke Specification Orchestrator.html`, the updated prototype) adds a **Project overview** dashboard as the landing screen, in its `repository` layout: triage of what's waiting on a human, plus situational awareness of the pipeline, running sessions, record-sync health, and — the piece that makes it genuinely useful for a Product Engineer — **live repository state**: which spec branches are ahead/behind, which have uncommitted changes, what each branch's diff looks like, and whether a pull request is open. None of that git/PR data exists in the coordinator today (confirmed: no `repo`/`gitBranches`/`git-status` contract, no git-shell-out beyond `clone`). This specification brings the whole `repository` dashboard into the real client wired to the live store, adds the coordinator-side capability to compute that git/PR state, and removes the non-functional macOS traffic-light bar (`ChromeBar`) that serves no purpose in this build (there is no signed Electron desktop shell shipping yet; see [SPEC-022](022.electron-desktop-app.md)).

## What changes

- ADDED client-shell — a new **Overview** screen (`view: 'dashboard'`), the first screen after opening a project, replacing the specification library as the landing view, in the template's **`repository`** layout (triage + activity, a repository panel, then sessions/sync and pipeline/audit).
- ADDED git-status — the coordinator computes live git branch status (ahead/behind the default branch, working-tree dirty count, diff line/file stats) and GitHub PR status per specification branch, via new read-only `git`/`gh` queries scoped to the project root, and republishes it as a new `repo.status` domain event.
- MODIFIED client-shell — opening or resuming a project routes to `dashboard` instead of `library`; the Specifications nav item remains, unchanged, as its own destination.
- REMOVED client-shell — the desktop window-chrome bar (traffic lights + centred wordmark) is deleted from the shell entirely; the `chrome` store field and its Settings toggle ("Window chrome": Desktop/Browser) are removed along with it. *(breaking: removes a user-visible Settings control.)*

## Requirements

### Requirement: A single Overview screen surfaces what needs a human and what agents are doing
`capability: dashboard` · `delta: ADDED (feat/spec-025-overview-dashboard)`

The system SHALL provide an `Overview` screen, routed as `view: 'dashboard'`, composed entirely from the live store — `cards`, `specs`, `projections`, `audit`, `events`, `notifs`, `project`, `repo`, `gitBranches` (`packages/client/src/store.ts`) — with no hardcoded or demo values. The screen SHALL render, top to bottom: a **triage** panel ("Waiting on you") aggregating every open human gate, every card in `review`, every card in `diff`, and every projection with `health !== 'ok'`, alongside an **activity** rail; a **repository** panel (see the next requirement); then a **sessions in flight** panel listing cards in `authoring` or `implementing` and a **record sync** panel summarising `projections` by `system`, alongside a **pipeline** panel summarising `specs` grouped by `status` and a **recent governed actions** rail (`audit`). This is the template's `repository` layout — there is one Overview layout, not a togglable variant. When a project has no specs and no cards, the screen SHALL render an empty state instead of empty panels.

#### Scenario: Nothing needs a decision
- **WHEN** no card has an open human gate, no card is in `review` or `diff`, and no projection has `health !== 'ok'`
- **THEN** the "Waiting on you" panel shows a calm confirmation state (a positive status dot and "Nothing needs a decision — the harness is working."), not an empty list with no explanation

#### Scenario: A permission gate surfaces in triage
- **WHEN** a card has `needsHuman: true`
- **THEN** the triage panel lists it with a "Decide" action that raises the same permission overlay used by the delivery board (`packages/client/src/screens/board-session-diff-permission.tsx`)
- **AND** selecting a diff-ready card's "Review diff" action navigates to that card's diff view exactly as the board does today

#### Scenario: New project, nothing authored yet
- **WHEN** a project has zero specs and zero cards
- **THEN** the Overview screen shows an empty state directing the user to author a first specification
- **AND** no panel renders with misleading zero/blank content

### Requirement: A repository panel shows live branch, diff and PR status per specification
`capability: dashboard` · `delta: ADDED (feat/spec-025-overview-dashboard)`

The Overview screen SHALL include a **Repository** panel bound to the live store's `repo` (project identity) and `gitBranches` (per-spec branch status) fields. The panel header SHALL show the repository name, default branch, and current `HEAD` short SHA. Each row SHALL show: the branch name and its owning `specId`; ahead/behind counts relative to the default branch; the working-tree dirty-file count, rendered as **"—" (not `0`)** when the branch is not the one currently checked out in the project root, since dirty state is only known for the checked-out branch; added/removed diff line counts and file count relative to the default branch; and a pull-request badge (`open` / `draft` / none) with its number when linked. Selecting a row SHALL navigate to that spec's diff view if a `diff`-column card exists for it, else to the delivery board — matching the navigation the board itself already uses. The panel SHALL show a per-row degraded notice (not a fabricated value) when the coordinator could not compute a row's git or PR data (see the next requirement).

#### Scenario: Ahead/behind and diff stats render for every branch, checked out or not
- **WHEN** a specification's branch has 2 commits ahead and 0 behind the default branch, with a diff of +41/−6 across 5 files
- **THEN** the repository panel row shows those exact ahead/behind and diff numbers, regardless of whether that branch is currently checked out

#### Scenario: Dirty count is honest about what is actually known
- **WHEN** the project root currently has `spec/payment-retry` checked out with 1 uncommitted file, and a different row is `spec/rate-limits` (not checked out)
- **THEN** the `spec/payment-retry` row shows a dirty count of `1`
- **AND** the `spec/rate-limits` row shows "—" for dirty, never a fabricated `0`

#### Scenario: Selecting a row with a diff opens that diff
- **WHEN** a user selects a repository-panel row whose spec has a card in the `diff` column
- **THEN** the client navigates to that card's diff view
- **AND** selecting a row with no `diff`-column card navigates to the delivery board instead

#### Scenario: A row degrades gracefully when git/PR data could not be computed
- **WHEN** the coordinator's most recent `repo.status` computation for a branch failed (e.g. `gh` not installed, or the branch has no upstream)
- **THEN** that row shows a clear "status unavailable" notice for the affected fields
- **AND** no other row is affected

### Requirement: The coordinator computes and republishes git and GitHub PR status per specification
`capability: git-status` · `delta: ADDED (feat/spec-025-overview-dashboard)`

`ProjectContext` (`packages/coordinator/src/project-context.ts`) SHALL gain a repository-status capability, implemented as a new `packages/coordinator/src/git-operations.ts` utility (mirroring the existing `spawnSync`-based pattern in `workspace.ts`) exposing: `gitRepoIdentity(root)` (remote name, default branch, `HEAD` short SHA — via `git remote get-url origin`, `git symbolic-ref`, `git rev-parse`); `gitAheadBehind(root, defaultBranch, branch)` and `gitDiffStat(root, defaultBranch, branch)`, both computed against **remote-tracking refs** so they do not require the branch to be checked out; `gitDirtyCount(root)`, computed via `git status --porcelain` against the root's **currently checked-out** branch only; and `githubPrStatus(branch)`, which queries `gh pr view <branch> --json number,state,isDraft` for the branch's open/draft state (the PR **number** itself is not re-derived — it is read from the `prNumber` the coordinator already tracks per SPEC-008's PR-webhook integration on `SpecLibraryRecord`). Every one of these commands SHALL be read-only (no `git push`, `git commit`, `gh pr create/merge`, or any mutating call), run with a bounded timeout, scoped to the project's own validated root exactly as other `ProjectContext` filesystem operations are, and never require or handle a permission gate (they change nothing). A failure (missing `git`/`gh` binary, command timeout, no upstream) for one branch SHALL be caught, traced with a reason (NFR-7), and SHALL NOT crash the context or block other branches' results.

The coordinator SHALL emit the result as a new `repo.status` domain event (`packages/contracts/src/events.ts`), one per specification branch, and a `repo.identity` event once per project (re-emitted if `HEAD` or the remote changes). Recomputation SHALL be triggered by: (1) `project.open`; (2) a bounded background refresh (no more than once per 60 seconds) while the project is open; (3) immediately, for the affected branch only, after a `diff.finalized` or `session.status` event changes that specification's card; and (4) an explicit client-issued `repo.status.refresh` op (optionally scoped to one `specId`), dispatched the same way other per-context ops are (`server.ts`'s `dispatch`).

#### Scenario: Repo status recomputes after a diff finalizes
- **WHEN** a `diff.finalized` event is recorded for a session belonging to `SPEC-014`
- **THEN** the coordinator recomputes and re-emits `repo.status` for `SPEC-014`'s branch only, not the whole project

#### Scenario: A missing `gh` binary degrades one field, not the whole system
- **WHEN** the `gh` CLI is not installed on the host
- **THEN** every branch's `repo.status` event carries a PR status of "unavailable" rather than a guessed value
- **AND** ahead/behind, dirty count, and diff stats — which do not depend on `gh` — are still computed and published normally
- **AND** the coordinator does not crash or stop processing other events

#### Scenario: A client-requested refresh is scoped and read-only
- **WHEN** a client sends `repo.status.refresh` for a single `specId`
- **THEN** only that specification's branch is recomputed and re-published
- **AND** no git or GitHub mutating command is ever issued by this capability

#### Scenario: Opening an existing project

- **THEN** the client shows the Overview screen, not the specification library

#### Scenario: Specifications nav still works
- **WHEN** a user on the Overview screen clicks "Specifications" in the sidebar

## Design

### Architectural decision

The Overview is a projection screen, like the delivery board, for everything except repository status: `cards`, `specs`, `projections`, `audit`, `events` are already real in `packages/client/src/store.ts` / `packages/client/src/live.ts`. Git and PR status are genuinely new — no such contract, event, or shell-out exists in the coordinator today (confirmed against `project-context.ts`, `server.ts`, `contracts/src/events.ts`). That capability is added following the exact pattern already established for `workspace.ts`'s `spawnSync`-based git calls and for `SpecLibraryRecord`'s existing `prNumber`/webhook integration (SPEC-008) — reused, not duplicated. `ProjectContext` remains the sole owner of a project's filesystem root (SPEC-018); the new git queries run through it, not through the harness adapter (adapter-opencode has no git awareness and should not gain any). The chrome-bar removal is a pure deletion; nothing depends on `store.chrome` outside the call sites named below.

### Target architecture

- **New screen** `packages/client/src/screens/overview.tsx`, registered in `SCREENS.dashboard` and `CRUMBS.dashboard = ['Overview']` in `packages/client/src/root.tsx`.
- **Sidebar** (`packages/client/src/shell.tsx`): add a `Project` group above `Specification` with a single `{ id: 'dashboard', name: 'gauge', label: 'Overview' }` item (the `gauge` icon already exists in `icons.tsx:62`).
- **Routing**: `picker-init-library.tsx:190` (`enter()`) sets `view: state === 'method-ready' ? 'dashboard' : 'init'` (was `'library'`); any other project-open call sites that assumed `'library'` are updated the same way.
- **Shared UI**: the screen composes from existing `Page`, `SectionHead`, and `Empty` (`packages/client/src/utils.tsx`) and existing `Button`, `Badge`, `StatusDot` (`packages/client/src/ds.tsx`) — no new design-system primitives needed.
- **Chrome removal**: delete `ChromeBar` and its call site in `Shell` (`shell.tsx:15-26`, `:186`); delete `chrome` from the store's initial state and any `set({ chrome })` call sites; delete the Settings row at `harnesses-settings.tsx:156`.
- **New coordinator utility** `packages/coordinator/src/git-operations.ts`: `gitRepoIdentity`, `gitAheadBehind`, `gitDiffStat`, `gitDirtyCount`, `githubPrStatus` (all read-only `spawnSync`/`spawn` calls with a bounded timeout, modelled on the existing calls in `workspace.ts:96,121-122`).
- **`ProjectContext` extension** (`project-context.ts`): a `refreshRepoStatus(specId?: string)` method that calls the utility above per branch (from the spec library's existing `branch` field), stores the result, and emits `repo.status` / `repo.identity` through the same event path other domain events already use into the read model.
- **Read model** (`packages/coordinator/src/read-model.ts`, mirrored in `packages/client/src/live.ts`): a new `repoStatusBySpec: Map<specId, RepoStatus>` and `repoIdentity: RepoIdentity | null`, folded from `repo.status` / `repo.identity` events, exposed to the client as `store.gitBranches` (array, one row per spec) and `store.repo`.
- **New op** `repo.status.refresh` (optional `specId`), dispatched via `server.ts`'s existing per-context `dispatch()` path alongside `revert`/`diff.refresh`.

### Data model

The Overview screen reads (read-only, no writes) `cards`, `specs`, `projections`, `audit`, `events` (unchanged shapes) plus two new store fields populated from the coordinator:

```
RepoIdentity { name: string; remote: string; default: string; head: string; lastMerge: string }
// lastMerge is derived from the existing `specs` list's most recently `merged` entry — no new git parsing needed.

RepoStatus (one per specification branch, → client `gitBranches[]`) {
  specId: string; branch: string;
  ahead: number; behind: number;                 // vs default, via remote-tracking refs
  dirty: number | null;                          // null when this branch is not the checked-out one
  added: number; removed: number; files: number;  // git diff --stat vs default
  pr: { number: number; status: 'open' | 'draft' } | null;  // number reused from SpecLibraryRecord (SPEC-008)
  degraded?: { field: 'ahead' | 'dirty' | 'diff' | 'pr'; reason: string }[];
}
```

### Interfaces and contracts

- New wire events in `packages/contracts/src/events.ts`: `RepoIdentityEvent { type: "repo.identity", ...RepoIdentity }` and `RepoStatusEvent { type: "repo.status", ...RepoStatus }`, modelled directly on the existing `SpecRenamedEvent`/`DiffFinalizedEvent` shapes (`events.ts:57-64,168-174`).
- New client-invocable op `repo.status.refresh` (`{ specId?: string }`), handled like `diff.refresh` — routed to `activeCtx(conn).refreshRepoStatus(specId)`.
- No changes to existing ops or events; `SpecLibraryRecord.prNumber` (SPEC-008) is read, never written, by this capability.

### Cross-cutting
- **Design template:** the Overview screen follows the `arke-design` skill (`.claude/skills/arke-design/`) — specifically the "Project overview dashboard" screen in its **`repository`** layout (`Specification Orchestrator.html`'s embedded `bd79c1a7…` asset).
- **Security (NFR-1):** every git/`gh` command this capability runs is read-only and scoped to the project's already-validated root; no new mutating capability is introduced, so no new permission gate is needed.
- **Observability (NFR-7):** a failed git/`gh` call is traced with its reason, matching the existing dead-letter pattern in `adapter-opencode`, rather than silently defaulting to a fabricated value.
- **Accessibility:** triage and repository-panel row actions are real buttons/rows with visible focus states, matching the board's existing permission/diff controls.

### Testing
- **Unit (git-operations):** ahead/behind and diff-stat computed correctly against remote-tracking refs without checkout; dirty count returns a real count for the checked-out branch and `null` for others; a missing `git`/`gh` binary or command timeout is caught and reported as a degraded field, never a thrown error or a fabricated `0`.
- **Unit (read model):** `repo.status`/`repo.identity` events fold into `repoStatusBySpec`/`repoIdentity`; a `diff.finalized` for one spec re-triggers refresh for that spec only.
- **Unit (client dashboard):** triage aggregation covers all four sources (gate, review, diff, projection-unhealthy) and produces the calm empty state when none apply; pipeline counts match `specs` grouped by `status`; the repository panel renders ahead/behind/diff/PR per row and shows "—" for dirty on non-checked-out branches.
- **Component:** opening a ready project renders the Overview screen, not the library; clicking "Specifications" still reaches the library; a triage "Decide" action opens the same permission overlay the board uses; a repository row navigates to diff or board correctly; no `ChromeBar` node renders in any store state.
- **Integration:** a mock project root with two branches (one checked out and dirty, one not) produces one `repo.status` event per branch with correct ahead/behind/dirty/diff, and the PR badge reflects a mocked `gh pr view` response.
- **Regression:** Settings screen renders with no "Window chrome" row; no remaining reference to `store.chrome`.

### Definition of done
Opening or resuming a project lands on a real-data Overview screen in the template's `repository` layout, including live git branch/PR status computed host-side; the traffic-light chrome bar and its Settings toggle are fully removed; a missing `git`/`gh` binary degrades gracefully per-field rather than crashing or fabricating data; existing board/library/settings behaviour is unaffected; suite green; a non-author reviewer has signed off.

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Overview replaces the library as the landing screen; library stays reachable from the sidebar | Matches the template's new default view (`view: 'dashboard'` after empty/setup) without removing existing navigation |
| 2 | Ship the template's `repository` dashboard layout, including live git/PR status, as one Overview (no `focus`/`repository` toggle) | The user asked for the repository version specifically; a togglable variant would be unused complexity |
| 3 | Ahead/behind and diff stats are computed via remote-tracking refs, not by checking out each branch | The coordinator manages one checked-out branch per project root today (no worktree-per-branch model, per SPEC-018); remote-tracking refs give correct, non-destructive answers for every branch without switching what's checked out |
| 4 | Dirty working-tree count is `null` (rendered "—"), not `0`, for any branch that isn't currently checked out | Uncommitted-change state is genuinely undefined for a branch that isn't checked out; reporting `0` would be a fabricated "clean" claim |
| 5 | PR number is reused from the existing SPEC-008 webhook-tracked `SpecLibraryRecord.prNumber`; only open/draft state is freshly queried via `gh` | Avoids re-deriving data the coordinator already has correctly; narrows the new `gh` dependency to the one field it doesn't already track |
| 6 | All new git/`gh` calls are read-only, bounded-timeout, and never gated | They mutate nothing (no push/commit/PR-create/merge), so the existing permission-gate machinery doesn't apply and shouldn't be forced onto them |
| 7 | Chrome-bar removal is an outright deletion, not a default-off toggle | The bar is non-functional in this build (no signed desktop shell yet) and the user asked for it gone, not hidden |

## Open questions
- Should the coordinator eventually manage a git worktree per specification branch so working-tree dirty state can be reported for *every* branch, not just the one currently checked out? Decision #4 above is the honest answer for now; a worktree-per-branch model would be a larger follow-on capability.
- What is the right steady-state background-refresh interval (spec proposes ≤60s) — should it be configurable per project, and should it pause entirely when the Overview screen isn't the active view (to cut idle `git`/`gh` calls)?
- Does `gh` need to be an explicitly probed/reported host dependency (alongside the existing harness probes in SPEC-005/016), so a missing `gh` shows up as a setup issue rather than only as a degraded dashboard row?
