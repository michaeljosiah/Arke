# OKF grounding layer — typed grounding on the docs/ tree

## Why

The specification agent is grounded on *how to work* (AGENTS.md) and, at authoring time, on ad-hoc uploaded files — but it has no durable grounding on *what the project is and why*: the product, the business, the domain. This specification gives Arke a durable grounding layer that draws foundational context from the **OKF `docs/` tree by `type`** (no special folder) and injects it — alongside the existing-spec corpus and the codebase — into authoring and review. So every spec is grounded on the **business** and on the **code**. It builds on the OKF convention and the generated spec index from [SPEC-026](026.okf-grounding-and-spec-index.md).

## What changes

- ADDED grounding — foundational business/product/domain context is authored as **typed OKF documents across `docs/`** (no dedicated folder): documents tagged `type: product-overview` / `business-context` / `domain-glossary` / … are selected *by type* and ground every authoring and review session.
- ADDED grounding — a **two-tier grounding split**: committed truth = the typed OKF documents anywhere in `docs/` (shared, public-safe) vs. local material in the git-ignored `.arke/grounding/` (sensitive-not-to-commit, or ephemeral per-effort uploads).
- MODIFIED grounding — the authoring/review context injection is upgraded to a **precisely-specified typed grounding digest**: authoritative business grounding, the existing-spec index digest, and (separately framed) session uploads — eager-map/lazy-body.

**Depends on:** SPEC-026 (OKF convention + the generated `docs/specifications/index.md` this consumes as the spec-index digest), SPEC-020 (`groundingUpload`/`groundingList`), SPEC-007 (`groundingSummary`/`buildReviewerPrompt`). Builds on `parseFrontmatter` (`contracts/src/spec-doc.ts`).

## Requirements

### Requirement: Foundational grounding is authored as typed OKF documents in `docs/`
`capability: grounding` · `delta: ADDED (feat/spec-027-okf-grounding-layer)`

The project's foundational context — the durable answer to *what is this project, for whom, why, and how does it make money* — SHALL be authored as OKF documents **anywhere under `docs/`** (per the SPEC-026 convention), tagged with a grounding `type` from the open vocabulary (`product-overview`, `business-context`, `domain-glossary`, `architecture`, `convention`). There is **no dedicated grounding folder**; the grounding digest selects these documents **by `type`**, wherever they live. Because they live under `docs/` (tracked), they are reviewed and shared by construction — they survive a fresh clone and never diverge per-machine. Such a document is **baseline environmental truth, not a lifecycle-governed artefact**: it never acquires a `status`, never gets a board card, and never enters the draft→delivered flow, and it is read-only grounding — never written back into a spec. (This specification authors *requirements for the grounding mechanics*; it does not make any grounding document's *content* a governed spec.)

#### Scenario: Grounding survives a clone
- **WHEN** the repository is freshly cloned
- **THEN** the typed grounding documents under `docs/` are present (tracked git content, not runtime state)

#### Scenario: Grounding is selected by type, not folder
- **WHEN** a document tagged `type: product-overview` is added under any `docs/` subfolder
- **THEN** the grounding digest includes it, regardless of location

#### Scenario: Grounding is not lifecycle-governed
- **WHEN** a grounding document is added or edited
- **THEN** it acquires no `status`, no board card, and no lifecycle transition

---

### Requirement: Grounding is two-tier — committed truth vs. local material
`capability: grounding` · `delta: ADDED (feat/spec-027-okf-grounding-layer)`

Grounding SHALL have two homes with distinct guarantees. **Committed** grounding — the typed OKF documents under `docs/` (tracked) — is shareable, public-repo-safe project truth. **Local** grounding (`.arke/grounding/`, git-ignored per the existing `.arke/*` rule) is for material that MUST NOT be committed — sensitive business/client/endpoint detail — or for ephemeral per-effort uploads (`groundingUpload`). The system SHALL NOT relocate local grounding into the tracked tree automatically; promoting local material to committed truth is a deliberate human act. Local grounding SHALL be listed **recursively** so `groundingUpload`'s nested paths are all surfaced (today `groundingList` lists only top-level entries — this widens it, or `groundingUpload` SHALL reject nested paths; recursive listing is preferred). Because committing a grounding document to the tracked `docs/` tree is a real leak surface on a public repo, the definition of done SHALL include a documented reviewer-checklist note for grounding-document commits; no automated secret-scan is in scope, but the risk SHALL be called out rather than left implicit.

#### Scenario: Sensitive material stays out of git
- **WHEN** a file is placed in `.arke/grounding/`
- **THEN** it is git-ignored, never committed, never auto-copied into the tracked `docs/` tree, yet available to the local authoring agent

#### Scenario: Nested local uploads are all surfaced
- **WHEN** `groundingUpload` writes a nested path under `.arke/grounding/`
- **THEN** the recursive listing includes it (or the upload is rejected with a clear reason)

### Requirement: Authoring and review receive a precisely-specified typed grounding digest
`capability: grounding` · `delta: MODIFIED (feat/spec-027-okf-grounding-layer)`

There are **two distinct injection sites**, and this requirement corrects both. (1) The **reviewer** grounding is `groundingSummary()`, injected into the reviewer prompt via `buildReviewerPrompt` in `convenePanel` — today AGENTS.md-only. (2) The **authoring** grounding is the `specContext` assembly in the prompt-send/dispatch path — today it names **only** `.arke/grounding/` uploaded files ("source material for this discussion"); it does not inject AGENTS.md or any `docs/` list. Both SHALL be upgraded to a **typed grounding digest** with three clearly-labelled parts, defined precisely enough to test:

- **(a) business grounding** — every `docs/` document whose `type` is a grounding type (`product-overview` | `business-context` | `domain-glossary` | `architecture` | `convention`), selected by type across the whole tree (not a folder): its `type`, `title`, relative path, and a summary = the first non-empty markdown paragraph after the frontmatter, truncated to a configured budget (default 500 chars). Framed as foundational context the specification must be consistent with.
- **(b) spec-index digest** — for each spec in the SPEC-026 generated index: `number`, `title`, `status`, `capabilities`, relative path; ordered by `NNN`. Framed as the corpus to avoid duplicating/contradicting and to cross-link.
- **(c) session uploads** — the `.arke/grounding/` local tier, by explicit path, framed as source material for this discussion.

Injection SHALL follow **eager map, lazy body**: inject the digest above (bounded, high-signal), and let the agent read full bodies on demand. Because the agent's `glob`/`grep` skip dot-dirs and git-ignored paths, any **lazy body in the `.arke/grounding/` local tier SHALL be referenced by explicit path** (the agent cannot discover it by search) — committed grounding bodies under `docs/` are tracked and discoverable normally. A total digest size budget SHALL bound the injected text so it stays bounded as the corpus grows.

#### Scenario: The author knows the existing corpus
- **WHEN** an authoring session starts
- **THEN** its context includes the spec-index digest (number, title, status, capabilities, links), so it can reference related specs and avoid duplicating them

#### Scenario: Business grounding frames the draft, distinctly from uploads
- **WHEN** an authoring session starts and `docs/` contains any grounding-typed document
- **THEN** the business grounding is injected as authoritative foundational context, labelled distinctly from the `.arke/grounding/` session uploads

#### Scenario: A local lazy body is reachable
- **WHEN** a `.arke/grounding/` upload is offered as a lazy body
- **THEN** it is referenced by explicit path (not left for `glob`/`grep`, which skip the git-ignored dot-dir)

## Design

### Architectural decision

Grounding is a **read-only injection layer** over the OKF `docs/` tree (SPEC-026), selected by `type` rather than folder. It never writes back into a spec and never becomes a governed artefact — it sits *underneath* the lifecycle as input. Two tiers (committed `docs/` vs. private `.arke/grounding/`) keep sensitive material out of git while still grounding the local agent.

### Target architecture

- **`buildGroundingDigest()`** (coordinator) — walks `docs/`, parses frontmatter, filters by grounding `type`, and assembles the three-part digest `{ businessGrounding: GroundingDoc[]; specIndexDigest: SpecIndexEntry[]; sessionUploads: { path: string }[] }`, honouring the size budget. Shared by both injection sites.
- **Reviewer path** — `groundingSummary()` calls `buildGroundingDigest()`; `buildReviewerPrompt` renders it.
- **Authoring path** — the `specContext` assembly calls the same helper and renders the three labelled sections; local-tier uploads referenced by explicit path.
- **Local listing** — `groundingList()` becomes recursive (or `groundingUpload` rejects nested paths).

### Cross-cutting

- **Security / privacy:** the two-tier split is the control — sensitive detail lives in the git-ignored `.arke/grounding/` and is never auto-promoted. A committed grounding document under `docs/` carries the same sanitisation duty as the rest of the tracked tree; the DoD adds a reviewer-checklist note. (Consistent with keeping endpoint/client docs out of a public history.)
- **Performance:** the `docs/` walk is O(n) over markdown files; cache per project-context and invalidate on the SPEC-026 watcher's signal to avoid re-walking on every turn.
- **Design template:** any UI touch (e.g. surfacing grounding in the cockpit) follows the `arke-design` skill; this slice is coordinator + prompt assembly.

### Testing
- Unit: digest composition (fields, ordering, summary extraction, size budget); by-type selection across the tree; local-tier explicit-path rendering.

### Definition of done
- All scenarios pass; `npm run typecheck` + `npm run build` green.
- Grounding-typed OKF docs under `docs/` are selected by type + injected as authoritative grounding at both sites; `.arke/grounding/` git-ignored, listed recursively, never auto-promoted; a reviewer-checklist note for grounding-document commits is documented.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | No dedicated grounding folder; grounding selected by `type` across `docs/` | Aligns with SPEC-026's "whole `docs/` is OKF"; a special folder contradicts it |
| 2 | Grounding is *not lifecycle-governed* (reworded from "no spec about it") | Removes the literal contradiction that this spec authors requirements for the grounding mechanics (review, reviewer-b) |
| 3 | Local tier listed recursively; lazy bodies referenced by explicit path | `glob`/`grep` skip git-ignored dot-dirs, so search cannot reach `.arke/grounding/` (review, reviewer-a/-b) |
| 4 | Precisely-specified digest (fields, ordering, summary rule, size budget) | The review found "typed grounding" underspecified to test (reviewer-b, blocking); corrected injection anchors (reviewer-a, blocking) |
| 5 | Split from the combined OKF spec | Grounding (`grounding`) and index generation (`spec-library`) are independent capabilities; this is the grounding half — see SPEC-026 Decision #9 |
