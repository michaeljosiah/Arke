# Conformance sentinel — delivered code kept honest against its specification

## Why

Everything in Arke flows **spec → code**: gated authoring, review, and one-way projections, up to `delivered`. But delivery is not the end of a codebase's life — the moment a spec is `delivered`, the code keeps moving (hotfixes, unrelated PRs, direct commits), and nothing in the corpus watches for the **delivered code drifting away from the specification that justified it**. That is the exact flank the "code is the source of truth, specs always drift" critique attacks. Arke's answer to drift is currently only the *forward* direction (generate downstream from the spec); it has no *reverse* guard. The conformance sentinel makes the spec load-bearing **after** delivery too, by converting drift from silent to loud — a governed signal, not a stale file nobody notices.

## What changes

- ADDED conformance — every `delivered` spec records a **footprint** (the repository paths its delivery changed), so "which code does this spec govern?" is a deterministic, stored fact rather than a guess.
- ADDED conformance — a **conformance state** (`conformant` / `drifted` / `unknown`) is projected onto `delivered` cards, **orthogonal** to the governed `SpecStatus` and never a hard gate on its own.
- ADDED drift-detection — a **two-tier check** (deterministic executable checks first, an independent reviewer panel second) evaluates the current code against the spec's requirements, on changes that touch the footprint.
- ADDED drift-detection — drift is raised **only on agreement**; a single-model or uncertain verdict is logged, never raised, so the sentinel stays quiet enough to be trusted.
- ADDED conformance — a confirmed drift **proposes, never auto-acts**: it surfaces on the board and the trace and waits for one of three governed human resolutions (**ratify** — amend the spec to match the code, in place / code corrected to spec / accepted exception).

**Depends on:** SPEC-024 (lifecycle gating — `delivered`, `applyTransition`, reopen edges), SPEC-008 (lifecycle, normative-hash), SPEC-007 (independent review panel), SPEC-014 (deterministic projection & integrations), SPEC-015 (audit trace & observability), SPEC-010 (delivery board). **Relates to:** SPEC-030 (cross-repo ripple), SPEC-035 (agent-adjudicated review).

## Requirements

### Requirement: Delivered specs record a conformance footprint
`capability: conformance` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

On reaching `delivered`, the coordinator SHALL record the set of repository paths the delivery changed as the specification's **footprint**, derived deterministically from the delivery diff (SPEC-024's delivered merge / SPEC-028's implementer session), and persist it as a projection (`spec.footprint { specId, paths[], source }`). A specification MAY declare or override its footprint with a `conformance:` frontmatter block — `paths:` globs to widen or narrow the surface, or `off` to opt a spec out of sentinel coverage entirely. A `delivered` spec with **no** footprint (opted out, or delivered before this capability existed) SHALL be reported `unknown`, never silently treated as `conformant`; absence of evidence is not conformance.

#### Scenario: Delivery captures the footprint
- **WHEN** a spec reaches `delivered`
- **THEN** its changed-path set is recorded as `spec.footprint` with `source: "delivery-diff"`
- **AND** the delivered card's conformance state initialises to `conformant`

#### Scenario: Frontmatter override is honoured
- **WHEN** a spec's `conformance:` frontmatter declares `paths:` globs
- **THEN** the declared globs replace the derived footprint for that spec

#### Scenario: No footprint is reported unknown, not conformant
- **WHEN** a `delivered` spec has `conformance: off` or no recorded footprint
- **THEN** its conformance state is `unknown` and it is excluded from drift checks
- **AND** it is never reported `conformant` on the strength of missing evidence

### Requirement: A footprint change on a delivered spec enqueues a check
`capability: drift-detection` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

When a change lands on the mainline that touches one or more paths in a `delivered` spec's footprint, and Arke did **not** originate that change as the spec's own delivery, the coordinator SHALL enqueue a conformance check for that spec. Following SPEC-024's host-optional stance, the trigger SHALL work with **or without** a git host: a merge webhook where a host is configured, and a local post-merge signal or an explicit `arke conformance check [specId]` op where host-less. Checks SHALL be **debounced and batched** per spec (a burst of commits collapses to one check) so the sentinel does not thrash, and every enqueue SHALL be recorded (`conformance.enqueued { specId, trigger, paths }`). A spec whose delivery is the origin of the change SHALL NOT trigger a check against itself.

#### Scenario: Unrelated change to the footprint triggers a check
- **WHEN** a merge touches a path inside a delivered spec's footprint and was not that spec's own delivery
- **THEN** a conformance check is enqueued for that spec and recorded as `conformance.enqueued`

#### Scenario: The spec's own delivery does not self-trigger
- **WHEN** the change on the mainline is the delivery diff of the spec itself
- **THEN** no conformance check is enqueued for that spec

#### Scenario: Host-less trigger works
- **WHEN** no git host is configured and `arke conformance check` is run after a local merge
- **THEN** checks are enqueued for every delivered spec whose footprint the merge touched

#### Scenario: A burst collapses to one check
- **WHEN** several commits touch a spec's footprint within the debounce window
- **THEN** exactly one conformance check runs for that spec, not one per commit

---

### Requirement: Two-tier evaluation — deterministic first, judged second
`capability: drift-detection` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

A conformance check SHALL evaluate the current code against each of the spec's requirements in two tiers. **Tier 1 (deterministic):** any requirement with a projected executable conformance check (a projection under SPEC-014 — e.g. a generated assertion or test bound to an `R-n` scenario) SHALL be executed in the harness, and its pass/fail is **authoritative** for that requirement. **Tier 2 (judged):** requirements without an executable check SHALL be evaluated by an **independent reviewer panel** reusing SPEC-007's provable-distinctness guarantee, each reviewer returning `satisfied` / `violated` / `uncertain` for the requirement together with cited `file:line` evidence. All evaluation SHALL run **inside the harness host**; the browser is never in the credential path and never reads the repository directly (NFR — the wager). The check SHALL emit one `conformance.checked { specId, perRequirement[], state }` result.

#### Scenario: A deterministic check decides its requirement
- **WHEN** a requirement has a projected executable conformance check
- **THEN** that check runs in the harness and its result is authoritative for the requirement, with no model vote consulted for it

#### Scenario: A non-mechanizable requirement is judged independently
- **WHEN** a requirement has no executable check
- **THEN** an independent panel of provably-distinct reviewers evaluates it against the current code and returns per-reviewer verdicts with cited evidence

#### Scenario: Evaluation stays host-side
- **WHEN** any tier of a check runs
- **THEN** repository and agent access happen inside the harness host and the browser neither holds credentials nor reads the repo

### Requirement: Drift is raised only on agreement; uncertainty is logged, not raised
`capability: drift-detection` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

A requirement SHALL be reported **`violated`** only when either its Tier-1 deterministic check fails, or **at least two provably-distinct** Tier-2 reviewers independently agree it is violated **with cited evidence**. A lone violated verdict, or any `uncertain`, SHALL NOT raise a drift signal — it SHALL be recorded as `conformance.low-confidence { specId, requirement, verdicts }` and surfaced as advisory only. This precision bar is a hard requirement, not a tuning knob: a sentinel that cries wolf is worse than none, because a false-loud signal trains the team to ignore the true one. The spec's overall conformance state SHALL be `drifted` if **any** requirement is `violated`, else `conformant`.

#### Scenario: Two independent reviewers agree — drift is raised
- **WHEN** two provably-distinct reviewers both find a requirement violated with cited evidence
- **THEN** the requirement is reported `violated` and the spec's state becomes `drifted`

#### Scenario: A lone or uncertain verdict does not raise drift
- **WHEN** only one reviewer finds a violation, or a reviewer returns `uncertain`
- **THEN** no drift signal is raised; it is recorded as `conformance.low-confidence` and shown as advisory
- **AND** the spec's state is not set to `drifted` on that requirement alone

#### Scenario: A failed deterministic check raises drift on its own
- **WHEN** a Tier-1 executable conformance check fails
- **THEN** its requirement is reported `violated` regardless of any model vote

---

### Requirement: A confirmed drift proposes and surfaces — it never auto-acts
`capability: conformance` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

On a confirmed drift, the coordinator SHALL set the spec's conformance state to `drifted`, surface it on the delivered board card (a conformance badge with the violated requirement, scenario, and cited evidence), emit `conformance.drift-detected { specId, requirement, scenario, evidence, verdicts }` to the append-only trace (SPEC-015), and notify (SPEC-022 desktop notification where available). It SHALL **NOT** modify the specification, edit the code, open a PR, or write to any system of record — resolution is a human decision (propose · decide · execute, the non-negotiable rule). The conformance state SHALL be a **projection attached to `delivered` specs only**, distinct from `SpecStatus`; it SHALL NOT change the governed `status` by itself, and SHALL NOT gate, block, or delay the delivery of any other specification.

#### Scenario: Drift surfaces without side-effects
- **WHEN** a drift is confirmed for a delivered spec
- **THEN** the card shows a `drifted` badge with the requirement and evidence, `conformance.drift-detected` is traced, and the human is notified
- **AND** no spec text, code, PR, or system of record is modified

#### Scenario: Conformance state does not move the lifecycle by itself
- **WHEN** a spec becomes `drifted`
- **THEN** its governed `SpecStatus` remains `delivered`; only the "code corrected to spec" resolution re-enters delivery, while ratify and accept keep it `delivered`
- **AND** no other spec's delivery is blocked or delayed

---

### Requirement: A human resolves a drift one of three governed ways
`capability: conformance` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

From a `drifted` spec, a human SHALL choose exactly one governed resolution, each recorded as `conformance.resolved { specId, resolution, actor, reason? }` on the trace. **(1) Ratify — amend the spec to match the code, in place** — the drift is legitimate (the implementation revealed a gap the specification missed, or a deliberately better approach emerged) and the shipped code is the desired behaviour: the human is shown the drift as a **proposed spec amendment** (which an agent MAY draft), reviews it, and on acceptance the specification text is updated in place to match the code, after which the conformance check re-runs — and, the code now matching the amended spec, **passes** — returning the state to `conformant`. Ratification SHALL NOT reset the lifecycle: the spec **stays `delivered`**, no re-review panel is required, and **no delivery is re-dispatched** — the work is already done and is being *ratified, not redone*. The human's acceptance is the gate **by default**; a review of the amendment is not forced. A project MAY opt in to a lightweight independent check that the amended wording faithfully matches the code for amendments above a configurable size, but this is **off by default**. **(2) Code corrected to spec** — the code is wrong: a corrective delivery is dispatched against the existing approved spec (SPEC-028 single-session delivery), and the drift clears when that delivery lands and the next check passes. **(3) Accepted exception** — a deliberate, recorded tolerance that changes neither code nor spec: the state moves to `conformant` with a **required** `reason`, and the accepting requirement is excluded from re-raising until the code changes again. Every resolution SHALL route through a gated op (like every governed transition, SPEC-024) so it is auditable regardless of trigger; a ratified amendment SHALL be recorded on the trace and in the spec's git history like any other authored change.

#### Scenario: Ratify amends the spec in place without a reset
- **WHEN** a human resolves a drift as "ratify"
- **THEN** the spec text is updated to match the code, the conformance check re-runs and passes, and the state returns to `conformant`
- **AND** the spec stays `delivered` — no re-review is forced and no delivery is re-dispatched

#### Scenario: Ratification defaults to human acceptance as the gate
- **WHEN** a drift is ratified and no amendment-review threshold is configured
- **THEN** the human's acceptance alone ratifies the amendment — no independent review panel is required
- **AND** the amendment is recorded on the trace and in the spec's git history

#### Scenario: Code corrected to spec
- **WHEN** a human resolves a drift as "code corrected to spec"
- **THEN** a corrective implementer session is dispatched against the existing spec and the card shows the correction in flight
- **AND** the conformance state returns to `conformant` when the next check passes

#### Scenario: Accepted exception requires a reason
- **WHEN** a human accepts a drift as a deliberate exception
- **THEN** the resolution is rejected unless a `reason` is supplied
- **AND** on acceptance the state is `conformant`, the exception is recorded, and that requirement does not re-raise until the code changes again

## Design

### Architectural decision

Conformance is modelled as a **read-model projection orthogonal to the governed lifecycle**, not a new `SpecStatus`. The lifecycle (SPEC-008/024) stays exactly four values; drift is a *badge* on `delivered` cards that only a human resolution acts on — and most resolutions (ratify, accept) keep the spec `delivered` rather than resetting it, so ratifying legitimate drift ratifies finished work instead of re-opening it. This preserves the "governance is a small set of gated ops" invariant and answers the philosophical question directly — *is this drift a fix or a regression?* — by refusing to answer it automatically: the sentinel detects and proposes; the human decides which of the two it is. The two-tier check (deterministic-authoritative, judged-only-on-agreement) is the "executable projections keep specs honest, models cover the rest" synthesis made concrete.

### Target architecture

- **Contracts** (`packages/contracts`): add `spec.footprint`, `conformance.enqueued`, `conformance.checked`, `conformance.low-confidence`, `conformance.drift-detected`, `conformance.resolved`; the `ConformanceState` enum (`conformant | drifted | unknown`) as a read-model field on delivered specs (distinct from `SpecStatus`); the `conformance:` frontmatter block (`paths?: string[]`, `off?: boolean`); the per-requirement verdict shape. All zod-first, validated at the boundary.
- **Coordinator** (`packages/coordinator`): a **sentinel scheduler** that maps a mainline change's paths to affected delivered specs (via stored footprints), debounces, and enqueues checks; a **footprint recorder** hung off the `delivered` transition (SPEC-024); a **conformance folder** that folds check results into the read model and pushes ordered events to the client; the three resolution ops wired into the gated-op dispatcher — ratify (#1) updates the spec text in place and re-runs the check (no lifecycle transition), code-corrected (#2) dispatches a corrective SPEC-028 delivery, accept (#3) records the exception — so no common path forces a `delivered → in-review` reset. No cloud backend on the hot path.
- **Harness / adapters** (`packages/adapter-*`): the check **executor** runs Tier-1 executable checks and drives the Tier-2 reviewer panel inside the harness host; results return over the normalised event seam. Capability-flagged so an adapter that cannot run checks degrades to judged-only (or reports `unknown`).
- **Client** (`packages/client`): a conformance badge on delivered board cards; a drift panel showing the violated requirement, scenario, and cited `file:line` evidence; the three-way resolution affordance (propose·decide·execute). Thin realisation layer, no authoritative state.
- **CLI** (SPEC-017): `arke conformance check [specId]` for the host-less / CI trigger.

### Data model

- `spec.footprint` — `{ specId, paths: string[], source: "delivery-diff" | "frontmatter", recordedAt }`, one current projection per delivered spec.
- `ConformanceState` — read-model field on delivered specs: `conformant | drifted | unknown` (+ the violated-requirement detail when `drifted`).
- Trace events (append-only, SPEC-015): `conformance.enqueued`, `conformance.checked`, `conformance.low-confidence`, `conformance.drift-detected`, `conformance.resolved`.

### Interfaces and contracts

- New ops: `conformance.check { specId? }`; `conformance.resolve { specId, resolution: "ratify" | "code-corrected" | "accept", reason?, amendment? }` (gated). `ratify` carries the accepted amendment text (agent-drafted or human-edited) applied to the spec in place.
- New events/errors listed above; `conformance.resolve` rejects "accept" without a `reason` (`conformance.reason-required`).
- Frontmatter: optional `conformance: { paths?: string[], off?: boolean }`.

### Cross-cutting

- **Design template:** the conformance badge, drift panel, and resolution affordance follow the `arke-design` skill (`.claude/skills/arke-design/`) — shadcn neutral tokens, Geist, Lucide, and the prototype screens; drift uses the teal accent (SPEC-033) for attention, not a raw red alarm.
- **Security / governance (the wager):** all evaluation runs host-side; the browser never reads the repo or holds credentials; every check, signal, and resolution is on the append-only trace before any client sees it; no agent output (a proposed correction) reaches the repo or a system of record without the human resolution in between.
- **Precision / cost:** the agreement bar (R4) and debounce/batch (R2) bound both false-loud noise and token spend; Tier-1 executable checks are preferred precisely because they are cheap and unambiguous. Checks are opt-out per spec (`conformance: off`) and never block unrelated delivery.
- **Observability:** check latency, drift rate, and false-positive resolutions (accepted-exception ratio) are surfaced via SPEC-015's OTLP path so the sentinel's own trustworthiness is measurable.

- [ ] Coordinator: sentinel scheduler — map a mainline change's paths → affected delivered specs → debounced, batched `conformance.check` enqueue; `conformance.enqueued` traced; self-delivery exclusion.

**Phase C — signal & resolution**
- [ ] Client: drift panel (requirement + scenario + `file:line` evidence) and the three-way resolution affordance; teal-accented `drifted` badge.
- [ ] Coordinator: `conformance.resolve` gated op — #1 (ratify) applies the accepted amendment to the spec in place, re-runs the check (expected `conformant`), and keeps the spec `delivered` with no re-review forced and no re-delivery (human-accept is the default gate; optional light amendment-check above a configurable size, off by default); #2 dispatches a corrective SPEC-028 delivery; #3 records accepted-exception with required `reason`; `conformance.resolved` traced; ratified amendment committed to the spec's git history; re-raise suppression for accepted exceptions until the code changes.
- [ ] CLI + host-less trigger: `arke conformance check [specId]`; local post-merge signal.
- [ ] Observability: check latency, drift rate, accepted-exception ratio to the SPEC-015 OTLP path.

### Testing
- **Unit (footprint):** delivery records the changed-path set; frontmatter `paths`/`off` override; no footprint ⇒ `unknown`, never `conformant`.
- **Unit (trigger):** footprint-touching merge enqueues exactly one check per spec after debounce; the spec's own delivery does not self-trigger; host-less `arke conformance check` enqueues for every touched footprint.
- **Unit (two-tier):** a projected executable check is authoritative; a non-mechanizable requirement goes to the independent panel; evaluation runs host-side only.
- **Unit (agreement):** two distinct reviewers agreeing ⇒ `violated`; a lone/uncertain verdict ⇒ `low-confidence`, not `drifted`; a failed deterministic check ⇒ `violated` alone.
- **Unit (no side-effects):** a confirmed drift writes badge + trace + notification and touches no spec/code/PR/system-of-record; `SpecStatus` unchanged; no other spec blocked.
- **Unit (resolution):** #1 (ratify) applies the amendment in place, re-checks to `conformant`, leaves the spec `delivered` with no re-delivery and no forced re-review, and records the amendment on the trace + git; #2 dispatches a corrective session and clears on the next passing check; #3 rejects without a `reason`, then suppresses re-raise until the code changes; every resolution traced through the gated op.
- **Integration:** deliver a spec → mutate its footprint on the mainline → sentinel enqueues → two-tier check confirms drift → card shows `drifted` with evidence → each of the three resolutions drives the correct governed outcome; end-to-end with **and** without a git host.

### Definition of done
Delivered specs carry a footprint and a conformance state orthogonal to `SpecStatus`; a footprint-touching change runs a debounced two-tier check host-side; drift is raised only on deterministic failure or ≥2-reviewer agreement, uncertainty logged not raised; a confirmed drift surfaces and traces without any side-effect; all three resolutions run as gated, audited ops (ratify amends the spec in place with no lifecycle reset and human-accept as the default gate; code-corrected re-delivers; accept tolerates with a reason); works host-optional; suite green; a non-author reviewer has signed off.

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Conformance is a read-model projection, not a 5th `SpecStatus` | Keeps the lifecycle at four gated values (SPEC-008/024); drift is advisory-until-decided, so it must not silently move governed state |
| 2 | Footprint is captured from the delivery diff, overridable in frontmatter | Deterministic and grounded in what actually shipped; globs let a spec widen/narrow or opt out without guessing |
| 3 | Two tiers, deterministic authoritative | Executable checks are cheap and unambiguous — the "executable projections keep specs honest" half; models cover only what can't be mechanized |
| 4 | Drift raised only on ≥2-reviewer agreement or a failed deterministic check | A false-loud sentinel is worse than none: it trains the team to ignore the true signal. Precision is a hard requirement, not a knob |
| 5 | Confirmed drift proposes, never auto-acts | The non-negotiable propose·decide·execute rule; "is this drift a fix or a regression?" is a human judgement, by design |
| 6 | Three resolutions; ratify (#1) amends the spec in place with no lifecycle reset | Legitimate drift — a gap the spec missed, or a better approach found in implementation — is *ratified, not redone*: the work is already `delivered`, so the spec stays `delivered` while its text catches up, and the check re-passing is itself the proof the amendment matches the code. Forcing a `delivered → in-review` reset + re-delivery would treat finished work as unfinished. "Code corrected" re-enters delivery; "accept" tolerates |
| 7 | Host-optional trigger | Mirrors SPEC-024: governance must not require a git host; webhook where present, `arke conformance check` / local post-merge where not |
| 8 | Ratification defaults to human-accept only (no forced re-review) | The behaviour is already delivered and was independently arrived at; requiring a full review panel to ratify a legitimate drift is friction without payoff. An optional lightweight amendment-check for large changes is available but off by default — the spec change is still recorded on the trace and in git regardless |

## Open questions
- **Footprint granularity:** file-level is the baseline; is symbol/region-level worth it later to cut false triggers on large shared files, or does that overfit? (Lean: start file-level, measure the false-trigger rate via the observability signal before investing.)
- **Scheduling model:** event-driven only (on merge), or also a periodic sweep to catch out-of-band changes (force-push, rebase) the webhook path misses? (Lean: event-driven for v1, a low-frequency reconciliation sweep as a fast follow.)
- **Cross-repo drift:** when a spec is cross-repo (SPEC-030), does a footprint span repos, and does a ripple pointer's target repo participate in the same check? (Defer to a SPEC-030 follow-up; keep v1 single-repo.)
- **Accepted-exception decay:** should an accepted exception expire after N further changes to the requirement's evidence region, forcing periodic re-confirmation rather than a permanent silence?
