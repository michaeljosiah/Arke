# Arke Desktop — a one-click, native Electron app

## Why
Today Arke runs as a coordinator process + a Vite dev client + a browser tab, brought up by `arke up` (SPEC-017) — a terminal and a second toolchain stand between a product engineer and the product. A browser tab also cannot hand the host a real project path, so opening a project is a typed-path / recents flow rather than a native picker. SPEC-001 already scaffolded the shell as **`apps/desktop`** (`@arke/desktop`) — *"an Electron desktop shell that embeds the coordinator and serves the React client as one signed app"* — but it is inert. This spec **fills in that skeleton**: a signed, double-click app that embeds the coordinator, gives a native folder dialog (a real path straight to `project.open`), surfaces the human-in-the-loop gates as OS notifications, and auto-updates — Arke as a product, not a dev stack.

## What changes
- ADDED desktop-shell — fill in the existing **`apps/desktop`** (`@arke/desktop`) skeleton (SPEC-001 R-1): an **Electron** app whose main process **embeds the coordinator in-process** (`startCoordinator()`) and renders the built **`@arke/client`** in a sandboxed renderer, driving it over the same WebSocket as the browser. (breaking: no)
- ADDED native-integration — affordances a browser cannot give: a real **folder picker** to open a project (a genuine absolute path → `project.open`), an application menu + accelerators, single-instance focus, and window-state persistence. (breaking: no)
- ADDED notifications — OS notifications for attention states derived from concrete stream events (`permission.asked`, `elicitation.asked`, a task `session.status:waiting|error`, `panel.complete` / `panel.config-error` / `panel.reviewer-error`), de-duplicated by domain id and pruned on resolution, mutable. (breaking: no)
- ADDED service-lifecycle — app launch brings the whole stack up and quit tears down exactly what it started, with the harness-missing case handled and a main-derived "work-in-flight" gate; the shell drives the system only *through* the coordinator (NFR-1/7). (breaking: no)
- ADDED packaging — signed, notarised per-OS installers (dmg / nsis / AppImage) with in-app **auto-update**. (breaking: no)
- MODIFIED coordinator — a thin, additive programmatic entry `startCoordinator(opts): Promise<{ url; stop() }>` (constructing a `Coordinator` directly with explicit root/paths — not the import-time env constants) and a compiled-JS `dist` build + `exports` so the desktop bundle can embed it, plus a `workInFlight(): boolean` query; behaviour otherwise unchanged. (breaking: no)
- MODIFIED client — three small, **browser-safe** additive changes so one build serves both surfaces: resolve the coordinator URL **lazily at connect time** from `window.arke?.coordinator?.url` (else today's `VITE_ARKE_COORDINATOR_URL ?? ws://127.0.0.1:4319`), **self-host the Geist fonts** (remove the remote Google Fonts `<link>`), and set a **relative Vite `base` (`./`)**; no behavioural fork. (breaking: no)

## Requirements

### Requirement: One launch brings the whole stack up, ready
`capability: service-lifecycle` · `delta: ADDED (feat/electron-desktop-app)`

Launching the app SHALL start an **embedded** coordinator in-process via `startCoordinator({ root, manageHarness, … })`, bind it to a local port, and reveal the workspace only once it is ready — `startCoordinator()` resolving IS the readiness signal, and it returns the **actual bound URL** (built from `Coordinator.start()`'s returned port), which the renderer receives via the preload `coordinator.url` bridge (never a hardcoded port). The embedded coordinator's **default context SHALL be rooted at a neutral app-state directory** (Electron `userData`), NOT `process.cwd()` (which in a packaged app is the read-only resources dir), and SHALL NOT spawn a managed harness for that neutral root — the managed harness (SPEC-016) is started per **real** project when it is opened. While it comes up a native loading state SHALL be shown, never a blank window. If the app is pointed at an external coordinator via `ARKE_COORDINATOR_URL` (an `arke up` instance), it SHALL **attach** to that URL instead of embedding one, and quitting SHALL leave that external coordinator running. If the coordinator fails to become ready, the app SHALL surface the reason in-window with a retry.

#### Scenario: launch → ready → open-a-project
- **WHEN** the app is launched with no `ARKE_COORDINATOR_URL` to attach to
- **THEN** it embeds a coordinator whose default context is rooted at the app-state dir (no managed harness spawned for it), shows a loading state, and — once `startCoordinator()` resolves with the bound URL — reveals the launch/open-project screen with no user project yet open

#### Scenario: no stray project state under the app bundle
- **WHEN** the embedded coordinator starts before any project is opened
- **THEN** it does NOT create a `.arke/` or spawn `opencode serve` under the app's resources / working directory — the neutral default root lives under `userData`

#### Scenario: the renderer connects via the bridged URL, not a literal
- **WHEN** the renderer connects (and on every reconnect)
- **THEN** it resolves the URL lazily from `window.arke.coordinator.url` (the actual bound `ws://127.0.0.1:<port>`), so an ephemeral or attached port works and a reconnect never falls back to a `4319` literal

#### Scenario: attach to an already-running coordinator
- **WHEN** `ARKE_COORDINATOR_URL` names an existing coordinator
- **THEN** the app connects to that URL instead of embedding one, and quitting leaves that external coordinator (and its harness) running

#### Scenario: the managed harness is missing on a fresh install
- **WHEN** a real project is opened in managed mode but `opencode` is not found on the host
- **THEN** the app does not hard-fail: it surfaces a guided "install the harness" step (not a stack trace) and lets the user retry once it is present (Decision #8)

#### Scenario: a coordinator that fails to start is surfaced
- **WHEN** the coordinator cannot become ready (port conflict, invalid config)
- **THEN** the app shows the reason in-window with a retry, rather than a dead or blank window

### Requirement: The renderer is the untrusted client; the host process is the trust boundary
`capability: desktop-shell` · `delta: ADDED (feat/electron-desktop-app)`

The renderer SHALL run with `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true`, load only local first-party assets under a **strict CSP** (no remote content — made possible by self-hosting the fonts), and reach the coordinator solely over the local WebSocket — it SHALL hold no credentials and have no direct filesystem, process, or network privilege. Credentials, git, filesystem, and the harness SHALL live in the coordinator (running in the Electron main process), so the SPEC-001 / NFR-1 client↔host credential boundary is enforced as the **renderer↔main OS process boundary** (the renderer is a separate sandboxed process regardless of where the coordinator runs). The `preload` `contextBridge` SHALL expose only a small, enumerated set — `openProjectDialog()`, `notify()`, `onMenu()`, and `coordinator.url` — and NOTHING that returns a credential or an arbitrary host capability. (Work-in-flight is derived in main from the in-process coordinator, not pushed from the renderer — see FR-6 — so no `setBusy` is on the bridge.)

#### Scenario: the renderer has no privilege and no secrets
- **WHEN** the renderer is running
- **THEN** it has no Node integration, holds no credential, and cannot read the filesystem or spawn a process directly; any privileged action happens in the main/coordinator process, reached only over the WebSocket

#### Scenario: the preload surface is an allowlist
- **WHEN** the preload bridge is inspected
- **THEN** it exposes exactly `openProjectDialog` / `notify` / `onMenu` / `coordinator.url` and no general-purpose fs / process / credential access

#### Scenario: a strict CSP holds because nothing is remote
- **WHEN** the UI loads under the packaged CSP
- **THEN** all assets (including fonts) resolve locally, no remote origin is fetched, and `setWindowOpenHandler` denies arbitrary navigation

### Requirement: The desktop client is the web client, with only browser-safe additive changes
`capability: desktop-shell` · `delta: ADDED (feat/electron-desktop-app)`

The window SHALL render the built **`@arke/client`** and drive the coordinator through the same request/response + event-stream WebSocket protocol (SPEC-003) — no parallel business-logic surface in the shell — and a **single build** SHALL serve both browser and desktop. Achieving that requires exactly three small, **browser-safe** client changes, and no others: (a) resolve the coordinator URL **lazily at connect time** as `window.arke?.coordinator?.url ?? (VITE_ARKE_COORDINATOR_URL ?? ws://127.0.0.1:4319)` — lazily (not the current import-time module constant) so the preload-injected URL is picked up and a reconnect cannot revert to the default, and a no-op in a plain browser where `window.arke` is absent; (b) **self-host the Geist / Geist Mono fonts** in the `@arke/client` build, removing the remote Google Fonts `<link>` (a strict CSP + offline both benefit — this applies to the shared client build; the PRD's illustrative remote-font markup is not normative for the shipped client); (c) set a **shared relative Vite `base` (`./`)** so assets load under both `http://localhost` (browser) and the desktop `app://` handler. The shell SHALL NOT reimplement any coordinator operation.

#### Scenario: same client, same protocol, one build
- **WHEN** an operation runs in the desktop app (e.g. approve a draft, configure an agent)
- **THEN** it is issued from the renderer to the coordinator over the WebSocket exactly as in the browser, from the same client bundle — not through an Electron-only code path

#### Scenario: the URL resolution is a lazy no-op in the browser
- **WHEN** the same client build runs in a plain browser tab (no `window.arke`) and later reconnects
- **THEN** it derives its WS URL from `VITE_ARKE_COORDINATOR_URL`/default at each connect exactly as today, so the browser surface is unchanged

#### Scenario: assets load in both surfaces
- **WHEN** the packaged renderer loads over `app://` and the browser build loads over `http://localhost`
- **THEN** the relative `base` resolves `./assets/*` + the self-hosted fonts in both, with `index.html` returned for the app root (the client is store-routed, so no URL-route SPA fallback is needed)

### Requirement: Open a project from a native folder picker
`capability: native-integration` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL offer a native OS folder-selection dialog whose result is a real absolute path. The flow keeps the "renderer drives the coordinator over WS" invariant: `openProjectDialog()` (preload → main) returns the picked path to the **renderer**, and the **renderer** then sends `project.open { path }` (SPEC-018) over its WebSocket to the embedded coordinator — the main process does not open the project on the renderer's behalf, so the renderer's connection resolves its own active project. Because the coordinator is already up at launch, `project.open` has a running target. Recent projects SHALL be reachable from the OS application menu and the launch screen; selecting one opens it in the **single** running coordinator, never a second one. The picked path SHALL be canonicalised and validated by the coordinator (the trust boundary), not the renderer.

#### Scenario: pick a folder and open it
- **WHEN** the user chooses "Open project…" and selects a directory in the native dialog
- **THEN** `openProjectDialog()` returns the real absolute path to the renderer, which sends `project.open` over its WebSocket; the coordinator validates the path and opens that project context (SPEC-018) with its managed harness, and the renderer's active project binds to it

#### Scenario: recents open in the running coordinator
- **WHEN** the user picks a recent project from the application menu
- **THEN** the renderer sends `project.open` for it to the already-running coordinator (no second coordinator is spawned)

### Requirement: Single-instance, window state, and the application menu
`capability: native-integration` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL be single-instance: a second launch (or an OS "open with") SHALL focus the existing window and route any project path to it rather than starting a second app or coordinator. Window size and position SHALL persist across launches (stored in Electron `userData`). A native application menu SHALL provide the standard platform roles (about / quit / edit / view / window / help) plus Arke actions (Open project…, New specification, Reload) each bound to a platform-standard accelerator; developer tools SHALL be available only in development builds.

#### Scenario: a second launch focuses the existing window
- **WHEN** the app is launched again while an instance is already running
- **THEN** the existing window is focused (and any supplied project path is routed to the renderer to open), and no second coordinator starts

#### Scenario: window bounds persist
- **WHEN** the app is resized/moved, then quit and relaunched
- **THEN** the window restores its previous size and position

#### Scenario: devtools are hidden in production
- **WHEN** a packaged production build runs
- **THEN** the developer-tools menu item and shortcut are absent

### Requirement: OS notifications for human-in-the-loop attention
`capability: notifications` · `delta: ADDED (feat/electron-desktop-app)`

When the coordinator's event stream reports a state that needs a human, the app SHALL raise a native OS notification whose body carries **no** spec content or secret, and clicking it SHALL focus the window and navigate to the relevant screen. The triggers SHALL be the **canonical normalised domain events** the renderer actually receives (not raw provider names or derived flags): a decision is needed — `permission.asked` (SPEC-012) or `elicitation.asked` (SPEC-011, the normalised event with `elicitationId`; `question.asked` is only OpenCode's raw name and never on the wire); a task needs a human — task `session.status` with `status: "waiting"` (blocked on a human) or `status: "error"` (a failed fan-out task, SPEC-009); a review finished or could not run — `panel.complete` (including `{status:"failed"}` when all reviewers errored), `panel.config-error`, or `panel.reviewer-error` (SPEC-007). Because SPEC-003's per-connection `seq` restarts on reconnect and the snapshot **replaces** read-model state (re-delivering open permissions/elicitations), notifications SHALL be **de-duplicated by a stable domain id** — `{kind, permissionId | elicitationId | sessionId | panelId}` — and each id SHALL be **pruned when its gate resolves** (`permission.replied`, `elicitation.replied` / `elicitation.rejected`, the session leaving `waiting`/`error`, `panel.complete`) so the set does not grow unbounded and a legitimately re-raised later gate still notifies. The app SHALL request OS notification permission on first use and degrade gracefully if it is denied, and the user SHALL be able to mute notifications.

#### Scenario: a pending decision raises one notification
- **WHEN** a `permission.asked` or `elicitation.asked` event arrives and notifications are permitted and not muted
- **THEN** a native notification is shown whose body names the action class but contains no spec content or secret, and clicking it focuses the window and opens the gate

#### Scenario: a reconnect does not replay old alerts
- **WHEN** the client reconnects and the fresh snapshot re-delivers a still-open permission the app already notified
- **THEN** no duplicate notification fires, because its `permissionId` is already in the notified set — until `permission.replied` prunes it

#### Scenario: permission denied degrades gracefully
- **WHEN** the user denies the OS notification permission
- **THEN** no OS notification is raised and no error is thrown; the in-app indicators still update

#### Scenario: mute suppresses notifications
- **WHEN** the user has muted notifications
- **THEN** no OS notification is raised, though the in-app indicators still update

### Requirement: Graceful shutdown, crash detection, and a main-derived work-in-flight gate
`capability: service-lifecycle` · `delta: ADDED (feat/electron-desktop-app)`

On quit the app SHALL call the coordinator's `stop()`, which (via `Coordinator.stop()` → each `ProjectContext.stop()`) **transitively drains the trace** (`Trace.drain()`, SPEC-015) and stops managed harnesses before the process exits. "Work in flight" SHALL be a **defined predicate derived in the main process from the in-process coordinator** (authoritative — not a renderer signal that can go stale across a reconnect): via `coordinator.workInFlight()`, true when any session has an unfinished dispatch (dispatched with no subsequent `turn.quiescent`), OR any queued/running fan-out task exists (SPEC-009 FanOutStore), OR any permission/elicitation is open. The app SHALL confirm before quitting while work is in flight, and SHALL treat an indeterminate state as busy (fail-safe). If the embedded coordinator raises a fatal error (startup failure, or a managed harness exits), the app SHALL detect it, surface the reason, and offer to re-initialise the coordinator without losing project state (durable on disk under each project's `.arke/`) — the window SHALL NOT be left as a dead shell.

#### Scenario: quit drains the trace and stops the harness
- **WHEN** the app that embedded the coordinator is quit with no work in flight
- **THEN** it calls `coordinator.stop()`, which transitively flushes each context's trace (`Trace.drain()`) and stops managed harnesses, then exits

#### Scenario: quitting with work in flight confirms first
- **WHEN** the user quits while `coordinator.workInFlight()` is true (a session mid-dispatch, a running/queued task, or an open permission/elicitation)
- **THEN** the app asks for confirmation before shutting the coordinator down

#### Scenario: a fatal coordinator error is detected and recoverable
- **WHEN** the embedded coordinator fails to start or a managed harness exits unexpectedly
- **THEN** the app surfaces the reason and offers to re-initialise the coordinator, resuming from on-disk project state without data loss

### Requirement: Signed, auto-updating distributable
`capability: packaging` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL ship as per-OS installers (macOS `dmg`, Windows `nsis`, Linux `AppImage`) that are **code-signed and notarised when signing credentials are configured** (an `electron-builder` sign step gated on certs/notarisation creds present in the build environment), so a signed release installs without OS security warnings, and SHALL support in-app auto-update via `electron-updater` with signature verification before apply. An update MAY be **downloaded** in the background at any time, but in managed mode SHALL NOT be **applied** while `coordinator.workInFlight()` is true — applying restarts the app, tearing down the embedded coordinator + managed harness — so it prompts and applies only at a quiescent point or on the next launch (in **attached** mode the external coordinator survives the restart, so no work is interrupted). The DoD gates on the pipeline producing installers that sign+notarise **when credentials are present**; an actual signed public release (org certs + update feed + Apple's notarisation network step) is a release-time step, not a code check.

#### Scenario: a signed build installs cleanly
- **WHEN** a release built with valid signing credentials is run on macOS or Windows
- **THEN** it installs without a Gatekeeper / SmartScreen block, because it is signed and (macOS) notarised

#### Scenario: an update defers its apply until quiescent (managed mode)
- **WHEN** a newer version has downloaded while `coordinator.workInFlight()` is true in managed mode
- **THEN** the app does not apply it mid-turn; it prompts and applies at a quiescent point or on next launch, so no in-flight coordinator work is interrupted

#### Scenario: an unverified update is refused
- **WHEN** a downloaded update fails signature verification
- **THEN** it is not applied and the failure is surfaced

## Design

### Architectural decision
Fill in the existing **`apps/desktop`** (`@arke/desktop`) Electron skeleton (SPEC-001 R-1; AGENTS.md architecture map; PRD §8.6 / D16), not a new package. The main process **embeds the coordinator in-process** via a thin `startCoordinator()` export — the skeleton's own plan. The renderer is the sandboxed, near-unchanged `@arke/client` (three browser-safe additive changes), connecting over the same `ws://127.0.0.1:<bound-port>` as the browser; native affordances cross a narrow `preload` `contextBridge`, operations cross the WebSocket. Electron over Tauri stands (Decision #1). Crash-isolation via a `utilityProcess` is a considered hardening follow-up (Decision #3 / open question), deferred to keep v1 aligned with the skeleton.

### Target architecture
```
apps/desktop (@arke/desktop, Electron; main/preload built to JS)
  ├─ lifecycle: startCoordinator({ root: userData, manageHarness }) IN-PROCESS → { url, stop };
  │             default context on a NEUTRAL root (no harness until a real project opens);
  │             single-instance; window-state; quit → stop() (transitive Trace.drain);
  │             work-in-flight via coordinator.workInFlight(); fatal-error surface + re-init;
  │             attach mode when ARKE_COORDINATOR_URL is set
  ├─ native:    folder dialog · Notification · application menu · electron-updater
  └─ preload:   contextBridge → { openProjectDialog(), notify(), onMenu(), coordinator.url }
        │  (Electron IPC — native only, allowlisted)
        ▼
  renderer (sandboxed): @arke/client ── ws://127.0.0.1:<bound> ──▶ coordinator (in main)
        (same build as browser; lazy URL from the bridge)             │
                                                                      └─▶ per-project HarnessAdapter → opencode serve (SPEC-016)
                                                                          read model + trace (single source of truth)
```
The renderer loads the built client (relative `base: './'`) via a first-party `app://` protocol handler over the packaged `dist`. The coordinator is embedded (compiled to JS for the Electron main; see below), not forked; a second coordinator is never started, and `start()`'s returned bound port becomes `coordinator.url`.

### Data model
No new persistent **domain** entities. The app persists only local UI/runtime state in `userData`: window bounds, a notification-mute flag, and the **neutral default-context root** used before any project is opened. Notification de-dup is an in-memory `{kind, id}` set, pruned as gates resolve. All project + audit state stays under each project's `.arke/` (SPEC-015 / SPEC-018).

### Interfaces and contracts
- **Coordinator (additive):** `startCoordinator(opts: { root: string; port?: number; manageHarness?: boolean; attachUrl?: string; paths?: { trace; sessions; grants } }): Promise<{ url: string; stop(): Promise<void> }>` — constructs a `Coordinator` **directly** (the current runnable path is a private `bootstrap()`; the module-level `PORT`/`REPO_ROOT`/`*_PATH` constants are import-time env reads), threading the desktop's explicit `root`/`paths` through opts rather than those constants, and returns `{ url }` built from `start()`'s bound port. `stop()` is the existing graceful path. Plus `workInFlight(): boolean` (the FR-6 predicate over the read model + FanOutStore + pending gates). Delivered as a compiled-JS `dist` build with a package `exports` map so the Electron main bundle imports JS, not `.ts`.
- **Client (additive, browser-safe):** the coordinator URL is resolved **lazily inside the connect path** (not the import-time `COORDINATOR_URL` const) as `window.arke?.coordinator?.url ?? (VITE_ARKE_COORDINATOR_URL ?? ws://127.0.0.1:4319)`; Geist / Geist Mono self-hosted in the build; shared relative Vite `base: './'`. Nothing else.
- **Preload bridge (native-only, allowlisted):** `window.arke.openProjectDialog(): Promise<string|null>`, `window.arke.notify({ kind, id, actionClass? }): void`, `window.arke.onMenu(cb)`, `window.arke.coordinator: { url }`. No method returns a credential or arbitrary host access; no `setBusy` (work-in-flight is main-derived).
- **Coordinator protocol (reused, unchanged):** the renderer speaks the SPEC-003 WS request/response + event stream; opening a project is the renderer sending `project.open { path }` (SPEC-018). The shell adds **no** coordinator ops beyond the two additive methods above.
- **Notification triggers ↔ events:** `permission.asked` / `elicitation.asked` → decision-needed; task `session.status:waiting` (blocked) / `session.status:error` (failed, SPEC-009) → needs-human; `panel.complete` (incl. `{status:"failed"}`) / `panel.config-error` / `panel.reviewer-error` (SPEC-007) → review finished/failed. De-dup key `{kind, permissionId|elicitationId|sessionId|panelId}`, pruned on `permission.replied` / `elicitation.replied|rejected` / session leaving waiting|error / `panel.complete`.

### Cross-cutting
- **Security (NFR-1/5):** `contextIsolation` + `sandbox` + no `nodeIntegration`; a strict renderer CSP (achievable because fonts are self-hosted); `webSecurity` on; no remote content; `setWindowOpenHandler` denies navigation; the preload surface is a small allowlist. Credentials live only in the coordinator (main process); the renderer is a separate sandboxed process, so the SPEC-001 client↔host split is a real OS boundary regardless of the coordinator's in-process hosting.
- **Reuse over fork:** `@arke/coordinator` and `@arke/client` are reused with only the small, enumerated additive changes above — no behavioural fork, one client build for both surfaces. Bringing the stack up duplicates the *intent* of `arke up` (SPEC-017) in Electron's runtime; the CLI is C#/.NET (SPEC-017 Decision #7) and cannot share code.
- **Multi-project (SPEC-018):** one embedded coordinator; its **default context is rooted at a neutral `userData` dir with no managed harness**, and real projects (each with their managed harness, SPEC-016) are opened within it by the renderer via `project.open`. There is no "projectless" coordinator — the neutral default is a real, harness-less context that keeps the app from spawning `opencode` or writing `.arke/` under its own bundle before the user picks a project.
- **Harness dependency (SPEC-016):** the managed harness (`opencode`) is spawned by the coordinator per real project. The shell forces managed mode for real projects (via `startCoordinator`/per-project config); on the first managed open it **detects** `opencode` and shows a guided install step if absent (Decision #8, firm for v1), rather than hard-failing.
- **Design template:** the shell's only own UI is the launch / loading state + native chrome; it follows the [`arke-design` skill](../../.claude/skills/arke-design/SKILL.md). Every actual app screen is the existing client.
- **Packaging:** `electron-builder` for per-OS installers; the sign/notarise step is gated on configured credentials in the build env; `electron-updater` against a release feed (identity + feed are open questions). The existing release workflow (the v0.1.0 tag flow) extends to publish desktop artefacts.

### Testing
- **Unit (main process, Node test):** the de-dup set (a re-delivered `permissionId` fires once; a resolved id is pruned so a later re-raise notifies again); `workInFlight()` gating quit-confirm + update-apply (fail-safe when the coordinator can't answer); the preload surface is exactly the allowlist; attach-vs-embed on `ARKE_COORDINATOR_URL`; `startCoordinator()` returns a bound URL and `stop()` drains.
- **Integration (Electron test driver, e.g. Playwright for Electron, against a MockAdapter coordinator — no live OpenCode):** launch with a temp `userData` root asserts **no `.arke/` is created under the app resources dir** and no `opencode` spawn before a project; open-project via a mocked native dialog → renderer sends `project.open` → roster loads; MockAdapter emits `permission.asked` → one notification and `elicitation.asked` → one notification, each click routes to its gate; a reconnect re-delivering the open permission fires **no** second notification; task `session.status:waiting` → needs-human notification; quit with `workInFlight()` true confirms; quit drains the trace.
- **Manual (release-validation, not gated):** a build signed with real credentials installs without OS warnings on macOS + Windows; an update downloads and, at a quiescent point, applies on restart; the harness-missing guided-install flow on a machine without `opencode`.

### Definition of done
All scenarios pass; the app fills in `apps/desktop` and brings the full stack up on double-click with **no terminal**, embedding the coordinator on a neutral default root (no stray `.arke/`/harness before a project) and opening a project via a native dialog (renderer-driven `project.open`); the renderer is sandboxed with no credentials and drives the coordinator over WS from the **same client build** as the browser (lazy bridged URL); notifications key off the canonical events (`permission.asked` / `elicitation.asked` / task `session.status:waiting|error` / `panel.*`) and de-dup+prune by domain id; quit calls `coordinator.stop()` (transitive trace drain) and gates on the main-derived `workInFlight()`; the packaging pipeline signs+notarises **when credentials are configured**; the coordinator's and client's changes are limited to the enumerated additive ones; typecheck + tests green; a reviewer signed off. (Issuing an actual signed public release is a separate release-time step.)

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Electron over Tauri** | Arke's backend is a stateful Node coordinator that spawns `opencode` and does git / fs / credential work; Electron runs it with ~no porting and the client is Chromium-tested. Tauri would still ship Node as a sidecar + a Rust shell + three system webviews (Linux WebKitGTK divergence). Matches the skeleton's own note. Warrants a dedicated ADR. |
| 2 | Fill in the existing **`apps/desktop`** (`@arke/desktop`), not a new package | SPEC-001 R-1 + AGENTS.md + PRD §8.6/D16 already mandate this workspace as "the Electron shell that embeds the coordinator (one signed app)". A new `packages/desktop` would contradict the grounding and orphan the skeleton. |
| 3 | Coordinator **embedded in-process** (`startCoordinator()`), not a `utilityProcess` fork | Both embedding and forking need a compiled-JS coordinator (the Electron main runs JS, not TS) — so compilation is not the differentiator. Embedding wins because it avoids an IPC readiness channel and uses `start()`'s in-process bound port directly as readiness + URL, and it matches the skeleton/PRD. Crash-isolation via `utilityProcess` is a deferred hardening follow-up. |
| 4 | The shell is a **client of the coordinator**; the client stays one build with only browser-safe additive changes, resolved **lazily** | One read model + one trace (as the CLI, SPEC-017 #1). The URL resolution must be lazy (connect-time), not the import-time `COORDINATOR_URL` const, so the preload-injected URL takes effect and a reconnect can't revert to `4319`; self-hosted fonts + relative base are browser-safe, so one `@arke/client` build serves both. |
| 5 | Renderer gets the coordinator URL from the **preload bridge**, never a hardcoded port | `server.ts` binds `ARKE_COORDINATOR_PORT ?? 4319` and returns the **actual** bound port; SPEC-016 allows an ephemeral port and attach mode targets an arbitrary URL — so `coordinator.url` must be resolved and injected. |
| 6 | Open a project by returning the path to the **renderer**, which sends `project.open` over WS | Preserves "the renderer drives the coordinator over WS" and lets the renderer's connection resolve its own active project (SPEC-018); the main process only supplies the native dialog. |
| 7 | Notifications key off **canonical normalised events** + a domain-id **de-dup with prune-on-resolve** | The wire events are `permission.asked` / `elicitation.asked` (`question.asked` is only OpenCode's raw name), task `session.status:waiting` (blocked) / `error` (failed), and `panel.complete`/`config-error`/`reviewer-error` — not derived read-model flags. SPEC-003's `seq` restarts + snapshot-replace re-deliver open state, so de-dup MUST be by `permissionId`/`elicitationId`/`sessionId`/`panelId`, pruned as each gate resolves to avoid unbounded growth + stale suppression. |
| 8 | Harness **detect + guide** on first managed open is the firm v1 | A one-click product must not stack-trace on a fresh machine without `opencode`. (The only open question is whether to *also* bundle it as a fast-follow — see below — not whether to detect-and-guide.) |
| 9 | Auto-update **defers its apply while `workInFlight()`** in managed mode; attach mode is exempt | Applying an `electron-updater` update restarts the app, tearing down the embedded coordinator + managed harness (Decision #3) — so the "no interrupt" guarantee holds only by deferring the apply (download may proceed); an attached external coordinator survives the restart. |
| 10 | Work-in-flight is **derived in main from the in-process coordinator**, not pushed by the renderer | The renderer's `setBusy` signal can go stale across a WS reconnect; because the coordinator is in-process in main, main queries it directly (`workInFlight()`) for an authoritative answer, and treats an indeterminate state as busy. Removes `setBusy` from the preload surface. |
| 11 | Signing/notarisation in the **DoD gates on "signs when credentials configured"** | Code-signing / notarisation are external, credential- and account-gated (macOS notarisation is a network submission); the code DoD guarantees the pipeline, not an actual signed public release. |

## Open questions
- **Bundle `opencode` with the app** as a fast-follow (removing the first-launch prerequisite entirely), on top of the firm detect-and-guide v1 (Decision #8)? Bundling grows the installer and couples the release cadence to the harness version.
- **Update feed + signing identity:** GitHub Releases via `electron-updater`, or a self-hosted feed? Which certs — Apple Developer ID + notarisation, and Windows OV/EV — and where do they live in CI?
- **Crash isolation:** revisit a `utilityProcess`-hosted coordinator (Decision #3) as a hardening follow-up once the in-process v1 ships?
- **Deep-linking (`arke://`)** to open a project or a spec from outside the app — in scope for v1, or later?
