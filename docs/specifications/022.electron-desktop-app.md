# Arke Desktop — a one-click, native Electron app

## Why
Today Arke runs as a coordinator process + a Vite dev client + a browser tab, brought up by `arke up` (SPEC-017) — a terminal and a second toolchain stand between a product engineer and the product. A browser tab also cannot hand the host a real project path, so opening a project is a typed-path / recents flow rather than a native picker. A signed, double-click **desktop app** removes the terminal, gives a real folder dialog (an absolute path straight to the coordinator), surfaces the human-in-the-loop gates as OS notifications, and ships as an auto-updating binary — Arke as a product, not a dev stack.

## What changes
- ADDED desktop-shell — an **Electron** app (`packages/desktop`) that supervises the existing **coordinator** (in a Node `utilityProcess`) and renders the existing **web client** in its window, so the desktop and browser clients are the *same* client driving the *same* coordinator over the *same* WebSocket. (breaking: no)
- ADDED native-integration — affordances a browser cannot give: a real **folder picker** to open a project (a genuine absolute path → `project.open`), OS **notifications** for attention states (permission waiting, review divergence, task needs-human), an application menu + accelerators, single-instance focus, and window-state persistence. (breaking: no)
- ADDED service-lifecycle — app launch brings the whole stack up (coordinator + a managed harness by default, SPEC-016); quit tears down exactly what it started, with crash detection + restart; the shell drives the system only *through* the coordinator (NFR-1/7), never around it. (breaking: no)
- ADDED packaging — signed, notarised per-OS installers (dmg / nsis / AppImage) with in-app **auto-update**. (breaking: no)

## Requirements

### Requirement: One launch brings the whole stack up, ready
`capability: service-lifecycle` · `delta: ADDED (feat/electron-desktop-app)`

Launching the app SHALL start and supervise the coordinator (in managed-harness mode by default, SPEC-016), wait until it reports ready, and only then present the workspace UI; while it comes up a native loading state SHALL be shown, never a blank window. If a coordinator is already listening on the configured port (e.g. started by `arke up`), the app SHALL **attach** to it rather than spawn a second one. Quitting SHALL gracefully stop exactly the processes the app started — the coordinator and any harness it manages — and SHALL NOT stop a coordinator/harness it attached to. If the coordinator fails to become ready, the app SHALL surface the reason in-window with a retry, not fail silently.

#### Scenario: launch → ready → workspace
- **WHEN** the app is launched with no coordinator already running
- **THEN** it spawns the coordinator in managed-harness mode (so the coordinator owns an `opencode serve`, SPEC-016), shows a loading state, and reveals the workspace only once the coordinator is ready

#### Scenario: attach to an already-running coordinator
- **WHEN** the app is launched while a coordinator is already listening on the configured port
- **THEN** it attaches to that coordinator instead of spawning a second one
- **AND** quitting the app leaves that externally-started coordinator (and its harness) running

#### Scenario: quit stops only what launch started
- **WHEN** the app started the coordinator itself and is then quit
- **THEN** the coordinator and the harness it manages are stopped, and no other process is touched

#### Scenario: a coordinator that fails to start is surfaced
- **WHEN** the coordinator cannot become ready (port conflict, invalid config, harness unreachable)
- **THEN** the app shows the reason in-window with a retry, rather than presenting a dead or blank window

### Requirement: The renderer is the untrusted client; the coordinator is the host trust boundary
`capability: desktop-shell` · `delta: ADDED (feat/electron-desktop-app)`

The renderer SHALL run with `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true`, load only local first-party assets under a strict CSP (no remote content, no arbitrary navigation), and reach the coordinator solely over the local WebSocket — it SHALL hold no credentials and have no direct filesystem, process, or network privilege. All privileged work — credentials, git, filesystem, and spawning the harness — SHALL live in the coordinator (Node) process, so the SPEC-001 / NFR-1 client↔host credential boundary is enforced as an **OS process boundary**. The `preload` `contextBridge` SHALL expose only a small, enumerated set of native operations (folder dialog, notification, menu events) and NOTHING that returns a credential or an arbitrary host capability.

#### Scenario: the renderer has no privilege and no secrets
- **WHEN** the renderer is running
- **THEN** it has no Node integration, holds no credential, and cannot read the filesystem or spawn a process directly
- **AND** any privileged action happens in the coordinator process, reached only over the WebSocket

#### Scenario: the preload surface is an allowlist
- **WHEN** the preload bridge is inspected
- **THEN** it exposes exactly the enumerated native operations (open-folder, notify, menu events, the coordinator URL) and no general-purpose fs/process/credential access

#### Scenario: no remote content
- **WHEN** the app loads its UI or the client attempts a navigation
- **THEN** only local first-party assets load; remote origins and new-window navigations are denied by the window open handler + CSP

### Requirement: The desktop client is the web client, unmodified
`capability: desktop-shell` · `delta: ADDED (feat/electron-desktop-app)`

The window SHALL render the existing built **`@arke/client`** and drive the coordinator through the same request/response + event-stream WebSocket protocol (SPEC-003), so behaviour is identical to the browser and there is no parallel business-logic surface in the shell. The shell SHALL NOT reimplement coordinator operations — native affordances augment the client, they do not replace the coordinator API — and a single build of the client SHALL serve both browser and desktop.

#### Scenario: same client, same protocol
- **WHEN** an operation runs in the desktop app (e.g. approve a draft, configure an agent)
- **THEN** it is issued from the renderer to the coordinator over the WebSocket, exactly as in the browser — not through an Electron-only code path

#### Scenario: a new coordinator op needs no shell change
- **WHEN** the coordinator adds a new operation and the client is updated to use it
- **THEN** the desktop app picks it up with the new client build, with no change to the Electron shell

### Requirement: Open a project from a native folder picker
`capability: native-integration` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL offer a native OS folder-selection dialog whose result is a real absolute path, and open that project by sending `project.open` to the coordinator (SPEC-018) — the capability a browser tab cannot provide. Recent projects SHALL be reachable from the OS application menu and the launch screen; selecting one opens it in the **single** running coordinator, never a second one. The picked path SHALL be canonicalised and validated by the coordinator (the trust boundary), not the renderer.

#### Scenario: pick a folder and open it
- **WHEN** the user chooses "Open project…" and selects a directory in the native dialog
- **THEN** the real absolute path is sent as `project.open` to the coordinator, which validates it and opens that project context (SPEC-018), and the workspace binds to it

#### Scenario: recents open in the running coordinator
- **WHEN** the user picks a recent project from the application menu
- **THEN** it opens within the already-running coordinator (no second coordinator is spawned)

### Requirement: Single-instance, window state, and the application menu
`capability: native-integration` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL be single-instance: a second launch (or an OS "open with") SHALL focus the existing window and route any project path to it rather than starting a second app or coordinator. Window size and position SHALL persist across launches. A native application menu SHALL provide the standard platform roles (about / quit / edit / view / window / help) plus Arke actions (Open project…, New specification, Reload) each bound to a platform-standard accelerator; developer tools SHALL be available only in development builds.

#### Scenario: a second launch focuses the existing window
- **WHEN** the app is launched again while an instance is already running
- **THEN** the existing window is focused (and any supplied project path is opened in it), and no second coordinator starts

#### Scenario: window bounds persist
- **WHEN** the app is resized/moved, then quit and relaunched
- **THEN** the window restores its previous size and position

#### Scenario: devtools are hidden in production
- **WHEN** a packaged production build runs
- **THEN** the developer-tools menu item and shortcut are absent

### Requirement: OS notifications for human-in-the-loop attention
`capability: notifications` · `delta: ADDED (feat/electron-desktop-app)`

When the coordinator's event stream reports a state that needs a human — a pending permission (SPEC-012), a review-panel divergence (SPEC-007), or a task moved to needs-human (SPEC-009) — the app SHALL raise a native OS notification whose body carries **no** spec content or secret, and clicking it SHALL focus the window and navigate to the relevant screen. Notifications SHALL be derived from the same event stream (no polling) and de-duplicated so a reconnect does not re-fire past alerts, and the user SHALL be able to mute them.

#### Scenario: a pending permission raises a notification
- **WHEN** the event stream reports a pending permission and notifications are not muted
- **THEN** a native notification is shown whose body names the action class but contains no spec content or secret
- **AND** clicking it focuses the window and opens the permission gate

#### Scenario: a reconnect does not replay old alerts
- **WHEN** the client reconnects and re-receives events it has already seen
- **THEN** no duplicate notifications are fired for the already-seen states

#### Scenario: mute suppresses notifications
- **WHEN** the user has muted notifications
- **THEN** no OS notification is raised, though the in-app indicators still update

### Requirement: Graceful shutdown, crash detection, and recovery
`capability: service-lifecycle` · `delta: ADDED (feat/electron-desktop-app)`

On quit the app SHALL request a graceful coordinator shutdown that flushes the trace (SPEC-015) and stops the managed harness before the process exits, and SHALL confirm before quitting while work is in flight. If the coordinator process exits unexpectedly, the app SHALL detect it, surface the reason, and offer to restart it — project state is durable on disk under each project's `.arke/`, so a restart resumes without data loss and the window is never left as a dead, disconnected shell.

#### Scenario: quit drains the trace and stops the harness
- **WHEN** the app that started the coordinator is quit
- **THEN** it requests a graceful shutdown that flushes the trace and stops the managed harness, then exits

#### Scenario: quitting with work in flight confirms first
- **WHEN** the user quits while a turn/task is running
- **THEN** the app asks for confirmation before shutting the coordinator down

#### Scenario: a crashed coordinator is detected and restartable
- **WHEN** the coordinator process exits unexpectedly
- **THEN** the app surfaces the reason and offers to restart it, and a restart resumes from the on-disk project state without data loss

### Requirement: Signed, auto-updating distributable
`capability: packaging` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL ship as per-OS installers (macOS `dmg`, Windows `nsis`, Linux `AppImage`), **code-signed and notarised** so it installs without OS security warnings, and SHALL support in-app auto-update: it checks for updates, downloads in the background, and applies on the user's confirmation at restart. An update SHALL be integrity-verified (signature) before it is applied, and applying an update SHALL NOT interrupt or discard in-flight coordinator work.

#### Scenario: a signed build installs cleanly
- **WHEN** a released installer is run on macOS or Windows
- **THEN** it installs without a Gatekeeper / SmartScreen block, because it is signed and (macOS) notarised

#### Scenario: an update is offered and applied on restart
- **WHEN** a newer version is available
- **THEN** the app downloads it in the background and prompts the user, applying it on the next restart

#### Scenario: an unverified update is refused
- **WHEN** a downloaded update fails signature verification
- **THEN** it is not applied and the failure is surfaced

## Design

### Architectural decision
An **Electron** shell (Decision #1 — chosen over Tauri because Arke's backend is a stateful **Node** coordinator that spawns `opencode serve` and does git / filesystem / credential work: Electron runs it with near-zero porting and the client is already Chromium-tested, whereas Tauri would still bundle Node as a sidecar — a partial size win traded for a Rust shell + three divergent system webviews, notably WebKitGTK on Linux). The **main process** stays lean — window, lifecycle, native menus / dialogs / notifications / updater. The **coordinator** runs in a **Node `utilityProcess`** (its own process, mirroring the standalone `arke up` topology) so a coordinator crash never takes down the window and the trust boundary is an OS process boundary. The **renderer** is the sandboxed, unmodified `@arke/client`, connecting to the coordinator over the same `ws://127.0.0.1:<port>` as the browser. Native affordances cross a narrow `preload` `contextBridge`; operations cross the WebSocket to the coordinator — exactly the CLI's stance (SPEC-017 Decision #1: a client of the coordinator, never its own embedded runtime).

> This decision warrants its own ADR (Electron over Tauri); the full rationale lives in Decision #1 below until it is written up.

### Target architecture
```
Electron main (packages/desktop, TS)
  ├─ lifecycle: spawn+supervise coordinator utilityProcess (managed harness, SPEC-016);
  │             single-instance lock (attach if already listening); window-state;
  │             graceful drain on quit; crash → surface + restart
  ├─ native:    folder dialog · Notification · application menu · autoUpdater
  └─ preload:   contextBridge → { openProjectDialog(), notify(), onMenu(), coordinator.url }
        │  (Electron IPC — native only, allowlisted)
        ▼
  renderer (sandboxed): @arke/client ── ws://127.0.0.1:4319 ──▶ coordinator (utilityProcess)
        (identical to the browser client)                              │
                                                                       └─▶ HarnessAdapter → opencode serve (SPEC-016)
                                                                           read model + trace (single source of truth)
```
The renderer loads the built client via a first-party `app://` protocol handler (packaged `dist`), not `file://`, so ESM + `fetch` behave. The coordinator entry is the existing `@arke/coordinator` server run under `utilityProcess.fork`; a second coordinator is never spawned if one is already listening (attach).

### Data model
No new persistent **domain** entities. The app persists only local UI / runtime state in Electron's `userData` dir: window bounds, a notification-mute flag, and a run handle (the coordinator `utilityProcess` pid) so quit stops exactly what it started. All project + audit state stays under each project's `.arke/` (SPEC-015 / SPEC-018) — the shell is stateless about the domain.

### Interfaces and contracts
- **Preload bridge (native-only, allowlisted):** `window.arke.openProjectDialog(): Promise<string|null>`, `window.arke.notify({ kind, sessionId?, actionClass? }): void`, `window.arke.onMenu(cb)`, `window.arke.coordinator: { url }`. No method returns a credential or arbitrary fs / process access.
- **Coordinator protocol (reused, unchanged):** the renderer speaks the SPEC-003 WS request/response + event stream; opening a project is `project.open { path }` (SPEC-018) carrying the native-dialog path; every operation already exists. **The shell adds no coordinator ops.**
- **Supervisor contract:** launch → single-instance lock; if the port is free, `utilityProcess.fork(@arke/coordinator)` with `ARKE_*` env (project root, managed-harness); else attach. Await readiness (the coordinator's `listening` signal / a health ping), then create the window. Quit → send a shutdown request, await trace drain (SPEC-015) + harness stop, then exit.

### Cross-cutting
- **Security (NFR-1/5):** `contextIsolation` + `sandbox` + no `nodeIntegration`; a strict renderer CSP; `webSecurity` on; no remote content; `setWindowOpenHandler` denies arbitrary navigation; the preload surface is a small allowlist. Credentials live only in the coordinator process, making the SPEC-001 client↔host trust split a real OS boundary.
- **Reuse over fork:** the `@arke/coordinator` and `@arke/client` packages are used **unchanged**; the `packages/desktop` package only supervises + renders + bridges natives. Bringing the stack up duplicates the *intent* of `arke up` (SPEC-017) in Electron's own runtime, because the CLI is C#/.NET (SPEC-017 Decision #7) and cannot be shared as code — both remain thin clients of the same coordinator (Decision #2).
- **Multi-project (SPEC-018):** one coordinator, per-project contexts; the app opens projects **within** the single coordinator, never spawning a second.
- **Harness dependency (SPEC-016):** the managed harness (`opencode`) is an external binary the coordinator spawns; v1 assumes it is installed (as the CLI does). Whether to bundle it is an open question.
- **Design template:** the shell's only own UI is the launch / loading state + native chrome; it follows the [`arke-design` skill](../../.claude/skills/arke-design/SKILL.md). Every actual app screen is the existing client.
- **Packaging:** `electron-builder` for per-OS installers; signing / notarisation per OS; `electron-updater` against a release feed. The existing release workflow (the v0.1.0 tag flow) extends to publish desktop artefacts.

### Testing
- **Unit (main process, Node test):** supervisor readiness / attach / teardown against a fake coordinator; single-instance path routing; notification de-dup + content-free body; quit-drain ordering; the preload surface is exactly the allowlist.
- **Integration (Electron test driver, e.g. Playwright for Electron):** launch → loading → coordinator ready → workspace; a mocked native folder dialog → `project.open` → roster loads (driven against a **MockAdapter** coordinator, no live OpenCode); a permission event raises a notification whose click routes to the gate; quit stops only what launch started.
- **Manual:** a signed build installs without OS warnings on macOS + Windows; an update is offered and applied on restart without interrupting a running turn.

### Definition of done
All scenarios pass; the desktop app brings the full stack up on double-click with **no terminal** and opens a project via a native dialog; the renderer is sandboxed with no credentials and drives the coordinator over WS **identically to the browser**; notifications route the human-in-the-loop gates; quit drains + stops only what it started; signed installers auto-update; typecheck + tests green; a reviewer signed off. The `@arke/coordinator` and `@arke/client` packages are unchanged.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Electron over Tauri** | Arke's backend is a stateful Node coordinator that spawns `opencode` and does git / fs / credential work; Electron runs it with ~no porting and the client is Chromium-tested. Tauri would still ship Node as a sidecar (partial size win) while adding a Rust shell + three system webviews (Linux WebKitGTK divergence). Warrants a dedicated ADR. |
| 2 | The shell is a **client of the coordinator**, not an embedded runtime | One read model + one trace; the desktop app supervises + renders + bridges natives and drives operations over WS — the same principle as the CLI (SPEC-017 #1). No parallel business logic in the shell. |
| 3 | Coordinator in a Node **`utilityProcess`**, not the main process | Keeps main lean; a coordinator crash doesn't kill the window; mirrors the standalone `arke up` topology and makes the trust boundary an OS process boundary. |
| 4 | Renderer is the **unmodified `@arke/client`**, sandboxed, over the same WS | Desktop == browser behaviour; one client build; the SPEC-001 client↔host split becomes a real OS boundary; native affordances go over a narrow preload allowlist only. |
| 5 | Native folder picker → `project.open` with a real path | The concrete capability a browser tab cannot provide; the coordinator still canonicalises / validates the path (trust boundary, SPEC-018). |
| 6 | **Attach-if-listening** + single-instance | Never spawn a second coordinator; a coordinator started by `arke up` is reused; a second launch focuses the window. |
| 7 | Signed + notarised installers with `electron-updater` | A distributable product installs cleanly and stays current; updates are integrity-verified and never interrupt in-flight work. |

## Open questions
- **Bundle `opencode` with the app, or require it installed** (as the CLI does)? Bundling removes a prerequisite but grows the installer and couples the release cadence to the harness version.
- **Update feed + signing identity:** GitHub Releases via `electron-updater`, or a self-hosted feed? Which certs — Apple Developer ID + notarisation, and Windows OV/EV?
- **Shared supervisor:** should the desktop app and `arke up` share the "bring the stack up" logic, or is the SPEC-017 C#/.NET split (Decision #7) a permanent duplication? (They cannot share code today; both are thin clients of the same coordinator.)
- **Deep-linking (`arke://`)** to open a project or a spec from outside the app — in scope for v1, or later?
