# Arke Desktop — a one-click, native Electron app

## Why
Today Arke runs as a coordinator process + a Vite dev client + a browser tab, brought up by `arke up` (SPEC-017) — a terminal and a second toolchain stand between a product engineer and the product. A browser tab also cannot hand the host a real project path, so opening a project is a typed-path / recents flow rather than a native picker. SPEC-001 already scaffolded the shell as **`apps/desktop`** (`@arke/desktop`) — *"an Electron desktop shell that embeds the coordinator and serves the React client as one signed app"* — but it is inert. This spec **fills in that skeleton**: a signed, double-click app that embeds the coordinator, gives a native folder dialog (a real path straight to `project.open`), surfaces the human-in-the-loop gates as OS notifications, and auto-updates — Arke as a product, not a dev stack.

## What changes
- ADDED desktop-shell — fill in the existing **`apps/desktop`** (`@arke/desktop`) skeleton (SPEC-001 R-1): an **Electron** app whose main process **embeds the coordinator in-process** (`startCoordinator()`, managed harness by default, SPEC-016) and renders the built **`@arke/client`** in a sandboxed renderer, driving it over the same WebSocket as the browser. (breaking: no)
- ADDED native-integration — affordances a browser cannot give: a real **folder picker** to open a project (a genuine absolute path → `project.open`), an application menu + accelerators, single-instance focus, and window-state persistence. (breaking: no)
- ADDED notifications — OS notifications for attention states derived from concrete stream events (`permission.asked` / `question.asked`, task `session.status:error`, `panel.complete` / `panel.config-error`), de-duplicated by domain id, mutable. (breaking: no)
- ADDED service-lifecycle — app launch brings the whole stack up and quit tears down exactly what it started, with the harness-missing case handled and a defined "work-in-flight" gate; the shell drives the system only *through* the coordinator (NFR-1/7). (breaking: no)
- ADDED packaging — signed, notarised per-OS installers (dmg / nsis / AppImage) with in-app **auto-update**. (breaking: no)
- MODIFIED coordinator — a thin, additive programmatic entry `startCoordinator(): Promise<{ url }>` and a compiled-JS build so the shell can embed it; behaviour otherwise unchanged. (breaking: no)
- MODIFIED client — three small, **browser-safe** additive changes so one build serves both surfaces: read the coordinator URL from `window.arke?.coordinator?.url` when present (else today's default), **self-host the Geist fonts** (remove the remote Google Fonts `<link>`), and set a **relative Vite `base`** for packaged loading; no behavioural fork. (breaking: no)

## Requirements

### Requirement: One launch brings the whole stack up, ready
`capability: service-lifecycle` · `delta: ADDED (feat/electron-desktop-app)`

Launching the app SHALL start an **embedded** coordinator in-process (`startCoordinator()`) in managed-harness mode by default (SPEC-016), bind it to a local port, and reveal the workspace only once the coordinator is ready — `startCoordinator()` resolving IS the readiness signal, and it returns the **actual bound URL** (`server.ts start()` already returns the bound port), which the renderer receives via the preload `coordinator.url` bridge (never a hardcoded port). While it comes up a native loading state SHALL be shown, never a blank window. If the app is explicitly pointed at an already-running coordinator (an `arke up` instance, via a setting/env), it SHALL **attach** to that URL instead of embedding one, and quitting SHALL leave that external coordinator running. If the coordinator fails to become ready, the app SHALL surface the reason in-window with a retry, not fail silently. The coordinator boots **without a project** (its default context, SPEC-018); the workspace opens projects into it.

#### Scenario: launch → ready → open-a-project
- **WHEN** the app is launched with no coordinator to attach to
- **THEN** it embeds a coordinator in managed-harness mode (so the coordinator owns an `opencode serve`, SPEC-016), shows a loading state, and — once `startCoordinator()` resolves with the bound URL — reveals the launch/open-project screen with no project yet open

#### Scenario: the renderer connects via the bridged URL, not a literal
- **WHEN** the renderer is created
- **THEN** it reads `window.arke.coordinator.url` (the actual bound `ws://127.0.0.1:<port>`) and connects to that, so an ephemeral or attached port works — no `4319` literal is assumed

#### Scenario: attach to an already-running coordinator
- **WHEN** the app is configured to attach to an existing coordinator URL
- **THEN** it connects to that coordinator instead of embedding one, and quitting the app leaves that external coordinator (and its harness) running

#### Scenario: the managed harness is missing on a fresh install
- **WHEN** managed-harness mode is on but `opencode` is not found on the host
- **THEN** the app does not hard-fail: it surfaces a guided "install the harness" step (not a stack trace) and lets the user retry once it is present (see Decision #8)

#### Scenario: a coordinator that fails to start is surfaced
- **WHEN** the coordinator cannot become ready (port conflict, invalid config, harness unreachable)
- **THEN** the app shows the reason in-window with a retry, rather than presenting a dead or blank window

### Requirement: The renderer is the untrusted client; the host process is the trust boundary
`capability: desktop-shell` · `delta: ADDED (feat/electron-desktop-app)`

The renderer SHALL run with `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true`, load only local first-party assets under a **strict CSP** (no remote content — made possible by self-hosting the fonts), and reach the coordinator solely over the local WebSocket — it SHALL hold no credentials and have no direct filesystem, process, or network privilege. Credentials, git, filesystem, and the harness SHALL live in the coordinator (running in the Electron main process), so the SPEC-001 / NFR-1 client↔host credential boundary is enforced as the **renderer↔main OS process boundary** (the renderer is a separate sandboxed process regardless of where the coordinator runs). The `preload` `contextBridge` SHALL expose only a small, enumerated set of operations — `openProjectDialog()`, `notify()`, `onMenu()`, `setBusy()`, and `coordinator.url` — and NOTHING that returns a credential or an arbitrary host capability.

#### Scenario: the renderer has no privilege and no secrets
- **WHEN** the renderer is running
- **THEN** it has no Node integration, holds no credential, and cannot read the filesystem or spawn a process directly; any privileged action happens in the main/coordinator process, reached only over the WebSocket

#### Scenario: the preload surface is an allowlist
- **WHEN** the preload bridge is inspected
- **THEN** it exposes exactly `openProjectDialog` / `notify` / `onMenu` / `setBusy` / `coordinator.url` and no general-purpose fs / process / credential access

#### Scenario: a strict CSP holds because nothing is remote
- **WHEN** the UI loads under the packaged CSP
- **THEN** all assets (including fonts) resolve locally, no remote origin is fetched, and `setWindowOpenHandler` denies arbitrary navigation

### Requirement: The desktop client is the web client, with only browser-safe additive changes
`capability: desktop-shell` · `delta: ADDED (feat/electron-desktop-app)`

The window SHALL render the built **`@arke/client`** and drive the coordinator through the same request/response + event-stream WebSocket protocol (SPEC-003) — no parallel business-logic surface in the shell — and a **single build** SHALL serve both browser and desktop. Achieving that requires exactly three small, **browser-safe** client changes, and no others: (a) derive the coordinator URL from `window.arke?.coordinator?.url` when present, falling back to today's `VITE_ARKE_COORDINATOR_URL ?? ws://127.0.0.1:4319` when absent (so the browser is unaffected); (b) **self-host the Geist / Geist Mono fonts** in the client build, removing the remote Google Fonts `<link>` (a strict CSP + offline both benefit); (c) set a **relative Vite `base` (`./`)** so the built assets load under a first-party `app://` protocol handler. The shell SHALL NOT reimplement any coordinator operation.

#### Scenario: same client, same protocol, one build
- **WHEN** an operation runs in the desktop app (e.g. approve a draft, configure an agent)
- **THEN** it is issued from the renderer to the coordinator over the WebSocket exactly as in the browser, from the same client bundle — not through an Electron-only code path

#### Scenario: the URL shim is a no-op in the browser
- **WHEN** the same client build runs in a plain browser tab (no `window.arke`)
- **THEN** it derives its WS URL exactly as today, so the browser surface is unchanged

#### Scenario: assets load over app://
- **WHEN** the packaged renderer loads
- **THEN** the built client (relative `base`) is served by the `app://` protocol handler from the packaged `dist`, with `index.html` returned for the app root, and all `./assets/*` + self-hosted fonts resolve

### Requirement: Open a project from a native folder picker
`capability: native-integration` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL offer a native OS folder-selection dialog whose result is a real absolute path, and open that project by sending `project.open` (SPEC-018) to the **embedded** coordinator — the capability a browser tab cannot provide. Because the coordinator is already up and bound at launch, `project.open` has a running coordinator to target. Recent projects SHALL be reachable from the OS application menu and the launch screen; selecting one opens it in the **single** running coordinator, never a second one. The picked path SHALL be canonicalised and validated by the coordinator (the trust boundary), not the renderer.

#### Scenario: pick a folder and open it
- **WHEN** the user chooses "Open project…" and selects a directory in the native dialog
- **THEN** the real absolute path is sent as `project.open` to the already-running embedded coordinator, which validates it and opens that project context (SPEC-018), and the workspace binds to it

#### Scenario: recents open in the running coordinator
- **WHEN** the user picks a recent project from the application menu
- **THEN** it opens within the already-running coordinator (no second coordinator is spawned)

### Requirement: Single-instance, window state, and the application menu
`capability: native-integration` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL be single-instance: a second launch (or an OS "open with") SHALL focus the existing window and route any project path to it rather than starting a second app or coordinator. Window size and position SHALL persist across launches (stored in Electron `userData`). A native application menu SHALL provide the standard platform roles (about / quit / edit / view / window / help) plus Arke actions (Open project…, New specification, Reload) each bound to a platform-standard accelerator; developer tools SHALL be available only in development builds.

#### Scenario: a second launch focuses the existing window
- **WHEN** the app is launched again while an instance is already running
- **THEN** the existing window is focused (and any supplied project path is opened in it), and no second coordinator starts

#### Scenario: window bounds persist
- **WHEN** the app is resized/moved, then quit and relaunched
- **THEN** the window restores its previous size and position

#### Scenario: devtools are hidden in production
- **WHEN** a packaged production build runs
- **THEN** the developer-tools menu item and shortcut are absent

### Requirement: OS notifications for human-in-the-loop attention
`capability: notifications` · `delta: ADDED (feat/electron-desktop-app)`

When the coordinator's event stream reports a state that needs a human, the app SHALL raise a native OS notification whose body carries **no** spec content or secret, and clicking it SHALL focus the window and navigate to the relevant screen. The triggers SHALL be the concrete domain events (not derived read-model flags or UI computations): a decision is needed (`permission.asked` / `question.asked`, SPEC-012), a task needs a human (`session.status` with `status: "error"` for a task, SPEC-009), and a review finished or could not run (`panel.complete` / `panel.config-error` / `panel.reviewer-error`, SPEC-007). Because SPEC-003's per-connection `seq` restarts on reconnect and the snapshot **replaces** read-model state (so an open permission is re-delivered), notifications SHALL be **de-duplicated by a stable domain id** — `permissionId` / `questionId` / `sessionId` / `panelId` plus the trigger kind, held for the app session — so a reconnect does not re-fire past alerts. The app SHALL request OS notification permission on first use and degrade gracefully if it is denied, and the user SHALL be able to mute notifications.

#### Scenario: a pending decision raises one notification
- **WHEN** a `permission.asked` (or `question.asked`) event arrives and notifications are permitted and not muted
- **THEN** a native notification is shown whose body names the action class but contains no spec content or secret, and clicking it focuses the window and opens the gate

#### Scenario: a reconnect does not replay old alerts
- **WHEN** the client reconnects and the fresh snapshot re-delivers a still-open permission the app already notified
- **THEN** no duplicate notification fires, because its `permissionId` is already in the notified set

#### Scenario: permission denied degrades gracefully
- **WHEN** the user denies the OS notification permission
- **THEN** no OS notification is raised and no error is thrown; the in-app indicators still update

#### Scenario: mute suppresses notifications
- **WHEN** the user has muted notifications
- **THEN** no OS notification is raised, though the in-app indicators still update

### Requirement: Graceful shutdown, crash detection, and a defined work-in-flight gate
`capability: service-lifecycle` · `delta: ADDED (feat/electron-desktop-app)`

On quit the app SHALL invoke the coordinator's graceful stop, which **drains the trace** (`Trace.drain()`, SPEC-015) and stops the managed harness before the process exits. "Work in flight" SHALL be a **defined predicate**, surfaced from the read model the renderer already holds: any session that is not quiescent (no `turn.quiescent` since its last dispatch), OR any queued/running fan-out task (SPEC-009), OR any open permission/question — the renderer computes this boolean and pushes it to the main process via `setBusy()`. The app SHALL confirm before quitting while work is in flight. If the embedded coordinator raises a fatal error (startup failure, or the managed harness exits), the app SHALL detect it (it holds the coordinator in-process), surface the reason, and offer to re-initialise the coordinator without losing project state (durable on disk under each project's `.arke/`) — the window SHALL NOT be left as a dead, disconnected shell.

#### Scenario: quit drains the trace and stops the harness
- **WHEN** the app that embedded the coordinator is quit with no work in flight
- **THEN** it calls the coordinator's graceful stop, which flushes the trace (`Trace.drain()`) and stops the managed harness, then exits

#### Scenario: quitting with work in flight confirms first
- **WHEN** the user quits while `setBusy(true)` (a non-quiescent session, a running/queued task, or an open permission)
- **THEN** the app asks for confirmation before shutting the coordinator down

#### Scenario: a fatal coordinator error is detected and recoverable
- **WHEN** the embedded coordinator fails to start or its managed harness exits unexpectedly
- **THEN** the app surfaces the reason and offers to re-initialise the coordinator, and a re-init resumes from the on-disk project state without data loss

### Requirement: Signed, auto-updating distributable
`capability: packaging` · `delta: ADDED (feat/electron-desktop-app)`

The app SHALL ship as per-OS installers (macOS `dmg`, Windows `nsis`, Linux `AppImage`) that are **code-signed and notarised when signing credentials are configured**, so a signed release installs without OS security warnings, and SHALL support in-app auto-update via `electron-updater` with signature verification before apply. Because applying an update restarts the app — which tears down the **embedded** coordinator and its managed harness — an update in managed mode SHALL NOT be applied while work is in flight: the app prompts and applies only at a quiescent point or on the next launch (in **attached** mode the external coordinator survives the restart, so no work is interrupted). The DoD gates on the packaging pipeline producing installers that sign+notarise **when credentials are present**; issuing an actual signed public release (with the org's certificates and update feed) is a release-time step, not a code check.

#### Scenario: a signed build installs cleanly
- **WHEN** a release built with valid signing credentials is run on macOS or Windows
- **THEN** it installs without a Gatekeeper / SmartScreen block, because it is signed and (macOS) notarised

#### Scenario: an update defers until work is quiescent (managed mode)
- **WHEN** a newer version is available while work is in flight in managed mode
- **THEN** the app does not apply it mid-turn; it prompts and applies at a quiescent point or on next launch, so no in-flight coordinator work is interrupted

#### Scenario: an unverified update is refused
- **WHEN** a downloaded update fails signature verification
- **THEN** it is not applied and the failure is surfaced

## Design

### Architectural decision
Fill in the existing **`apps/desktop`** (`@arke/desktop`) Electron skeleton (SPEC-001 R-1; AGENTS.md architecture map; PRD §8.6 / D16), not a new package. The main process **embeds the coordinator in-process** via a thin `startCoordinator()` export — the skeleton's own plan (*"the coordinator … runs inside Electron's main process with no extra runtime, and Electron serves the same React client the browser uses … one signed app"*). This is chosen over a `utilityProcess` fork because (a) it matches the grounded skeleton/PRD, and (b) the coordinator is **TypeScript**, so any out-of-process fork would need a compiled, forkable JS file *plus* an IPC readiness channel; embedding lets the desktop's own build bundle `@arke/coordinator` to JS and use `start()`'s returned bound port directly as both the readiness signal and the URL handed to the renderer. The **renderer** is the sandboxed, near-unchanged `@arke/client` (three browser-safe additive changes), connecting over the same `ws://127.0.0.1:<bound-port>` as the browser; native affordances cross a narrow `preload` `contextBridge`, operations cross the WebSocket. Electron over Tauri stands (Decision #1). Crash-isolation via a `utilityProcess` is a considered hardening follow-up (Decision #3 / open question), deferred to keep v1 aligned with the skeleton.

### Target architecture
```
apps/desktop (@arke/desktop, Electron)                            main process (Node, built to JS)
  ├─ lifecycle: startCoordinator() IN-PROCESS → { url } (managed harness, SPEC-016);
  │             single-instance lock; window-state; graceful stop (Trace.drain) on quit;
  │             fatal-error surface + re-init; attach mode if pointed at an external URL
  ├─ native:    folder dialog · Notification · application menu · electron-updater
  └─ preload:   contextBridge → { openProjectDialog(), notify(), onMenu(), setBusy(), coordinator.url }
        │  (Electron IPC — native only, allowlisted)
        ▼
  renderer (sandboxed): @arke/client ── ws://127.0.0.1:<bound> ──▶ coordinator (in main)
        (same build as the browser)                                    │
                                                                       └─▶ HarnessAdapter → opencode serve (SPEC-016)
                                                                           read model + trace (single source of truth)
```
The renderer loads the built client (relative `base: './'`) via a first-party `app://` protocol handler over the packaged `dist` (with `index.html` for the app root; the client is store-routed, so no URL-route SPA fallback is needed — only relative asset paths). The coordinator is embedded, not forked; a second coordinator is never started, and `start()` returns the bound port that the preload bridge hands to the renderer.

### Data model
No new persistent **domain** entities. The app persists only local UI / runtime state in Electron's `userData` dir: window bounds and a notification-mute flag. Notification de-dup is an in-memory set of `{kind, id}` for the app session. All project + audit state stays under each project's `.arke/` (SPEC-015 / SPEC-018) — the shell is stateless about the domain.

### Interfaces and contracts
- **Coordinator (additive):** `startCoordinator(opts?): Promise<{ url: string; stop(): Promise<void> }>` — a thin programmatic wrapper over the existing `bootstrap()` + `Coordinator.start()` (which already returns the bound port), plus a build that emits compiled JS so the desktop bundle can import it. `stop()` performs the existing graceful path (`Trace.drain()` + harness stop). No behavioural change to the coordinator's operations.
- **Client (additive, browser-safe):** coordinator-URL resolution reads `window.arke?.coordinator?.url` first (else `VITE_ARKE_COORDINATOR_URL ?? ws://127.0.0.1:4319`); Geist / Geist Mono self-hosted in the build (remote `<link>` removed); Vite `base: './'`. Nothing else.
- **Preload bridge (native-only, allowlisted):** `window.arke.openProjectDialog(): Promise<string|null>`, `window.arke.notify({ kind, id, actionClass? }): void`, `window.arke.onMenu(cb)`, `window.arke.setBusy(inFlight: boolean): void`, `window.arke.coordinator: { url }`. No method returns a credential or arbitrary fs / process access.
- **Coordinator protocol (reused, unchanged):** the renderer speaks the SPEC-003 WS request/response + event stream; opening a project is `project.open { path }` (SPEC-018) carrying the native-dialog path. The shell adds **no** coordinator ops.
- **Notification triggers (concrete events):** `permission.asked` / `question.asked` → decision-needed; task `session.status:error` (SPEC-009) → needs-human; `panel.complete` / `panel.config-error` / `panel.reviewer-error` (SPEC-007) → review finished/failed. De-dup key = `{kind, permissionId|questionId|sessionId|panelId}`.
- **Work-in-flight predicate:** the renderer derives `inFlight = anySessionNotQuiescent || anyQueuedOrRunningFanOutTask || anyOpenPermissionOrQuestion` from the read model and pushes it via `setBusy()`; the main process gates quit-confirm and update-apply on it.

### Cross-cutting
- **Security (NFR-1/5):** `contextIsolation` + `sandbox` + no `nodeIntegration`; a strict renderer CSP (achievable because fonts are now self-hosted); `webSecurity` on; no remote content; `setWindowOpenHandler` denies navigation; the preload surface is a small allowlist. Credentials live only in the coordinator (main process); the renderer is a separate sandboxed process, so the SPEC-001 client↔host split is a real OS boundary regardless of the coordinator's in-process hosting.
- **Reuse over fork:** `@arke/coordinator` and `@arke/client` are reused with only the small, enumerated additive changes above (a programmatic entry + JS build; a URL shim + self-hosted fonts + relative base) — no behavioural fork, one client build for both surfaces. Bringing the stack up duplicates the *intent* of `arke up` (SPEC-017) in Electron's runtime, because the CLI is C#/.NET (SPEC-017 Decision #7) and cannot share code; both remain thin clients of the same coordinator.
- **Multi-project (SPEC-018):** one embedded coordinator, per-project contexts opened within it; it boots without a project (default context) and the launch screen opens projects into it. The desktop app owns a **single** coordinator (its bound port is internal, surfaced to the renderer via the bridge); attach mode targets one external coordinator URL.
- **Harness dependency (SPEC-016):** the managed harness (`opencode`) is spawned by the coordinator. For a "one-click product", v1 **detects** `opencode` at first launch and shows a guided install step if it is absent (Decision #8), rather than hard-failing; **bundling** the harness is a fast-follow (open question).
- **Design template:** the shell's only own UI is the launch / loading state + native chrome; it follows the [`arke-design` skill](../../.claude/skills/arke-design/SKILL.md). Every actual app screen is the existing client.
- **Packaging:** `electron-builder` for per-OS installers; signing / notarisation gated on configured credentials; `electron-updater` against a release feed (identity + feed are open questions). The existing release workflow (the v0.1.0 tag flow) extends to publish desktop artefacts.

### Testing
- **Unit (main process, Node test):** the notification de-dup set (a re-delivered `permissionId` fires once); the work-in-flight predicate → quit-confirm + update-defer gating; the preload surface is exactly the allowlist; attach-vs-embed selection; `startCoordinator()` returns a bound URL and `stop()` drains.
- **Integration (Electron test driver, e.g. Playwright for Electron, against a MockAdapter coordinator — no live OpenCode):** launch → loading → ready → open-project via a mocked native dialog → `project.open` → roster loads; MockAdapter emits `permission.asked` → one notification, click routes to the gate; a reconnect re-delivering the open permission fires **no** second notification; `session.status:error` on a task → notification; quit with `setBusy(true)` confirms; quit drains the trace.
- **Manual (release-validation, not gated):** a build signed with real credentials installs without OS warnings on macOS + Windows; an update is offered and, at a quiescent point, applied on restart.

### Definition of done
All scenarios pass; the app fills in `apps/desktop` and brings the full stack up on double-click with **no terminal**, embedding the coordinator and opening a project via a native dialog; the renderer is sandboxed with no credentials and drives the coordinator over WS from the **same client build** as the browser; notifications are keyed to concrete events and de-duped; quit drains the trace and gates on a defined work-in-flight predicate; the packaging pipeline produces installers that sign+notarise **when credentials are configured**; the coordinator's and client's changes are limited to the small, enumerated additive ones above; typecheck + tests green; a reviewer signed off. (Issuing an actual signed public release is a separate release-time step.)

|---|----------|-----------|
| 1 | **Electron over Tauri** | Arke's backend is a stateful Node coordinator that spawns `opencode` and does git / fs / credential work; Electron runs it with ~no porting and the client is Chromium-tested. Tauri would still ship Node as a sidecar (partial size win) + a Rust shell + three system webviews (Linux WebKitGTK divergence). Matches the skeleton's own note. Warrants a dedicated ADR. |
| 2 | Fill in the existing **`apps/desktop`** (`@arke/desktop`), not a new package | SPEC-001 R-1 + AGENTS.md + PRD §8.6/D16 already mandate this workspace as "the Electron shell that embeds the coordinator (one signed app)". A new `packages/desktop` would contradict the grounding and orphan the skeleton. |
| 3 | Coordinator **embedded in-process** (`startCoordinator()`), not a `utilityProcess` fork | Matches the skeleton/PRD; the coordinator is TypeScript, so a fork needs a compiled JS entry + an IPC readiness channel, whereas embedding uses `start()`'s returned bound port directly as readiness + URL. Crash-isolation via `utilityProcess` is a deferred hardening follow-up. |
| 4 | The shell is a **client of the coordinator**; the client stays one build with only browser-safe additive changes | One read model + one trace (as the CLI, SPEC-017 #1); the URL shim / self-hosted fonts / relative base are browser-safe, so a single `@arke/client` build serves both surfaces with no behavioural fork. |
| 5 | Renderer gets the coordinator URL from the **preload bridge**, never a hardcoded port | `server.ts` binds `ARKE_COORDINATOR_PORT ?? 4319` and returns the **actual** bound port; SPEC-016 allows an ephemeral port and attach mode targets an arbitrary URL — so `coordinator.url` must be resolved and injected, not literal `4319`. |
| 6 | Native folder picker → `project.open` with a real path, into the already-running embedded coordinator | The concrete capability a browser tab cannot provide; the coordinator (up at launch, before any project) canonicalises / validates the path (trust boundary, SPEC-018). |
| 7 | Notifications key off **concrete stream events** + a domain-id **de-dup** | needs-human is a derived read-model flag and "divergence" is a UI mark — not events; the real signals are `permission.asked`/`question.asked`, task `session.status:error`, `panel.complete`/`panel.config-error`/`panel.reviewer-error`. SPEC-003's `seq` restarts + snapshot-replace on reconnect re-deliver open state, so de-dup MUST be by `permissionId`/`questionId`/`sessionId`/`panelId`, not `seq`. |
| 8 | Harness **detect + guide** on first launch (v1); bundle as a fast-follow | A one-click product must not stack-trace on a fresh machine without `opencode`; detect it and guide installation. Bundling removes the prerequisite entirely but grows the installer and couples release cadence to the harness — deferred. |
| 9 | Auto-update **defers while work is in flight** in managed mode; attach mode is exempt | Applying an `electron-updater` update restarts the app, tearing down the embedded coordinator + managed harness (Decision #3) — so the "no interrupt" guarantee only holds by deferring in managed mode; an attached external coordinator survives the restart. |
| 10 | Signing/notarisation in the **DoD gates on "signs when credentials configured"** | Code-signing / notarisation are external, credential- and account-gated; the code DoD can guarantee the pipeline, not an actual signed public release (which is a release-time step). |

## Open questions
- **Bundle `opencode` with the app** (removing the first-launch prerequisite entirely), or keep detect-and-guide (Decision #8)? Bundling grows the installer and couples the release cadence to the harness version.
- **Update feed + signing identity:** GitHub Releases via `electron-updater`, or a self-hosted feed? Which certs — Apple Developer ID + notarisation, and Windows OV/EV — and where do they live in CI?
- **Crash isolation:** revisit a `utilityProcess`-hosted coordinator (Decision #3) as a hardening follow-up once the in-process v1 ships?
- **Deep-linking (`arke://`)** to open a project or a spec from outside the app — in scope for v1, or later?
