Per-key API rate limiting

Why

A single noisy API key can exhaust shared capacity and degrade the service for everyone. There is no per-key ceiling today, so one integration's burst becomes an outage for the rest. This adds a fair, per-key limit at the gateway.

What changes

  • ADDED rate-limiting — each API key gets an independent request budget enforced at the gateway.
  • MODIFIED api-gateway — the gateway rejects over-budget requests with 429 and a Retry-After header (breaking: no — keys under their budget are unaffected).

Requirements

Requirement: Enforce a per-key request budget

capability: rate-limiting · delta: ADDED (feat/api-rate-limiting)

The system SHALL enforce an independent request budget per API key, and SHALL count only the requests made with that key against its own budget — never against another key's.

Scenario: A key within its budget is served

  • WHEN a key makes requests below its configured limit within the window
  • THEN every request is served normally

Scenario: A key over its budget is throttled

  • WHEN a key exceeds its configured limit within the window
  • THEN further requests for that key are rejected until the window resets
  • AND other keys are unaffected

Requirement: Signal throttling with a 429 and Retry-After

capability: api-gateway · delta: MODIFIED (feat/api-rate-limiting)

When a request is throttled, the gateway MUST respond with HTTP 429 Too Many Requests and MUST include a Retry-After header telling the caller when to try again.

Scenario: A throttled response is actionable

  • WHEN the gateway rejects a request for exceeding the budget
  • THEN the response status is 429
  • AND a Retry-After header gives the seconds until the window resets

Design

Architectural decision

Enforce the limit at the gateway with a fixed-window counter per key held in a shared cache, so the budget is checked once, close to the edge, before any request reaches an upstream service.

Target architecture

The gateway resolves the API key, atomically increments that key's counter for the current window in the shared cache, and compares it against the key's configured limit. Under budget, the request proceeds; over budget, the gateway short-circuits with a 429.

Interfaces and contracts

  • Cache key: ratelimit:<api-key-id>:<window-start>; value is the count; TTL is the window length.
  • Response headers on every call: X-RateLimit-Limit, X-RateLimit-Remaining, and — when throttled — Retry-After.

Cross-cutting

  • Security: the limit is keyed on the authenticated API key id, never on a client-supplied header.
  • Performance: a single atomic increment per request; the check adds one cache round-trip at the edge.

Tasks

  • fixed-window counter with per-window TTL in the shared cache
  • gateway middleware: increment, compare, short-circuit on over-budget
  • 429 + Retry-After and the X-RateLimit-* headers
  • per-key limit configuration

Testing

  • Unit: a key's counter is isolated from other keys; the window resets on TTL expiry.
  • Integration: under-budget served; over-budget 429 with a correct Retry-After.
  • Manual: drive a key past its limit and confirm the 429 + header, and that a second key is unaffected.

Definition of done

All scenarios above pass, checks are green, and a reviewer has signed off.
