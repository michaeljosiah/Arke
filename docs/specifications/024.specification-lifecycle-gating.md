# Specification lifecycle gating — delivered, decoupled delivery, host-optional governance

## Why

The governance contract ([`../specification-lifecycle-and-delivery.html`](../specification-lifecycle-and-delivery.html)) settled the model — *Arke governs the specification, git delivers the code, one op with two triggers, host-optional* — but the implementation has loose gates: two promotion doors (one ungated), no well-formedness check, delivery welded to approval, a git-verb terminal state, and no host-less path. This specification tightens them. It is the governed-lifecycle half of the split from the original SPEC-023; the board projection fix is [SPEC-023](023.one-card-per-spec-board-fold.md), on which this depends.

## What changes

- MODIFIED spec-lifecycle — the terminal governed status is renamed **`merged` → `delivered`** (names the governance outcome, not the git mechanism; correct for local merges). *(breaking: the `SpecStatus`/`BoardColumn` value changes.)*
- MODIFIED spec-lifecycle — delivery is **decoupled from approval**: `approved` fires no side-effects and rests as the backlog; an explicit `spec.deliver` op starts implementation (and downstream-artefact generation) on a recorded branch.
- MODIFIED spec-lifecycle — a **single gated promotion door**: the ungated `spec.promote` is deleted; all callers (board, CLI, coordinator) route through the existing gated `approveDraft` sequence.
- ADDED spec-lifecycle — a **well-formedness gate** (new parsing, not existing anatomy) rejects promotion of a malformed specification with `spec.malformed`.
- ADDED spec-lifecycle — **one op, two triggers**: every governed transition (including reopen/regression) is an op whose gate is identical for a webhook or a human; safe manual moves dispatch the op and are audited; illegal transitions are refused server-side regardless of caller.
- ADDED spec-lifecycle — **host-optional governance**: a local-merge path to `delivered` when no git host is configured, plus a governance-level indicator (host-enforced / team / solo).

**Depends on:** SPEC-023 (one-card-per-spec board), SPEC-007 (review panel), SPEC-008 (lifecycle), SPEC-013 (generation).

## Requirements

### Requirement: The terminal governed status is `delivered`
`capability: spec-lifecycle` · `delta: MODIFIED (feat/spec-024-lifecycle-gating)`

The governed `status` SHALL be one of exactly `draft`, `in-review`, `approved`, `delivered`; the terminal value is **`delivered`**. The rename SHALL update every consumer of the `SpecStatus` / `BoardColumn` value `merged`, specifically: the `SpecStatus` and `BoardColumn` enums (`contracts/src/spec.ts`, `events.ts`); the `setStatus("merged", "pr-merged")` call site (`project-context.ts:718`); `deriveColumn` (`read-model.ts:247`, `live.ts`); the library status badge colour mapping (`picker-init-library.tsx`, `ds.tsx`/`utils.tsx`); the CLI; and SPEC-008's status-badge scenario and SPEC-010's `deriveColumn` row. The git-side `WebhookTransition.kind: "merged"` (`spec-lifecycle.ts:170`, `mapWebhookEvent`) SHALL **NOT** be renamed — it correctly names the git event; only the `SpecStatus` value it maps to changes. Legacy on-disk `status: merged` SHALL be normalised to `delivered` during the project-open reconciliation pass (rewriting the frontmatter), so no permanent read-model-vs-frontmatter divergence (`spec.divergence-warning`, SPEC-008) is produced.

#### Scenario: Merge sets delivered and flattens deltas
- **WHEN** the delivery merge lands on the mainline (webhook or local)
- **THEN** the specification's `status` is set to `delivered` and its delta tags flatten (idempotently)

#### Scenario: No `merged` status is ever written
- **WHEN** any transition writes the terminal status
- **THEN** the value written and read is `delivered`; no code path writes or reads `status: merged`

#### Scenario: Legacy merged is normalised without a divergence warning
- **WHEN** a project opens containing a spec whose frontmatter says `status: merged`
- **THEN** the reconciliation pass rewrites it to `delivered`
- **AND** no `spec.divergence-warning` is emitted for that spec

### Requirement: Delivery is decoupled from approval
`capability: spec-lifecycle` · `delta: MODIFIED (feat/spec-024-lifecycle-gating)`

Reaching `approved` SHALL fire **no side-effects** — it removes both `this.fanOut(specId)` and `this.generate(specId)` from the `approved` case (`project-context.ts:712–713`). `approved` is a stable resting state (the backlog); the approved document lives in the library and its delta tags remain "pending delivery". An explicit `spec.deliver { specId, branch? }` op SHALL start delivery: it records a delivery branch on the specification, then runs **both** single-session delivery ([SPEC-028](028.single-session-delivery.md), `deliverImplementation()` — a single implementer session receives the whole task checklist, superseding SPEC-009's per-task fan-out) and downstream-artefact generation (SPEC-013, `generate()` — moved here from approval). `spec.deliver` SHALL be rejected if a delivery for that spec is already `implementing` or queued (no double-dispatch: a synchronous in-memory claim closes the race between the guard check and the async `createSession` call), and if the spec is not `approved`.

#### Scenario: Approval parks the spec with no side-effects
- **WHEN** a specification reaches `approved`
- **THEN** no task session is dispatched and no downstream-artefact generation runs
- **AND** its card rests in the `approved` backlog lane

#### Scenario: Deliver dispatches the implementer and generates on a recorded branch
- **WHEN** a human issues `spec.deliver` for an `approved` spec
- **THEN** the coordinator records the delivery branch, dispatches a single implementer session carrying the full task checklist ([SPEC-028](028.single-session-delivery.md)), and runs downstream-artefact generation
- **AND** the card moves to `implementing`

#### Scenario: Duplicate deliver is rejected
- **WHEN** `spec.deliver` is issued for a spec that is already delivering
- **THEN** the op is rejected with a named error and no additional sessions are dispatched

#### Scenario: Deltas flatten only at delivered
- **WHEN** a spec is `approved` but not delivered
- **THEN** its requirement delta tags remain "pending delivery" and flatten only at `delivered`

### Requirement: A single gated promotion door
`capability: spec-lifecycle` · `delta: MODIFIED (feat/spec-024-lifecycle-gating)`

There SHALL be exactly one operation that advances `draft → in-review`, and it SHALL enforce the full existing `approveDraft` precondition set, in order: **(1)** the specification is well-formed (below); **(2)** an adjudicated review panel has completed (SPEC-007) — else `review.gate-failed`; **(3)** no authoring session is still running; **(4)** the branch guard `HEAD == frontmatter.branch` holds — else `spec.branch-mismatch`; **(5)** git is available — all under the serialized `approvalInFlight` lock. The ungated `spec.promote` op (`project-context.ts:763`) SHALL be **deleted**, and every caller re-pointed at this gated op: the board "Promote to review" action, and the CLI `SpecPromoteCommand` (`cli/Arke.Cli/Commands/OperationCommands.cs:476`). A caller that cannot satisfy the branch guard (e.g. the board when `HEAD` is not the spec's branch) SHALL receive `spec.branch-mismatch` with guidance, not a silent bypass.

#### Scenario: Promotion without a completed panel is rejected
- **WHEN** promotion is attempted for a spec with no completed, adjudicated review panel
- **THEN** it is rejected with `review.gate-failed` and the spec stays `draft`

#### Scenario: Every caller runs the same gate
- **WHEN** the board action or the CLI `spec promote` issues a promotion
- **THEN** the same gated op runs the full precondition set
- **AND** there is no operation that reaches `in-review` without it

#### Scenario: Branch mismatch is surfaced, not bypassed
- **WHEN** a promotion is issued while `HEAD` is not the spec's frontmatter `branch`
- **THEN** it is rejected with `spec.branch-mismatch`

### Requirement: Well-formedness gate before promotion
`capability: spec-lifecycle` · `delta: ADDED (feat/spec-024-lifecycle-gating)`

A specification SHALL NOT advance out of `draft` unless a **well-formedness validator** passes. `SPEC_ANATOMY` (`contracts/src/spec.ts`) today models only section presence and does **not** model SHALL/MUST statements or WHEN/THEN scenarios; this requirement therefore ADDS parsing: the validator SHALL check (a) the mandated sections are present (existing `SPEC_ANATOMY` / `parseSpecDoc`), (b) at least one requirement contains a SHALL or MUST statement, and (c) at least one `#### Scenario:` block contains both a WHEN and a THEN. On failure, promotion SHALL be rejected with `spec.malformed { missing: string[] }` naming what is absent, so the cockpit can surface it. This is new parser work, not a walk of the current `SPEC_ANATOMY` shape.

#### Scenario: Missing scenarios blocks promotion
- **WHEN** a draft has requirements but no `#### Scenario:` with WHEN/THEN
- **THEN** promotion is rejected with `spec.malformed` whose `missing` includes "scenarios"

#### Scenario: Missing SHALL/MUST blocks promotion
- **WHEN** a draft has requirement headings but no SHALL/MUST statement
- **THEN** promotion is rejected with `spec.malformed` whose `missing` includes "normative statements"

#### Scenario: A well-formed draft promotes
- **WHEN** a draft has the mandated sections, a SHALL/MUST requirement, a WHEN/THEN scenario, an adjudicated panel, and a matching branch
- **THEN** promotion succeeds and `status` becomes `in-review`

### Requirement: One op, two triggers — including reopen and regression
`capability: spec-lifecycle` · `delta: ADDED (feat/spec-024-lifecycle-gating)`

Every governed transition SHALL be a coordinator operation whose gate is identical regardless of trigger — a git-host webhook or a human. This covers the forward transitions and the **reopen/regression** edges: `approved → in-review` on a material change (SPEC-008 normative-hash), `pr-closed → draft`, `pr-reopened → in-review`, and reopen of a `delivered` spec on a material change. A human move SHALL **dispatch the transition op**, never write `status`/`column` directly; the client offers only a **legal adjacent** transition, but the server SHALL reject any illegal or non-adjacent transition **regardless of caller** (board, CLI, or direct `ArkeTransport.send` / API) — the "offered" restriction is a UI affordance, not the gate. Every manual transition SHALL be audited as `spec.status { reason: "manual", actor, from, to }`. When a `delivered` (or `approved`-delivering) spec is reopened, its in-flight delivery sessions SHALL be marked `interrupted` and the card SHALL surface the reopen; delivery does not silently continue against a superseded contract.

#### Scenario: Manual approve runs the same gate as a webhook
- **WHEN** a human moves a card from `in-review` to `approved`
- **THEN** the coordinator runs the full approval gate (including the non-author check) and, on success, emits `spec.status` with `reason: "manual"` and the actor recorded
- **AND** the emitted status and any rejection error are identical to the webhook-triggered path

#### Scenario: A non-adjacent transition is refused server-side
- **WHEN** a caller sends a direct op to move a `draft` spec to `approved`, or to `approved` without a completed panel, bypassing the UI's adjacency restriction
- **THEN** the server rejects it with the gate's named error and writes no `status` or `column`

#### Scenario: Material change reopens an approved spec
- **WHEN** the Requirements or Design of an `approved` spec are materially edited
- **THEN** the spec regresses to `in-review` and the change ripples to its projections

#### Scenario: Reopening a delivered spec interrupts in-flight delivery
- **WHEN** a `delivered` spec is reopened by a material change while a follow-up delivery session is running
- **THEN** that in-flight session is marked `interrupted` and the card surfaces the reopen

### Requirement: Host-optional governance with an explicit assurance level
`capability: spec-lifecycle` · `delta: ADDED (feat/spec-024-lifecycle-gating)`

No governed transition SHALL require a configured git host. With a host, PR / review / merge webhooks drive transitions and branch protection enforces the non-author approver. Without a host, the human triggers the same gated ops and the coordinator reaches `delivered` by a **local branch merge** — new functionality: today `flattenAndMerge` (`project-context.ts:730`) only writes the flattened file and performs no `git merge`, so a merge module SHALL be added. A local merge that **conflicts** SHALL be rejected with a named error, leaving the spec `approved` (or its prior state), never a half-merged tree. The board SHALL surface a **governance-level indicator**: *host-enforced* (webhooks + branch protection), *team* (an in-app approver identity distinct from the owner), or *solo* (self-approval permitted but flagged). Solo-mode self-approval SHALL be recorded as `governance.self-approval-allowed-solo`.

#### Scenario: The board moves with no git host configured
- **WHEN** no git host is configured and a human drives a spec through the gates
- **THEN** it progresses `draft → in-review → approved → delivered`, the coordinator performing a local merge to reach `delivered`
- **AND** the governance-level indicator reads *solo* or *team* accordingly

#### Scenario: A conflicting local merge is rejected cleanly
- **WHEN** the coordinator's local merge to the mainline conflicts
- **THEN** the transition is rejected with a named error and the spec stays `approved`
- **AND** no partial/half-merged state is left

#### Scenario: Solo self-approval is flagged, not silently allowed
- **WHEN** in solo mode the owner approves their own specification
- **THEN** the approval is permitted but recorded as `governance.self-approval-allowed-solo` and the indicator shows the reduced assurance

## Design

### Architectural decision

Governance transitions become a small set of gated ops behind one dispatcher (`applyTransition(op, trigger)`) shared by `handleWebhook` and the client/CLI op path — the trigger differs, the gate does not. `approved` is made side-effect-free; `spec.deliver` carries single-session delivery ([SPEC-028](028.single-session-delivery.md)) and generation. The terminal governed value is `delivered`; the git-side transition name stays `merged`. Git is demoted to an optional accelerator with a local-merge fallback.

### Target architecture

- **Contracts** (`spec.ts`, `events.ts`): `SpecStatus`/`BoardColumn` `merged → delivered`; add `spec.deliver`, `spec.malformed { missing[] }`, `governance.self-approval-allowed-solo`, the governance-level type, and (already optional) `spec.status.reason`/`actor`.
- **Coordinator** (`project-context.ts`, `spec-lifecycle.ts`): remove `fanOut`+`generate` from the `approved` case (:712–713); add `spec.deliver` (record branch → `deliverImplementation` + generate; re-delivery guard — see [SPEC-028](028.single-session-delivery.md)); delete `promoteSpec` (:763) and re-point callers at the gated `approveDraft` sequence (:1148); add the well-formedness validator ahead of that sequence; add `applyTransition(op, trigger)` used by both `handleWebhook` and the op dispatcher; add a local-merge module for the host-less path; rename `setStatus("merged")` (:718) to `delivered`; add the legacy-`merged` reconciliation on project-open.
- **CLI** (`cli/Arke.Cli/Commands/OperationCommands.cs`): `SpecPromoteCommand` re-pointed at the gated op; add `spec deliver` if surfaced.
- **Client** (`board-session-diff-permission.tsx`): the `Delivered` lane label; the governance-level badge; gated manual-move affordance (drag/menu) that dispatches the op, offers only legal adjacent lanes, and confirms the write.

### Interfaces and contracts

- New ops: `spec.deliver { specId, branch? }`; the unified promotion op (gated `approveDraft`).
- New events / errors: `spec.malformed { missing }`, `governance.self-approval-allowed-solo`; `spec.status` carries `reason`/`actor`.
- `SpecStatus`/`BoardColumn`: `merged → delivered` (contract change; the persisted trace's historical `status: merged` values are read-compatible via the reconciliation/normalisation).

### Cross-cutting
- **Design template:** the `Delivered` lane, governance badge, and manual-move affordance follow the `arke-design` skill (`.claude/skills/arke-design/`).
- **Security / governance (NFR-1/7):** no `status`/`column` is written from the client; illegal transitions are rejected server-side for **all** callers, not just the UI; self-approval is fail-closed except audited solo mode; every transition and dead-letter is traced before any client sees it.
- **Migration:** legacy `status: merged` normalised to `delivered` on project-open; the trace remains an append-only historical record (old `merged` events are not rewritten).

### Definition of done
Terminal status/column is `delivered` with no `merged` remaining (and `WebhookTransition.kind` intact); `approved` fires no side-effects and `spec.deliver` exists with a re-delivery guard; one gated promotion door across board + CLI with a working well-formedness gate; reopen/regression transitions and non-adjacent rejection covered; the board moves end-to-end with no git host via local merge; suite green; a non-author reviewer has signed off; SPEC-023 merged (board fold dependency).

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Terminal status `delivered`, not `merged` | Names the governance outcome, correct for local merges; `WebhookTransition.kind:"merged"` stays as the git-event name |
| 2 | `generate()` moves to `spec.deliver`, not approval | Approval must be side-effect-free so `approved` is a true resting backlog; downstream-artefact generation is part of delivery |
| 3 | Delete `spec.promote`; one gated door (`approveDraft`) for board + CLI | Two doors (one ungated) let governance be bypassed; a single gate is the only safe design |
| 4 | Well-formedness is NEW parser work | `SPEC_ANATOMY` models only section presence — it has no notion of SHALL statements or WHEN/THEN scenarios; the gate must add that parsing rather than claim it exists |
| 5 | Reopen/regression are first-class one-op transitions | The governance contract's reopen edges must run the same gate; in-flight delivery on a reopened spec is interrupted, not silently continued |
| 6 | Illegal transitions rejected server-side for all callers | "Legal adjacent only" is a UI affordance; the real boundary is the server rejecting any illegal op from board, CLI, or API |
| 7 | Local-merge is genuinely new coordinator functionality | `flattenAndMerge` only writes the flattened file; reaching `delivered` host-less needs a real `git merge` with conflict handling |
| 8 | Legacy `merged` normalised on open, not left divergent | Read-time coercion without rewrite would trip `spec.divergence-warning` forever; reconciliation rewrites the frontmatter once |

## Open questions — RESOLVED (2026-07-05)
- **Reopen-from-`delivered`:** ✅ **In-place reopen.** A material change (or manual reopen) to a `delivered` spec regresses it to `in-review` and interrupts any in-flight follow-up delivery session (`interruptInFlightDelivery`) — it is the same spec, not a new version. Delivery must not continue against a superseded contract.
- **Team-mode identity host-less:** ✅ **In-app actor name.** A manual approval carries an `actor` (a name/handle) recorded on `spec.status { reason:"manual", actor }` and in the trace; it must differ from the owner to count as a team approval. Honour-system, audited, no crypto — meaningful without a full identity system. A host-less owner self-approval is permitted only in solo mode and flagged `governance.self-approval-allowed-solo`.
- **`generate()` placement:** ✅ **On deliver only.** Downstream-artefact generation runs as part of `spec.deliver`, keeping `approved` fully side-effect-free (Decision #2). Artefacts appear when delivery actually starts, not at approval.
