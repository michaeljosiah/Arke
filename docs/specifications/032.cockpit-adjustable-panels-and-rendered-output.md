# Authoring cockpit — adjustable panels and rendered output

## Why
The cockpit today pins the conversation to a fixed 430px column and renders both the agent
transcript and the specification preview as plain `pre-wrap` text — so a Product Engineer cannot
give the conversation more room when the discussion is the work, and reads unformatted markdown
(raw `#`, `-`, fenced code, tables) on both sides. OpenCode's desktop web app (`v2`) already solves
the reading half well — it renders agent output as formatted, syntax-highlighted, copyable markdown
and dispatches by output kind — and is the reference we mirror. This change makes the split
adjustable and makes both surfaces render markdown, so the cockpit reads the way the agents actually
write. It extends the authoring-cockpit surface (SPEC-006) covering FR-1, FR-14.

## What changes
- MODIFIED authoring-cockpit — the conversation/preview split is a **draggable, persisted** divider (widen the chat, shrink the preview, or the reverse) instead of a fixed 430px column
- MODIFIED authoring-cockpit — the specification preview **renders markdown by default** (retaining the section-by-section anatomy and delta highlighting) with a control to switch to a **raw** monospaced view of the file's exact text
- MODIFIED authoring-cockpit — agent turns in the conversation **render as formatted markdown** (headings, lists, tables, links, blockquotes, task lists, inline + fenced code); human turns stay literal   (breaking: no)
- ADDED agent-output-rendering — a shared, sanitised markdown renderer with subtle neutral syntax-highlighted, copyable code blocks, used by both cockpit panels and reusable by other agent-output surfaces

## Requirements

### Requirement: Adjustable split between the conversation and the specification
`capability: authoring-cockpit` · `delta: MODIFIED (feat/cockpit-panels-and-rendering)`

The cockpit SHALL separate its conversation panel (left) and specification preview (right) with a
draggable divider that reallocates horizontal space between them; the chosen split SHALL persist
across reloads; both panels SHALL be clamped to a minimum width so neither collapses below a legible
size; the divider SHALL be operable by keyboard and expose a reset to the default split. The divider
replaces the current fixed 430px conversation column.

#### Scenario: Dragging widens the conversation and narrows the preview
- **WHEN** the engineer drags the divider towards the preview
- **THEN** the conversation panel widens and the preview narrows by the same amount in real time
- **AND** releasing the pointer settles the split at the dragged position

#### Scenario: Minimum widths clamp the drag
- **WHEN** the engineer drags the divider past the point where either panel would fall below its minimum width
- **THEN** the divider stops at the clamp and neither panel shrinks below its minimum
- **AND** the conversation and preview each remain at least their minimum legible width

#### Scenario: The split persists across reloads
- **WHEN** the engineer has set a split and reloads the app
- **THEN** the cockpit restores the previously chosen split rather than the default
- **AND** the persisted value is a client-side view preference, not authoritative domain state

#### Scenario: Reset restores the default split
- **WHEN** the engineer double-clicks the divider (or focuses it and presses Home)
- **THEN** the split returns to the default ratio

#### Scenario: The divider is keyboard-operable and announced
- **WHEN** the divider receives focus and the engineer presses ArrowLeft / ArrowRight
- **THEN** the split moves by a fixed step in the pressed direction, clamped to the minimums
- **AND** the divider exposes `role="separator"`, `aria-orientation="vertical"`, and a current-position `aria-valuenow`, with a visible focus ring (NFR-6)

### Requirement: The preview renders markdown by default with a raw view
`capability: authoring-cockpit` · `delta: MODIFIED (feat/cockpit-panels-and-rendering)`

The specification preview SHALL render the working file as formatted markdown by default —
retaining the section-by-section order defined by `SPEC_ANATOMY` and the delta-tag highlighting from
SPEC-006 — and SHALL provide a control to switch to a raw, monospaced view of the file's exact text;
the chosen mode SHALL persist across reloads; both modes SHALL remain read-only views of the on-disk
file, and the in-flight-write and refreshed indicators SHALL continue to work in both modes. The
preview SHALL NOT hold a writable copy of the specification body (SPEC-006 invariant unchanged).

#### Scenario: Default mode is rendered markdown
- **WHEN** the preview loads a working file
- **THEN** it renders markdown prose as formatted output (headings, lists, tables, emphasis, links, inline and fenced code), not as escaped `pre-wrap` source
- **AND** the mode toggle defaults to the rendered view

#### Scenario: Delta-tagged requirements stay highlighted in rendered mode
- **WHEN** a requirement in the working file carries `delta: ADDED | MODIFIED | REMOVED`
- **THEN** the rendered view keeps the SPEC-006 delta treatment (coloured left border + badge; REMOVED shown as a struck-through tombstone), with the requirement's prose rendered as markdown
- **AND** an untagged requirement renders in the neutral, settled style

#### Scenario: Raw mode shows the file's exact source
- **WHEN** the engineer switches the preview to raw mode
- **THEN** the panel shows the working file's exact markdown source in Geist Mono, including frontmatter and the `capability:`/`delta:` metadata lines
- **AND** the text is selectable and copyable but read-only

#### Scenario: The mode preference persists
- **WHEN** the engineer selects raw (or rendered) mode and reloads
- **THEN** the preview restores that mode

#### Scenario: Both modes track the on-disk file
- **WHEN** an agent writes to the working file and the preview refreshes (per SPEC-006's `spec.file` poll / fallback)
- **THEN** the change is reflected in whichever mode is active
- **AND** the in-flight-write indicator and the "refreshed" indicator behave as specified in SPEC-006 in both modes

### Requirement: The conversation renders each agent output kind distinctly
`capability: authoring-cockpit` · `delta: MODIFIED (feat/cockpit-panels-and-rendering)`

The conversation SHALL render each kind of agent output distinctly, mirroring OpenCode's part-typed
rendering over the output kinds Arke's transcript carries: assistant **text** SHALL render as
formatted markdown; **tool calls** SHALL render as compact tool cards (tool name, target path when
present, and result when present) visually distinct from prose; a streaming turn SHALL render its
markdown incrementally without flicker and show an in-progress caret; **human** turns SHALL render as
literal text, never parsed as markdown. The existing thinking/tool activity indicator is retained.

#### Scenario: Agent text renders as markdown
- **WHEN** an agent turn's text contains markdown (emphasis, lists, a link, inline `code`, a fenced block)
- **THEN** the conversation renders it as formatted markdown, not as escaped source

#### Scenario: Streaming output renders incrementally and safely
- **WHEN** an assistant turn is streaming (`isStreaming`) and its text so far ends mid-construct (e.g. an unterminated fenced code block)
- **THEN** the partial text renders without throwing and without flicker, treating the open construct as in-progress (the unterminated fence renders as a code block)
- **AND** an in-progress caret is shown until the turn finalises

#### Scenario: Human input is rendered literally
- **WHEN** a human turn contains characters that look like markdown (e.g. `# heading`, `*text*`)
- **THEN** the conversation shows them verbatim, not parsed as markdown

#### Scenario: Tool calls render as distinct tool cards
- **WHEN** an agent turn carries `toolCalls`
- **THEN** each tool call renders as a compact card showing the tool name (and target path / result when present), visually distinct from the prose of the turn
- **AND** while the turn is in flight with no visible text yet, the thinking indicator names the active tool (retained from SPEC-020)

### Requirement: Fenced and inline code render highlighted and copyable
`capability: agent-output-rendering` · `delta: ADDED (feat/cockpit-panels-and-rendering)`

Fenced code blocks SHALL render on a distinct neutral surface in Geist Mono with **subtle,
low-saturation** syntax highlighting consistent with the design contract — neutral greys with the
teal brand accent (SPEC-033) as the single restrained accent — and a per-block copy action that
copies the exact source; an unknown or absent language SHALL fall back to
unhighlighted monospace; highlighting SHALL degrade gracefully to plain monospace when the
highlighter is unavailable (still loading, or offline); inline code SHALL be visually distinct from
surrounding prose. Highlighting SHALL never block or delay display of the surrounding text.

#### Scenario: A fenced code block is highlighted with a copy action
- **WHEN** the rendered content contains a fenced block with a known language (e.g. ` ```ts `)
- **THEN** the block renders on a neutral code surface in Geist Mono with subtle neutral highlighting and a copy control
- **AND** the highlighting palette is low-saturation — neutral greys plus the teal brand accent (SPEC-033) as the single restrained accent for keywords/strings — not full-spectrum colour

#### Scenario: Copy copies the exact source
- **WHEN** the engineer activates a code block's copy control
- **THEN** the exact code text is written to the clipboard and the control confirms the copy
- **AND** the copied text excludes the highlighting markup and the fence markers

#### Scenario: Unknown or absent language falls back to plain monospace
- **WHEN** a fenced block declares no language or a language the highlighter does not know
- **THEN** the block renders as plain, unhighlighted monospace on the same code surface (still copyable)

#### Scenario: The highlighter being unavailable never blocks the turn
- **WHEN** the syntax highlighter has not finished loading (or is unavailable offline)
- **THEN** code renders immediately as plain monospace and upgrades to highlighted output once the highlighter is ready, without re-flowing the surrounding text

#### Scenario: Inline code is distinct
- **WHEN** prose contains inline `code`
- **THEN** it renders in Geist Mono with a subtle neutral background, distinct from the prose

### Requirement: Agent- and file-sourced markdown is rendered safely
`capability: agent-output-rendering` · `delta: ADDED (feat/cockpit-panels-and-rendering)`

The renderer SHALL treat all markdown — whether from the agent transcript or the working file — as
untrusted: it SHALL NOT execute or inject raw HTML embedded in the markdown; it SHALL restrict links
to safe protocols (`http`, `https`, `mailto`) and open external links in a new tab with
`rel="noopener noreferrer"`; and the render pipeline SHALL be client-side only, holding no
credentials and making no calls to any system of record (NFR-1, NFR-5).

#### Scenario: Embedded raw HTML is inert
- **WHEN** rendered markdown contains raw HTML such as `<script>` or an event-handler attribute
- **THEN** it is not executed or injected as live DOM; the renderer emits only its own safe element set (raw HTML is dropped or shown as text, never run)

#### Scenario: A dangerous link protocol is neutralised
- **WHEN** rendered markdown contains a link with a `javascript:` (or other non-allowlisted) protocol
- **THEN** the link is neutralised (rendered inert / stripped), not clickable to that protocol

#### Scenario: External links open safely
- **WHEN** rendered markdown contains an `https://` link
- **THEN** it opens in a new tab with `rel="noopener noreferrer"`

## Design

### Architectural decision
Introduce one shared, sanitised markdown renderer (a design-system component) and use it on both
cockpit panels, so agent prose and specification prose render identically; make the panel split a
draggable, persisted divider; give the preview a rendered/raw switch. This mirrors OpenCode v2's
`session-ui` rendering (below) adapted to Arke's React 19 thin client and monochrome design contract.
No coordinator events, commands, or persistent domain state are added — this is a pure
client-rendering and layout change over the existing SPEC-003 transcript events and SPEC-006
`spec.file` read.

**Mirrored from OpenCode v2 (`packages/session-ui/src/components/`, the web app that powers its
desktop shell):**
- `message-part.tsx` — dispatch by output kind (text → markdown, tool → tool card). Arke's transcript
  carries `text` + `toolCalls` (`@arke/contracts` `TranscriptEntry`), so Arke dispatches over those
  two kinds. OpenCode's reasoning / file / question parts have no equivalent in Arke's event model
  and are out of scope.
- `markdown.tsx`, `markdown-stream.ts` — streaming-aware markdown with per-block reuse and per-code
  copy buttons. Arke gets streaming stability from React's reconciler (keyed blocks) rather than
  OpenCode's `morphdom` DOM patching, and memoises the parse by content signature.
- `markdown-shiki.worker.ts` — **shiki** for code highlighting. Arke adopts shiki with a **subtle
  neutral** theme; the off-main-thread worker + incremental stable/unstable highlighting is a
  deferred optimisation (see Open questions).
- `basic-tool.tsx` — tool cards. Arke refines the existing `ToolChips` into the tool-card treatment.

### Target architecture
All work is in `packages/client`. No package boundaries change.

```
packages/client/src/
  ds.tsx
    └── <Markdown text mode="chat|preview" /> ........... NEW shared renderer
          react-markdown + remark-gfm
          ├── components.code → <CodeBlock> (shiki, lazy) + copy button
          ├── components.a    → safe external link (allowlist + rel=noopener)
          ├── disallow raw HTML (no rehype-raw); urlTransform allowlists protocols
          └── memoised by content signature (textSig)
    └── <SplitPane>  ..................................... NEW draggable/persisted divider
          role=separator, aria-valuenow, ArrowL/R + Home, min-width clamps,
          persists ratio to localStorage (arke.cockpit.split)
  markdown-theme.ts  .................................... NEW shiki highlighter setup
          lazy createHighlighter({ themes:[neutral-light,neutral-dark], langs:[curated] })
          low-saturation custom theme mapped onto the neutral ramp; graceful fallback
  screens/cockpit.tsx (LiveCockpit)
    ├── <SplitPane> wraps [conversation | LivePreview] (replaces fixed width:430)
    ├── AgentMessage(role:'agent')  → renders children via <Markdown mode="chat">
    │        human turns stay literal (pre-wrap); ToolChips → tool cards
    └── LivePreview
             ├── header: rendered | raw switch (persisted: arke.cockpit.previewMode)
             ├── rendered: existing parseSpecDoc sections + delta highlighting,
             │              with each section/requirement's prose via <Markdown mode="preview">
             └── raw: working file's exact text in Geist Mono, read-only, selectable
```

The conversation's `AgentMessage` (in `ds.tsx`) swaps its `pre-wrap` agent body for `<Markdown>`;
human turns keep the literal pill. `LivePreview` (in `cockpit.tsx`) keeps `parseSpecDoc` +
`RequirementBlock` + `PreviewSection` and the delta treatment, replacing only the plain-text prose
nodes (`requirementProse`, `section.markdown`) with `<Markdown>`, and adds the rendered/raw switch.

### Data model
No new persistent or domain entities, and no new contracts. Two **client-only view preferences**
persist to `localStorage` (not the coordinator — these are picture, not truth, keeping the
thin-client invariant from AGENTS.md):
- `arke.cockpit.split` — the conversation/preview split ratio (number, clamped on read).
- `arke.cockpit.previewMode` — `"rendered" | "raw"`.

Defaults when unset: split ≈ the current 430px feel (default conversation ≈ 38% of the cockpit width,
minimum 340px conversation / 380px preview — tuned in review); preview mode `"rendered"`.

### Interfaces and contracts
No coordinator commands or events are added or changed. The renderer consumes the same inputs as
today: `TranscriptEntry` (`text`, `toolCalls`, `isStreaming`) from SPEC-003 events, and the
`spec.file` text from SPEC-006.

`<Markdown>` component (design system):
```typescript
// packages/client/src/ds.tsx
interface MarkdownProps {
  text: string;                    // untrusted markdown from agent transcript or working file
  mode?: 'chat' | 'preview';       // spacing/typography density; both share the pipeline
  streaming?: boolean;             // append an in-progress caret; tolerate partial constructs
}
```
- Parser: `react-markdown` + `remark-gfm` (tables, task lists, strikethrough, autolinks).
- **No `rehype-raw`** — raw HTML is not parsed into live DOM (safe by default).
- `urlTransform` allowlists `http`/`https`/`mailto`; anchors render via a custom `a` component that
  adds `target="_blank" rel="noopener noreferrer"`.
- `code`: a custom `CodeBlock` renders inline vs fenced; fenced blocks call the lazy shiki highlighter
  (`markdown-theme.ts`) and render a copy button; unknown language or a not-yet-ready highlighter →
  plain monospace, upgraded in place when shiki resolves.
- Memoised by `textSig(text)` so a re-render with unchanged text does not re-parse/re-highlight.

`markdown-theme.ts`:
- Lazy `import('shiki')` + `createHighlighter` on first use (code-split; excluded from initial load).
- Curated language set for authoring (e.g. `ts, tsx, js, json, bash/shell, md, python, go, rust,
  yaml, sql, diff, html, css`); anything else falls back to plain.
- Two custom **low-saturation neutral** themes (light + dark) mapped onto the design token ramp
  (`--foreground`, `--muted-foreground`, `--neutral-600/700`, with the teal brand accent
  `--primary`/`--ring` from SPEC-033 as the single restrained accent); selected by the root `.dark`
  class per the design system.

### Cross-cutting
- **Design template:** the UI follows the `arke-design` skill (`.claude/skills/arke-design/`) — the
  shadcn neutral token contract, Geist / Geist Mono, Lucide icons, and the prototype screens (see
  [SKILL.md](../../.claude/skills/arke-design/SKILL.md)). Code surfaces use `--secondary`/`--muted`
  (or the near-black `--neutral-950` treatment already used for the review preview block) with Geist
  Mono; the highlight theme is low-saturation neutral greys with the teal brand accent (SPEC-033) as
  its single restrained accent for keywords/strings — it introduces no other hues. Prose
  typography (heading sizes, list spacing, blockquote, table borders) is expressed with existing
  tokens, not new hex/px. Copy/label copy stays sentence-case, British spelling, no emoji.
- **Security (NFR-1, NFR-5):** agent output and file text are untrusted; the renderer emits only its
  own safe element set (no raw HTML, no `rehype-raw`), allowlists link protocols, and sets
  `rel="noopener noreferrer"` on external links. The pipeline is client-side only, holds no
  credentials, and makes no system-of-record calls. This is the "validated at the boundary" ethos
  applied to rendering.
- **Accessibility (NFR-6):** the divider is a focusable `role="separator"` with `aria-valuenow` and
  ArrowLeft/Right + Home keyboard control and a visible focus ring; the rendered/raw switch and code
  copy buttons are labelled controls; the existing ARIA live region for streaming output is retained;
  reduced-motion is respected (no drag animation; caret respects the preference).
- **Performance (NFR-3):** markdown is memoised by content signature; only changed blocks re-render
  during streaming (React keys); shiki is lazy-loaded and code-split so it never weighs on initial
  paint and never blocks text display. Off-main-thread / incremental highlighting (OpenCode's worker)
  is deferred unless authoring-sized output proves janky.
- **Resilience (NFR-8):** a markdown parse or highlight failure falls back to plain monospaced text
  for that block rather than breaking the turn or the preview; the highlighter being unavailable
  (loading / offline) yields plain code that upgrades when ready.
- **Multi-project scoping (SPEC-018):** unchanged — the preview still reads the active project's
  working file via `spec.file`; this change touches only client rendering and layout.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | `react-markdown` + `remark-gfm` rather than OpenCode's `marked` + `morphdom` | Idiomatic React; the reconciler already gives OpenCode's streaming DOM stability via keyed blocks, so no manual DOM patching is needed |
| 2 | `shiki` for highlighting (matching OpenCode), lazy-loaded and code-split | Faithful mimic; shiki's custom-theme support lets code stay on-brand; lazy loading keeps it off the initial paint and out of the text-display path |
| 3 | A **subtle neutral** highlight theme keyed to the teal brand accent, not full colour | Keeps code quiet (neutral greys) while using the teal brand accent (SPEC-033) as the single restrained accent, consistent with the app; chosen with the owner at authoring time |
| 4 | Split ratio + preview mode persisted to `localStorage`, not the coordinator | They are client-side view preferences (picture, not truth); persisting them on the host would violate the thin-client invariant |
| 5 | Rendered preview keeps the section-by-section + delta structure rather than a blind full-file render | Preserves SPEC-006's contract-diff reading (delta highlighting is the point of the preview); only the prose within sections upgrades from plain text to markdown |
| 6 | Raw view is the escape hatch, showing exact source incl. frontmatter/metadata | Engineers still need to inspect frontmatter, branch, and `delta:` lines that the rendered view abstracts into badges |
| 7 | No new coordinator events/commands; no `rehype-raw` | The change is pure client rendering over existing events; disallowing raw HTML keeps agent/file output safe by default |
| 8 | One shared `<Markdown>` component for both panels | Agent prose and spec prose render identically, and the component is reusable by the review panel (007) / session detail (011) later |

## Open questions
- **Remote images** in agent markdown (`![](https://…)`): auto-load (offline/privacy consideration, since the client otherwise never fetches externally) or render as a neutral link chip / alt text? Proposed default: render with `max-width:100%` + lazy loading, but revisit if the privacy posture argues for a click-to-load chip.
- **Off-main-thread / incremental highlighting** (OpenCode's shiki worker + stable/unstable projection): needed for authoring-sized output, or is memoised main-thread shiki fast enough? Deferred until measured.
- **Reuse now vs later:** apply the shared `<Markdown>` to the review panel (007) and session detail (011) in this change, or keep this scoped to the cockpit and follow up? Proposed: cockpit-only now, shared component so the follow-up is trivial.
- **Persist split/mode per-project or globally?** Proposed: global (a personal layout preference), revisit if per-project layouts are wanted.
- **Default split ratio and minimum widths** — confirm the exact numbers in design review (proposed conversation ≈ 38%, min 340/380px).
