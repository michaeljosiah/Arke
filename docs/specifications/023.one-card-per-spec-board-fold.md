# One card per specification — board fold & faithful session linkage

## Why

The delivery board renders raw harness session ids (`ses_…`) as their own cards, so one specification appears as several duplicates — the visible bug behind the governance contract ([`../specification-lifecycle-and-delivery.html`](../specification-lifecycle-and-delivery.html)). This specification makes the board faithful: **one card per specification**, sessions folded in, with correct navigation and linkage. It is the urgent, low-risk half of the split from the original SPEC-023; the governed-lifecycle changes (the `delivered` rename, decoupled delivery, gating) are [SPEC-024](024.specification-lifecycle-gating.md).

## What changes

- MODIFIED delivery-board — a specification is exactly **one card**, keyed on `spec_id`; harness sessions fold into it instead of minting their own. *(breaking: supersedes SPEC-010 Requirement "Card column computed…" and Decision #4, which keyed cards on `sessionId`.)*
- ADDED delivery-board — the card's column is a defined **aggregate** of its folded sessions' states, including an explicit rule for concurrent human gates and interrupted sessions.
- ADDED delivery-board — selecting a folded card that aggregates more than one session resolves to the correct session detail (session picker), preserving SPEC-011 navigation.
- MODIFIED opencode-adapter — faithful session→specification linkage in the session-ownership graph: a session with no title-encoded `spec_id` links via its parent authoring session, else is dead-lettered — never treated as its own specification.

> Scope note: this specification does **not** rename the terminal column/status (that is SPEC-024). The board fold uses the existing `merged` terminal column unchanged, so it can ship independently.

## Requirements

### Requirement: A specification is exactly one card
`capability: delivery-board` · `delta: MODIFIED (feat/spec-023-board-fold)`

The board SHALL render **exactly one card per specification**, keyed on `spec_id` (the card's `id` and `title` are the `spec_id` and human title — never a `sessionId`). The authoring session and any delivery (task) sessions belonging to a specification SHALL fold into that one card and SHALL NOT appear as cards of their own. The read model SHALL resolve a `session.status` event to its specification's card by `specId` (replacing the current `ensureCard(sessionId, …)` at `read-model.ts:87` and `live.ts:196`, which mints a session-keyed card). The card's column is a pure function of the specification's frontmatter `status` and the aggregate of its folded sessions (see the next requirement).

#### Scenario: Real harness sessions do not create duplicate cards
- **WHEN** a specification has an authoring session and two delivery sessions with raw ids `ses_a`, `ses_b`, `ses_c`
- **THEN** the board shows exactly one card for that specification, whose id and title are its `spec_id` and human title
- **AND** no card identified by `ses_a`, `ses_b`, or `ses_c` appears

#### Scenario: A running delivery session moves the spec's single card
- **WHEN** a delivery session for a spec transitions to `running`
- **THEN** that spec's one card moves to `implementing`
- **AND** no additional card is created for the session

---

### Requirement: The card column is a defined aggregate of its sessions
`capability: delivery-board` · `delta: ADDED (feat/spec-023-board-fold)`

The card's `column` SHALL be computed from the specification's frontmatter `status` and the aggregate state of all its folded sessions, by this precedence (evaluated in order):

| Condition | Column |
|---|---|
| **any** folded session has an open human gate (`needsHuman === true`) | `needs-human` |
| **any** delivery session is `interrupted` or `error` | `needs-human` |
| **any** delivery session is `running` | `implementing` |
| **no** delivery session is running **and any** is `done` (diff/PR awaits) | `diff` |
| `status === "draft"` | `authoring` |
| `status === "in-review"` | `review` |
| `status === "approved"` (no active delivery session) | `approved` |
| `status === "merged"` | `merged` |
| _(no match)_ | `authoring` (default) |

The aggregate SHALL be **recomputed from all folded sessions** on every relevant event, not toggled from the single changed session: the card's `needsHuman` is true **iff at least one** folded session has an open gate, so closing one gate while another remains open SHALL leave the card in `needs-human`. An `interrupted` or `error` delivery session SHALL surface on the card (as `needs-human`) rather than silently reverting the card to `approved`.

#### Scenario: Two concurrent gates, only one clears
- **WHEN** two delivery sessions of the same spec each have an open `permission.asked`, and a `permission.replied` closes one
- **THEN** the spec's card remains in `needs-human`
- **AND** it leaves `needs-human` only when the last open gate is replied to

#### Scenario: One running plus one done session
- **WHEN** a spec has one `running` and one `done` delivery session
- **THEN** the card is in `implementing` (any-running wins over any-done)

#### Scenario: Interrupted delivery surfaces, does not silently revert
- **WHEN** a spec's only delivery session transitions to `interrupted`
- **THEN** the card surfaces the failure in `needs-human`
- **AND** the card does NOT quietly return to the `approved` backlog lane

---

### Requirement: Selecting a folded card navigates to the right session
`capability: delivery-board` · `delta: ADDED (feat/spec-023-board-fold)`

Because a card now aggregates multiple sessions, selecting it SHALL resolve to the correct session-detail view (SPEC-011), which is keyed on `sessionId`. When the card has exactly one relevant session, selecting it SHALL open that session's detail directly. When it has more than one, selecting it SHALL present a **session picker** (the folded `sessions[]` with role/status), and choosing an entry opens that session's detail by its `sessionId`. This supersedes SPEC-010's assumption that a card's `id` is itself the `sessionId` passed to session detail (`board-session-diff-permission.tsx` `open()` sets `activeCard: c.id`).

#### Scenario: Single-session card opens detail directly
- **WHEN** a spec's card has exactly one active session and the user selects it
- **THEN** the session-detail view opens for that session's `sessionId`
- **AND** no picker is shown

#### Scenario: Multi-session card shows a picker
- **WHEN** a spec's card aggregates two or more sessions and the user selects it
- **THEN** a session picker lists the folded sessions with their roles and statuses
- **AND** choosing one opens session detail for that session's `sessionId`

### Requirement: Faithful session-to-specification linkage
`capability: opencode-adapter` · `delta: MODIFIED (feat/spec-023-board-fold)`

When the session-ownership graph resolves a session's owning specification (the identity carried on `SessionRecord`, populated at `session.created` / `session.updated` and read by later `session.status` events via `lookup()`), it SHALL NOT fall back to the raw session id. Resolution order: (1) a valid `spec_id` encoded in the session title; else (2) the specification owning this session's **parent authoring session** (`parentSessionId` on `SessionRecord`), which is the task session's origin; else (3) **dead-letter** the session to the trace with a reason. The `specId` on any emitted `session.status` event SHALL therefore be a real `spec_id` or explicitly absent — never a `ses_…` string. This replaces `specId: s.title ?? s.id` at `normalize.ts:135` (the graph/identity resolution, not the event emission — later `session.status` events inherit the resolved value through `lookup()`).

#### Scenario: Task session links via its parent authoring session
- **WHEN** a delivery session is created whose title does not encode a `spec_id`, but whose `parentSessionId` is an authoring session owned by `SPEC-X`
- **THEN** the session is linked to `SPEC-X` and folds into that spec's card
- **AND** no card whose id equals the session id is created

#### Scenario: Unlinkable session is dead-lettered, not shown
- **WHEN** a session encodes no `spec_id` and has no linkable parent authoring session
- **THEN** the coordinator writes a dead-letter record to the trace with the session id and reason
- **AND** the board shows no card for that session
- **AND** no `session.status` event carries that session's `ses_…` id as a `specId`

## Design

### Architectural decision

The board remains a read-only projection; the change is to fold by `spec_id` instead of keying by `sessionId`, with a defined aggregate over the folded sessions and explicit navigation when a card fans out to several sessions. Linkage is fixed in the session-ownership graph — the one place identity is resolved — so every downstream `session.status` inherits a real `spec_id`.

### Target architecture

- **Read model** (`packages/coordinator/src/read-model.ts`; mirror in `packages/client/src/live.ts`). `spec.status` ensures the card keyed on `specId`. `session.status` resolves its `specId` and **updates that spec's card**, aggregating the session into a `sessions[]` list and recomputing `needsHuman` / running / done — replacing `ensureCard(event.sessionId, …)` (read-model.ts:87, live.ts:196). `deriveColumn` (read-model.ts:234, live.ts:51) becomes a function of `(status, aggregate(sessions))` per the table above; the `merged` value is unchanged (renamed in SPEC-024).
- **Linkage** (`packages/adapter-opencode/src/normalize.ts`). The `session.created`/`session.updated` identity resolution replaces `specId: s.title ?? s.id`: parse a `spec_id` from the title; else resolve via `parentSessionId`'s owning spec; else return a dead-letter outcome for that session (a new outcome distinct from the existing malformed-frame dead-letter). `lookup()` continues to feed `session.status`.
- **Client** (`packages/client/src/screens/board-session-diff-permission.tsx`). One card per spec; `open()` resolves to a session (direct when one, picker when many) rather than assuming `activeCard` is a `sessionId`; the diff view opens for the chosen session.

### Data model

`CardState` is keyed on `specId` and folds its sessions:

```
CardState {
  id: string             // spec_id — the card identity (was sessionId)
  title: string          // human title, never a session id
  column: BoardColumn     // derived; terminal value still "merged" (SPEC-024 renames)
  status: SpecStatus      // draft | in-review | approved | merged
  sessions: SessionRef[]  // { sessionId, role, status, needsHuman } for each folded session
}
```

### Interfaces and contracts

- No new coordinator ops. `CardState.id` semantics change from `sessionId` to `spec_id`; consumers that assumed `id === sessionId` (session-detail navigation) move to the `sessions[]` list.
- Session-detail navigation (SPEC-011) continues to receive a `sessionId` — now chosen from the folded card rather than being the card id.
- A new dead-letter reason for unlinkable sessions is written to the trace (NFR-7).

### Cross-cutting
- **Design template:** the folded card and session picker follow the `arke-design` skill (`.claude/skills/arke-design/`) — shadcn neutral tokens, Geist, Lucide, the prototype screens; do not re-derive styling.
- **Security / observability (NFR-1/7):** no `column` is ever written from the client; every dead-lettered session is traced with its reason before any client sees the board.
- **Dependency:** none blocking. SPEC-024 depends on this (it renames the folded card's terminal column); this does not depend on SPEC-024.

### Testing
- **Unit (read model):** three sessions on one spec → one card; a `ses_…` session never becomes a card; `deriveColumn` covers every table row incl. two-gates-one-clears, running+done, interrupted; aggregate recomputed (not toggled).
- **Unit (linkage):** title `spec_id` wins; no title but parent authoring session → linked; neither → dead-letter; emitted `specId` is never a `ses_…` string.
- **Component:** single-session card select → detail; multi-session select → picker → detail by chosen `sessionId`.
- **Integration:** mock adapter scripts a spec + authoring + two task sessions → board shows one card walking `authoring → implementing → diff`; no duplicate `ses_…` cards; a `permission.asked` on one task holds the card in `needs-human` until replied.

### Definition of done
The board shows exactly one card per specification with no `ses_…` duplicates; the column aggregate handles concurrent gates and interrupted sessions per the table; selecting a multi-session card navigates correctly via a picker; unlinkable sessions are dead-lettered not shown; suite green; a non-author reviewer has signed off.

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | One card per `spec_id`; sessions fold in | The specification is the unit of work; a session is execution detail. Supersedes SPEC-010's `sessionId` card key (Decision #4), the source of the duplicate-card defect |
| 2 | Aggregate recomputed from all sessions, not toggled | Toggling from the changed session alone would clear `needsHuman` while another gate is still open; the aggregate must be a function of all folded sessions |
| 3 | Interrupted/error delivery surfaces as `needs-human` | A failed delivery must not silently revert the card to the `approved` backlog lane; the human needs to see it |
| 4 | Multi-session card select → session picker | A folded card can no longer be its own `sessionId` for SPEC-011 navigation; a picker resolves which session's detail/diff to open |
| 5 | Linkage fixed in the ownership graph via `parentSessionId`, not the pure event emitter | Identity is resolved once, in the graph; `normalize()` stays table-testable; every `session.status` inherits a real `spec_id` |
| 6 | Terminal column left as `merged` here | The `merged → delivered` rename is SPEC-024; keeping it out of this spec lets the urgent board fix ship independently |

## Open questions
- Should the session picker also appear for a single-session card (for consistency), or only when there is genuine ambiguity? (Lean: direct-open when one, picker when many.)
- Does the folded card need a compact per-session status strip on its face, or is the picker-on-select sufficient for v1?
