# Single-session delivery — one implementer session per spec, checklist-based completion

## Why
Forcing an approved spec's tasks into concurrent, per-task child sessions ([SPEC-009](009.parallel-task-execution.md)) assumed every task was independent enough to run unattended and in isolation. That assumption breaks when a spec's tasks share context, depend on one another, or benefit from being tackled in a particular order — the coordinator was making a sequencing decision that properly belongs to the implementer. Delivery now hands the whole task checklist to ONE implementer session and lets the agent decide how to tackle it.

## What changes
- ADDED single-session-delivery — `spec.deliver` dispatches exactly one implementer session carrying the full unchecked task list; the agent decides sequencing/parallelism itself
- ADDED single-session-delivery — one dedicated git worktree per delivery, on a deterministic `<featureBranch>--delivery` sibling branch, not one worktree per task
- ADDED single-session-delivery — completion is detected by re-parsing the spec's `## Tasks` checklist after each settled assistant turn; `session.status done` is emitted only once every task is checked off
- REMOVED task-fanout — the coordinator no longer dispatches one child session per task
- REMOVED parallel-execution — no more concurrency queue, per-task worktrees, or `ARKE_MAX_CONCURRENT_TASKS` limit; a delivery is exactly one session

**Supersedes:** [SPEC-009](009.parallel-task-execution.md) in full — see the superseded callout there.

## Requirements

### Requirement: Deliver dispatches one implementer session with the full task checklist
`capability: single-session-delivery` · `delta: ADDED (feat/single-session-delivery)`

When `spec.deliver` starts delivery for an `approved` specification, the system SHALL parse the task list from the specification's `## Tasks` section and dispatch exactly ONE session by calling `adapter.createSession()` followed by `adapter.dispatchAsync()` to the `implementer` agent, whose prompt lists every unchecked task (`buildDeliveryPrompt`); the system SHALL NOT dispatch one session per task. A `spec.deliver` issued while a delivery session for that spec is already `running` or `idle` SHALL be rejected with a named error and SHALL NOT dispatch a duplicate session.

#### Scenario: A spec with several unchecked tasks gets one dispatch
- **WHEN** `spec.deliver` starts delivery for a spec whose `## Tasks` section has multiple unchecked items
- **THEN** exactly one `adapter.dispatchAsync()` call is made, to the `implementer` agent
- **AND** its prompt text includes every unchecked task

#### Scenario: Already-checked tasks are not re-prompted
- **WHEN** a spec has a mix of checked and unchecked tasks
- **THEN** the dispatched prompt lists only the unchecked tasks

#### Scenario: Re-delivery while live is refused, not double-dispatched
- **WHEN** `spec.deliver` is issued again for a spec whose delivery session is still `running` or `idle`
- **THEN** the op is rejected with `'<specId>' is already delivering`
- **AND** no additional session is dispatched

#### Scenario: A spec with no actionable tasks fails gracefully
- **WHEN** `spec.deliver` starts delivery for a spec whose `## Tasks` section is absent, or every item is already checked
- **THEN** the coordinator emits a `session.status error` event on the spec session
- **AND** writes a `warn` trace entry with `reason: "no-tasks"`
- **AND** no `dispatchAsync` call is issued

### Requirement: One dedicated worktree per delivery, on a deterministic sibling branch
`capability: single-session-delivery` · `delta: ADDED (feat/single-session-delivery)`

The system SHALL dispatch the delivery session into ONE git worktree, checked out on a branch deterministically named `<featureBranch>--delivery` (`deliveryWorktreeBranch`) — a sibling of the feature branch, not a child path (which would be a git ref directory/file conflict) and not the feature branch itself (which may already be checked out in the human's own working directory). A pre-existing local branch of that name SHALL cause the dispatch to fail cleanly, with no session created, rather than silently reuse or overwrite it. If the session fails to be created or dispatched after the worktree exists, OR the harness later reports `session.status error` for an already-live delivery session, the system SHALL remove the worktree and delete the branch so a subsequent retry starts clean — the deterministic branch name must never outlive the delivery attempt that created it, or every retry would trip the collision guard above.

#### Scenario: One worktree, one branch, no per-task branches
- **WHEN** a delivery is dispatched for a spec
- **THEN** exactly one worktree is created, on branch `<featureBranch>--delivery`
- **AND** no per-task branches (e.g. `<featureBranch>--task-N`) are created

#### Scenario: A pre-existing delivery branch fails the dispatch cleanly
- **WHEN** a branch named `<featureBranch>--delivery` already exists (e.g. an orphaned worktree from a prior run)
- **THEN** the dispatch fails with no session created and no worktree touched
- **AND** a `warn` trace entry records the collision

#### Scenario: A failure after worktree creation cleans up for a retry
- **WHEN** the worktree is created but `adapter.createSession()` or `dispatchAsync()` throws
- **THEN** the worktree is removed and the branch deleted
- **AND** a subsequent `spec.deliver` for the same spec is not blocked by the failed attempt

#### Scenario: A harness error on an already-live session also cleans up, not just a pre-dispatch failure
- **WHEN** the harness reports `session.status error` for a delivery session that already completed its worktree/dispatch
- **THEN** that delivery's worktree is removed and its branch deleted
- **AND** a subsequent `spec.deliver` for the same spec actually redispatches a new implementer session, not just receives an accepted-but-inert response

### Requirement: The delivery session runs IN its worktree
`capability: single-session-delivery` · `delta: ADDED (feat/spec-028-worktree-cwd)`

The delivery session SHALL run in its own worktree, not the project's primary checkout: the coordinator passes the worktree path as the session's `cwd` (`CreateSessionInput.cwd`), and the harness adapter SHALL scope EVERY request for that session (create, prompt, diff, todos, revert, command) to that directory, while every other session continues to use the primary directory. The adapter SHALL validate the `cwd` is within the project root and refuse a path that escapes it (never trusting a caller path verbatim). Because the implementer therefore edits the spec's `## Tasks` checklist in the WORKTREE's copy, the completion oracle SHALL read the checklist from the worktree (falling back to the primary checkout only when the worktree mapping is unavailable, e.g. after a coordinator restart). Task-checklist parsing SHALL tolerate CRLF line endings, since a git worktree checkout may carry `\r\n`.

#### Scenario: Every request for the delivery session is scoped to the worktree
- **WHEN** a delivery session created with a `cwd` sends a prompt or fetches its diff
- **THEN** those harness requests carry the worktree directory, not the primary project directory
- **AND** a concurrently-live authoring session's requests still carry the primary directory

#### Scenario: The oracle reads the worktree's checklist
- **WHEN** the implementer checks tasks off in its worktree's copy of the spec
- **THEN** the completion oracle sees those checkmarks and completes the delivery
- **AND** checkmarks written only to the primary checkout do NOT complete it

#### Scenario: A CRLF worktree checklist still parses
- **WHEN** the worktree's spec file uses `\r\n` line endings (Windows `core.autocrlf`)
- **THEN** the task lines are parsed and completion is detected exactly as with `\n`

#### Scenario: A cwd that escapes the project root is refused
- **WHEN** a session is created with a `cwd` outside the project root
- **THEN** the adapter refuses it rather than scoping requests to an arbitrary directory

#### Scenario: A worktree session's permission reply is routed to its worktree
- **WHEN** a delivery turn running in the worktree raises a permission prompt and the human decides it
- **THEN** the pending-check and the reply are scoped to the worktree directory, not the primary — the decision is confirmed rather than reported stale/unconfirmed against the wrong directory

### Requirement: Completion is a checklist oracle, not the harness's idle status
`capability: single-session-delivery` · `delta: ADDED (feat/single-session-delivery)`

Because a single delivery session may take several turns — including turns a human steers via the board's task composer — the system SHALL NOT treat the harness's `idle` status as delivery-complete, and SHALL NOT treat it as anything but in-progress delivery either: the board column derivation SHALL group a `task`-kind session's `idle` status with `running` (both map to the `implementing` column), never falling back to the spec's backlog (`approved`) status while a delivery session merely sits idle between turns. After each settled, non-streaming assistant turn on a delivery session, the system SHALL re-parse the owning specification's `## Tasks` section and emit a synthetic `session.status done` event for that session only when every task item is checked off (`- [x]`). The board's task-session composer SHALL treat `running` and `idle` delivery sessions as steerable; only a genuinely terminal status (`done`, `error`, `interrupted`) SHALL disable it.

This idle/running grouping is load-bearing, not cosmetic: with the OpenCode harness, a turn settling emits `session.status: idle` BEFORE the finalising, non-streaming `message.updated` the completion oracle above reads — so an in-progress, steerable delivery genuinely sits in `idle` between turns whenever its checklist isn't yet complete, and this is not a transient state the board can afford to mis-render.

#### Scenario: One of two tasks checked — still running
- **WHEN** an assistant turn settles on a delivery session and one of two tasks is now checked off
- **THEN** the session's status remains `running`
- **AND** the composer remains open for a follow-up turn

#### Scenario: Every task checked — session marked done
- **WHEN** an assistant turn settles and every task in the spec's `## Tasks` section is now checked off
- **THEN** the coordinator emits `session.status done` for that session
- **AND** the board surfaces the card for diff review

#### Scenario: Idle alone never completes a delivery
- **WHEN** a delivery session goes idle after a turn that leaves at least one task unchecked
- **THEN** no `done` status is emitted
- **AND** the session stays steerable

#### Scenario: An idle, incomplete delivery keeps its card in `implementing`
- **WHEN** a delivery session's status is `idle` and its spec's checklist is not yet fully checked off
- **THEN** the board column for that spec's card is `implementing`
- **AND** it does NOT fall back to the `approved` backlog lane

### Requirement: A synchronous claim closes the duplicate-dispatch race
`capability: single-session-delivery` · `delta: ADDED (feat/single-session-delivery)`

The system SHALL record an in-memory claim (`specId → sessionId`) synchronously, before any `await`, at the start of dispatching a delivery session, so a concurrent `spec.deliver` for the same spec — arriving after the guard check but before `adapter.createSession()` resolves — observes the claim and no-ops rather than double-dispatching. The claim SHALL be released when the harness reports `session.status error` for the delivery session, and when the owning specification is reopened (interrupting any in-flight delivery), so a fresh `spec.deliver` is not permanently blocked by a failed or superseded attempt.

Because the claim is in-memory only, it does not survive a coordinator process restart. When the claim is missing for an incoming event, the system SHALL fall back to resolving the owning spec from the read model's own session→spec index (populated independently, as soon as the harness's live event stream resumes identity resolution for that still-running session) — re-adopting ownership for any `task`-kind session that is still live (`running`/`waiting`/`idle`, not already `done`/`error`/`interrupted`) — so the checklist completion oracle keeps working across a restart rather than silently stalling for the rest of that delivery's lifetime.

#### Scenario: Concurrent deliver calls do not race a duplicate dispatch
- **WHEN** two `spec.deliver` calls for the same spec are issued back-to-back, before the first's `createSession` resolves
- **THEN** only one session is ultimately dispatched

#### Scenario: A harness-reported error releases the claim
- **WHEN** the harness reports `session.status error` for a live delivery session
- **THEN** the claim is released
- **AND** a subsequent `spec.deliver` for the same spec is accepted, not rejected as "already delivering"

#### Scenario: Delivery ownership recovers after a coordinator restart
- **WHEN** the coordinator restarts while a delivery session is still running in the harness, and that session later settles a turn completing its checklist
- **THEN** the coordinator — despite never itself having dispatched that session — resolves its owning spec via the read model and emits `session.status done`

### Requirement: Task fan-out into concurrent child sessions is removed
`capability: task-fanout` · `delta: REMOVED (feat/single-session-delivery)`

The system SHALL NOT dispatch one child session per task item on delivery. There SHALL be no `FanOutRecord`/`FanOutStore` persistence, no per-task `session.status` fan-out, and no `spec.fanout` op.

#### Scenario: No per-task sessions are created
- **WHEN** an approved spec with N unchecked tasks is delivered
- **THEN** at most one task-kind session is dispatched for that delivery, never N

#### Scenario: `spec.fanout` no longer exists
- **WHEN** the coordinator's op dispatch table is inspected
- **THEN** there is no `spec.fanout` case

### Requirement: Concurrent per-task execution and its concurrency queue are removed
`capability: parallel-execution` · `delta: REMOVED (feat/single-session-delivery)`

The system SHALL NOT run concurrent per-task sessions, and SHALL NOT enforce a concurrency limit or queue (`ARKE_MAX_CONCURRENT_TASKS`) — a delivery is exactly one session, so there is nothing left to cap or queue.

#### Scenario: No concurrency limit is consulted
- **WHEN** a delivery is dispatched
- **THEN** no `ARKE_MAX_CONCURRENT_TASKS` (or equivalent) value is read or enforced

## Design

### Architectural decision
Replace the decider/dispatcher fan-out pair (SPEC-009) with a single dispatch path: `deliver()` parses the task checklist once, claims a slot, creates one worktree on a sibling branch, and dispatches one session carrying the whole list as its prompt. Completion is moved out of the dispatch path entirely and into the coordinator's event pump, as a pure re-read of the spec file's checklist on each settled turn — `observeDeliveryProgress()` — mirroring how `observeReviewerEvent`/`observeGeneration` already fold harness events into read-model transitions.

### Target architecture
```
spec.deliver (approved spec, branch)
        │
        ▼
 deliverImplementation(specId, featureBranch)
    ├── parseTasks(spec markdown) → ParsedTask[]  (no actionable tasks → graceful error)
    ├── claim specId → sessionId (sync, pre-await — closes the TOCTOU race)
    ├── branch collision check (deliveryWorktreeBranch already exists?)
    ├── git worktree add -b <featureBranch>--delivery
    ├── adapter.createSession({ specId, parent: specId })
    └── adapter.dispatchAsync({ agent: "implementer", parts: [buildDeliveryPrompt(...)] })
           ├── on success: emit session.status running kind:task; claim → real sessionId
           └── on failure: remove worktree + branch, release claim, emit session.status error
        │
        ▼
 adapter.streamEvents() ──► observeDeliveryProgress(event)
    ├── session.status error  → release claim
    └── message.updated (settled, assistant) → re-parse spec's ## Tasks
           └── all checked? → emit session.status done; release claim
```

### Data model
No new persisted store. Delivery state is two in-memory maps on `ProjectContext`, rebuilt from the read model / harness events rather than a durable ledger (`deliverySessions: specId → sessionId`, `deliverySessionOwner: sessionId → specId`) — since a delivery is exactly one session per spec, the existing read model (session list per card) is already sufficient state to reconstruct "is a delivery live" after a restart; no fan-out-specific restart-idempotency store (the old `FanOutRecord`) is needed.

### Interfaces and contracts
`packages/coordinator/src/delivery.ts` (replaces `fanout.ts`/`fanout-store.ts`) exports the pure pieces: `parseTasks`, `taskKey` (stable content-hash task identity, invariant to reordering — retained from SPEC-009's own fix), `specSlug`, `deliveryWorktreeBranch`, `buildDeliveryPrompt`. These are internal to the coordinator, not part of `@arke/contracts`. No `DomainEvent`, `HarnessAdapter`, or wire-protocol change: delivery reuses the existing `session.status`/`message.updated` events and `createSession`/`dispatchAsync` adapter methods. The CLI's `arke spec deliver <SPEC_ID> [--branch]` (`SpecDeliverCommand`) calls `spec.deliver` directly — it replaces the CLI's old `arke spec fanout`, which called the now-deleted `spec.fanout` op.

### Cross-cutting
- **Security:** the worktree path is derived from a SHA-1 hash of the delivery branch name (`.arke/worktrees/<hash>`) and the `git worktree add`/`branch` commands take only coordinator-derived arguments — no client- or spec-content-supplied value is interpolated into the shell command.
- **Observability:** `spec.deliver`, `dispatch.started`, `dispatch.complete`, `dispatch.failed`, `delivery.complete`, and `delivery.interrupted` (SPEC-024 reopen) trace entries give a durable record of a delivery's lifecycle from dispatch through completion or interruption.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | One implementer session per delivery, not one per task | The agent — not the coordinator — is best placed to decide whether a spec's tasks are independent enough to parallelise, or must be sequenced; forcing concurrency assumed independence that doesn't always hold |
| 2 | Sibling branch `<featureBranch>--delivery`, not a `/delivery` child path or the feature branch itself | A child path under an existing branch name is a git ref directory/file conflict; using the feature branch itself would collide with the human's own working directory, which is commonly already checked out on it after approving a spec |
| 3 | Completion is a re-parsed checklist, not harness `idle` | A single session may take several turns, some human-steered; `idle` no longer means "this task is done," so the coordinator needs its own oracle — the same checklist the agent is told to maintain |
| 4 | Synchronous pre-`await` claim for idempotency, mirroring `generate()` (SPEC-013) | The same TOCTOU race exists here as in generation dispatch; reusing the proven pattern rather than inventing a new one |
| 5 | Delivery state kept as in-memory maps, no new durable store | The read model already tracks live task sessions per spec; a delivery is at most one session, so no fan-out-style restart ledger is needed |
| 6 | `ARKE_MAX_CONCURRENT_TASKS` and the concurrency queue are deleted outright, not deprecated in place | There is nothing left to queue or cap once a delivery is one session; keeping a dead config knob would be a false affordance |
| 7 | A harness error on an already-live session gets the SAME worktree/branch cleanup as a pre-dispatch failure, via a shared `removeDeliveryWorktree` helper keyed on `specId` | Without it, the deterministic `<featureBranch>--delivery` branch outlives the errored attempt and every retry trips the branch-collision guard forever — the claim being released is not enough on its own; caught in PR review (PR #61) |
| 8 | `idle` groups with `running` for board-column purposes (`implementing`), not just for composer steerability | OpenCode's own turn-settle ordering emits `session.status: idle` before the completion oracle's `message.updated`, so an in-progress, incomplete delivery visibly sits in `idle` between turns; treating it as anything but `implementing` would bounce the card back to the `approved` backlog mid-delivery; caught in PR review (PR #61) |
| 9 | Delivery ownership falls back to the read model's `specForSession` when the in-memory claim is missing, rather than adding a new durable store | The read model already re-learns sessionId → specId as soon as the harness's live stream resumes identity resolution for a still-running session after restart (this is already how `rebuildSessionGraph()`-style recovery works) — reusing that existing recovery path is simpler and sufficient, versus persisting a parallel ownership ledger just for delivery; caught in PR review (PR #61) |

## Open questions
- If a human wants genuinely parallel execution for a spec whose tasks really are independent, that is now entirely the implementer agent's own tool-call decision (e.g. spawning its own sub-agents), not a coordinator concern. Should Arke's agent-authoring guidance (the `implementer` agent's system prompt) say more about when to parallelise its own work? Not addressed here.
- The old `FanOutRecord`'s restart-idempotency guarantee (durable, survives a coordinator crash mid-dispatch) has no equivalent for the brief window between claiming a delivery slot and the harness's first `session.status` event — a crash in that narrow window could in principle allow one duplicate dispatch on restart. Judged acceptable (the window is a single synchronous statement plus one `createSession` round-trip) but not proven with a restart test. (Distinct from, and narrower than, the general restart-ownership-loss gap Decision #9 fixes — that gap covered the ENTIRE rest of a delivery's lifetime, not just this one narrow window.)
- The worktree binding (adapter `sessionCwd` map + coordinator `deliveryWorktrees` map) is in-memory only, so a coordinator restart mid-delivery loses it: post-restart, the adapter's requests for that session fall back to the primary directory and the oracle reads the primary checkout. Both fall back TOGETHER, so they stay mutually consistent, but a delivery interrupted by a restart effectively needs re-driving. Reconstructing the binding on restart (the worktree path is deterministic from the spec's branch) is a possible future refinement.
- The reliability of running the `implementer` agent in a non-primary directory depends on OpenCode's per-directory agent loading, which the adapter's own comments note is racy (it self-heals by falling back to the default agent). The worktree checks out the feature branch, which has `.opencode/agents/implementer.md` committed, so the agent file is present — but end-to-end reliability against a live OpenCode server in a worktree is not yet verified here.
