# Azure Repos as a lifecycle host — a neutral forge seam

## Why

Arke's specification lifecycle is driven by **pull-request / branch state** (SPEC-008): a spec advances
draft → in-review → approved → delivered as a PR is opened, reviewed, and merged, observed via webhooks. That
whole path is **hard-coded to GitHub** — `mapWebhookEvent`/`verifyGithubSignature` parse GitHub webhook
shapes, the ingress is `POST /webhooks/github` keyed on `x-hub-signature-256`/`x-github-event`,
`githubPrStatus` shells `gh pr view` for the board (SPEC-025), and the auto-PR delivery instruction
(SPEC-031) tells the implementer to run `gh pr create`. A team whose code lives in **Azure DevOps Repos**
cannot run the loop at all.

This spec introduces a **neutral forge seam** — a `ForgeAdapter`, the VCS/PR-host analogue of the
`HarnessAdapter` — so GitHub and Azure Repos are two leaves behind one interface. The coupling is lean and
concentrated (webhook verify+map, PR status, remote parsing, the auto-PR command); **everything else is
already host-agnostic** — plain git (branch/push/merge/commit, the host-less `localMerge` delivery fallback),
branch-based webhook routing (`findSpecByBranch`), the lifecycle state machine, and the config format. So the
change is: extract GitHub's behaviour into a leaf, add an Azure Repos leaf, and select the forge correctly on
each path. **v1 is repos only** (the lifecycle host); Azure Boards work-item projection and Azure Pipelines
CI status are named follow-ups.

**Two grounding corrections that shape the design (from a deep review of the actual code):**

1. **Webhook forge selection is by URL path, not the git remote — the two are different resolution paths.**
   Webhook ingress verifies + maps the payload *before any project/branch is known* (`server.ts` `handleHttp`
   validates once against a single secret, then fans `handleWebhook` to every context, which only then routes
   by branch). So the ingress forge MUST be chosen by the route (`/webhooks/github` vs `/webhooks/azure`),
   independent of any project's remote. The **remote-based** `resolveForge(root)` governs only the paths that
   already hold a project `root` — the board PR-status read and the delivery auto-PR instruction.
2. **Azure DevOps Service Hooks do NOT HMAC-sign the payload** the way GitHub does — a subscription
   authenticates with **HTTP Basic auth** (or a secret in the URL). So `verifyWebhook` is genuinely
   forge-specific: it cannot assume GitHub's `X-Hub-Signature-256` HMAC.

The GitHub coupling lives in **7 coordinator files** (the sixth-and-seventh being `projection.ts` — which
already declares an `azure-devops` integration keyed on `AZURE_DEVOPS_PAT`/`AZURE_DEVOPS_ORG` for the
deferred work-item projection, and a `DEFAULT_BLOCKED_DOMAINS` guard that blocks `dev.azure.com`); everything
else is host-agnostic.

## What changes

- ADDED forge-seam — a `ForgeAdapter` interface abstracts every VCS/PR-host touchpoint (`verifyWebhook`,
  `mapWebhookEvent`, `pullRequestStatus`, `normalizeRemote`, `defaultBranch`, `autoOpenPrInstruction`). GitHub's
  current pure functions (`mapWebhookEvent`, `verifyGithubSignature`, `githubPrStatus`) move into a
  `GitHubForge` leaf **behaviour-preserving**; `normaliseRemote` is **refactored** (see below) since Azure needs
  a richer shape. The coordinator/lifecycle/board/delivery code calls the resolved adapter, never a
  `github`-named function.
- ADDED forge-seam — the forge is selected on **two distinct paths**: (a) **webhook ingress** by the request
  **URL path** (`/webhooks/github` → GitHubForge, `/webhooks/azure` → AzureReposForge), verified with that
  forge's `verifyWebhook`; (b) **project operations** (board PR status, auto-PR) by `resolveForge(root)` from
  the git remote (`github.com` → github; `dev.azure.com` / `*.visualstudio.com` → azure-repos),
  config-overridable, **defaulting to GitHub** so every existing project is unaffected.
- ADDED spec-lifecycle — an `AzureReposForge` leaf maps Azure DevOps **Service Hook** events
  (`git.pullrequest.created`/`git.pullrequest.updated`/`git.push`) to the SAME neutral `LifecycleTransition`s,
  verified via Azure's Basic-auth model (NOT an HMAC), routed by branch.
- MODIFIED delivery — the auto-PR instruction (SPEC-031) and PR-status read are **parameterised by forge**:
  an Azure project emits `az repos pr create` / reads status via `az repos pr`, a GitHub project keeps
  `gh pr create` / `gh pr view`. The host credential (a GitHub token or an Azure **PAT**) stays host-side in
  the CLI's environment — never persisted or returned (NFR-1). The Azure PAT var is reconciled with the
  existing `projection.ts` `AZURE_DEVOPS_PAT`, and the `az` shell-out is confirmed exempt from
  `DEFAULT_BLOCKED_DOMAINS` (as `gh` is for `api.github.com`). *(breaking: no — a GitHub project resolves the
  GitHub forge and behaves identically.)*

## Requirements

### Requirement: A neutral forge seam abstracts the VCS/PR host; GitHub's mapping/verify/PR-status unchanged
`capability: forge-seam` · `delta: ADDED (feat/spec-038-azure-repos-forge)`

The coordinator SHALL route every VCS/PR-host-specific operation through a `ForgeAdapter` interface —
minimally `verifyWebhook(headers, rawBody, secret)`, `mapWebhookEvent(eventName, payload)` →
`LifecycleTransition`, `pullRequestStatus(root, branch)` → `{ number, status } | null`,
`normalizeRemote(url)`, and `autoOpenPrInstruction(baseBranch)` — so no lifecycle/board/delivery code names a
specific host. GitHub's existing pure functions `mapWebhookEvent`, `verifyGithubSignature`, and
`githubPrStatus` SHALL be **moved into a `GitHubForge` leaf without behavioural change** (their existing unit
tests pass unchanged through the leaf). `normaliseRemote` — which today returns `string | null`
(`"host/owner/repo"`) and has **no production callers** (only its own test) — SHALL be **refactored** to
return a structured `{ host, owner, repo, project? }` (Azure Repos carries an org **and** a project), so this
one function is a deliberate shape change, NOT a byte-for-byte move. Plain git operations
(branch/push/merge/commit, `localMerge`) and branch-based webhook routing SHALL remain shared and
forge-agnostic.

#### Scenario: GitHub's mapping and signature verdict are unchanged behind the seam
- **WHEN** a GitHub `pull_request`/`pull_request_review`/`push` webhook is verified + mapped, or a GitHub
  PR-status read runs, through the `GitHubForge` leaf
- **THEN** the `LifecycleTransition` / signature verdict / `{ number, status }` is byte-for-byte what the
  coordinator produced before the seam existed

#### Scenario: No lifecycle/board/delivery code names a host directly
- **WHEN** the webhook handler, the board PR-status read, or the delivery-prompt builder runs
- **THEN** each calls the resolved `ForgeAdapter`, never a `github`-named function directly

### Requirement: The forge is selected by URL path at webhook ingress, and by the remote for project ops
`capability: forge-seam` · `delta: ADDED (feat/spec-038-azure-repos-forge)`

Webhook ingress SHALL select the forge from the request **URL path** — `POST /webhooks/github` → the GitHub
forge, `POST /webhooks/azure` → the Azure Repos forge — and verify with THAT forge's `verifyWebhook` before
mapping, because the payload is verified + mapped before any project/branch is known (a single coordinator
secret, then fan-out routed by branch). The board/delivery paths, which already hold a project `root`, SHALL
select the forge via `resolveForge(root, config)` — the git remote (`github.com` → github; `dev.azure.com` /
`*.visualstudio.com` → azure-repos) with an optional `.arke/config.json` `forge` block taking precedence, and
**defaulting to GitHub** when unrecognised so no existing project regresses. For v1 the webhook secret stays a
single coordinator-level credential (`ARKE_WEBHOOK_SECRET` for GitHub's HMAC; a configured Basic-auth
credential for Azure); a **per-project forge secret is out of scope** (it entangles `hostConfigured()`, which
also feeds the second-human approval gate — a governance blast radius flagged as a follow-up).

#### Scenario: The webhook forge is chosen by the route, not a project remote
- **WHEN** a request arrives at `POST /webhooks/azure`
- **THEN** the Azure forge verifies + maps it (independent of any project's remote), and `/webhooks/github`
  continues to serve GitHub unchanged

#### Scenario: An Azure remote resolves the Azure forge for board/delivery; unknown defaults to GitHub
- **WHEN** a project's `origin` is `https://dev.azure.com/org/project/_git/repo`
- **THEN** `resolveForge(root)` returns the Azure forge for its PR-status read + auto-PR instruction
- **AND** a `github.com`/absent/unrecognised remote (no `forge` config) resolves GitHub (today's behaviour)

### Requirement: Azure Repos webhooks map to the same lifecycle, verified Azure's way (not HMAC)
`capability: spec-lifecycle` · `delta: ADDED (feat/spec-038-azure-repos-forge)`

The `AzureReposForge` SHALL map Azure DevOps **Service Hook** events to the SAME `LifecycleTransition`s the
GitHub forge produces, reading the branch from `resource.sourceRefName` (stripping `refs/heads/`) and routing
by `findSpecByBranch`. Because Azure has **no dedicated review event** — approvals, completion, and
re-activation all arrive as `git.pullrequest.updated` carrying the whole PR resource — the mapper SHALL
disambiguate within that event: `resource.status` `completed` → `merged`, `abandoned` → `closed-unmerged`,
and `active` → `reopened` **only when** the coordinator's last-known `SpecRecordState.status` was a closed
state (otherwise a no-op, since Azure has no explicit reopen signal); a reviewer whose `vote === 10` (approved)
who is a **person** (NOT a container/team reviewer, `isContainer !== true`) → `approved`, with that reviewer's
`uniqueName`/`displayName` as the approver so the self-approval gate compares a real identity; and
`git.pullrequest.created` → `opened`; `git.push` with a forced update → `force-push`. Mapping SHALL be
idempotent (the same `git.pullrequest.updated` re-fires on every edit — re-asserting an already-applied
transition must not double-apply). `verifyWebhook` for the Azure forge SHALL validate the request using
Azure's model — **HTTP Basic auth** (the configured credential, compared constant-time) — and MUST NOT expect
GitHub's `X-Hub-Signature-256` HMAC. An unrecognised event/payload → `{ kind: "ignored", reason }`.

#### Scenario: An Azure PR-completed event advances the spec to delivered
- **WHEN** a `git.pullrequest.updated` Service Hook arrives with `resource.status === "completed"` for a
  spec's source branch
- **THEN** it maps to `merged` and the spec advances to `delivered` exactly as a GitHub merge does

#### Scenario: A human reviewer approval maps to approved; a team/container vote does not misattribute
- **WHEN** a `git.pullrequest.updated` carries a reviewer with `vote === 10` and `isContainer !== true`
- **THEN** it maps to `approved` with that person as the approver (a container/team reviewer's vote does NOT set the approver)

#### Scenario: An unsigned/mis-authenticated Azure webhook is rejected (not HMAC-checked)
- **WHEN** an Azure webhook arrives without the configured Basic-auth credential
- **THEN** `verifyWebhook` fails and the request is rejected (fail-closed), NOT compared against a GitHub HMAC

### Requirement: PR status and the auto-PR instruction are forge-parameterised, credentials host-side, unblocked
`capability: delivery` · `delta: MODIFIED (feat/spec-038-azure-repos-forge)`

`pullRequestStatus` and the auto-PR delivery instruction (SPEC-031) SHALL dispatch on the resolved forge: a
GitHub project reads status via `gh pr view` and instructs `gh pr create`; an Azure project reads status via
`az repos pr` and instructs `az repos pr create` (its `--source-branch`/`--target-branch` flags differ from
`gh`'s `--base`, so the instruction is forge-authored, not a token swap), both normalised to the same
`{ number, status }` shape. The webhook ingress SHALL serve `POST /webhooks/azure` alongside the unchanged
`POST /webhooks/github`. The host credential — a GitHub token or an Azure **PAT** — SHALL be read by the CLI
from the host environment and SHALL NEVER be persisted or returned (NFR-1). The Azure PAT variable SHALL be
reconciled with the existing `projection.ts` convention (`AZURE_DEVOPS_PAT`), and the `az` shell-out SHALL be
exempt from `DEFAULT_BLOCKED_DOMAINS` (which blocks `dev.azure.com`) the same way `gh`'s `api.github.com`
traffic is — otherwise Arke's own tool-guard would block the delivery agent from opening the PR.

#### Scenario: An Azure project's delivery opens the PR with the Azure CLI, unblocked
- **WHEN** an Azure-Repos project with `autoOpenPr` enabled finishes its checklist
- **THEN** the instruction directs `az repos pr create` (not `gh`), the board reads that PR via the Azure
  forge, and the `az` call to `dev.azure.com` is NOT caught by `DEFAULT_BLOCKED_DOMAINS`

#### Scenario: `az repos pr` status parses to the neutral shape, including no-PR
- **WHEN** `az repos pr` reports an open PR for a branch (or none)
- **THEN** it is parsed to `{ number, status } | null` — Azure's empty-list/JSON output handled on its own
  terms (the GitHub `gh` stderr sniff does not transfer)

## Design

### Architectural decision

Introduce a `ForgeAdapter` seam mirroring the proven `HarnessAdapter` pattern: a small neutral interface with
GitHub and Azure Repos as leaves. Extract GitHub's pure lifecycle functions into a `GitHubForge` leaf
behaviour-preserving (contain the risk to the new Azure leaf + the resolver); `normaliseRemote` is the one
deliberate refactor (its `string` shape can't carry Azure's org+project, and it has no production callers so
the change is safe). Select the forge on the two real paths — **URL-path at webhook ingress** (verify+map
before the project is known) and **remote-resolved for board/delivery** (which hold a `root`). The seam is
thin because the coupling is thin: plain git, branch routing, the state machine, and `localMerge` stay
shared. v1 covers the **lifecycle host** only; Azure Boards work-items (the `projection.ts` `azure-devops`
integration already scaffolded for it), Azure Pipelines CI-gate status, and Azure support for cross-repo
linkage (SPEC-030) are named follow-ups.

### Target architecture

- **`packages/coordinator/src/forge/`** (new): `ForgeAdapter` interface + `GitHubForge` (moved GitHub logic) +
  `AzureReposForge` (new) + `resolveForge(root, config)` (remote → forge, config override, GitHub default) +
  `forgeForWebhookPath(path)` (`/webhooks/github|azure` → forge).
- **`packages/coordinator/src/spec-lifecycle.ts`**: the pure GitHub functions move to `GitHubForge`;
  `LifecycleTransition` stays the shared neutral type; `normativeHash`/flatten untouched.
- **`packages/coordinator/src/server.ts`**: `handleHttp` routes `POST /webhooks/{github|azure}` to
  `forgeForWebhookPath`, calls that forge's `verifyWebhook` (GitHub HMAC / Azure Basic-auth) then
  `mapWebhookEvent`, and fans the resulting neutral transition to contexts (branch-routed as today).
- **`packages/coordinator/src/git-status.ts`** + **`delivery.ts`** + **`project-context.ts`**: use the
  `resolveForge(root)` adapter's `pullRequestStatus`/`autoOpenPrInstruction`. `hostConfigured()` stays a
  single coordinator-level "a webhook secret is configured" check for v1 (a per-project/per-forge secret is a
  follow-up because it also feeds `approveGate`).
- **`packages/coordinator/src/projection.ts`**: reconcile the Azure PAT var; ensure the forge CLI shell-out is
  not caught by `DEFAULT_BLOCKED_DOMAINS` (mirror the `gh`/`api.github.com` treatment).

### Interfaces and contracts

- `ForgeAdapter` added to the coordinator (internal seam, not a wire/contract change).
- `LifecycleTransition` unchanged, shared across forges. The board `{ number, status }` shape unchanged.
- `normalizeRemote` return type changes from `string | null` to `{ host, owner, repo, project? } | null` — an
  internal function with no production callers, so no external break; its unit test is updated to the new shape.
- `.arke/config.json` MAY carry an optional `forge` block; absent → resolve from the remote → default GitHub.

### Cross-cutting

- **Security (NFR-1):** the Azure PAT / GitHub token stays host-side in the CLI env; never persisted/returned.
  Azure webhook Basic-auth credentials are host-side config, compared constant-time.
- **Determinism / no regression:** the GitHub forge is behaviour-preserving; a GitHub project is unaffected.
- **Governance blast radius:** `hostConfigured()` gates BOTH the board read and the second-human approval gate;
  v1 leaves it a single coordinator-level check to avoid touching governance.
- **Host risk:** Azure PR ops use the `az` CLI (as GitHub uses `gh`), host-side auth, in v1 — smaller surface
  than a bespoke REST client.

### Testing
- **Unit:** `GitHubForge` `mapWebhookEvent`/`verifyWebhook`/`pullRequestStatus` byte-identical to the pre-seam
  functions (reuse the existing lifecycle tests through the leaf); `AzureReposForge.mapWebhookEvent` over **real
  Azure Service-Hook payload fixtures** (created→opened, completed→merged, abandoned→closed-unmerged, human
  reviewer vote 10 → approved, container reviewer vote → NO approver, active-with-prior-closed→reopened, forced
  push→force-push, unknown→ignored, idempotent re-fire); Azure `verifyWebhook` accepts the configured Basic-auth
  and rejects a missing/wrong one (fail-closed) and does NOT expect an HMAC; a captured **`az repos pr` JSON
  fixture** parses to `{ number, status }` incl. the no-PR case (the `gh` stderr sniff does not transfer);
  `resolveForge` maps github/dev.azure.com/visualstudio.com/unknown and defaults to GitHub; `forgeForWebhookPath`
  maps the two routes; the delivery instruction emits `az repos pr create` for Azure and `gh pr create` for GitHub.
- **Live acceptance (gated on a reachable Azure DevOps org + a PAT):** a real spec → PR opened in Azure Repos →
  Service Hook advances the lifecycle → the board shows the PR → merge → delivered, end to end. Blocked until an
  Azure org + PAT are available (host-side); the unit layer above exercises every leaf hermetically first.

### Definition of done
A project whose code lives in Azure Repos runs the full authoring → review → delivery → board loop, its
lifecycle driven by Azure Service Hooks (verified via Basic auth) and its PR opened via the Azure CLI, behind
a neutral `ForgeAdapter`; a GitHub project is byte-for-byte unchanged (its mapping/verify/PR-status); the `az`
shell-out is not blocked by Arke's own guard; credentials stay host-side; the unit suite is green with
`typecheck` + `build`; and a non-author reviewer has signed off. The live-acceptance run against a real Azure
org is the remaining gate (a named follow-up when an org + PAT are available); Azure Boards work-items, Azure
Pipelines CI status, and per-project forge secrets are out of scope.

## Open questions
- Azure Service Hooks are configured per **event type** (one subscription per event) — the setup note must
  enumerate the required subscriptions (PR created, PR updated, push). Should Arke offer an API helper to
  create them? v1: document the manual subscriptions.
- The Azure PAT var: the `az` CLI reads `AZURE_DEVOPS_EXT_PAT`, while `projection.ts` standardises on
  `AZURE_DEVOPS_PAT`. v1: set the CLI's var from the same host-side value (document both), don't ship a rival
  config key. A single reconciled convention is preferable — decide during implementation.
- Should `defaultBranch` query the host API (GitHub/Azure) instead of the local main/master inference, now
  that a forge adapter exists? v1: keep local inference (host-agnostic); a forge-API query is a later refinement.
