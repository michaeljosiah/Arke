# Azure Repos as a lifecycle host — a neutral forge seam

## Why

Arke's specification lifecycle is driven by **pull-request / branch state** (SPEC-008): a spec advances
draft → in-review → approved → delivered as a PR is opened, reviewed, and merged, observed via webhooks. That
whole path is **hard-coded to GitHub** — `mapWebhookEvent`/`verifyGithubSignature` parse GitHub webhook
shapes, the ingress is `POST /webhooks/github` keyed on `x-hub-signature-256`/`x-github-event`,
`githubPrStatus` shells `gh pr view` for the board (SPEC-025), and the auto-PR delivery instruction
(SPEC-031) tells the implementer to run `gh pr create`. A team whose code lives in **Azure DevOps Repos**
cannot run the loop at all.

This spec introduces a **neutral forge seam** — a `ForgeAdapter`, the VCS/PR-host analogue of the
`HarnessAdapter` — so GitHub and Azure Repos are two leaves behind one interface. The coupling is lean and
concentrated (webhook verify+map, PR status, remote parsing, the auto-PR command); **everything else is
already host-agnostic** — plain git (branch/push/merge/commit, the host-less `localMerge` delivery fallback),
branch-based webhook routing (`findSpecByBranch`), the lifecycle state machine, and the config format. So the
change is: extract GitHub's behaviour into a leaf **byte-for-byte unchanged**, add an Azure Repos leaf, and
resolve the forge per project. **v1 is repos only** (the lifecycle host); Azure Boards work-item projection
and Azure Pipelines CI status are named follow-ups.

**A grounding correction (drives Requirement 3).** Azure DevOps **Service Hooks do NOT sign the payload with
an HMAC** the way GitHub does — a subscription authenticates with **HTTP Basic auth** (a configured
username/password) or a secret embedded in the target URL. So webhook verification is genuinely
**forge-specific**: `verifyWebhook` cannot assume GitHub's `X-Hub-Signature-256` HMAC. The seam takes the raw
request (headers + body) and lets each leaf verify its own way.

## What changes

- ADDED forge-seam — a `ForgeAdapter` interface abstracts every VCS/PR-host touchpoint (`verifyWebhook`,
  `mapWebhookEvent`, `pullRequestStatus`, `normalizeRemote`, `defaultBranch`, `autoOpenPrInstruction`). The
  coordinator, lifecycle, board, and delivery code call the resolved adapter instead of GitHub-specific
  functions. GitHub's current behaviour is extracted into a `GitHubForge` leaf **unchanged** (no regression).
- ADDED forge-seam — the forge is **resolved per project** from the git remote URL (`github.com` → github;
  `dev.azure.com` / `*.visualstudio.com` → azure-repos), overridable by an optional `.arke/config.json`
  `forge` block; it **defaults to GitHub** so every existing project is unaffected.
- ADDED spec-lifecycle — an `AzureReposForge` leaf maps Azure DevOps **Service Hook** events
  (`git.pullrequest.created`/`git.pullrequest.updated`/`git.push`, reviewer votes) to the SAME neutral
  `LifecycleTransition`s, verified via Azure's Basic-auth model (NOT an HMAC), routed by branch.
- MODIFIED delivery — the auto-PR instruction (SPEC-031) and PR-status read are **parameterised by forge**:
  an Azure project emits `az repos pr create` / reads status via `az repos pr`, a GitHub project keeps
  `gh pr create` / `gh pr view`. The host credential (a GitHub token or an Azure **PAT**) stays host-side in
  the CLI's environment — never persisted or returned (NFR-1, unchanged). *(breaking: no — a GitHub project
  resolves the GitHub forge and behaves identically.)*

## Requirements

### Requirement: A neutral forge seam abstracts the VCS/PR host, GitHub behaviour unchanged
`capability: forge-seam` · `delta: ADDED (feat/spec-038-azure-repos-forge)`

The coordinator SHALL route every VCS/PR-host-specific operation through a `ForgeAdapter` interface —
minimally `verifyWebhook(headers, rawBody, secret)`, `mapWebhookEvent(eventName, payload)` →
`LifecycleTransition`, `pullRequestStatus(root, branch)` → `{ number, status } | null`,
`normalizeRemote(url)` → `{ host, owner, repo } | null`, and `autoOpenPrInstruction(baseBranch)` → the
delivery-prompt command — so no lifecycle/board/delivery code names a specific host. GitHub's existing
behaviour (`verifyGithubSignature`, `mapWebhookEvent`, `githubPrStatus`, `normaliseRemote`, the
`gh pr create` instruction) SHALL be **moved into a `GitHubForge` leaf without behavioural change**: an
existing GitHub project's webhook mapping, signature check, PR-status read, and delivery prompt SHALL be
byte-for-byte identical to today. Plain git operations (branch/push/merge/commit, `localMerge`) and
branch-based webhook routing SHALL remain shared and forge-agnostic.

#### Scenario: The GitHub path is unchanged behind the seam
- **WHEN** a GitHub `pull_request`/`pull_request_review`/`push` webhook is received (or a PR-status read runs)
- **THEN** the resolved `GitHubForge` produces the identical `LifecycleTransition` / signature verdict / PR
  status the coordinator produced before the seam existed

#### Scenario: No lifecycle/board/delivery code names a host directly
- **WHEN** the webhook handler, the board PR-status read, or the delivery-prompt builder runs
- **THEN** each calls the resolved `ForgeAdapter`, never a `github`-named function directly

### Requirement: The forge is resolved per project and defaults to GitHub
`capability: forge-seam` · `delta: ADDED (feat/spec-038-azure-repos-forge)`

Each project context SHALL resolve its `ForgeAdapter` from the git remote — a `github.com` remote → the
GitHub forge; a `dev.azure.com` or `*.visualstudio.com` remote → the Azure Repos forge — with an optional
`.arke/config.json` `forge` block (`{ host, org/owner, project?, repo }`) taking precedence when present.
When neither the remote nor config identifies a supported forge, resolution SHALL **default to GitHub** so no
existing project regresses. Resolution SHALL be a pure function of the remote/config (no network), stable on
the hot path.

#### Scenario: An Azure remote resolves the Azure Repos forge
- **WHEN** a project's `origin` remote is `https://dev.azure.com/org/project/_git/repo` (or the `ssh` form)
- **THEN** the project resolves the Azure Repos forge

#### Scenario: An unknown or GitHub remote defaults to GitHub
- **WHEN** the remote is `github.com`, absent, or an unrecognised host and no `forge` config is set
- **THEN** the project resolves the GitHub forge (today's behaviour, unchanged)

### Requirement: Azure Repos webhooks map to the same lifecycle, verified Azure's way (not HMAC)
`capability: spec-lifecycle` · `delta: ADDED (feat/spec-038-azure-repos-forge)`

The `AzureReposForge` SHALL map Azure DevOps **Service Hook** events to the SAME `LifecycleTransition`s the
GitHub forge produces: `git.pullrequest.created` (PR opened) → `opened`; `git.pullrequest.updated` with the
resource `status` `completed` → `merged`, `abandoned` → `closed-unmerged`, and a re-activation → `reopened`;
a reviewer vote of *approved* (`resource.reviewers[].vote === 10`) → `approved` (carrying the reviewer as the
approver, for the self-approval gate); `git.push` with a forced update → `force-push`. The branch SHALL be
read from the Azure payload (`resource.sourceRefName`, stripping `refs/heads/`) and routed by
`findSpecByBranch`. `verifyWebhook` for the Azure forge SHALL validate the request using Azure's model —
**HTTP Basic auth** (the configured `Authorization: Basic …` credential) or a shared-secret token — and MUST
NOT assume GitHub's `X-Hub-Signature-256` HMAC (Azure Service Hooks do not sign the payload). An event or
payload the forge does not recognise SHALL map to `{ kind: "ignored", reason }`, never a wrong transition.

#### Scenario: An Azure PR-completed event advances the spec to delivered
- **WHEN** an `git.pullrequest.updated` Service Hook arrives with `resource.status === "completed"` for a
  spec's source branch
- **THEN** it maps to the `merged` transition and the spec advances to `delivered` exactly as a GitHub merge does

#### Scenario: An Azure reviewer approval maps to the approved transition
- **WHEN** a Service Hook reports a reviewer vote of approved on a spec's PR
- **THEN** it maps to `approved` with the reviewer as the approver (subject to the same self-approval gate)

#### Scenario: An unsigned/mis-authenticated Azure webhook is rejected
- **WHEN** an Azure webhook arrives without the configured Basic-auth credential (and a secret is configured)
- **THEN** `verifyWebhook` fails and the request is rejected (fail-closed), NOT checked against a GitHub HMAC

### Requirement: PR status and the auto-PR instruction are forge-parameterised, credentials host-side
`capability: delivery` · `delta: MODIFIED (feat/spec-038-azure-repos-forge)`

`pullRequestStatus` and the auto-PR delivery instruction (SPEC-031) SHALL dispatch on the resolved forge: a
GitHub project reads status via `gh pr view` and instructs `gh pr create`; an Azure project reads status via
the Azure CLI (`az repos pr …`) and instructs `az repos pr create`, both normalised to the same
`{ number, status }` shape and the same delivery-prompt structure. The webhook ingress SHALL accept the
Azure route (`POST /webhooks/azure`) alongside the unchanged `POST /webhooks/github`, each verified + mapped
by its forge. The host credential — a GitHub token or an Azure **PAT** (`AZURE_DEVOPS_EXT_PAT` /
`System.AccessToken`) — SHALL be read by the CLI from the host environment and SHALL NEVER be persisted to
`.arke/config.json`/global config or returned from any method (NFR-1, mirroring the current `gh` boundary).

#### Scenario: An Azure project's delivery opens the PR with the Azure CLI
- **WHEN** an Azure-Repos project with `autoOpenPr` enabled finishes its delivery checklist
- **THEN** the delivery instruction directs the implementer to `az repos pr create` (not `gh pr create`),
  and the board reads that PR's status via the Azure forge

#### Scenario: The Azure webhook route is served and forge-verified
- **WHEN** an Azure Service Hook POSTs to `/webhooks/azure`
- **THEN** the coordinator verifies it with the Azure forge and applies the mapped transition; `/webhooks/github`
  continues to serve GitHub unchanged

## Design

### Architectural decision

Introduce a `ForgeAdapter` seam mirroring the proven `HarnessAdapter` pattern: a small, neutral interface
with GitHub and Azure Repos as leaves, resolved per project from the git remote (config-overridable). Extract
the current GitHub code into a `GitHubForge` leaf **without changing its behaviour** (the pure functions —
`verifyGithubSignature`, `mapWebhookEvent`, `normaliseRemote`, `githubPrStatus` — move behind the interface),
so the GitHub path is provably unchanged and the risk is contained to the new Azure leaf + the resolver. The
seam is intentionally thin because the coupling is thin: plain git, branch routing, the lifecycle state
machine, and the `localMerge` delivery fallback are already host-agnostic and stay shared. v1 covers the
**lifecycle host** only; Azure Boards work-items, Azure Pipelines CI-gate status, and Azure support for
cross-repo linkage (SPEC-030) are named follow-ups.

### Target architecture

- **`packages/coordinator/src/forge/`** (new): `ForgeAdapter` interface + `GitHubForge` (the moved GitHub
  logic) + `AzureReposForge` (new) + `resolveForge(root, config)`.
  - `ForgeAdapter`: `id`; `verifyWebhook(headers, rawBody, secret)` → `{ ok; eventName? }`;
    `mapWebhookEvent(eventName, payload)` → `LifecycleTransition`; `pullRequestStatus(root, branch)`;
    `normalizeRemote(url)` → `{ host, owner, repo }`; `defaultBranch(root)`; `autoOpenPrInstruction(base)`.
  - `GitHubForge`: delegates to the (moved) `verifyGithubSignature`/`mapWebhookEvent`/`githubPrStatus`/
    `normaliseRemote` — behaviour-preserving.
  - `AzureReposForge`: ADO Service-Hook event mapping (`git.pullrequest.*` + reviewer votes), Basic-auth
    `verifyWebhook`, `az repos pr` status, `dev.azure.com`/`visualstudio.com` remote parsing, `az repos pr
    create` instruction.
- **`packages/coordinator/src/spec-lifecycle.ts`**: the pure GitHub functions move to `GitHubForge`;
  `LifecycleTransition` stays the shared neutral type; `normativeHash`/flatten are untouched.
- **`packages/coordinator/src/server.ts`**: the webhook ingress routes `POST /webhooks/{github|azure}` to the
  matching forge's `verifyWebhook` + `mapWebhookEvent`; the per-forge secret comes from the host env/config.
- **`packages/coordinator/src/git-status.ts`** + **`delivery.ts`** + **`project-context.ts`**: call the
  resolved forge's `pullRequestStatus`/`autoOpenPrInstruction`; `hostConfigured()` generalises to "a forge
  secret is configured for this project's forge".

### Interfaces and contracts

- `ForgeAdapter` added to the coordinator (not a wire/contract change; internal seam).
- `LifecycleTransition` is unchanged and shared across forges.
- `.arke/config.json` MAY carry an optional `forge` block; absent → resolve from the remote → default GitHub.
- No new `DomainEvent`; the board's `{ prNumber, status }` shape is unchanged (both forges normalise to it).

### Cross-cutting

- **Security (NFR-1):** the Azure PAT / GitHub token stays host-side in the CLI environment; never persisted
  or returned. Azure webhook Basic-auth credentials are host-side config, compared constant-time.
- **Determinism / no regression:** the GitHub forge is behaviour-preserving; a GitHub project is unaffected.
- **Alpha/host risk:** Azure PR ops use the `az` CLI (as GitHub uses `gh`) rather than a bespoke REST client
  in v1 — smaller surface, host-side auth, consistent with the current approach.

### Testing
- **Unit:** `GitHubForge.mapWebhookEvent`/`verifyWebhook` produce byte-identical results to the pre-seam
  functions (regression — reuse the existing lifecycle tests through the leaf); `AzureReposForge.mapWebhookEvent`
  over **real Azure Service-Hook payload fixtures** (created→opened, completed→merged, abandoned→closed-unmerged,
  reviewer-approved→approved, forced push→force-push, unknown→ignored); `verifyWebhook` accepts the configured
  Basic-auth and rejects a missing/wrong one (fail-closed) and does NOT expect an HMAC; `resolveForge` maps
  github/dev.azure.com/visualstudio.com/unknown correctly and defaults to GitHub; the delivery instruction emits
  `az repos pr create` for Azure and `gh pr create` for GitHub.
- **Live acceptance (gated on a reachable Azure DevOps org + a PAT):** a real spec authored → PR opened in
  Azure Repos → Service Hook advances the lifecycle → the board shows the PR → merge → delivered, end to end.
  Blocked until an Azure DevOps org + PAT are available (host-side).

### Definition of done
A project whose code lives in Azure Repos runs the full authoring → review → delivery → board loop, its
lifecycle driven by Azure Service Hooks and its PR opened via the Azure CLI, behind a neutral `ForgeAdapter`;
a GitHub project is byte-for-byte unchanged; credentials stay host-side; the unit suite is green with
`typecheck` + `build`; and a non-author reviewer has signed off. The live-acceptance run against a real Azure
org is the remaining gate (a named follow-up when an org + PAT are available), and Azure Boards work-items +
Azure Pipelines CI status are out of scope.

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | A neutral `ForgeAdapter` seam (GitHub + Azure Repos leaves), mirroring `HarnessAdapter` | The coupling is thin and concentrated; a seam contains the change and keeps lifecycle/board/delivery host-agnostic — the same pattern that made the harness layer extensible |
| 2 | Extract GitHub **without behavioural change**; add Azure as a new leaf | The GitHub path is load-bearing and well-tested; moving it behind the interface unchanged makes the risk the new leaf + resolver, not a rewrite |
| 3 | Azure `verifyWebhook` uses **Basic auth**, not an HMAC | Azure DevOps Service Hooks do NOT sign the payload (unlike GitHub's `X-Hub-Signature-256`); assuming HMAC would make every Azure webhook fail — verification MUST be forge-specific |
| 4 | Forge resolved from the git **remote** (config-overridable), default GitHub | A project's host is knowable from its remote with no network + no new required config; defaulting to GitHub guarantees zero regression for existing projects |
| 5 | PR ops via the `az` CLI (as GitHub uses `gh`), not a bespoke REST client, in v1 | Smaller surface, host-side auth (NFR-1), consistent with the current delivery/board approach; a coordinator-side REST client is a possible later optimisation |
| 6 | v1 = **repos only**; work-items + Pipelines CI + cross-repo Azure deferred | The lifecycle host is the headline that unblocks Azure-Repos teams; Azure Boards projection (the SPEC-014 registry) and CI-gate status are separable, additive follow-ups |

## Open questions
- Azure Service Hooks are configured per **event type** (one subscription per event) rather than one webhook
  for all — does the setup note need to enumerate the required subscriptions (PR created/updated, push), and
  should Arke offer a helper to create them via the API? v1: document the manual subscriptions.
- Does `/webhooks/azure` need per-repo secret scoping (multiple Azure projects on one coordinator), or is a
  single Basic-auth credential per coordinator enough for v1? v1: single credential; revisit with multi-project.
- Should `defaultBranch` query the host API (GitHub/Azure) instead of the local main/master inference, now
  that a forge adapter exists? v1: keep local inference (host-agnostic); a forge-API query is a later refinement.
