# Auto-PR configuration — let the implementer open the PR on delivery

## Why
Delivery ([SPEC-028](028.single-session-delivery.md)) ends with the implementer's checklist complete and the card in the diff-review lane, waiting for a human to review the diff and open a pull request ([SPEC-011](011.session-detail-and-rescue.md)). For a trusted, fast-moving project that per-diff gate is friction the engineer may want to trade away — letting the implementer open the PR itself as the final step of delivery. This adds a per-project setting that opts into exactly that, while keeping the human gate as the default.

## What changes
- ADDED project-config — a per-project `delivery.autoOpenPr` preference (default `false`) persisted in `.arke/config.json`, read and written through `delivery.settings` / `delivery.configure` ops
- ADDED single-session-delivery — when `autoOpenPr` is on, the delivery prompt instructs the implementer to open a pull request (`gh pr create --fill`) once every task is checked off
- MODIFIED single-session-delivery — the delivery prompt is now a function of the auto-PR preference; with it off (the default) the prompt is unchanged and delivery still stops at the diff-review gate
- ADDED project-config — a Settings › Governance toggle that flips the preference live

**Relates to:** [SPEC-011](011.session-detail-and-rescue.md) (the diff-review gate this relaxes), [SPEC-028](028.single-session-delivery.md) (the delivery prompt this extends).

## Requirements

### Requirement: A per-project auto-PR preference, defaulting off
`capability: project-config` · `delta: ADDED (feat/spec-030-auto-pr-config)`

The system SHALL persist a per-project boolean `delivery.autoOpenPr` in the project's canonical config file `.arke/config.json` (SPEC-005/019 — all project config lives in that one file). The default, when the key is absent or the file is missing/unreadable, SHALL be `false`. Reading it SHALL be exposed as a `delivery.settings` op returning `{ autoOpenPr }`; writing it SHALL be a `delivery.configure { autoOpenPr }` op that performs a read-modify-write PRESERVING every other key in the file (registry, settings, providers, …) and refuses to overwrite a file that exists but is not valid JSON. Because enabling auto-PR is a standing authorization for future deliveries to open PRs without a per-diff human click, `delivery.configure` SHALL record the decision to the audit trace **fail-safe before** applying the config change (`writeOrThrow`, mirroring `approveDraft`): if the audit append cannot land, the config SHALL NOT be flipped.

#### Scenario: Absent config reads as off
- **WHEN** `delivery.settings` is requested for a project whose `.arke/config.json` has no `delivery` block (or no file)
- **THEN** it returns `{ autoOpenPr: false }`

#### Scenario: Configure round-trips and preserves other keys
- **WHEN** `delivery.configure { autoOpenPr: true }` is issued for a project whose config already has a `registry` block
- **THEN** a subsequent `delivery.settings` returns `{ autoOpenPr: true }`
- **AND** the `registry` block (and any `settings`/`providers`) is unchanged on disk

#### Scenario: A malformed config is not clobbered
- **WHEN** `delivery.configure` is issued and `.arke/config.json` exists but is not valid JSON
- **THEN** the write is refused with an error
- **AND** the existing file bytes are left untouched

#### Scenario: The authorization is audited before it takes effect
- **WHEN** `delivery.configure` is issued and the audit trace cannot be written
- **THEN** the op fails and `.arke/config.json` is NOT changed (no un-audited standing authorization)

### Requirement: Auto-PR instructs the implementer to open the PR on delivery
`capability: single-session-delivery` · `delta: ADDED (feat/spec-030-auto-pr-config)`

When a delivery is dispatched ([SPEC-028](028.single-session-delivery.md)) for a project with `autoOpenPr` on, the delivery prompt handed to the implementer SHALL include an instruction to open a pull request once every task in the checklist is checked off, via `gh pr create --fill`. The instruction SHALL NOT hard-code a `--base` branch: the harness runs in the project's own checkout on the feature branch (the delivery worktree is not wired into the harness cwd — a known [SPEC-028](028.single-session-delivery.md) gap), so `gh pr create --fill` opens the PR from the current (feature) branch against the repository's default branch — exactly the [SPEC-024](024.specification-lifecycle-gating.md) delivery PR (feature → mainline). Leaving the base to `gh`'s default also keeps a spec branch name out of the shell command (no injection via a crafted `branch:` frontmatter value). When `autoOpenPr` is off (the default), the delivery prompt SHALL contain no PR instruction, and delivery SHALL stop at the human diff-review gate exactly as before (SPEC-011 unchanged). The auto-PR decision in effect for a dispatch SHALL be recorded on the delivery's dispatch trace entry.

This is the propose-decide-execute boundary for code output ([SPEC-011](011.session-detail-and-rescue.md)) reframed rather than removed: the engineer's config choice is a STANDING, pre-authorized decision to execute (open the PR) without a per-diff click. It relaxes SPEC-011's "a PR SHALL never be opened automatically without an explicit human approval on the diff" — the approval is given once, at config time, instead of per delivery.

#### Scenario: Auto-PR on appends the instruction
- **WHEN** a delivery is dispatched for a project with `autoOpenPr` on
- **THEN** the implementer's prompt tells it to open a pull request (`gh pr create --fill`) once every task is checked off
- **AND** the instruction interpolates no branch name into the shell command (the base is left to `gh`'s default — the repository's default branch)

#### Scenario: Auto-PR off is the unchanged default
- **WHEN** a delivery is dispatched for a project with `autoOpenPr` off (or unset)
- **THEN** the prompt contains no PR instruction
- **AND** the card lands in the diff-review lane for the human to open the PR (SPEC-011)

#### Scenario: The dispatch trace records the decision
- **WHEN** any delivery is dispatched
- **THEN** its `dispatch.started` trace entry carries the `autoOpenPr` value that shaped the prompt

### Requirement: The preference is editable in Settings and seeded on connect
`capability: project-config` · `delta: ADDED (feat/spec-030-auto-pr-config)`

The connection snapshot SHALL carry the active project's `delivery.autoOpenPr` so the client renders the toggle's true state without an extra round-trip. Settings › Governance SHALL present a toggle that reads that state and, on change, issues `delivery.configure` (a governed write — refused, not queued, while offline). The toggle MAY update optimistically, but when the write is refused or fails it SHALL roll back to the previous value and surface a notice, so the toggle never reads "on" while the persisted config still reads `false`. The default runtime mode toggle and the rest of the governance surface SHALL be unaffected.

#### Scenario: Toggle reflects the persisted value on connect
- **WHEN** a client connects to a project with `autoOpenPr` on
- **THEN** the Settings auto-PR toggle shows on

#### Scenario: Flipping the toggle persists via the coordinator
- **WHEN** the engineer flips the auto-PR toggle
- **THEN** the client issues `delivery.configure` with the new value
- **AND** the next delivery for that project reflects the new preference

#### Scenario: A failed persist rolls the toggle back
- **WHEN** the engineer flips the toggle but the `delivery.configure` write is refused (e.g. offline) or fails
- **THEN** the toggle returns to its previous value
- **AND** a notice surfaces the failure — the UI never claims a setting that did not persist

## Design

### Architectural decision
Auto-PR is delivered **prompt-side, not coordinator-side**: rather than build (currently non-existent) coordinator PR-opening (`git push` + `gh pr create`), the delivery prompt itself instructs the implementer — which runs in the project checkout with git tooling — to open the PR. This keeps the whole feature to one config flag + a conditional prompt fragment, fits single-session-delivery's "the agent decides how to tackle the work" philosophy, and is fully unit-testable via prompt assertions. The trade-off (recorded in the decision log) is that the PR is opened by the agent, outside the coordinator's governed/traced path — acceptable because the engineer explicitly opts in, and the dispatch trace still records that auto-PR was in effect. The instruction leaves the PR base to `gh`'s default (current branch → repo default branch) rather than hard-coding one: the harness runs in the project's own checkout on the feature branch (the SPEC-028 delivery worktree is created but not wired into the harness cwd — the adapter dispatches with a fixed `directory`), so the current branch is the feature branch and `gh pr create --fill` yields the correct feature → mainline delivery PR without interpolating a branch name into a shell command.

### Target architecture
```
Settings toggle ──delivery.configure {autoOpenPr}──► ProjectContext
                                                        └─ setAutoOpenPr(.arke/config.json)  (read-modify-write, preserve keys)

spec.deliver ──► deliverImplementation
                   ├─ loadAutoOpenPr(.arke/config.json)  → boolean
                   ├─ trace dispatch.started { autoOpenPr }
                   └─ buildDeliveryPrompt(specPath, tasks, autoOpenPr ? {autoOpenPr} : {})
                                                              └─ appends "open a PR (gh pr create --fill) when done"

connection snapshot ──{ delivery: { autoOpenPr } }──► client store.autoOpenPr ──► Settings toggle state
```

### Data model
No new store. The preference is one boolean under a `delivery` block in the existing `.arke/config.json`:
```json
{ "registry": { … }, "delivery": { "autoOpenPr": true } }
```
`loadAutoOpenPr(configPath)` reads it (false on absent/unparseable/wrong-type — only literal `true` opts in). `setAutoOpenPr(configPath, value)` read-modify-writes it atomically (temp + rename), preserving every other key and refusing to clobber invalid JSON. Both live in `packages/coordinator/src/delivery-config.ts` (side-effecting file I/O, kept out of the pure `delivery.ts`).

### Interfaces and contracts
- Ops (internal, coordinator dispatch table — not `@arke/contracts`): `delivery.settings` → `{ autoOpenPr }`; `delivery.configure { autoOpenPr }` → `{ ok, autoOpenPr }`.
- `buildDeliveryPrompt(specPath, tasks, opts?: { autoOpenPr? })` — the third argument is new and optional, so existing callers are unaffected.
- Connection snapshot gains `delivery: { autoOpenPr }`.
- Client: `setAutoOpenPr(value)` in `live.ts` (governed write + optimistic store update); `store.autoOpenPr` seeded in `applySnapshot`.

### Cross-cutting
- **Governance (SPEC-011):** this is the one place Arke lets code output reach a PR without a per-diff human click. It is off by default, opt-in, per-project, and audited on the dispatch trace. The relaxation is explicit and reversible (flip the toggle back).
- **Security:** the config write only ever sets a boolean; no client- or spec-supplied string is interpolated into a shell command. The PR itself is opened by the agent under its own harness permissions, not by the coordinator.
- **Design template:** the Settings toggle follows the `arke-design` skill (`.claude/skills/arke-design/`) — the existing `Row` + `Switch` pattern in the Governance group.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Prompt-driven, not coordinator-driven, PR opening | Avoids building non-existent coordinator `git push` + `gh pr create`; one flag + a conditional prompt fragment; fits single-session-delivery; fully unit-testable. Trade-off: the PR is opened by the agent, outside the governed/traced coordinator path (the dispatch trace still records that auto-PR was in effect) |
| 2 | Off by default, opt-in, per-project | Preserves SPEC-011's human diff gate as the safe baseline; the relaxation is a deliberate, reversible choice for a trusted project, not a global default |
| 3 | Stored in `.arke/config.json` under a `delivery` block | The canonical single project config file (SPEC-005/019); a dedicated block avoids colliding with `settings` (adapter/process-advisory) and keeps the file hand-editable |
| 4 | Read-modify-write preserves other keys; refuses to clobber invalid JSON | The config file is hand-editable and holds the registry; a setter that dropped other keys — or overwrote a half-edited file — would be a footgun |
| 5 | The instruction leaves the PR base to `gh`'s default (`gh pr create --fill`), not a hard-coded `--base <branch>` | Corrected in PR review: the SPEC-028 delivery worktree is not wired into the harness cwd (the adapter dispatches with a fixed `directory`), so the agent actually runs on the feature branch in the project checkout. A hard-coded `--base <featureBranch>` would make head == base (no commits, PR fails); leaving base to gh's default gives the correct feature → mainline delivery PR (SPEC-024) and keeps a spec branch name out of the shell command (injection-safe) |
| 6 | `delivery.configure` records the authorization fail-safe (`writeOrThrow`) BEFORE applying the config change | Enabling auto-PR is a standing authorization for future PRs-without-per-diff-approval; it must not take effect with no durable audit record if the trace is unwritable — same governed-write discipline as `approveDraft` (caught in PR review) |
| 7 | The Settings toggle rolls back on a failed/refused persist | An optimistic toggle left "on" after a refused write would claim a setting the project config doesn't hold, so the next delivery wouldn't open a PR despite the UI saying it would (caught in PR review) |

## Open questions
- The SPEC-028 delivery worktree is created but not wired into the harness cwd (the adapter dispatches with a fixed `directory`), so the implementer runs in the project checkout on the feature branch rather than the isolated `<featureBranch>--delivery` worktree. Auto-PR is designed around that reality today (`gh pr create --fill` → feature → mainline). When worktree isolation is actually wired (a SPEC-028 follow-up touching the adapter's per-session cwd), the auto-PR base could become the feature branch and the instruction should be revisited.
- The agent needs `gh` auth + a configured remote to actually open the PR; when neither is present the instruction is a best-effort no-op (the agent reports it couldn't). A future coordinator-side, host-optional PR-open (mirroring SPEC-024's local-merge fallback) could make this deterministic and bring it back under the governed/traced path — deferred.
- Should auto-PR also imply auto-approval of the diff gate on the board (so the card doesn't sit in the diff lane), or is the opened PR itself the signal? Left as-is for now: delivery still marks the card `done` via the checklist oracle; the PR is extra.
