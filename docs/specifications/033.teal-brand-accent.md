# Teal brand accent

## Why
Arke ships a deliberately monochrome UI (brand accent `mono` → near-black primary), but the product
wants a teal brand accent: a single restrained colour on the primary actions and focus states that
gives the app an identity while keeping the quiet, neutral character everywhere else. The theme
engine already supports selectable accents (`ACCENT_HEX.teal = '#0E7490'`, applied by `applyTheme`
to `--primary`/`--ring`); this change makes teal the default and records it as the design contract.

## What changes
- MODIFIED design-system — the default **brand accent** is **teal (`#0E7490`)** instead of `mono`: `--primary` and `--ring` (primary buttons, the `//Arke` wordmark, active/selected states, focus rings) render teal app-wide, with near-white primary foreground
- MODIFIED design-system — the `arke-design` design contract is amended so "quiet monochrome" means neutral surfaces/text/hover with a **teal brand accent**, rather than no colour at all
- Unchanged — the neutral `--accent` hover token, all surfaces and body text stay monochrome; the semantic palette (destructive red, success green, warning amber) is untouched; the accent remains user-selectable (mono/indigo/teal/green/amber), now defaulting to teal

## Requirements

### Requirement: The brand accent is teal by default, app-wide
`capability: design-system` · `delta: MODIFIED (feat/teal-brand-accent)`

The application SHALL use teal (`#0E7490`) as its default brand accent, applied through the existing
theme engine to `--primary` and `--ring` so that every surface the design system tints with the
brand accent — primary buttons, the `//Arke` wordmark badge, active/selected navigation, and focus
rings — renders teal, with `--primary-foreground` remaining near-white. Neutral surfaces, body text,
and the neutral `--accent` hover token SHALL remain monochrome; the change is a brand tint, not a
recolour of the whole UI.

#### Scenario: Primary actions and focus render teal
- **WHEN** the app loads with the default accent
- **THEN** primary buttons, the `//Arke` wordmark badge, and the keyboard focus ring render in teal (`#0E7490`) with near-white foreground on the primary
- **AND** neutral surfaces, body text, and hover backgrounds (`--accent`) remain monochrome

#### Scenario: The semantic palette is unaffected
- **WHEN** a destructive, success, or warning affordance is shown
- **THEN** it keeps its existing colour (red / green / amber), distinct from the teal brand accent
- **AND** teal is used only as the brand accent, never to signal a status

### Requirement: The accent remains selectable, defaulting to teal
`capability: design-system` · `delta: MODIFIED (feat/teal-brand-accent)`

The existing accent selector SHALL continue to offer the full set (`mono`, `indigo`, `teal`,
`green`, `amber`); the default selection SHALL be `teal`; choosing `mono` SHALL restore the
near-black monochrome primary.

#### Scenario: Default selection is teal
- **WHEN** the app initialises without a stored accent preference
- **THEN** the selected accent is `teal`

#### Scenario: Reverting to mono restores the monochrome primary
- **WHEN** the engineer selects `mono` in the accent selector
- **THEN** `--primary`/`--ring` fall back to the near-black monochrome values and no teal tint remains

### Requirement: Teal accent meets contrast in both themes
`capability: design-system` · `delta: ADDED (feat/teal-brand-accent)`

The teal brand accent SHALL meet WCAG AA contrast against its foreground and against the surface it
sits on, in both the light and dark themes; if `#0E7490` does not clear AA on the dark theme's
near-black background, a dark-theme teal variant SHALL be defined so the accent stays legible and the
focus ring stays visible (NFR-6).

#### Scenario: Teal primary is legible in light and dark
- **WHEN** the app renders a teal primary button (and focus ring) in the light theme and in the dark theme
- **THEN** the teal-vs-foreground and teal-vs-surface contrast meets WCAG AA in both
- **AND** where the single `#0E7490` value fails AA on the dark background, a calibrated dark-theme teal is used instead

## Design

### Architectural decision
Flip the default and record it in the contract — do not add new machinery. The store already holds an
`accent` field and `applyTheme` already maps a non-`mono` accent onto `--primary`,
`--primary-foreground`, and `--ring`; teal is already in `ACCENT_HEX`. The change is: default the
accent to `teal`, verify both themes, and amend the `arke-design` skill so future UI work treats teal
as the brand accent.

### Target architecture
- `packages/client/src/store.ts` — default `accent: 'mono'` → `accent: 'teal'`.
- `packages/client/src/store.ts` `applyTheme` — unchanged mechanism; verify it sets teal on `--primary`/`--ring` for both light and dark. If a dark-theme teal is needed, extend `ACCENT_HEX` (or `applyTheme`) to pick a theme-aware teal value.
- `packages/client/src/tweaks.tsx` — the accent selector already lists teal; confirm the default swatch reflects `teal` (the `accent ?? 'graphite'` fallback should resolve to the store default).
- **Design contract:** amend `.claude/skills/arke-design/` — the readme's "nothing renders teal/orange" line and the SKILL.md "quiet monochrome" framing are updated to: neutral surfaces/text with a **teal brand accent** on `--primary`/`--ring`. The token files stay the shadcn neutral base; teal is applied as the brand accent layer (matching how `applyTheme` overrides at runtime), not by rewriting the neutral ramp.

### Data model
None. `accent` is an existing client-side view preference; only its default changes.

### Interfaces and contracts
No new events, commands, or tokens. The brand accent continues to be expressed as `--primary` and
`--ring`; any UI that already uses those tokens inherits teal with no per-component change. This is
what keeps SPEC-032's rendered output consistent — its code-highlight accent and markdown links read
from `--primary`/`--ring`, so they pick up teal automatically.

### Cross-cutting
- **Design template:** this spec **amends** the `arke-design` skill (`.claude/skills/arke-design/`).
  The monochrome principle stands for surfaces, text, iconography, and the neutral hover token; the
  brand accent is now teal. Destructive red stays the one reserved status red; success green and
  warning amber are unchanged.
- **Accessibility (NFR-6):** teal primary and the teal focus ring must clear WCAG AA against their
  foreground and surface in both themes; a dark-theme teal is defined if `#0E7490` does not.
- **Consistency with SPEC-032:** the cockpit rendered-output spec uses the brand accent
  (`--primary`/`--ring`) as its single restrained code-highlight accent and link colour, so teal is
  applied there through the same tokens — the two specs share one accent source of truth.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Flip the default accent rather than build new theming | The `accent` field, `ACCENT_HEX.teal`, and `applyTheme` already exist; teal is a one-line default change plus a contract amendment |
| 2 | Teal is a brand tint on `--primary`/`--ring` only, not a recolour of surfaces/text/hover | Preserves the "quiet infrastructure" character; the app stays neutral apart from the restrained brand accent |
| 3 | Keep the accent user-selectable with `mono` as the escape hatch | Users who prefer the pure monochrome look can restore it; teal is the default, not a lock-in |
| 4 | The brand accent stays the single source for SPEC-032's code accent + links | One token (`--primary`/`--ring`) drives both, so the accent never drifts between surfaces |

## Open questions
- Does `#0E7490` clear WCAG AA on the dark theme's `#0A0A0A` background, or is a lighter dark-theme teal needed? Resolve during the dark-theme pass.
- Should the teal accent also tint the launch/splash "probing harness" indicator, or does that stay the reserved green? Proposed: leave the harness-reachability green as-is (it is a status signal, not brand).
