# Voice-enabled specification authoring — Voxa voice loop in the authoring cockpit

## Why

Authoring a specification is a conversation — the Product Engineer thinks out loud with `spec-author`
and `architect` — but the cockpit only accepts typed text, which caps the pace of the highest-value
loop in the product at typing speed. [Voxa](https://github.com/michaeljosiah/voxa) is a frame-based
real-time voice pipeline for .NET that already ships the whole hard part (VAD → STT → agent →
sentence aggregation → TTS over one WebSocket, with barge-in), an official browser client
(`@voxa/client`), and a host seam (`IAgentTurnDriver`, VDX-007) purpose-built for plugging a foreign
agent loop — ours — into its composed pipeline. This spec adds a *voice channel* to the cockpit
without adding a voice *architecture* to Arke: the coordinator stays thin, the client stays a
realisation layer, and every voice-originated action lands in the trace like any other.

## What changes

- ADDED voice-sidecar — a local Voxa voice service (.NET, loopback-only) managed by the coordinator; its agent stage forwards final transcripts into the authoring session and speaks the co-author's streamed reply
- ADDED client-voice-capture — the cockpit gains push-to-talk / open-mic capture and bot-audio playback via `@voxa/client`, connected directly to the sidecar on localhost
- ADDED voice-authoring — voice-originated messages flow through the existing coordinator → `HarnessAdapter` path, are tagged with their modality, and are fully audit-traced; barge-in interrupts spoken playback instantly
- MODIFIED coordinator config — `.arke/config.json` gains an optional `voice` section (sidecar URL/launch, STT/TTS provider selection, mode) (breaking: no — absent section means voice is off and nothing changes)

## Requirements

### Requirement: Voice is optional and additive
`capability: voice-authoring` · `delta: ADDED (feat/spec-029-voxa-voice-authoring)`

The system SHALL treat voice as an opt-in channel: with no `voice` section in `.arke/config.json`
(or `voice.enabled: false`), the coordinator SHALL NOT launch or probe a voice sidecar, the client
SHALL NOT render voice controls, and all existing behaviour SHALL be unchanged.

#### Scenario: No voice config
- **WHEN** a project's `.arke/config.json` has no `voice` section
- **THEN** the coordinator starts exactly as today, with no sidecar process and no voice log lines
- **AND** the cockpit renders no microphone affordance

### Requirement: The voice sidecar is local and inside the trust boundary
`capability: voice-sidecar` · `delta: ADDED (feat/spec-029-voxa-voice-authoring)`

The voice sidecar SHALL bind loopback only, SHALL be reachable by the client only on
`ws://127.0.0.1:<port>/voice`, and SHALL introduce no cloud dependency on the hot path (PRD D2).
When configured with Voxa's local speech tier (whisper.cpp STT, Piper/Kokoro TTS, Silero VAD) the
voice loop SHALL function with zero network access; cloud STT/TTS providers MAY be configured
explicitly, in which case only audio/transcripts — never repository content beyond what the user
speaks — leave the machine.

#### Scenario: Loopback only
- **WHEN** the sidecar is running
- **THEN** its WebSocket endpoint accepts connections from 127.0.0.1 and refuses non-loopback binds

#### Scenario: Fully local operation
- **WHEN** the voice section selects the local speech tier and the machine is offline
- **THEN** speaking into the cockpit still produces transcripts and spoken replies

### Requirement: Coordinator owns the sidecar lifecycle
`capability: voice-sidecar` · `delta: ADDED (feat/spec-029-voxa-voice-authoring)`

When voice is enabled, the coordinator SHALL either launch the sidecar process (configured command)
or attach to an already-running one (configured URL), SHALL health-check it before advertising voice
readiness to the client, and SHALL surface sidecar failure as a typed status event — never a silent
dead microphone.

#### Scenario: Sidecar down
- **WHEN** the client requests voice readiness and the sidecar health check fails
- **THEN** the coordinator emits a voice-status event with a diagnosable reason
- **AND** the cockpit shows the microphone as unavailable with that reason

### Requirement: Client capture and playback use @voxa/client
`capability: client-voice-capture` · `delta: ADDED (feat/spec-029-voxa-voice-authoring)`

The cockpit SHALL embed `@voxa/client` for mic capture, gap-free playback, and typed voice events,
connecting directly to the sidecar's loopback WebSocket (audio does not transit the coordinator).
The client SHALL take both sample rates from the sidecar's `session` envelope and SHALL honour the
protocol version check. Push-to-talk SHALL be the default mode; open-mic (VAD-gated) SHALL be a
per-user toggle.

#### Scenario: Dictating a requirement
- **WHEN** the user holds push-to-talk and speaks
- **THEN** interim transcripts render live in the composer
- **AND** on release, the final transcript is submitted as the user's authoring message

#### Scenario: Barge-in
- **WHEN** the co-author's reply is being spoken and the user starts speaking
- **THEN** local playback stops within one audio buffer (the `@voxa/client` flush on
  `speaking{user,started}` / `interruption`)
- **AND** the in-flight agent turn is aborted through the same path as a typed-turn abort

### Requirement: Voice turns drive the real authoring session
`capability: voice-authoring` · `delta: ADDED (feat/spec-029-voxa-voice-authoring)`

A final transcript SHALL enter the authoring session through the same coordinator path as a typed
message (role selection, tier→model routing, `HarnessAdapter.sendMessage`), and the co-author's
streamed reply SHALL be both rendered as text in the cockpit and spoken by the sidecar. The sidecar
SHALL obtain the reply stream via a Voxa `IAgentTurnDriver` implementation that calls the
coordinator; it SHALL NOT talk to a harness directly.

#### Scenario: Round trip
- **WHEN** a final transcript "add a requirement that exports are rate-limited" is produced
- **THEN** the coordinator dispatches it to the `spec-author` role exactly as if typed
- **AND** the streamed reply appears in the cockpit transcript view
- **AND** the reply is spoken, sentence-by-sentence, as tokens stream

### Requirement: Voice-originated actions are fully traced
`capability: voice-authoring` · `delta: ADDED (feat/spec-029-voxa-voice-authoring)`

Every voice-originated message SHALL be recorded in `.arke/trace.ndjson` as a normal message event
carrying `modality: "voice"`; the read model and review flows SHALL treat it identically to typed
input. Raw audio SHALL NOT be persisted. Lifecycle gates (review convening, approval, delivery)
SHALL remain explicit UI actions — this spec adds no spoken command that crosses a gate.

#### Scenario: Audit
- **WHEN** a spec draft was partly authored by voice
- **THEN** the trace shows each voice message with `modality: "voice"` and its final transcript text
- **AND** no audio bytes exist anywhere under `.arke/`

#### Scenario: No spoken approvals
- **WHEN** the user says "approve the spec"
- **THEN** the utterance is delivered to the co-author as ordinary conversation
- **AND** no spec lifecycle transition occurs

## Design

### Architectural decision

**Voice is a sidecar, not a coordinator feature.** Voxa is .NET; Arke is Node. Embedding a speech
stack in the coordinator would bloat the trust boundary and violate "thin". Instead a loopback Voxa
server owns everything audio, and two narrow contracts connect it: the browser-side
`@voxa/client` WebSocket (audio + envelopes) and a server-side turn bridge (transcript in → token
stream out) from the sidecar to the coordinator. The audio hot path never touches the coordinator;
the message path never bypasses it.

### Target architecture

```
cockpit (React)                      coordinator (Node, :4319)            harness
  @voxa/client  ──ws (loopback)──▶  voxa sidecar (.NET, :5199)             │
  mic PCM ─────────────────────▶     VAD → STT ─ transcript ─┐              │
  ◀───────────────── bot PCM         TTS ◀─ SentenceAggregator│             │
  typed events (transcripts,              ArkeCockpitTurnDriver ──HTTP──▶ session.message ──▶ adapter
  speaking, interruption)                 (IAgentTurnDriver)  ◀──SSE────  reply token stream
```

- **Sidecar** — a small .NET host (`arke-voice`, shipped as a dotnet tool or a repo-local project)
  that is five lines of Voxa: `AddVoxa(config)` + `MapVoxaVoice("/voice").UseDefaults()` with a
  registered `ArkeCockpitTurnDriver`. Voxa's VDX-007 seam makes the custom agent stage compose under
  `UseDefaults()`, keeping the real VAD, the `LowLatency` profile, and interim-transcript coalescing
  without hand-building the pipeline.
- **`ArkeCockpitTurnDriver`** — implements Voxa's `IAgentTurnDriver`: on each final transcript it
  POSTs a message to a new coordinator endpoint (below) and re-emits the reply's streamed tokens as
  `LlmTextChunkFrame`s; Voxa's cancellation token (barge-in) maps to the coordinator's turn abort.
- **Coordinator additions** (`packages/coordinator`):
  - `voice` config in `.arke/config.json` (zod-validated in `packages/contracts`):
    `{ enabled, sidecar: { url } | { command, args, port }, role: "spec-author", mode: "push-to-talk" | "open-mic" }`.
  - Sidecar lifecycle: spawn/attach + `GET /healthz` probe; `voice.status` event to the client.
  - A loopback bridge surface for the driver: `POST /voice/turns` (final transcript, session id,
    role) → dispatches through the existing registry/adapter exactly like a client-typed message and
    streams the assistant tokens back (SSE or chunked response); `POST /voice/turns/{id}/abort`.
  - Message events gain optional `modality` metadata; the trace writer persists it.
- **Client additions** (`packages/client`): a `useVoice` hook wrapping `@voxa/client` (connect on
  demand, mic level, interim/final transcripts, speaking state), a push-to-talk control + status pill
  in the cockpit composer, and settings surface for mode/voice selection.

### Interfaces and contracts

- `@voxa/client` events consumed: `session`, `transcription` (interim → live composer preview;
  final → submit), `speaking`, `interruption`, `micLevel`, `error`. The wire protocol is versioned
  (`session.v`); the client warns on mismatch.
- Coordinator `POST /voice/turns` request: `{ sessionId, role, tier, text, modality: "voice" }` —
  deliberately the same shape the WS `session.message` handler folds, so the dispatch path is shared
  code, not a parallel one.
- Trace event delta: `message` events accept `modality?: "voice"` (absent = typed). Read model is
  unchanged (modality is display/audit metadata only).

### Cross-cutting

- **Latency.** Loopback transport is sub-millisecond; the budget that matters is speech-end → first
  spoken syllable. Voxa's `LowLatency` profile + eager sentence chunking targets sub-2 s with local
  models on CPU; the bridge adds one loopback HTTP hop (< 5 ms). The harness reply stream dominates —
  which is the same latency a typed turn already has.
- **Security.** Sidecar binds loopback; no new external surface. Cloud STT/TTS keys, when used, live
  in the sidecar's own config on the host, never in the client. No audio persistence.
- **Observability.** Sidecar exposes Voxa's diagnostics hub (stage latency waterfall) locally;
  coordinator logs voice.status transitions to the trace.
- **Design template:** the UI follows the `arke-design` skill (`.claude/skills/arke-design/`) —
  the mic control, status pill, and interim-transcript treatment reuse existing composer patterns.

### Dependencies (external, tracked)

1. **`@voxa/client` publication** — implemented in the Voxa repo (`clients/voxa-client`,
   VDX-005), not yet on npm. Until published, consume via a git/file dependency; the package has
   zero runtime deps.
2. **Voxa VDX-007** (`IAgentTurnDriver` under `UseDefaults()`) — merged to Voxa main (PR #91).
3. Local speech models download on first sidecar run (SHA-256-pinned via Voxa's model cache);
   offline thereafter.

### Testing

- Contracts/coordinator: unit tests for schema, lifecycle states, dispatch-path sharing (mock adapter), trace modality.
- Sidecar: .NET tests for `ArkeCockpitTurnDriver` against a fake coordinator (scripted SSE), including cancellation → abort.

- Manual: full local-tier session offline; barge-in feel; open-mic mode.

### Definition of done

All scenarios pass; `npm run typecheck && npm run build && npm test` green; the sidecar path proven
against a live OpenCode session end-to-end; spec status advanced through Arke's own review flow.

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Voice sidecar (.NET Voxa) instead of speech-in-coordinator | Coordinator stays thin (D12); Voxa already solves VAD/STT/TTS/barge-in; audio never transits the coordinator |
| 2 | Client connects to the sidecar directly on loopback | Audio hot path off the coordinator; `@voxa/client` handles capture/playback/flush |
| 3 | Transcripts dispatch through the existing message path, tagged `modality: "voice"` | One dispatch path to audit and test; PRD "every action recorded" holds for voice |
| 4 | No spoken lifecycle commands in v1 | Gates are the product's safety property; a misheard "approve" must be impossible by construction |
| 5 | Push-to-talk default, open-mic opt-in | Authoring rooms are noisy; PTT gives deterministic turn boundaries; VAD mode kept for hands-free |
