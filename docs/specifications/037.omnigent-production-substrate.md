# Omnigent meta-harness — from spike to production substrate

## Why

`@arke/adapter-omnigent` is the ADR-0002 spike: it proved the substrate thesis — a real OpenCode turn was
driven end-to-end through Omnigent's v1 HTTP API behind the neutral `HarnessAdapter` seam — but it is kept
**off the default composition** (the coordinator today rejects any `driver !== "opencode"` at connect,
`server.ts` `connectHarness`). Omnigent is a **meta-harness**: one backend-agnostic control plane over ~15
concrete harnesses (OpenCode, Claude Code, Codex, Cursor, Goose, …), with a server/runner split that mirrors
Arke's own coordinator/runner model (SPEC-018). Promoting it off the spike lets an Arke agent **role run on
whichever substrate serves the model it needs** — the payoff the neutral seam was built for — while Arke keeps
authority over the roster (harness-agnostic images + logical tiers, ADR-0004).

A live probe against **Omnigent 0.3.0** (this spec's grounding) surfaced the concrete gaps. The most
important is a **correctness** one, not just resilience: the spike's `normalize()` was written against
OpenAI-Responses shapes (`response.output_text.delta`, `response.completed`, nested `data.*`), but the live
control-plane stream emits a different envelope — `{ sequence_number, type, … }` with `session.*` /
`response.*` frames (`session.status`, `session.heartbeat`, `session.presence`,
`session.changed_files.invalidated`, `session.terminal_pending`, `session.input.consumed`,
`response.error`, and the elicitation frames). The spike normalizes against control-plane shapes the live
server does not send. Beyond that, the spike has no event-confirmed approvals, no reconnect, correlation
keyed on a stale field (`pending_id`) the live server replaced with `item_id`, and an in-memory-only session
map — the four production gaps named in the PRD (correlation, event-confirmed approvals, reconnect, version
pinning).

**A grounding honesty note (drives the requirements below).** The live probe captured the **control-plane**
frames but **not a successful assistant turn** — the runner failed on an expired OpenCode credential
(`Token refresh failed: 401`). So three wire facts remain **unconfirmed against 0.3.0** and every requirement
that touches them is explicitly marked **PROVISIONAL**: (1) the **assistant-content** frame shape that
carries the agent's output (the spike has a *nested* `item.content[]` capture from the 2026-06-29 run, but its
currency against the 0.3.0 flat envelope is unverified); (2) whether `sequence_number` is **non-null and
monotonic** on stream frames (the captured control frames showed `sequence_number: null`, and the spike's
`sse.ts` records the stream as "live-tail only, no sequence numbers"); (3) the exact resume/backfill surface.
The **correlation** fact *is* confirmed: `POST …/events` returned `{ queued: true, item_id }` and the
`session.input.consumed` frame echoed the same `item_id`. This spec therefore separates the **grounded** work
(control-plane normalize, correlation, event-confirmed approvals, durable store, dead-letter, version pin,
reconnect-by-resync) from the **live-gated** work (the assistant-content mapping and any `sequence_number`
optimisation), and gates **entry into the default composition** on the live-acceptance run.

## What changes

- ADDED omnigent-substrate — the adapter's `normalize()` is **re-grounded on the real Omnigent 0.3.0
  control-plane envelope** (`{ sequence_number, type }` with `session.*`/`response.*` frames), captured live
  and pinned as a fixture, so it emits correct `DomainEvent`s instead of matching shapes the server never
  sends. The **assistant-content** mapping is delivered PROVISIONALLY (against the spike's prior capture) and
  is only *confirmed* by the live-acceptance turn.
- ADDED adapter-resilience — **event-confirmed approvals** (a permission decision is `confirmed` only once
  the stream echoes its resolution), **correlation matching** (the live-confirmed `item_id` that
  `POST …/events` returns, matched against `session.input.consumed`, replacing the spike's stale `pending_id`),
  **reconnect + REST resync** (on stream close, reconnect with bounded backoff and re-sync missed state via
  REST — the proven OpenCode pattern — with a `sequence_number`-based gap-dedup *optimisation applied only if*
  0.3.0 proves to carry non-null monotonic sequences), a **durable session store** (survives an adapter
  restart), and a **dead-letter sink** (an unmapped frame is recorded, never silently dropped).
- ADDED harness-integration — **completion-aware `sendMessage`** (resolves when the turn reaches
  `session.status: idle`), **version pinning** (target a pinned Omnigent version; validate `/api/version` at
  `init`; fail loud on a mismatch), and best-effort **`listModels()`** (`models` capability declared only when
  it returns a real catalog). The adapter is made **constructable and registrable** — the coordinator can
  build an `OmnigentAdapter` and a project can explicitly select the Omnigent driver behind the SPEC-019
  readiness gate.
- Gated to a **named follow-up** (not v1, because they are unverified or ADR-0004-central-but-large): moving
  the adapter into the **default composition** (gated on the live-acceptance run confirming the provisional
  shapes, and on substrate-exclusivity enforcement per ADR-0004 Decision 5), **roster projection onto
  Omnigent** (`materializeAgent`/`materializeCapabilities` — v1 uses Omnigent's pre-provisioned `agent_id`s),
  and the optional capabilities `getDiff`/`getTodos`/`runCommand`/`revert`/`unrevert` (Omnigent-endpoint-backed
  but additive). The adapter continues to declare only the capabilities it truly supports.

## Requirements

### Requirement: The normalizer matches the real Omnigent control-plane envelope
`capability: omnigent-substrate` · `delta: ADDED (feat/spec-037-omnigent-substrate)`

`normalize()` SHALL map the **actual** Omnigent 0.3.0 stream envelope — a flat frame `{ sequence_number,
type, … }` — onto Arke `DomainEvent`s, driven by a fixture of **live-captured** frames (not synthetic
OpenAI-Responses shapes). For the **control-plane** frames (live-confirmed) it SHALL map: `session.status`
(`running`/`idle`/`failed`) → `session.status` (a `failed` status maps to `session.status: error`); the
elicitation-request frame → `permission.asked`. It SHALL recognise and **ignore** the non-domain control
frames (`session.heartbeat`, `session.presence`, `session.changed_files.invalidated`,
`session.terminal_pending`) — returning no events, not dead-lettering them. A `response.error` frame SHALL map
to `session.status: error`; because `SessionStatusEvent` carries no error field today, the frame's
`error.code`/`error.message` SHALL be routed to the trace / dead-letter sink for diagnosis (NOT asserted onto
the event — adding an error field to the contract is an out-of-scope follow-up). A frame whose `type` is
neither mapped nor a known-ignored control frame SHALL be dead-lettered, never silently dropped. The
normalizer stays a **pure function** `(frame, state) → DomainEvent[]`.

#### Scenario: A live status frame maps to a session status
- **WHEN** the stream yields `{ type: "session.status", status: "idle", conversation_id }`
- **THEN** `normalize()` emits a `session.status` domain event for that session with an idle status
- **AND** a `{ type: "session.status", status: "failed", error }` frame maps to `session.status: error`, with the code/message routed to the trace/dead-letter (not onto the event)

#### Scenario: A heartbeat is ignored, an unknown frame is dead-lettered
- **WHEN** the stream yields a `session.heartbeat` (or `session.presence`) frame
- **THEN** `normalize()` returns no domain events and the frame is NOT recorded as unmappable
- **AND** WHEN a frame carries an unrecognised `type`, it is surfaced to the dead-letter sink, not dropped

### Requirement: The assistant-content mapping is grounded and confirmed against a live turn
`capability: omnigent-substrate` · `delta: ADDED (feat/spec-037-omnigent-substrate)`

The mapping of Omnigent's **assistant-content** frames to `message.part` (streaming delta) and
`message.updated` (snapshot) SHALL be implemented against a **live-captured successful turn** and pinned into
the frame fixture. Because the 0.3.0 assistant-content shape was **not** captured in this spec's probe (the
runner failed on an expired credential), the mapping is **PROVISIONAL** until the live-acceptance turn
(Requirement: live acceptance) confirms it: the implementation MAY start from the spike's prior
`item.content[]` capture, but the requirement is only **satisfied** when a real assistant turn's frames are
captured, the fixture updated, and the mapping asserted against them. No claim that the assistant mapping is
correct SHALL be made on the strength of the fake-transport suite alone.

#### Scenario: A captured assistant turn drives the mapping
- **WHEN** a live successful turn is captured and its assistant-content frames are added to the fixture
- **THEN** `normalize()` maps its streaming deltas to `message.part` and its final snapshot to `message.updated`, asserted against the captured frames
- **AND** until that capture exists, the mapping is marked provisional and does not gate the fake-transport suite as "confirmed"

### Requirement: A permission decision is confirmed by a stream event, not the HTTP ack
`capability: adapter-resilience` · `delta: ADDED (feat/spec-037-omnigent-substrate)`

`respondToPermission()` SHALL resolve the elicitation over HTTP (`POST …/elicitations/{id}/resolve`) and
then MUST return `confirmed` **only after** the event stream reflects the resolution for that elicitation id
(the 202 HTTP ack alone is NOT confirmation — only events are authoritative, SPEC-002). It SHALL return the
`PermissionAck.status` dispositions the contract already defines and the OpenCode `PermissionCoordinator`
already implements: `stale` for an unknown/already-resolved id, `duplicate` for a repeated decision on the
same id, and `unconfirmed` on a bounded timeout with no confirming event. A confirming event that arrives
after the timeout SHALL not throw (it is reconciled or ignored).

#### Scenario: A resolved elicitation confirms on the event
- **WHEN** `respondToPermission({ permissionId, decision: "once" })` posts the resolve and the stream then
  reflects that elicitation resolved
- **THEN** the call returns `status: "confirmed"`

#### Scenario: No confirming event within the bound
- **WHEN** the resolve is accepted (202) but no confirming event arrives within the timeout
- **THEN** the call returns `status: "unconfirmed"` (never a false `confirmed`), and a later confirming event does not throw

### Requirement: Outbound messages are correlated to their stream frames via the server-echoed item id
`capability: adapter-resilience` · `delta: ADDED (feat/spec-037-omnigent-substrate)`

`sendMessage()`/`dispatchAsync()` SHALL capture the `item_id` that `POST …/events` returns
(`{ queued: true, item_id }` — **live-confirmed** in this spec's probe) and use it as the turn's correlation
key, matched against the `session.input.consumed` frame whose `data.item_id` echoes it (**also
live-confirmed**). This replaces the spike's `pending_id` read, which the live server does not return. Every
`DomainEvent` the adapter emits for that turn SHALL carry a stable `correlationId` derived from this mapping
(a caller-supplied `correlationId` is preserved when given). If a future server build omits the echo, the
adapter SHALL fall back to best-effort correlation (a generated id) rather than fail.

#### Scenario: The consumed frame echoes the outbound item id
- **WHEN** `POST …/events` returns `item_id: X` and the stream later yields `session.input.consumed` with `data.item_id: X`
- **THEN** the adapter binds that turn's correlationId to `X` and stamps it on the turn's emitted events

### Requirement: The stream reconnects and re-syncs on disconnect
`capability: adapter-resilience` · `delta: ADDED (feat/spec-037-omnigent-substrate)`

The per-session stream pump SHALL detect a closed/errored SSE stream and **reconnect with bounded
exponential backoff** rather than dying silently (the spike stops on first error), then **re-sync missed
state via REST** — the proven `@arke/adapter-opencode` pattern (which resyncs rather than replaying, because
the stream is live-tail). Reconnect SHALL be bounded and, on exhaustion, surface a terminal degraded
`session.status` rather than hang. Re-sync SHALL NOT re-emit an already-delivered event (idempotent).

**Sequence-based gap-dedup is an optimisation, not a precondition.** The spike's `sse.ts` records the 0.3.0
stream as *"live-tail only (no replay, no sequence numbers)"* and the control-plane capture showed
`sequence_number: null`. Therefore the adapter SHALL NOT depend on `sequence_number` for correctness: it
SHALL use monotonic `sequence_number` for gap detection + dedup **only if** the live-acceptance run confirms
0.3.0 emits non-null monotonic sequences; otherwise reconnect falls back to a full REST re-sync (dedup by
item/message identity). Whether sequences are usable is a live-acceptance question, not an assumption.

#### Scenario: A dropped stream reconnects and re-syncs
- **WHEN** the SSE stream closes mid-session and later state exists
- **THEN** the pump reconnects with backoff and re-syncs the session's state via REST, resuming live streaming
- **AND** no event already delivered before the drop is emitted a second time

#### Scenario: Reconnect exhaustion is terminal, not a hang
- **WHEN** reconnection fails past the bounded attempt window
- **THEN** the adapter emits a terminal degraded `session.status` for the session and stops retrying (no silent hang)

### Requirement: Identity is durable, send is completion-aware, and the Omnigent version is pinned
`capability: harness-integration` · `delta: ADDED (feat/spec-037-omnigent-substrate)`

The adapter's session graph (Omnigent session id → Arke `{ specId, kind }`) SHALL be **durable** — persisted
via a file-backed store (adopting the OpenCode `FileSessionStore`) so an adapter/coordinator restart
re-attaches streams to their specs. `sendMessage()` SHALL be **completion-aware** — it resolves when the
turn reaches quiescence (`session.status: idle`/completion for that turn's correlationId, via a turn-waiter
like the Codex adapter), so a synchronous caller does not poll; `dispatchAsync()` stays fire-and-watch.
`init()` SHALL read the server version (`GET /api/version`) and validate it against the **pinned** Omnigent
version the adapter targets; on an incompatible version it SHALL surface a readiness warning/refusal (fail
loud) rather than proceed against a drifted alpha API. `listModels()` SHALL be provided best-effort from the
host's configured harnesses / model catalog, with the `models` capability declared only when it returns a
real catalog. Credentials remain **host-side** and never cross the adapter's return values (NFR-1, unchanged
from the spike's `OmnigentConfig` — the token is never returned or logged).

#### Scenario: A synchronous send waits for quiescence
- **WHEN** `sendMessage()` posts a turn
- **THEN** it resolves once that turn's `session.status` reaches idle/completion, not on the bare 202

#### Scenario: A version mismatch is surfaced, not swallowed
- **WHEN** `init()` finds the server's `/api/version` outside the adapter's pinned/supported range
- **THEN** readiness reports the mismatch (not `ready: true`), so the coordinator does not silently drive a drifted API

#### Scenario: Identity re-attaches after a restart
- **WHEN** the adapter is restarted while sessions are live
- **THEN** it re-loads each session's `{ specId, kind }` from the durable store and re-attaches its stream

### Requirement: The coordinator can construct and select the Omnigent adapter behind the readiness gate
`capability: harness-integration` · `delta: ADDED (feat/spec-037-omnigent-substrate)`

The coordinator SHALL be able to **construct an `OmnigentAdapter`** and a project SHALL be able to
**explicitly select the Omnigent driver** — the hard `driver !== "opencode"` connect rejection
(`server.ts` `connectHarness`) SHALL be lifted for an explicit Omnigent selection, routed through the same
SPEC-019 connect flow that verifies readiness before persisting (the readiness now including the version
check). This makes Omnigent a **runnable, registrable** driver. It SHALL NOT be added to the **default**
composition in v1: default-composition entry is gated on (a) the live-acceptance run confirming the
provisional shapes, and (b) **substrate-exclusivity** enforcement — a project selects **either** leaf
harnesses **or** Omnigent, never both (ADR-0004 Decision 5), which SHALL be enforced at registry load before
Omnigent may coexist with leaf adapters. v1 uses Omnigent's **pre-provisioned `agent_id`s** on
`createSession`; projecting Arke's own roster onto Omnigent (`materializeAgent`) is a named follow-up.

#### Scenario: An explicit Omnigent connect is gated on readiness
- **WHEN** a project explicitly selects the Omnigent driver and connects
- **THEN** the coordinator constructs an `OmnigentAdapter`, verifies readiness (reachable + compatible version), and persists only on success — the same gate as an OpenCode connect
- **AND** it is NOT silently added to the default composition alongside leaf adapters

## Design

### Architectural decision

Keep the spike's shape — a thin `HarnessAdapter` over Omnigent's v1 HTTP API with a pure `normalize()` and a
per-session SSE pump fanned into one `EventChannel` — and **harden the seams a live 0.3.0 run proved wrong or
missing**, rather than rewrite. Re-ground `normalize()` on the real control-plane envelope (live-captured,
frozen as a fixture); the resilience layer (confirmed approvals, correlation, reconnect+resync, durable
store, dead-letter, completion-aware send) is adopted from the **already-proven** patterns in
`@arke/adapter-opencode` (`PermissionCoordinator` with exactly the `confirmed/unconfirmed/stale/duplicate`
dispositions, `FileSessionStore`, reconnect/backoff + `resyncViaRest`, dead-letter) and
`@arke/adapter-codex` (`turnWaiters` completion-aware send, fake-transport tests). Note the **one genuinely
new** piece: OpenCode reconnect *full-resyncs* (no gap replay); Omnigent's `sequence_number` gap-dedup — if
0.3.0 supports it — is new, and is treated as an optimisation gated on the live run, not a reused guarantee.
Arke's authority is unchanged (ADR-0004): the roster stays harness-agnostic; the adapter only projects down
(`model_override`); credentials never leave the host.

### Target architecture

- **`packages/adapter-omnigent/src/normalize.ts`** — rewritten switch over the real control-plane `type`
  vocabulary (`session.status`, `response.error` → status:error with detail to trace, elicitation-request,
  known-ignored control frames), keyed off `{ sequence_number, type }`; assistant-content mapping provisional
  (Requirement 2). Still `(frame, state) → DomainEvent[]`. A committed fixture of **live-captured** frames
  (`test/fixtures/omnigent-0.3.0-frames.jsonl`) is the ground truth — control-plane frames now, assistant
  frames added at the live-acceptance run.
- **`packages/adapter-omnigent/src/index.ts`** — a `PermissionCoordinator`-style confirm-by-event for
  `respondToPermission()`; correlation map `itemId ↔ correlationId` (from the `POST …/events` response +
  `session.input.consumed`); `pump()` reconnect with bounded backoff + REST resync (idempotent; optional
  sequence-dedup); `TurnWaiters` for completion-aware `sendMessage()`; a `DeadLetterSink`.
- **`packages/adapter-omnigent/src/session-graph.ts`** — a file-backed `FileSessionStore` (adopting the
  OpenCode pattern) so identity survives a restart.
- **`packages/adapter-omnigent/src/config.ts`** — a pinned `OMNIGENT_TARGET_VERSION`; `init()` validates
  `/api/version`. **`http.ts`** unchanged in shape (Bearer host-side, abort timeout).
- **`packages/coordinator/src/server.ts`** — construct an `OmnigentAdapter` and lift the
  `driver !== "opencode"` rejection for an **explicit** Omnigent selection, through the existing SPEC-019
  connect/readiness gate. **Not** wired into the default composition; substrate-exclusivity enforcement and
  default-composition entry are the named follow-up gated on the live run.

### Interfaces and contracts

- `HarnessAdapter` is unchanged. Declared `capabilities()` stays `{ events, permissions }`, adding `models`
  iff `listModels()` returns a real catalog. `respondToPermission()` returns the existing
  `PermissionAck` (`status: confirmed|unconfirmed|stale|duplicate`, verified present in
  `contracts/src/adapter.ts`). No new `DomainEvent`/contract field is added (a `session.status` error-detail
  field is a deferred follow-up; error detail goes to the trace).
- The live-frame fixture is the interface-of-record for `normalize()`; changing it requires a re-capture.

### Cross-cutting

- **Security (NFR-1):** the Omnigent token stays in `OmnigentConfig` host-side, never returned or logged;
  model credentials live in the runner (the OpenCode `auth.json`), never on the Arke wire — unchanged.
- **Observability (SPEC-015):** the dead-letter sink, reconnect, version-mismatch, and `response.error`
  detail are traced.
- **Resilience parity (SPEC-002):** confirmed approvals, reconnect + resync, and correlation bring Omnigent
  to the OpenCode adapter's resilience contract.
- **Alpha risk:** the pinned version + fail-loud mismatch + live-frame fixture bound the alpha-churn risk
  ADR-0002 flagged; the spike Dockerfile's `uv tool install omnigent` is pinned to the target version.

### Definition of done
The control-plane `normalize()` matches live Omnigent 0.3.0 frames (fixture-backed); approvals are
event-confirmed; outbound messages correlate via the live-confirmed `item_id`; the pump reconnects + resyncs
without duplication; identity is durable; unmapped frames are dead-lettered; `sendMessage()` is
completion-aware; the version is pinned with a fail-loud mismatch; the adapter is constructable/registrable
behind the readiness gate; the fake-transport suite is green with `typecheck` + `build`; and a non-author
reviewer has signed off. **Entry into the default composition is explicitly withheld** until the
live-acceptance run confirms the three provisional wire facts (assistant-content shape, `item_id` echo — the
first two — and whether `sequence_number` is usable), and until substrate-exclusivity is enforced — both
named follow-ups, not part of this DoD.

## Open questions
- Is `sequence_number` non-null and monotonic on 0.3.0 stream frames? The control-plane capture showed
  `null`. Resolved at the live-acceptance run; until then reconnect uses full REST resync, not sequence-dedup.
- Does Omnigent 0.3.0 expose a resume-from-`sequence_number` on `…/stream`, or must resync read `…/items`
  history? v1: full REST resync; a resume parameter is an optimisation if present.
