# Harness & model registry and routing

> **⚠️ Reversed decision (2026-07-03, SPEC-021 sync).** This spec originally routed **role → logical
> tier → registry-resolved model → instance**. That indirection has been **retired**: adopting
> Omnigent's declarative structure 100%, **agents now declare their own model + provider** in their
> image `executor` block (SPEC-016 revised), and the coordinator dispatches that model directly. The
> `.arke/config.json` `registry.instances`/`serves`/`roster` tier machinery — and `RegistryResolver` /
> `SessionRouter` — are gone from the live path (see `docs/design/dead-code-removal.md`). The registry
> is now a store of **provider/auth profiles** (endpoints + host-side `credentialsRef`) plus the
> **agent roster** (each agent's declared model). The requirements below carry `MODIFIED` deltas
> reflecting this; the tier-based requirements are superseded. See
> `docs/design/omnigent-agent-yaml-adoption.md`.

## Why
The system must know **which harness endpoint** to talk to and **which model** each agent runs on, with
credentials living in exactly one host-side place — so an operator can change an agent's model, or
connect a harness, without leaking secrets to the client. *(Originally: resolve role → tier → model →
instance. Superseded — the agent declares its own model; SPEC-021 sync.)*

## What changes
- MODIFIED registry — the coordinator maintains a per-project registry of **provider/auth profiles**
  (harness endpoint + host-side `credentialsRef`) and the **agent roster** (each agent's declared
  `provider/model`); the client reads it as a live projection `{ harnesses, agents, warnings }` (FR-4, FR-19). *(Superseded the tier `instances`/`serves`/`roster` registry.)*
- MODIFIED model-resolution — resolution is per-agent and direct: `AgentRegistry.modelFor(agent)` returns
  the agent's declared `{ provider, name, options? }`, sent on `SendMessageInput.model` at dispatch.
  Reviewer independence is enforced from the reviewers' **declared models** (pairwise-distinct,
  provider-qualified). *(Superseded the `ModelSelection {instanceId, tier, model}` resolver.)*
- MODIFIED routing — a project context talks to its **one connected harness**; the agent's declared
  model rides each dispatch. *(Superseded multi-instance tier routing / `SessionRouter`.)*
- ADDED model-discovery — a `models` capability and `listModels()` on `HarnessAdapter` let the coordinator
  read the **live model catalog** the connected harness serves; it powers the agent-model editor (SPEC-021)
  and roster display. *(Retained; catalog validation of a per-agent model is a SPEC-021 concern.)*
- MODIFIED opencode-integration — `OpenCodeAdapter` sends the agent's declared model on the message body
  (`body.model = { providerID, modelID, options }`); no injected tier `resolveModel`. (breaking: no)

> **Model stance (reversed here; SPEC-021 sync).** The **agent declares its own concrete model +
> provider** in its committed image `executor` block. The model id is **public** and lives in the image;
> only credentials are host-side (referenced by `executor.config.auth.profile`, never inlined — NFR-1).
> This replaces the original logical-tier indirection (a role referenced a tier; an instance's `serves`
> bound the tier to a model). Arke thereby aligns with Omnigent's per-agent-model model rather than
> diverging from it.
>
> **Substrate exclusivity & agent authority (per [ADR-0004](../decisions/0004-agent-model-vs-omnigent-and-the-substrate-mapping.md)).** A meta-harness substrate (Omnigent) is mutually exclusive per project with leaf harnesses — a project's registry is *either* leaf provider profiles *or* an Omnigent substrate, never both. On every substrate the agent roster remains authored in Arke; selecting a substrate does not disable agent creation. SPEC-016 (agent images) is the authority for the agent's model+provider.

## Requirements

### Requirement: Maintain a registry of provider profiles and the agent roster
`capability: registry` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

The system SHALL maintain, per project context, a registry of **provider/auth profiles** and the
**agent roster**. Each provider profile SHALL record a stable name, the harness kind, an endpoint
(host/port/baseUrl), and a host-side `credentialsRef`. The roster is the project's agent images, each
declaring its own `provider/model` (SPEC-016 executor). The **`credentialsRef` string itself SHALL NOT
appear** in any WebSocket frame, snapshot, event, or log entry visible to the client. **Model ids are
public** and MAY appear in the roster projection and the agent images; only credentials are host-side.
*(Superseded the tier `instances`/`serves`/`roster` registry — vendor model ids are no longer secret,
because the agent, not a hidden tier binding, declares the model.)*

#### Scenario: Registry loaded from config + agent images
- **WHEN** a project opens with `.arke/config.json` (provider profiles) and `agents/<name>/config.yaml` images present
- **THEN** the registry carries each provider profile (name, harness, endpoint, host-only credentialsRef) and each agent's declared model
- **AND** the connected harness's capability flags come from the SPEC-002 startup probe, not static config

#### Scenario: `credentialsRef` absent from all client-facing surfaces
- **WHEN** a client connects and receives the coordinator snapshot or any `registry.updated` event
- **THEN** no `credentialsRef` value, no Basic-auth token, no API key, and no credential path or naming string appears in the payload
- **AND** the agent roster in the projection carries each agent's public `provider/model` (a model id is not a secret)

### Requirement: Discover the model catalog a harness instance serves
`capability: model-discovery` · `delta: ADDED (feat/harness-and-model-registry)`

The system SHALL be able to read the **live model catalog** an instance actually serves, so the registry validates against the harness's real surface rather than against operator assumptions. A harness adapter SHALL advertise a `models` capability when its backend exposes a model catalog, and SHALL implement `listModels(): Promise<ModelInfo[]>` returning `{ id, provider, displayName? }` for each model the connected backend can serve. The capability SHALL be derived from the SPEC-002 startup probe (the catalog endpoint's presence), not from static config. An adapter whose backend exposes no catalog SHALL omit the `models` capability and MAY omit `listModels`; the registry then falls back to trusting the configured `serves` verbatim and SHALL record that the catalog was unavailable. A `ModelInfo` value SHALL carry only public catalog metadata — never a credential, an endpoint secret, or a host path.

The catalog source per substrate: OpenCode → its providers/models endpoint; Claude Code → the Anthropic model catalog; an Omnigent substrate → its model-listing surface aggregated across the harnesses that substrate drives ([ADR-0004](../decisions/0004-agent-model-vs-omnigent-and-the-substrate-mapping.md)). The catalog is read on demand (project-open, `registry.probe`, and config reload), never cached past a reload.

#### Scenario: Adapter advertises `models` when the backend exposes a catalog
- **WHEN** an instance responds to the SPEC-002 startup probe and its backend exposes a model-catalog endpoint
- **THEN** the registry entry for that instance includes the `models` capability flag
- **AND** `listModels()` returns one `ModelInfo {id, provider, displayName?}` per model the backend can serve

#### Scenario: Backend without a catalog degrades, not fails
- **WHEN** an instance's backend exposes no model-catalog endpoint
- **THEN** the `models` capability is absent and the registry does not call `listModels()`
- **AND** the configured `serves` models are trusted verbatim and a `catalogUnavailable: true` note is recorded for that instance (no warning is raised solely for the missing catalog)

#### Scenario: `ModelInfo` carries no secrets
- **WHEN** a client receives any registry projection derived from `listModels()`
- **THEN** each model entry carries only `id`, `provider`, and an optional `displayName` — no credential, endpoint secret, or host path

### Requirement: Validate configured `serves` against the live catalog
`capability: model-discovery` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

> **⚠️ Superseded (SPEC-021 sync).** There are no tier `serves` to validate — agents declare their own
> model. Validating a **declared agent model** against the live `listModels()` catalog (to catch a typo
> before dispatch) is a live, useful idea but is now scoped to **SPEC-021** (its `HarnessCapabilities` /
> materialisation design). The `listModels()` catalog itself is retained (it powers the SPEC-021 agent-model
> editor). The original tier-`serves` validation and `model-not-in-catalog` blocking below are historical.

When an instance advertises the `models` capability, the system SHALL validate every `serves[].model` for that instance against the catalog returned by `listModels()` at registry load and on every reload. A configured model absent from the live catalog SHALL be treated as a configuration error: the coordinator SHALL emit a `registry.warning` event with `reason: 'model-not-in-catalog'` and a `detail` naming the instance, the tier, and the offending model **label** (never a leaked vendor id beyond what the operator already wrote), and SHALL block routing for that instance's affected tier until the config is corrected — exactly as the reviewer-distinct check blocks routing. Validation SHALL be skipped (not failed) for instances without the `models` capability. The validation result feeds an **assisted setup** affordance: the configuration screen surfaces the catalog as the allowed set so an operator edits `serves` toward a valid model rather than guessing.

#### Scenario: Configured model present in the catalog passes
- **WHEN** the registry loads and every `serves[].model` for a `models`-capable instance appears in that instance's `listModels()` result
- **THEN** validation passes and routing is permitted for that instance

#### Scenario: Configured model absent from the catalog blocks routing for that tier
- **WHEN** a `serves[].model` for a `models`-capable instance is not present in its live catalog
- **THEN** the coordinator emits `registry.warning` with `reason: 'model-not-in-catalog'` naming the instance, tier, and offending model
- **AND** routing for that instance's affected tier is blocked until the config is corrected and reloaded cleanly
- **AND** instances/tiers not affected by the bad entry continue to route

#### Scenario: Validation skipped for a catalog-less instance
- **WHEN** an instance does not advertise the `models` capability
- **THEN** no catalog validation runs for it and its `serves` are trusted verbatim
- **AND** no `model-not-in-catalog` warning is raised for that instance

### Requirement: Resolve an agent to its declared model — directly
`capability: model-resolution` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

The system SHALL resolve the model an agent runs on **directly from the agent's own image**:
`AgentRegistry.modelFor(name)` returns the agent's declared `{ provider, name, options? }`, parsed from
`executor.config.model` (+ `options`). That value is sent on `SendMessageInput.model` at dispatch. An
agent that declares no model (or a bare/`gateway` sentinel) yields no override — the harness uses the
agent's own materialised/default model. There is no logical-tier lookup, no `ModelSelection`, and no
cross-instance selection. *(Superseded the tier resolver; `RegistryResolver`/`SessionRouter` were
deleted — see `docs/design/dead-code-removal.md`.)*

#### Scenario: An agent resolves to its own declared model
- **WHEN** `modelFor('implementer')` is called and the implementer image declares `github-copilot/gpt-5.5` with `options.reasoningEffort: xhigh`
- **THEN** it returns `{ provider: 'github-copilot', name: 'gpt-5.5', options: { reasoningEffort: 'xhigh' } }`
- **AND** that model is sent on the dispatch so the harness runs gpt-5.5 at xhigh

#### Scenario: An agent with no declared model uses the harness default
- **WHEN** `modelFor('x')` is called for an agent that declares no model (or a `gateway/…` sentinel)
- **THEN** it returns undefined
- **AND** the dispatch omits `model`, so the harness uses the agent's own materialised/default model

### Requirement: reviewer-a and reviewer-b declare distinct, concrete models
`capability: model-resolution` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

The system SHALL enforce review independence (SPEC-007) directly from the reviewer **agents' declared
models**: at least two reviewers, each agent image pinning a concrete, provider-qualified model, and
every pair distinct. `validateReviewers` compares the declared `executor.config.model` strings; a bare
name or a `gateway/…` sentinel is **not** concrete (both would fall to the harness default) and is
rejected. On any failure the review is refused with a `panel.config-error` and the projection carries a
`reviewer-models-identical` warning. *(Superseded the instance/tier-based check — reviewers no longer
pin instances; the agent IS the model.)*

#### Scenario: Reviewers declaring different models validate
- **WHEN** reviewer-a declares `github-copilot/claude-opus-4.8` and reviewer-b declares `github-copilot/claude-sonnet-4.5`
- **THEN** `validateReviewers` passes and the two model strings are not equal

#### Scenario: Same or non-concrete reviewer models are rejected
- **WHEN** both reviewers declare the same model, OR either declares a bare name / `gateway/…` sentinel
- **THEN** `validateReviewers` fails with a reason
- **AND** the panel is refused with `panel.config-error` and the snapshot carries a `reviewer-models-identical` warning

### Requirement: Credentials resolved on the host, never sent to the client
`capability: registry` · `delta: ADDED (feat/harness-and-model-registry)`

The system SHALL resolve credentials references (`credentialsRef`) on the coordinator host at session-create time and SHALL NOT include any credential value, nor the `credentialsRef` string itself, in any WebSocket frame, snapshot, or event pushed to the client. The client SHALL receive only instance identifiers, driver names, capability flags, and tier labels. The `file:` backend of `CredentialResolver` SHALL canonicalise the file path and restrict it to a configured safe root, rejecting paths that traverse outside it.

#### Scenario: Snapshot contains no credentials or refs
- **WHEN** a client connects and receives the coordinator snapshot
- **THEN** the snapshot includes the instance list with id, driver, host, caps, and tier labels
- **AND** no `credentialsRef` value, no Basic-auth token, no API key, and no credential naming string appears in the payload

#### Scenario: Adapter receives resolved credentials at session create
- **WHEN** the coordinator creates a session on a harness instance
- **THEN** it reads the credential from the host environment (env var, secrets file, or OS keychain) using the `credentialsRef` key
- **AND** passes it to the adapter constructor; the credential never leaves the coordinator process

#### Scenario: `file:` credential backend path validated
- **WHEN** a `credentialsRef` of the form `file:../../etc/passwd` is encountered
- **THEN** the `CredentialResolver` rejects it with a `CredentialPathError` before reading the file
- **AND** no file content is returned or logged

### Requirement: Route sessions by model, not harness mode
`capability: routing` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

> **⚠️ Superseded (SPEC-021 sync).** A project context now talks to its **one connected harness**; the
> agent's declared model rides each dispatch (`SendMessageInput.model`). There is no `ModelSelection`,
> no `SessionRouter`, and no cross-instance model routing (those were deleted — see
> `docs/design/dead-code-removal.md`). Multi-harness-per-context routing may return as a future spec,
> but is not the current contract. The historical text below describes the retired tier routing.

The system SHALL route every session to the harness instance that serves the required model, derived from tier resolution. No caller SHALL specify a harness instance directly; routing is always a consequence of the resolved `ModelSelection`. Sessions from multiple instances SHALL be aggregated on one delivery board.

#### Scenario: Session routed to the instance serving the model
- **WHEN** the coordinator creates a session for a role whose resolver returns `{ instanceId: 'opencode-local', tier: 'mid', model: 'gateway/mid-tier' }`
- **THEN** the session is opened on the adapter whose id is `opencode-local`
- **AND** the `SendMessageInput` carries `tier: 'mid'` and the adapter's `resolveModel` returns the configured concrete model

#### Scenario: Multi-harness board aggregates sessions
- **WHEN** two instances are registered — one for `capable` sessions and one for `mid` sessions — and both have active sessions
- **THEN** the delivery board shows cards from both instances under a common project view
- **AND** each card's `harness` field identifies its originating instance

#### Scenario: `resolveModel` closure is scoped to a single tier — mismatch is an error, not a guess
- **WHEN** the injected `resolveModel` closure (which captures a single `ModelSelection`) is called with a tier other than the one it was created for
- **THEN** it throws a typed `TierMismatchError` naming the expected and actual tiers
- **AND** no model is returned for the mismatched tier; the caller must obtain a new `ModelSelection` for a different tier via the registry

### Requirement: Instance unreachable mid-session — explicit failover or failure
`capability: routing` · `delta: ADDED (feat/harness-and-model-registry)`

When a registered harness instance becomes unreachable after sessions have been started on it, the coordinator SHALL mark the instance `reachable: false` in the snapshot and emit a `harness.reachability` event. If another instance serves the same tier, the coordinator SHALL route new sessions to the fallback and emit a `registry.warning` event with `reason: 'instance-failover'` identifying both the failed and fallback instances. In-flight sessions on the failed instance SHALL NOT be silently migrated; they SHALL be marked as `interrupted` and the client SHALL surface an explicit "Instance lost — session interrupted" state for each affected session.

#### Scenario: Instance lost, fallback available — new sessions rerouted
- **WHEN** a registered instance becomes unreachable and another instance serves the same tier
- **THEN** the coordinator marks the failed instance `reachable: false` and emits `harness.reachability` with the reason
- **AND** a `registry.warning` event is emitted with `reason: 'instance-failover'`, naming the failed and fallback instances
- **AND** new sessions for that tier are routed to the fallback instance

#### Scenario: Instance lost, no fallback — routing fails with clear error
- **WHEN** a registered instance becomes unreachable and no other instance serves the same tier
- **THEN** the coordinator emits a `registry.warning` event with `reason: 'no-instance-for-tier'`
- **AND** new sessions for that tier are refused with a `NoInstanceForTierError`
- **AND** the client renders an error state for the affected role

#### Scenario: In-flight sessions on the failed instance marked interrupted
- **WHEN** an instance becomes unreachable while sessions are running on it
- **THEN** each affected session is marked `interrupted` in the read model
- **AND** the client surfaces "Instance lost — session interrupted" for each affected card
- **AND** no automatic migration of in-flight sessions occurs

### Requirement: Harness & agent-roster screen shows the live registry
`capability: registry` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

The system SHALL present a screen showing the live **harness endpoints** (id, harness kind, endpoint,
reachability, capability flags) and the **agent roster** (each agent's name, harness, and declared
`provider/model` + reasoning effort). The screen SHALL reflect the live coordinator projection
`{ harnesses, agents, warnings }`, not a static client-side seed. It SHALL NOT display `credentialsRef`
values. The model id **is** shown (it is public; the operator authored it) so an operator can verify
which agent runs on which model — and, per SPEC-021, edit it. *(Superseded the tier-label-only "Model
tiering" table; there are no tiers.)*

#### Scenario: Screen reflects live harness + roster data
- **WHEN** the engineer opens the harnesses/agents screen
- **THEN** each harness endpoint is shown with reachability + caps, and each agent with its declared `provider/model`
- **AND** the data matches the coordinator's current snapshot
- **AND** no `credentialsRef` value appears anywhere in the rendered screen

#### Scenario: An agent's model is editable from the client (SPEC-021)
- **WHEN** the engineer edits an agent's model
- **THEN** the change is written to the agent's `config.yaml` on the host and the roster refreshes
- **AND** no credential value is captured in the client (an MCP secret is a `${VAR}`/profile reference)

## Design

> **⚠️ Design superseded in large part (SPEC-021 sync).** The code blocks below (`RegistryResolver`,
> `ModelSelection`, `SessionRouter`, the `instances`/`serves`/`roster` config, the `registry.updated`
> tier serves) describe the **retired** tier machinery and are kept for lineage only. The **current**
> design: `.arke/config.json` holds a `providers` map (host-side provider/auth profiles); the
> coordinator's **`AgentRegistry`** (`packages/coordinator/src/agent-registry.ts`) indexes agent images
> and answers `modelFor(agent)` → `AgentModel`; dispatch sends it on `SendMessageInput.model`; the
> projection is `{ harnesses, agents, warnings }`. See `docs/design/omnigent-agent-yaml-adoption.md`
> and `docs/design/dead-code-removal.md`. Read the requirements above for the current contract.

### Architectural decision
The registry is a **per-project-context** component (SPEC-018) — not a coordinator-side singleton — loaded from that project's config file on the host when the project is opened, and released on close/evict. It is the only place vendor model identifiers live, accessed only by that context's `RegistryResolver`; two open projects have two independent registries with no shared model/credential state. The client receives a projection of registry state — instance IDs, capabilities, tier labels, reachability — but never raw credentials, credential ref strings, or raw model IDs. Instance capabilities are derived from the SPEC-002 startup probe, not from static config, so the registry reflects the server's real surface. This mirrors the resolution mechanism described in `docs/agent-roster-and-model-resolution.md §2` and satisfies NFR-1 (credentials on host) and the agent roster's portability principle.

### Target architecture

```
Client (Harnesses screen / Settings)
  ↕ WebSocket snapshot + registry.updated events
Coordinator
  ├── RegistryLoader          — loads .arke/config.json at project-open time (per ProjectContext, not coordinator startup); watches for file changes with debounce; blocks routing during reload until assertReviewersDistinct AND catalog validation pass
  ├── RegistryResolver        — resolve(role) → ModelSelection (deterministic config order); assertReviewersDistinct(); validateServesAgainstCatalog(catalog); listInstances() (no credentials)
  ├── CredentialResolver      — env:/file:/keychain: backends; file: paths canonicalised + safe-root restricted
  ├── SessionRouter           — maps ModelSelection → adapter instance; opens session; handles failover + interrupted marking
  └── HarnessAdapters[]       — one per registered instance (OpenCodeAdapter, …); capabilities + model catalog (listModels) from SPEC-002 probe
       ↕ HTTP / SSE (per instance)
Harness hosts (opencode serve, claude-code serve, …)
```

> **Per-project scoping (SPEC-018):** `RegistryLoader` and `RegistryResolver` are **not** coordinator singletons — they live inside each `ProjectContext` alongside its `ReadModel`, `Trace`, and stores. A `ProjectContext` instantiates them when its project is **opened** (loading that project's `.arke/config.json`) and releases them on close/evict. The boxes above describe one project context's slice, not a process-wide registry.

**New coordinator module** (`packages/coordinator/src/registry.ts`):

```typescript
  serves: { tier: ModelTier; model: string }[];

  tier: ModelTier;
  model: string;                    // concrete provider/model string for the adapter; never sent to client

  // Deterministic: returns first matching instance in config order; prefer host/cwd match as tie-breaker
  resolve(role: string): ModelSelection { /* … */ }

```

### Configuration model
`.arke/config.json` at the repo root is — **per project** (SPEC-018) — the **single source of that project's context-local configuration**: within a project context that file is the single source for THAT project, and N open projects have N config files (one per root). It carries the
harness/model `registry` (instances + roster bindings, below) and `integrations` config — the
context-local settings.

**Process-wide settings are NOT per project (SPEC-018).** A single coordinator cannot run on
multiple WebSocket ports or apply two different concurrency caps, so genuinely process-wide
settings — the coordinator `port`, the `maxProjects` concurrency cap, the project idle-TTL, the
`OTLP endpoint`, and global query limits — come from a **global/launch-time source** (`ARKE_*`
environment / a global config under `ARKE_HOME`), NOT from any one project's `.arke/config.json`.
A `settings` block in a per-project config is advisory for that context (e.g. its permission
timeout) and MUST NOT set process-wide values; the launch-time source wins. Individual keys MAY
be overridden by `ARKE_*` environment variables (env wins; `ARKE_*` are overrides, not
the source of truth). Runtime artefacts under `.arke/` — `trace.ndjson`, `sessions.ndjson`,
`scaffold-manifest.json`, `projection-fallback.ndjson` — are local **state, not configuration**,
and are git-ignored; `.arke/config.json` is the one tracked file there. Vendor model ids live
only in this file, behind the internal gateway, never in the client.

**Config file shape** — the `registry` and `roster` sections of `.arke/config.json` (shown here
as YAML for readability; the file itself is JSON):

```yaml
instances:
  - id: claude-local
    driver: claude-code
    host: localhost
    cwd: .
    credentialsRef: claude-code/default
    serves:
      - { tier: capable, model: <claude-capable-model> }

  - id: opencode-local
    driver: opencode
    host: localhost
    cwd: .
    credentialsRef: opencode/gateway
    serves:
      - { tier: capable, model: <other-capable-model> }
      - { tier: mid,     model: <mid-model> }

roster:
  spec-author:  { tier: capable }
  architect:    { tier: capable }
  reviewer-a:   { tier: capable, instance: claude-local }
  reviewer-b:   { tier: capable, instance: opencode-local }
  implementer:  { tier: mid }
  researcher:   { tier: mid }
```

This is the identical YAML shape documented in `docs/agent-roster-and-model-resolution.md §2`; the spec makes it the authoritative source and the coordinator's `RegistryLoader` the sole consumer.

**`ModelTier`** is imported from `@arke/contracts/src/spec.ts`: `z.enum(['capable', 'mid', 'fast'])` — three logical tiers (capable = authoring/review, mid = implementation, fast = routine/classification & projection drafts). A registry instance's `serves` maps each tier to a concrete model; an unmapped tier falls back to the gateway default for that tier.

**New domain events** (additions to `@arke/contracts/src/events.ts`):

```typescript
export const RegistryUpdatedEvent = base.extend({

  instances: z.array(z.object({
    id: z.string(),
    driver: z.string(),
    endpoint: z.string(),
    reachable: z.boolean(),

});

export const RegistryWarningEvent = base.extend({
  type: z.literal('registry.warning'),
  reason: z.enum([
    'reviewer-models-identical',
    'no-instance-for-tier',
    'credential-missing',
    'instance-failover',
    'model-not-in-catalog',   // a configured serves[].model is absent from the instance's live catalog
  ]),
  detail: z.string().optional(),    // human-readable; never contains credential values or vendor model IDs
});
```

```typescript
  }
```

The adapter's `resolveModel` closure is injected from `InstanceConfig.serves` for the single resolved tier; it throws `TierMismatchError` if called for any other tier. A sub-session requiring a different tier must go back through `RegistryResolver` for a new `ModelSelection`.

**RegistryLoader debounce:** file-watch events are debounced by 200 ms before triggering a reload. During reload, `routingEnabled` is set to `false`; it is restored to `true` only after `assertReviewersDistinct()` passes. Sessions in flight are not interrupted by a reload; only new routing requests are held.

### Data model
No database. The registry is loaded from a config file on the coordinator host. The in-memory `RegistryResolver` is the runtime authority. Credential values are read from host environment variables or a secrets file at session-create time and held in memory only for the duration of the request.

**Resolution rule** (from `docs/agent-roster-and-model-resolution.md §2`, made normative here):

```
resolve(role):
  entry = roster[role]                     // { tier, instance? }
  if entry.instance:
    inst = instances[entry.instance]
    model = inst.serves.find(s => s.tier === entry.tier).model
    return { instanceId: inst.id, tier: entry.tier, model }
  else:
    // deterministic: config order; host/cwd match preferred as tie-breaker
    inst = instances.find(i => i.serves.some(s => s.tier === entry.tier))
          ?? throw NoInstanceForTierError(role, entry.tier)
    model = inst.serves.find(s => s.tier === entry.tier).model
    return { instanceId: inst.id, tier: entry.tier, model }
```

### Cross-cutting
- **Multi-project scoping (SPEC-018):** the coordinator supervises N isolated **project contexts**, each keyed by `projectId` with its own root, harness runner, read model, trace, and durable stores under its own `.arke/`. Everything this spec places on "the coordinator" — `RegistryLoader`, `RegistryResolver`, `SessionRouter`, and the per-instance adapters — is per–project context, loading that project's `.arke/config.json` at project-open time; each client connection resolves against its **active project**. See [SPEC-018](018.multi-project-workspaces.md).
- **Configuration:** context-local configuration — the harness/model registry and integrations — lives per project in that project's `.arke/config.json`, loaded when the project is opened (SPEC-018). Process-wide settings (coordinator port, `maxProjects`, idle-TTL, OTLP endpoint, global query limits) come from a global/launch-time source (`ARKE_*` env / a global config under `ARKE_HOME`), never from a single project's file. `ARKE_*` env vars override individual keys; runtime artefacts under `.arke/` are state, not config.
- **Design template:** the UI in this feature follows the `arke-design` skill (`.claude/skills/arke-design/`) — the shadcn neutral token contract, Geist typography, Lucide icons, and the prototype screens (`app/*.jsx`); see [SKILL.md](../../.claude/skills/arke-design/SKILL.md). Do not re-derive styling.
- **Security (NFR-1):** `credentialsRef` values AND the ref strings themselves are resolved and used only inside the coordinator host. The `CredentialResolver` `file:` backend canonicalises paths and restricts them to a configured safe root, rejecting traversal. The client snapshot and all events contain tier labels only; no credential value, no ref string, and no raw model string is ever sent to the client.
- **Observability (NFR-7):** Every `resolve(role)` call is written to the trace with `{ role, instanceId, tier, model: '<label>' }` — the human-readable tier label is logged for audit; the vendor model string is not included in the trace entry.
- **Resilience (NFR-4):** If a registered instance becomes unreachable mid-session, the coordinator marks it `reachable: false`, emits `harness.reachability`, and routes new sessions to a fallback if one exists. In-flight sessions are marked `interrupted`; they are not silently migrated. The reviewer-distinct check blocks routing on a bad reload until the config is corrected; sessions in flight are unaffected. `RegistryLoader` debounces file-watch events by 200 ms to prevent reload storms.
- **SPEC-002 alignment:** Instance capabilities in the registry are derived from the SPEC-002 startup capability probe, not from static config. The `resolveModel` injected into `OpenCodeAdapter` comes from `SessionRouter`, which derives it from the registry (connects SPEC-002 and SPEC-005).

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | YAML config file on the host, not a UI-editable database | Vendor model IDs must stay on the host behind the gateway; config-as-code fits git-backed audit trail |
| 2 | Resolution rule is a coordinator-side function, not client-side | Keeps model IDs off the wire and ensures the same rule governs every session regardless of which client connected |
| 3 | `resolveModel` injected into adapters by `SessionRouter`, not hard-coded in adapter | Adapters stay harness-adapter–interface-compliant; the registry is the single source of model truth |
| 4 | Reviewer-distinct rule enforced at startup and on reload; routing blocked during reload window | A misconfigured registry that silently produces same-model reviews undermines independence; blocking new sessions during reload prevents a race where the bad config briefly wins |
| 5 | Client `Harnesses` screen driven by snapshot projection, not a static seed | The design-baseline seed (`HARNESSES`, `TIERS` in store.ts) was a placeholder; live data is required by FR-19 |
| 6 | Capabilities derived from SPEC-002 startup probe, not static config | The server's real surface governs what is advertised; static config can drift from reality |
| 7 | `credentialsRef` string itself excluded from all client-facing payloads | Even the ref string leaks the naming convention for credentials; only ids, labels, and caps reach the client |
| 8 | Resolution order is deterministic (config order; host/cwd tie-breaker) | Non-deterministic "any instance" resolution is untestable and produces inconsistent session assignment; deterministic order is auditable |
| 9 | In-flight sessions marked `interrupted` on instance loss; no auto-migration | Silent migration would change the session's effective model without the engineer's knowledge; explicit `interrupted` state is honest and recoverable |
| 10 | `resolveModel` closure scoped to one tier; throws `TierMismatchError` for others | Prevents a sub-session from silently resolving to the wrong model by using a parent session's closure; sub-sessions must get their own `ModelSelection` |
| 11 | `CredentialResolver` `file:` backend restricted to safe root | A `credentialsRef: file:../../etc/passwd` in a compromised config could read arbitrary files; safe-root restriction contains the blast radius |
| 12 | ~~The logical tier is the only model knob; never pin a vendor model to a role (ADR-0004)~~ **REVERSED (16, SPEC-021 sync)** | Kept agents harness-agnostic via tier indirection — but the indirection had no user, added a whole registry/resolver layer, and diverged from Omnigent for no benefit. See #16. |
| 16 | **The agent declares its own concrete model + provider** in its image `executor` (reverses #12; SPEC-021 sync) | Adopting Omnigent's declarative structure 100% makes the image self-contained and portable; the model id is public so it lives in the image (only credentials are host-side, NFR-1); dispatch sends the declared model directly. The tier registry/resolver/router were deleted (`docs/design/dead-code-removal.md`). |
| 17 | The registry is a store of **provider/auth profiles** + the **agent roster**, not tier `instances`/`serves`/`roster` | With the model on the agent, `.arke/config.json` only needs the harness endpoint + a host-side `credentialsRef`; the roster's models come from the agent images. |
| 13 | Validate `serves` against the live catalog from `listModels()`; block the affected tier on a miss (ADR-0004 catalog discovery) | A typo'd or unsupported model otherwise fails only at first dispatch, mid-run; catalog validation fails fast at load and powers assisted setup. Catalog-less backends degrade (trust `serves`) rather than block. |
| 14 | Substrate exclusivity: a meta-harness substrate (Omnigent) is per-project mutually exclusive with leaf harnesses (ADR-0004) | A substrate sits at the same layer as Arke's own; mixing it with leaf instances duplicates the routing decision. The picker treats a substrate as a different kind of choice. |
| 15 | Agent authority stays Arke on every substrate; selecting a substrate does not disable agent creation or hand model choice to it (ADR-0004) | The roster + tiers are Arke's portable abstraction; `listModels()` reads the substrate's catalog to resolve tiers. Deferring authorship to the substrate would forfeit portability. |
