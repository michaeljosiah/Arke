# Governed delivery loop — verify-and-iterate delivery, bounded by a budget and a human boundary

## Why

Delivery today ([SPEC-028](028.single-session-delivery.md)) completes on a **self-reported checklist**: the implementer ticks every `- [x]` and the coordinator calls it `done`. That is precisely the failure the loop literature warns about — *the model that did the work is far too generous a grader*. There is no independent gate between "the agent says it's finished" and "the card surfaces for human review." A delivery loop closes that seam: it keeps iterating an implementer against an **independent verify gate** (the spec's own acceptance criteria — its requirements' scenarios — checked by a provably-distinct agent) until the work actually passes or a **budget** stops it — turning single-pass delivery into `execute → verify → iterate`, without ever letting the loop grade its own homework or bill in silence.

Arke is unusually well-placed to do this safely, because a loop's one scarce ingredient — a real, reviewed, durable verify gate — is exactly what Arke already manufactures (the reviewed spec), and the verifier itself already exists as [SPEC-039](039.conformance-sentinel.md)'s two-tier check. SPEC-039 uses that check to catch drift **after** delivery; this spec uses the **same** check as the gate **during** delivery.

## What changes

- ADDED delivery-loop — a delivery runs as a bounded loop with **first-class stop conditions and a budget** (max iterations, token budget, wall-clock); no delivery may run unbounded, and every halt reason is traced.
- MODIFIED single-session-delivery — completion requires the checklist to be ticked **and** an **independent verify pass**; a self-reported checklist alone no longer marks a delivery `done`.  *(breaking: the completion oracle's terminal condition changes.)*
- ADDED delivery-loop — a failed verify **feeds the failing criteria back** into the same session as the next iteration, and the loop learns (prior failures accrue in context) rather than restarting from zero.
- ADDED delivery-loop — an exhausted budget **halts and reports** into the rescue path ([SPEC-011](011.session-detail-and-rescue.md)); a loop never claims success it did not verify, and never keeps spending after a stop condition.
- ADDED delivery-loop — the loop is **bounded to the worktree**; a verified delivery produces a diff for human review, never an automatic merge / PR / system-of-record write.
- ADDED delivery-loop — **cost per accepted change** is recorded and surfaced ([SPEC-015](015.audit-trace-and-observability.md)), with an ADDED `delivery.reject` signal so discarded candidates count in the denominator; a loop that costs more than it returns is visible.
- MODIFIED auto-pr ([SPEC-031](031.auto-pr-configuration.md)) — when the loop is active, the implementer's standing auto-PR instruction is omitted and the PR opens only **after** the verify gate passes.  *(breaking: the checklist-complete auto-PR trigger moves to the verified boundary.)*

**Depends on:** SPEC-028 (single-session delivery — the loop extends its dispatch/oracle), SPEC-039 (conformance check — reused as the verify gate), SPEC-007 (provable model distinctness — maker ≠ checker), SPEC-005 (registry — agent-image model declarations; the tier resolver is removed), SPEC-011 (rescue & steering — the halt path), SPEC-015 (trace & observability), SPEC-024 (propose·decide·execute — the human boundary), SPEC-019 (config merge — budgets).

## Requirements

### Requirement: Every delivery loop is bounded by explicit stop conditions and a budget
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

A delivery loop SHALL carry a bounded budget with three dimensions — a **maximum iteration count**, a **token budget**, and a **wall-clock cap** — resolved from project configuration (extending the **existing** `delivery` config block, [SPEC-031](031.auto-pr-configuration.md)/[SPEC-019](019.global-and-project-config-merge.md)) with an optional per-spec override in a `delivery:` frontmatter block. Two of the three dimensions require **plumbing this spec ADDS**: no token/usage accounting exists at any layer today (no usage field on any domain event; neither adapter extracts one), and no per-session wall-clock exists (only op-scoped timeouts). Token accounting SHALL be added as optional usage fields on the turn-settling events, extracted by adapters and accumulated by the coordinator, **capability-flagged**: on a harness that cannot report usage the token dimension is inactive and surfaced as such, while the other dimensions still enforce — the "never unbounded" guarantee rests on the **iteration cap**, the one dimension enforceable today. The wall-clock is coordinator bookkeeping (dispatch timestamp vs. now), checked at turn boundaries **and enforced by an active watchdog**: a hung harness turn may never emit its settling event, so when the cap expires mid-turn the coordinator SHALL stop the loop anyway — mark the delivery needs-rescue, dispatch no further iterations, and, where the adapter exposes a turn-abort capability (capability-flagged; neither adapter is verified to expose one today), cancel the running turn. On an adapter **without** turn-abort, the wall-clock is therefore stated plainly as a **hard bound on the loop but a soft bound on the final turn's spend**: expiry immediately stops all further dispatch and surfaces needs-rescue, while the already-running turn's residual spend is stranded — bounded to that single turn and surfaced on the card — and the "never keeps spending after a stop condition" guarantee is scoped to loop-dispatched work. A hung turn can strand its own in-flight spend, but it can never extend the loop. Budget counters SHALL also **survive a coordinator restart**: on re-adopting a still-live delivery session (SPEC-028's restart recovery), the iteration count, token spend, and original dispatch timestamp are rebuilt from the trace (`delivery.iteration` and dispatch records); where the trace cannot establish them, the loop SHALL fail conservative — treat the budget as exhausted and route to rescue rather than resume with fresh counters. The loop SHALL halt on the **first** of: a verify pass (success), or **any** active budget dimension reaching its limit (stop). No delivery loop SHALL run unbounded: a delivery with no configured budget SHALL fall back to conservative built-in defaults, **never** to "infinite". Every budget consumption (tokens and iterations per pass) and the reason a loop halted SHALL be recorded on the trace. This requirement leads the spec deliberately — the guardrails are structural, not a later addition, because a loop that fails quietly is the central risk of the whole pattern.

#### Scenario: A loop stops at its iteration cap
- **WHEN** a delivery loop reaches its configured maximum iteration count without a verify pass
- **THEN** the loop halts and does not begin another iteration
- **AND** the halt reason `iteration-cap` is traced

#### Scenario: A loop stops at its token budget
- **WHEN** the tokens spent across a delivery loop's iterations reach the token budget
- **THEN** the loop halts before dispatching a further iteration
- **AND** the halt reason `token-budget` is traced

#### Scenario: No budget configured falls back to defaults, never infinite
- **WHEN** a delivery starts with no budget in config or frontmatter
- **THEN** conservative built-in default caps apply
- **AND** the loop is never allowed to run without a stop condition

### Requirement: Completion requires an independent verify pass, not a self-reported checklist
`capability: single-session-delivery` · `delta: MODIFIED (claude/spec-driven-dev-critique-0hkvm2)`

A delivery SHALL NOT be marked `done` on the task checklist alone. After the implementer session settles a turn in which every task in the spec's `## Tasks` section is checked off (SPEC-028's checklist oracle — the exact point where the synthetic `done` is emitted today), the system SHALL run a **verify gate**: the conformance check ([SPEC-039](039.conformance-sentinel.md), judged-only until its Tier-1 dependencies exist) applied to the **delivery worktree** against the specification's requirements and scenarios — identified by their parsed `### Requirement:` titles and `#### Scenario:` blocks (`ParsedRequirement`, the identity the parser actually exposes; the spec format defines no `R-n` labels, so verdicts SHALL key on requirement titles). Checker sessions run *in* the worktree via the existing per-session `cwd` threading (SPEC-028), reading the work directly rather than requiring a diff payload — the OpenCode adapter's diff returns counts without patch text (only Codex returns a patch), so the worktree, not a diff artifact, is the adapter-neutral verify target. The verify agent SHALL be **provably distinct** from the implementer that produced the work ([SPEC-007](007.multi-model-review-panel.md)'s distinctness guarantee): the maker never grades its own homework. A delivery SHALL be emitted `done` (surfacing for human diff review) **only** when the checklist is complete **and** verify passes. A checklist-complete-but-verify-failing state is **not** `done` — it is an iteration trigger (below). The maker and checker are **distinct agent images**: the tier→model resolver was removed from the codebase ("the agent is the model" — each agent declares a concrete `provider/model` and config-time effort in its image, and there is no per-dispatch tier or effort override), so a "stronger checker" is a configuration choice on the checker role's image (e.g. a higher `reasoningEffort`), and distinctness SHALL be enforced by comparing the checker's declared model against the implementer's via the existing `validateReviewers` mechanism. The gate's **pass bar is stricter than the sentinel's alarm bar, deliberately**: a verify pass SHALL require an affirmative `satisfied` verdict from every panel reviewer on every requirement — at the gate, a single evidence-backed `violated` verdict, an `uncertain`, or an `unknown` blocks the pass and triggers iteration (or rescue). SPEC-039's ≥2-reviewer quorum exists to avoid false *alarms* on already-delivered work; the gate's unanimity bar exists to avoid false *certification* of new work — precision there, recall here.

#### Scenario: Checklist complete but verify fails — not done
- **WHEN** the implementer checks off every task but the verify gate finds a requirement violated
- **THEN** no `session.status done` is emitted
- **AND** the delivery is not surfaced for human diff review as complete

#### Scenario: Checklist complete and verify passes — done
- **WHEN** every task is checked off and the verify gate passes on the delivery worktree
- **THEN** `session.status done` is emitted and the card surfaces for human diff review

#### Scenario: The checker is not the maker
- **WHEN** the verify gate runs on a delivery's worktree
- **THEN** the verifying agent's declared model is provably distinct from the implementer's (pairwise `validateReviewers`-style comparison)

#### Scenario: A lone evidence-backed violation blocks the gate
- **WHEN** one checker reports an evidence-backed `violated` verdict on a requirement while another is `satisfied` or `uncertain`
- **THEN** the verify gate does not pass and the loop iterates (budget permitting)
- **AND** the delivery is never emitted `done` on that check

### Requirement: A failed verify feeds back and iterates within budget, and the loop learns
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

When the verify gate fails and budget remains, the system SHALL continue the loop by feeding the **failing requirements and their cited `file:line` evidence** back into the **same** delivery session as the next iteration's prompt — via the existing `prompt.dispatch` steering channel, whose stale-session guard already admits `idle`/`running` sessions — then re-running the checklist oracle and verify gate after the next settled turn. Each iteration SHALL be recorded (`delivery.iteration { n, failing[], tokensSpent }`) so that state accrues across passes — the implementer is given what already failed and SHALL NOT be silently restarted from zero. Each iteration's verify SHALL re-run the **full requirement set**: no requirement-to-code dependency map exists, so "affected-only" scoping cannot be made deterministic (an edit to a shared utility can regress a requirement with no path-level relationship to the failing one) and is dropped from v1 — full re-verify is the only rule that actually delivers the regression guarantee, and its cost is bounded by the iteration cap. Scoped re-verification is a future optimisation gated on a proven impact-analysis mechanism.

#### Scenario: A failing requirement is fed back as the next iteration
- **WHEN** the verify gate reports a violated requirement and iteration budget remains
- **THEN** the next prompt to the same delivery session names that requirement and its cited evidence
- **AND** the iteration is recorded with its failing set and tokens spent

#### Scenario: The loop does not restart from zero
- **WHEN** a delivery loop enters its next iteration
- **THEN** the prior iterations' failing criteria are carried into the session's context, not discarded

#### Scenario: A regression in a previously-passing requirement is caught
- **WHEN** an iteration fixes the failing requirement but breaks one that previously passed
- **THEN** the re-verify surfaces the newly-broken requirement rather than declaring success

### Requirement: An exhausted budget halts and reports — it never bills in silence
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

When any active budget dimension is exhausted before verify passes, the system SHALL halt the loop and mark the delivery **needs-rescue** — realised **not** as a new session status (the `SessionStatus` enum is closed: `idle`/`running`/`waiting`/`error`/`done`/`interrupted`, and widening it would be a breaking contract ripple) but as the existing **`waiting`** status (semantically: blocked on a human) plus the `delivery.budget-exhausted { specId, dimension, iterations, tokens, failing[] }` event folded into the read model, from which the board derives its existing `needs-human` column. The existing desktop notification on a task session entering `waiting` then alerts the human with no new notification code. The board SHALL surface a summary of **what still fails** and **how much budget was spent** (iterations, tokens where metered, wall-clock); the delivery is never `done` and never a silent `error`. A halted loop SHALL route into the existing rescue and steering path ([SPEC-011](011.session-detail-and-rescue.md)) so a human can take over, steer, or abandon it. No loop SHALL report a success it did not verify, and no loop SHALL keep spending after a stop condition has tripped — this is the explicit guard against the "agent decides it is done too early, or spins while producing nothing" failure mode.

#### Scenario: Budget exhaustion routes to rescue with a summary
- **WHEN** a delivery loop exhausts a budget dimension without a verify pass
- **THEN** the delivery is marked `needs-rescue`, `delivery.budget-exhausted` is traced with the still-failing criteria and spend, and the card surfaces the summary for a human
- **AND** no further iteration is dispatched

#### Scenario: A stalled loop never reports false success
- **WHEN** the loop halts on a budget limit with requirements still failing
- **THEN** it is never emitted `done`
- **AND** its diff is not presented as a verified, ready-to-ship candidate

### Requirement: The loop is bounded to the worktree; the irreversible step stays a human decision
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

All iteration SHALL happen inside the delivery worktree ([SPEC-028](028.single-session-delivery.md)). A verified-`done` delivery SHALL produce a **diff for human review**, never an automatic merge or system-of-record write; a pull request is opened autonomously **only** under the project's standing SPEC-031 auto-PR opt-in — itself a recorded human decision at project scope — and only after the verify gate passes. Merging and every system-of-record write remain per-candidate governed human decisions (propose · decide · execute, [SPEC-024](024.specification-lifecycle-gating.md)). The reconciliation is explicit: **opening a PR publishes a proposal; merging it is the irreversible act** — with the opt-in set, the coordinator opens the PR at the verified boundary under that standing authorisation; without it, PR creation waits for the human's per-candidate decision. This **MODIFIES SPEC-031's auto-PR behaviour**: today `buildDeliveryPrompt` instructs the implementer to open the PR the moment every task is checked off — which under this spec would fire *before* the verify gate, letting unverified work publish. When the delivery loop is active, the standing auto-PR instruction SHALL be **omitted from the delivery prompt**, and the opt-in is honoured **after** the verify gate passes — via a coordinator-issued post-verify instruction to the session — so auto-PR moves to the verified boundary, not self-reported checklist completion. The loop's autonomy is bounded to producing a **verified candidate**; whether that candidate ships is always a human decision at the irreversible step. This is what makes an autonomous loop compatible with Arke's wager rather than a violation of it: the gate and the budget bound the *work*, and the human still bounds the *act*.

#### Scenario: A verified delivery still waits for a human at the boundary
- **WHEN** a delivery loop reaches a verified `done`
- **THEN** the result is a worktree diff surfaced for human review
- **AND** no merge, PR, or system-of-record write happens without a subsequent human decision

#### Scenario: The loop cannot cross the governed boundary by itself
- **WHEN** the loop runs to completion or halts
- **THEN** at no point does it merge or write a system of record autonomously
- **AND** it opens a PR only under the project's standing auto-PR opt-in, and only after a verify pass

#### Scenario: Auto-PR waits for the verify gate
- **WHEN** `delivery.autoOpenPr` is enabled and the implementer completes its checklist
- **THEN** no PR is opened before the verify gate passes
- **AND** on a verify pass the PR is opened per SPEC-031, at the verified boundary

### Requirement: Cost per accepted change is recorded and surfaced
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

For every delivery loop the system SHALL record the tokens (where metered) and iterations spent, and — once the human accepts or rejects the resulting diff at the boundary — SHALL compute and surface **cost per accepted change**. The accept signal is the existing `pr.approve` diff-gate (and the delivered lifecycle transition); the reject signal is **ADDED**, since no diff-reject op correlated to a delivery session exists today: a governed `delivery.reject { specId, sessionId, reason? }` op on the diff-review/rescue surface records `delivery.rejected` for a discarded or abandoned candidate, and the accept-rate denominator SHALL count every verified candidate — so discarded diffs cannot leave the rate misleadingly at 100% ([SPEC-015](015.audit-trace-and-observability.md)'s observability path). A rolling **accept rate** per project SHALL be available, and a loop whose accepted-output rate falls below a configurable floor SHALL be flagged as costing more than it returns. This makes visible the one metric the loop literature says almost nobody tracks — without it, a loop that produces ten diffs of which six are discarded silently moves the review burden back onto the human it was meant to relieve.

#### Scenario: An accepted delivery records its cost per accepted change
- **WHEN** a human accepts a delivery loop's verified diff
- **THEN** the tokens/iterations spent and the resulting cost-per-accepted-change are recorded and surfaced

#### Scenario: A low accept rate is flagged
- **WHEN** a project's rolling accept rate for delivery loops falls below the configured floor
- **THEN** the condition is surfaced so the loop can be reconsidered rather than left silently burning budget

## Design

### Architectural decision

The delivery loop is **not new plumbing** — it is a control layer that composes three things Arke already has: SPEC-028's dispatch/checklist oracle (the executor), SPEC-039's check (the verifier), and SPEC-007's distinctness enforcement over the agent images' declared models (maker ≠ checker — the tier resolver is removed, SPEC-016 revised; there are no tiers to compose with). Arke deliberately does **not** reimplement the harness's loop primitives (`/loop`, `/goal`, hooks, cron); it sits above the harness and supplies the parts the loop literature says teams need and individuals lack — the reviewed gate, first-class budgets/stop-conditions, durable state (the trace), and a human boundary at the irreversible act. The oracle's terminal condition changes from *checklist-complete* to *checklist-complete AND verify-pass*; everything else is a bounded iteration wrapper around the existing dispatch.

### Target architecture

```
spec.deliver ─► deliverImplementation (SPEC-028)  ── budget resolved (SPEC-005/019)
       │
       ▼
   ┌───────────────────────── delivery loop (bounded) ─────────────────────────┐
   │  EXECUTE  implementer session settles a turn (SPEC-028 worktree)           │
   │  ORACLE   re-parse ## Tasks — all [x]?  ── no ─► keep steering, same budget │
   │              │ yes                                                          │
   │  VERIFY   conformance check (SPEC-039, judged-only v1) run IN the worktree  │
   │              (session cwd), checker model validated distinct from maker's   │
   │              ├─ pass ─────────────────► session.status done ► human diff    │
   │              └─ fail & budget left ──► feed failing requirements + evidence │
   │                                          as next iteration (state accrues)  │
   │  STOP     any budget dimension exhausted ─► needs-rescue (SPEC-011) + report│
   └───────────────────────────────────────────────────────────────────────────┘
       │ (verified diff)
       ▼
   human decision at the boundary — merge / PR / system-of-record (SPEC-024)
```

- **Coordinator** (`packages/coordinator`): a `DeliveryLoop` controller wrapping `observeDeliveryProgress` (SPEC-028) — on a checklist-complete turn it invokes the verify gate instead of emitting `done` directly; folds `delivery.iteration` / `delivery.budget-exhausted` into the read model; resolves and decrements the budget; builds the feedback prompt from the failing verdicts.
- **Verifier** (SPEC-039): shared with the sentinel — the same extended panel target mode + per-requirement verdict schema, here pointed at the delivery worktree (checker sessions get the worktree as their `cwd`); judged-only until executable projections exist. The two triggers (during-delivery gate, post-delivery drift) share one check implementation.
- **Checker resolution:** maker (`implementer`) and checker (a reviewer-role agent image) declare their models config-time; pairwise `validateReviewers`-style distinctness against the implementer's declared model; a "stronger checker" is a config choice on the checker's image (e.g. `reasoningEffort`), not a runtime tier — no per-dispatch override exists or is added.
- **Client** (`packages/client`): iteration/budget indicator on the delivering card; the budget-exhausted summary in the rescue panel (SPEC-011); cost-per-accepted-change and accept-rate in the overview/observability surface (SPEC-025/015).
- **Config**: budget keys (`maxIterations`, `tokenBudget`, `wallClock`, `acceptRateFloor`) extend the **existing** `delivery` config block (`delivery-config.ts`, SPEC-031 auto-PR), parsed by the same lenient hand-rolled reader — `.arke/config.json` is not zod-modeled; zod-first applies to the event contracts only. `ARKE_*` overrides and per-spec frontmatter override.
- **Contracts/adapters (ADDED)**: optional usage fields on the turn-settling events (`message.updated` / `turn.quiescent`), adapter-extracted where the harness reports usage, capability-flagged; coordinator accumulation per delivery.

### Data model

- **Budget** — `{ maxIterations, tokenBudget, wallClock }` resolved per delivery; a running counter on the in-memory delivery state (no new durable store — consistent with SPEC-028).
- **Read-model additions** on a delivering card: `iteration` (n / max), `budgetSpent` (tokens, wall-clock), `lastFailing[]`, and terminal `needs-rescue`.
- **Trace events** (SPEC-015, append-only): `delivery.iteration`, `delivery.verify` (pass/fail + verdicts), `delivery.budget-exhausted`, `delivery.accepted` / `delivery.rejected` (for cost-per-accepted-change).

### Interfaces and contracts

- No new op: the loop is internal to `spec.deliver`'s lifecycle. New events/errors: `delivery.iteration`, `delivery.budget-exhausted`, `delivery.verify`; needs-rescue realised as `session.status waiting` + `delivery.budget-exhausted` in the read model (no new `SessionStatus` member). ADDED optional usage fields on turn-settling events (capability-flagged).
- Config: `delivery: { maxIterations, tokenBudget, wallClock, acceptRateFloor }` (SPEC-005/019); frontmatter `delivery:` override.
- The verify gate is SPEC-039's check invoked with `target: "worktree-diff"`.

### Cross-cutting

- **Design template:** the iteration/budget indicator, the budget-exhausted summary, and the cost/accept-rate surface follow the `arke-design` skill (`.claude/skills/arke-design/`) — teal accent (SPEC-033) for the "needs-rescue" attention state, not a raw alarm.
- **Security / governance (the wager):** the loop runs entirely host-side in the worktree; it never crosses the governed boundary autonomously (R5); every iteration, verify result, and halt is traced before any client sees it; the checker is credential-scoped like any harness agent.
- **Cost:** budgets and the accept-rate floor (R1, R6) are the structural cost controls; the "maker-and-checker doubles the bill" concern is met by pairing a cheap/fast maker image with a stronger checker image (a config choice), and by re-verifying only the affected + previously-failing criteria (R3) rather than the whole spec each pass.
- **Observability:** iteration count, verify pass-rate, budget-exhaustion rate, and cost-per-accepted-change flow to the SPEC-015 trace/span path (OTLP-exportable in design; no exporter exists yet) so the loop's own economics are measurable — the loop is judged by the metric it exists to improve.
- **Scope:** markdown specifications only in v1 — delivery refuses HTML specs (SPEC-036), and the loop inherits that boundary.

## Tasks

**Phase A — the gate (no iteration yet)**
- [ ] Config: budget keys extending the existing `delivery` block (`delivery-config.ts`) + frontmatter override + conservative built-in defaults; `ARKE_*` overrides.
- [ ] Coordinator: on a checklist-complete turn, invoke SPEC-039's check with the delivery worktree as the checker sessions' `cwd`, checker model validated distinct from the implementer's (`validateReviewers`-style), instead of emitting `done` directly; emit `done` only on checklist-complete AND verify-pass; `delivery.verify` traced.
- [ ] Client: surface a checklist-complete-but-verifying state on the card (distinct from `done`).

**Phase B — the loop**
- [ ] Contracts/adapters (ADDED): optional usage fields on turn-settling events; adapter extraction where the harness reports usage (capability-flagged); coordinator per-delivery accumulation. Token dimension inactive-and-surfaced on a non-reporting harness.
- [ ] Coordinator: `DeliveryLoop` controller — budget resolution + running counters (wall-clock = dispatch timestamp bookkeeping, checked at turn boundaries); on verify-fail with budget left, build the feedback prompt from failing verdicts and `prompt.dispatch` the next iteration into the same session; `delivery.iteration` traced; re-verify affected + previously-failing criteria (regression-safe).
- [ ] Coordinator: stop conditions — halt on the first of verify-pass or any active budget dimension; on exhaustion emit `session.status waiting` + `delivery.budget-exhausted` (board derives `needs-human`; desktop notification fires on `waiting` for free), route to SPEC-011 rescue.
- [ ] Client: iteration/budget indicator on the delivering card; budget-exhausted summary in the rescue panel.

**Phase C — economics**
- [ ] Coordinator: record `delivery.accepted`/`delivery.rejected` at the human boundary; compute cost-per-accepted-change and rolling accept rate.
- [ ] Client/observability: cost-per-accepted-change + accept-rate surface (SPEC-025/015), accept signal wired to `pr.approve` + delivered/closed transitions; flag when accept rate < floor.
- [ ] Observability: iteration count, verify pass-rate, budget-exhaustion rate, cost-per-accepted-change to the SPEC-015 trace/span path (OTLP-exportable; exporter TBD).

### Testing
- **Unit (budget):** first-of stop semantics (iteration cap, token budget, wall-clock); no-config falls back to defaults, never infinite; halt reasons traced.
- **Unit (gate):** checklist-complete-but-verify-fail is not `done`; checklist-complete + verify-pass is `done`; the checker resolves distinct from the maker.
- **Unit (loop):** a failing requirement is fed back into the same session with cited evidence; prior failures accrue (no restart-from-zero); a regression in a previously-passing requirement is caught on re-verify.
- **Unit (stop):** budget exhaustion → `needs-rescue` + `delivery.budget-exhausted` with still-failing set + spend; never `done`, never silent `error`; routes to SPEC-011.
- **Unit (boundary):** a verified `done` produces a diff only — no merge/PR/system-of-record write happens autonomously.
- **Unit (economics):** cost-per-accepted-change computed on accept; rolling accept rate; below-floor flag raised.
- **Integration:** deliver a spec whose first implementer pass fails one requirement's scenario → verify fails → feedback iteration fixes it → verify passes → `done` surfaces a verified diff → human accepts → cost-per-accepted-change recorded. And: a spec the implementer cannot satisfy within budget → loop halts at the cap → `needs-rescue` with a summary. Both host and host-less.

### Definition of done
Delivery completes only on checklist-complete AND an independent verify pass by a provably-distinct checker; the loop iterates failing criteria back with accruing state and is regression-safe; every loop is bounded by iteration/token/wall-clock budgets with no unbounded path; exhaustion halts to `needs-rescue` with a traced summary and never a false `done`; the loop never crosses the governed boundary autonomously; cost-per-accepted-change and accept rate are recorded and surfaced; suite green; a non-author reviewer has signed off; SPEC-039 landed (verifier dependency).

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Budgets/stop-conditions are the leading requirement, not a later add | A loop that fails quietly and expensively is the central risk of the pattern; the guardrails must be structural or the feature is a liability |
| 2 | Completion = checklist AND independent verify, not checklist alone | SPEC-028's oracle trusts the maker's self-report; the loop's whole value is an independent gate, so the terminal condition must change |
| 3 | Reuse SPEC-039's check as the gate, targeted at the worktree diff | One verifier serves both triggers — drift after delivery (SPEC-039) and the gate during delivery (here); no second checker to build or keep consistent |
| 4 | Maker ≠ checker via SPEC-007 distinctness + SPEC-005 tiers | The model that wrote the code grades itself too generously; a distinct, optionally-stronger checker is most of the quality, and the tiering lets a cheap maker pair with a strict checker to bound cost |
| 5 | Exhaustion → `needs-rescue`, never a silent `error` or a false `done` | The "Ralph Wiggum" failure is a loop that exits early or spins while spending; the only safe halt is one that reports what still fails and hands to a human |
| 6 | Autonomy bounded to the worktree; the human keeps the irreversible step | This is the reconciliation with propose·decide·execute — the gate/budget bound the work, the human bounds the act; without it the loop violates the wager |
| 7 | Arke governs loops, it does not reimplement loop plumbing | `/loop`, `/goal`, hooks, cron are harness features; Arke's altitude is the gate, budget, state, and boundary the harness loop lacks — reimplementing the primitive would compete with the harness instead of orchestrating it |
| 8 | Re-verify affected + previously-failing criteria, not the whole spec each pass | Full re-verification every iteration multiplies the checker's cost without proportional signal; scoping keeps the maker-checker bill bounded while still catching regressions |
| 9 | Token accounting is ADDED plumbing, capability-flagged; the iteration cap is the enforceable backbone | No usage field exists on any domain event and neither adapter extracts one — a "budget" that silently doesn't meter is the exact failure this spec exists to prevent (defensive review, 2026-07-20) |
| 10 | Needs-rescue is `waiting` + a read-model event, not a new `SessionStatus` | The status enum is closed and shared; `waiting` already means blocked-on-human, the board already derives `needs-human`, and the desktop already notifies on it (defensive review) |
| 11 | Checker strength is an agent-image config choice; no runtime tiers | The tier→model resolver was removed ("the agent is the model"); distinctness is enforced by comparing declared models (`validateReviewers`), not tier indirection (defensive review) |
| 12 | Verify targets the worktree via session `cwd`, not a diff payload | OpenCode's `getDiff` returns counts without patch text; running checkers in the worktree is adapter-neutral and reuses SPEC-028's cwd threading (defensive review) |
| 13 | Wall-clock enforced by an active watchdog; budget counters rebuilt from the trace on restart, failing conservative | A hung turn never reaches a turn boundary, and restart re-adoption with fresh in-memory counters would resume unbounded — both violate "never unbounded" (PR #84 round 2) |
| 14 | SPEC-031's auto-PR moves to the verified boundary | The checklist-complete auto-PR instruction fires before the verify gate, publishing unverified work — the exact self-graded completion this spec exists to close (PR #84 round 2) |
| 15 | Verdicts key on parsed `### Requirement:` titles; ADDED `delivery.reject` for the accept-rate denominator | The spec format defines no `R-n` labels — `ParsedRequirement` titles are the identity the parser exposes; and without a reject signal the accept rate can only ever read 100% (PR #84 round 2) |
| 16 | Full re-verify every iteration; affected-only scoping deferred behind a proven impact map (supersedes #8) | No requirement-to-code dependency map exists — a shared-utility edit regresses requirements with no path relationship, so scoping cannot be deterministic; cost stays bounded by the iteration cap (PR #84 round 3) |
| 17 | The gate requires unanimous affirmative satisfaction; the sentinel's quorum is for alarms only | Precision for post-delivery alarms, recall for pre-`done` certification — a lone evidence-backed violation must block `done` even though it must not raise a post-delivery alarm (PR #84 round 3) |
| 18 | Wall-clock on a no-abort adapter is a hard loop bound and a stated-soft final-turn spend bound; auto-PR under the standing SPEC-031 opt-in is the governed decision, merge stays per-candidate | Honesty about residual-turn spend rather than an implied guarantee; and a PR is a published proposal — the irreversible act is the merge (PR #84 round 3) |

## Open questions
- **Steering vs. autonomy:** SPEC-028 already lets a human steer a delivery mid-flight via the task composer. Should the loop pause for optional human steering between iterations (semi-autonomous), or only surface at verify-pass / budget-exhaustion (fully autonomous within budget)? (Lean: default fully-autonomous-within-budget, with an opt-in "review each iteration" mode for high-stakes specs.)
- **Wall-clock vs. token budget precedence:** when both are near their limit, is there a preferred dimension to report as *the* halt reason, or is first-crossed sufficient? (Lean: first-crossed, recorded precisely.)
- **Partial acceptance:** if a human accepts a `needs-rescue` diff after taking it over manually, how is cost-per-accepted-change attributed between the loop's spend and the human's rescue effort? (Defer; record both, attribute later.)
- **Flaky verify:** a non-deterministic Tier-2 panel could pass on iteration N and fail on N+1 for the same code. Does the loop need a stability check (verify twice, or require the same verdict across the panel) before declaring `done`? (Relates to SPEC-039's agreement bar; likely reuse it.)
- **Acceptable default budgets:** what are the conservative built-in caps (R1) — e.g. 5 iterations, a per-delivery token ceiling, a wall-clock in minutes — and should they scale with the spec's task count?
