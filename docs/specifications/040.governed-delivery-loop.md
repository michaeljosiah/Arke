# Governed delivery loop — verify-and-iterate delivery, bounded by a budget and a human boundary

## Why

Delivery today ([SPEC-028](028.single-session-delivery.md)) completes on a **self-reported checklist**: the implementer ticks every `- [x]` and the coordinator calls it `done`. That is precisely the failure the loop literature warns about — *the model that did the work is far too generous a grader*. There is no independent gate between "the agent says it's finished" and "the card surfaces for human review." A delivery loop closes that seam: it keeps iterating an implementer against an **independent verify gate** (the spec's own `R-n` acceptance criteria, checked by a provably-distinct agent) until the work actually passes or a **budget** stops it — turning single-pass delivery into `execute → verify → iterate`, without ever letting the loop grade its own homework or bill in silence.

Arke is unusually well-placed to do this safely, because a loop's one scarce ingredient — a real, reviewed, durable verify gate — is exactly what Arke already manufactures (the reviewed spec), and the verifier itself already exists as [SPEC-039](039.conformance-sentinel.md)'s two-tier check. SPEC-039 uses that check to catch drift **after** delivery; this spec uses the **same** check as the gate **during** delivery.

## What changes

- ADDED delivery-loop — a delivery runs as a bounded loop with **first-class stop conditions and a budget** (max iterations, token budget, wall-clock); no delivery may run unbounded, and every halt reason is traced.
- MODIFIED single-session-delivery — completion requires the checklist to be ticked **and** an **independent verify pass**; a self-reported checklist alone no longer marks a delivery `done`.  *(breaking: the completion oracle's terminal condition changes.)*
- ADDED delivery-loop — a failed verify **feeds the failing criteria back** into the same session as the next iteration, and the loop learns (prior failures accrue in context) rather than restarting from zero.
- ADDED delivery-loop — an exhausted budget **halts and reports** into the rescue path ([SPEC-011](011.session-detail-and-rescue.md)); a loop never claims success it did not verify, and never keeps spending after a stop condition.
- ADDED delivery-loop — the loop is **bounded to the worktree**; a verified delivery produces a diff for human review, never an automatic merge / PR / system-of-record write.
- ADDED delivery-loop — **cost per accepted change** is recorded and surfaced ([SPEC-015](015.audit-trace-and-observability.md)), so a loop that costs more than it returns is visible.

**Depends on:** SPEC-028 (single-session delivery — the loop extends its dispatch/oracle), SPEC-039 (conformance check — reused as the verify gate), SPEC-007 (provable model distinctness — maker ≠ checker), SPEC-005 (roster & tiers — maker/checker resolution), SPEC-011 (rescue & steering — the halt path), SPEC-015 (trace & observability), SPEC-024 (propose·decide·execute — the human boundary), SPEC-019 (config merge — budgets).

## Requirements

### Requirement: Every delivery loop is bounded by explicit stop conditions and a budget
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

A delivery loop SHALL carry a bounded budget with three dimensions — a **maximum iteration count**, a **token budget**, and a **wall-clock cap** — resolved from project configuration ([SPEC-005](005.harness-and-model-registry.md) / [SPEC-019](019.global-and-project-config-merge.md)) with an optional per-spec override in a `delivery:` frontmatter block. The loop SHALL halt on the **first** of: a verify pass (success), or **any** budget dimension reaching its limit (stop). No delivery loop SHALL run unbounded: a delivery with no configured budget SHALL fall back to conservative built-in defaults, **never** to "infinite". Every budget consumption (tokens and iterations per pass) and the reason a loop halted SHALL be recorded on the trace. This requirement leads the spec deliberately — the guardrails are structural, not a later addition, because a loop that fails quietly is the central risk of the whole pattern.

#### Scenario: A loop stops at its iteration cap
- **WHEN** a delivery loop reaches its configured maximum iteration count without a verify pass
- **THEN** the loop halts and does not begin another iteration
- **AND** the halt reason `iteration-cap` is traced

#### Scenario: A loop stops at its token budget
- **WHEN** the tokens spent across a delivery loop's iterations reach the token budget
- **THEN** the loop halts before dispatching a further iteration
- **AND** the halt reason `token-budget` is traced

#### Scenario: No budget configured falls back to defaults, never infinite
- **WHEN** a delivery starts with no budget in config or frontmatter
- **THEN** conservative built-in default caps apply
- **AND** the loop is never allowed to run without a stop condition

### Requirement: Completion requires an independent verify pass, not a self-reported checklist
`capability: single-session-delivery` · `delta: MODIFIED (claude/spec-driven-dev-critique-0hkvm2)`

A delivery SHALL NOT be marked `done` on the task checklist alone. After the implementer session settles a turn in which every task in the spec's `## Tasks` section is checked off (SPEC-028's checklist oracle), the system SHALL run a **verify gate**: the two-tier conformance check ([SPEC-039](039.conformance-sentinel.md)) — deterministic executable checks first, an independent reviewer panel second — applied to the **worktree diff** against the specification's `R-n` scenarios. The verify agent SHALL be **provably distinct** from the implementer that produced the work ([SPEC-007](007.multi-model-review-panel.md)'s distinctness guarantee): the maker never grades its own homework. A delivery SHALL be emitted `done` (surfacing for human diff review) **only** when the checklist is complete **and** verify passes. A checklist-complete-but-verify-failing state is **not** `done` — it is an iteration trigger (below). The maker and checker SHALL resolve through the roster/tier registry ([SPEC-005](005.harness-and-model-registry.md)) such that the checker MAY run at a stronger tier or higher effort than the maker.

#### Scenario: Checklist complete but verify fails — not done
- **WHEN** the implementer checks off every task but the verify gate finds a requirement violated
- **THEN** no `session.status done` is emitted
- **AND** the delivery is not surfaced for human diff review as complete

#### Scenario: Checklist complete and verify passes — done
- **WHEN** every task is checked off and the verify gate passes on the worktree diff
- **THEN** `session.status done` is emitted and the card surfaces for human diff review

#### Scenario: The checker is not the maker
- **WHEN** the verify gate runs on a delivery's worktree diff
- **THEN** the verifying agent resolves to a model provably distinct from the implementer that produced the diff

### Requirement: A failed verify feeds back and iterates within budget, and the loop learns
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

When the verify gate fails and budget remains, the system SHALL continue the loop by feeding the **failing requirements and their cited `file:line` evidence** back into the **same** delivery session as the next iteration's prompt, then re-running the checklist oracle and verify gate after the next settled turn. Each iteration SHALL be recorded (`delivery.iteration { n, failing[], tokensSpent }`) so that state accrues across passes — the implementer is given what already failed and SHALL NOT be silently restarted from zero. The loop SHALL re-verify only what the iteration could have affected plus the previously-failing criteria, so a fix does not have to re-prove the entire spec every pass, but a regression in a previously-passing requirement is still caught.

#### Scenario: A failing requirement is fed back as the next iteration
- **WHEN** the verify gate reports a violated requirement and iteration budget remains
- **THEN** the next prompt to the same delivery session names that requirement and its cited evidence
- **AND** the iteration is recorded with its failing set and tokens spent

#### Scenario: The loop does not restart from zero
- **WHEN** a delivery loop enters its next iteration
- **THEN** the prior iterations' failing criteria are carried into the session's context, not discarded

#### Scenario: A regression in a previously-passing requirement is caught
- **WHEN** an iteration fixes the failing requirement but breaks one that previously passed
- **THEN** the re-verify surfaces the newly-broken requirement rather than declaring success

### Requirement: An exhausted budget halts and reports — it never bills in silence
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

When any budget dimension is exhausted before verify passes, the system SHALL halt the loop, mark the delivery **`needs-rescue`** (never `done`, and never a silent `error`), surface on the board a summary of **what still fails** and **how much budget was spent** (iterations, tokens, wall-clock), and emit `delivery.budget-exhausted { specId, dimension, iterations, tokens, failing[] }`. A halted loop SHALL route into the existing rescue and steering path ([SPEC-011](011.session-detail-and-rescue.md)) so a human can take over, steer, or abandon it. No loop SHALL report a success it did not verify, and no loop SHALL keep spending after a stop condition has tripped — this is the explicit guard against the "agent decides it is done too early, or spins while producing nothing" failure mode.

#### Scenario: Budget exhaustion routes to rescue with a summary
- **WHEN** a delivery loop exhausts a budget dimension without a verify pass
- **THEN** the delivery is marked `needs-rescue`, `delivery.budget-exhausted` is traced with the still-failing criteria and spend, and the card surfaces the summary for a human
- **AND** no further iteration is dispatched

#### Scenario: A stalled loop never reports false success
- **WHEN** the loop halts on a budget limit with requirements still failing
- **THEN** it is never emitted `done`
- **AND** its diff is not presented as a verified, ready-to-ship candidate

---

### Requirement: The loop is bounded to the worktree; the irreversible step stays a human decision
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

All iteration SHALL happen inside the delivery worktree ([SPEC-028](028.single-session-delivery.md)). A verified-`done` delivery SHALL produce a **diff for human review**, not an automatic merge, pull request, or system-of-record write. The loop SHALL NOT merge, open a PR, or write to any system of record on its own; those remain governed human decisions (propose · decide · execute, [SPEC-024](024.specification-lifecycle-gating.md)). The loop's autonomy is bounded to producing a **verified candidate**; whether that candidate ships is always a human decision at the irreversible step. This is what makes an autonomous loop compatible with Arke's wager rather than a violation of it: the gate and the budget bound the *work*, and the human still bounds the *act*.

#### Scenario: A verified delivery still waits for a human at the boundary
- **WHEN** a delivery loop reaches a verified `done`
- **THEN** the result is a worktree diff surfaced for human review
- **AND** no merge, PR, or system-of-record write happens without a subsequent human decision

#### Scenario: The loop cannot cross the governed boundary by itself
- **WHEN** the loop runs to completion or halts
- **THEN** at no point does it open a PR, merge, or write a system of record autonomously

---

### Requirement: Cost per accepted change is recorded and surfaced
`capability: delivery-loop` · `delta: ADDED (claude/spec-driven-dev-critique-0hkvm2)`

For every delivery loop the system SHALL record the tokens and iterations spent, and — once the human accepts or rejects the resulting diff at the boundary — SHALL compute and surface **cost per accepted change** ([SPEC-015](015.audit-trace-and-observability.md)'s observability path). A rolling **accept rate** per project SHALL be available, and a loop whose accepted-output rate falls below a configurable floor SHALL be flagged as costing more than it returns. This makes visible the one metric the loop literature says almost nobody tracks — without it, a loop that produces ten diffs of which six are discarded silently moves the review burden back onto the human it was meant to relieve.

#### Scenario: An accepted delivery records its cost per accepted change
- **WHEN** a human accepts a delivery loop's verified diff
- **THEN** the tokens/iterations spent and the resulting cost-per-accepted-change are recorded and surfaced

#### Scenario: A low accept rate is flagged
- **WHEN** a project's rolling accept rate for delivery loops falls below the configured floor
- **THEN** the condition is surfaced so the loop can be reconsidered rather than left silently burning budget

## Design

### Architectural decision

The delivery loop is **not new plumbing** — it is a control layer that composes three things Arke already has: SPEC-028's dispatch/checklist oracle (the executor), SPEC-039's two-tier check (the verifier), and SPEC-007's distinctness + SPEC-005's tiers (maker ≠ checker). Arke deliberately does **not** reimplement the harness's loop primitives (`/loop`, `/goal`, hooks, cron); it sits above the harness and supplies the parts the loop literature says teams need and individuals lack — the reviewed gate, first-class budgets/stop-conditions, durable state (the trace), and a human boundary at the irreversible act. The oracle's terminal condition changes from *checklist-complete* to *checklist-complete AND verify-pass*; everything else is a bounded iteration wrapper around the existing dispatch.

### Target architecture

```
spec.deliver ─► deliverImplementation (SPEC-028)  ── budget resolved (SPEC-005/019)
       │
       ▼
   ┌───────────────────────── delivery loop (bounded) ─────────────────────────┐
   │  EXECUTE  implementer session settles a turn (SPEC-028 worktree)           │
   │  ORACLE   re-parse ## Tasks — all [x]?  ── no ─► keep steering, same budget │
   │              │ yes                                                          │
   │  VERIFY   two-tier conformance check (SPEC-039) on the worktree diff,       │
   │              run by a provably-distinct checker (SPEC-007/005)              │
   │              ├─ pass ─────────────────► session.status done ► human diff    │
   │              └─ fail & budget left ──► feed failing R-n + evidence back     │
   │                                          as next iteration (state accrues)  │
   │  STOP     any budget dimension exhausted ─► needs-rescue (SPEC-011) + report│
   └───────────────────────────────────────────────────────────────────────────┘
       │ (verified diff)
       ▼
   human decision at the boundary — merge / PR / system-of-record (SPEC-024)
```

- **Coordinator** (`packages/coordinator`): a `DeliveryLoop` controller wrapping `observeDeliveryProgress` (SPEC-028) — on a checklist-complete turn it invokes the verify gate instead of emitting `done` directly; folds `delivery.iteration` / `delivery.budget-exhausted` into the read model; resolves and decrements the budget; builds the feedback prompt from the failing verdicts.
- **Verifier** (SPEC-039): reused as-is, targeted at the worktree diff rather than a post-delivery mainline change. The two triggers (during-delivery gate, post-delivery drift) share one check implementation.
- **Roster/registry** (SPEC-005/007): maker (`implementer`) and checker (a `reviewer`-role agent) resolve to provably-distinct instances; the roster permits the checker at a stronger tier / higher effort.
- **Client** (`packages/client`): iteration/budget indicator on the delivering card; the budget-exhausted summary in the rescue panel (SPEC-011); cost-per-accepted-change and accept-rate in the overview/observability surface (SPEC-025/015).
- **Config** (SPEC-005/019): a `delivery` budget block (`maxIterations`, `tokenBudget`, `wallClock`, `acceptRateFloor`) with `ARKE_*` overrides and per-spec frontmatter override.

### Data model

- **Budget** — `{ maxIterations, tokenBudget, wallClock }` resolved per delivery; a running counter on the in-memory delivery state (no new durable store — consistent with SPEC-028).
- **Read-model additions** on a delivering card: `iteration` (n / max), `budgetSpent` (tokens, wall-clock), `lastFailing[]`, and terminal `needs-rescue`.
- **Trace events** (SPEC-015, append-only): `delivery.iteration`, `delivery.verify` (pass/fail + verdicts), `delivery.budget-exhausted`, `delivery.accepted` / `delivery.rejected` (for cost-per-accepted-change).

### Interfaces and contracts

- No new op: the loop is internal to `spec.deliver`'s lifecycle. New events/errors: `delivery.iteration`, `delivery.budget-exhausted`, `delivery.verify`; `needs-rescue` as a delivery sub-state distinct from `error`.
- Config: `delivery: { maxIterations, tokenBudget, wallClock, acceptRateFloor }` (SPEC-005/019); frontmatter `delivery:` override.
- The verify gate is SPEC-039's check invoked with `target: "worktree-diff"`.

### Cross-cutting

- **Design template:** the iteration/budget indicator, the budget-exhausted summary, and the cost/accept-rate surface follow the `arke-design` skill (`.claude/skills/arke-design/`) — teal accent (SPEC-033) for the "needs-rescue" attention state, not a raw alarm.
- **Security / governance (the wager):** the loop runs entirely host-side in the worktree; it never crosses the governed boundary autonomously (R5); every iteration, verify result, and halt is traced before any client sees it; the checker is credential-scoped like any harness agent.
- **Cost:** budgets and the accept-rate floor (R1, R6) are the structural cost controls; the article's warning that "the maker-and-checker trick that lifts quality also doubles the bill" is met by allowing a cheap/fast maker and reserving the stronger tier for the checker (SPEC-005), and by re-verifying only the affected + previously-failing criteria (R3) rather than the whole spec each pass.
- **Observability:** iteration count, verify pass-rate, budget-exhaustion rate, and cost-per-accepted-change flow to the SPEC-015 OTLP path so the loop's own economics are measurable — the loop is judged by the metric it exists to improve.

## Tasks

**Phase A — the gate (no iteration yet)**
- [ ] Config: `delivery` budget block (SPEC-005/019) + frontmatter override + conservative built-in defaults; `ARKE_*` overrides.
- [ ] Coordinator: on a checklist-complete turn, invoke SPEC-039's check on the worktree diff via a provably-distinct checker (SPEC-007/005) instead of emitting `done` directly; emit `done` only on checklist-complete AND verify-pass; `delivery.verify` traced.
- [ ] Client: surface a checklist-complete-but-verifying state on the card (distinct from `done`).

**Phase B — the loop**
- [ ] Coordinator: `DeliveryLoop` controller — budget resolution + running counters; on verify-fail with budget left, build the feedback prompt from failing verdicts and dispatch the next iteration into the same session; `delivery.iteration` traced; re-verify affected + previously-failing criteria (regression-safe).
- [ ] Coordinator: stop conditions — halt on the first of verify-pass or any budget dimension; on exhaustion mark `needs-rescue`, emit `delivery.budget-exhausted`, route to SPEC-011 rescue.
- [ ] Client: iteration/budget indicator on the delivering card; budget-exhausted summary in the rescue panel.

**Phase C — economics**
- [ ] Coordinator: record `delivery.accepted`/`delivery.rejected` at the human boundary; compute cost-per-accepted-change and rolling accept rate.
- [ ] Client/observability: cost-per-accepted-change + accept-rate surface (SPEC-025/015); flag when accept rate < floor.
- [ ] Observability: iteration count, verify pass-rate, budget-exhaustion rate, cost-per-accepted-change to the SPEC-015 OTLP path.

### Testing
- **Unit (budget):** first-of stop semantics (iteration cap, token budget, wall-clock); no-config falls back to defaults, never infinite; halt reasons traced.
- **Unit (gate):** checklist-complete-but-verify-fail is not `done`; checklist-complete + verify-pass is `done`; the checker resolves distinct from the maker.
- **Unit (loop):** a failing requirement is fed back into the same session with cited evidence; prior failures accrue (no restart-from-zero); a regression in a previously-passing requirement is caught on re-verify.
- **Unit (stop):** budget exhaustion → `needs-rescue` + `delivery.budget-exhausted` with still-failing set + spend; never `done`, never silent `error`; routes to SPEC-011.
- **Unit (boundary):** a verified `done` produces a diff only — no merge/PR/system-of-record write happens autonomously.
- **Unit (economics):** cost-per-accepted-change computed on accept; rolling accept rate; below-floor flag raised.
- **Integration:** deliver a spec whose first implementer pass fails one `R-n` → verify fails → feedback iteration fixes it → verify passes → `done` surfaces a verified diff → human accepts → cost-per-accepted-change recorded. And: a spec the implementer cannot satisfy within budget → loop halts at the cap → `needs-rescue` with a summary. Both host and host-less.

### Definition of done
Delivery completes only on checklist-complete AND an independent verify pass by a provably-distinct checker; the loop iterates failing criteria back with accruing state and is regression-safe; every loop is bounded by iteration/token/wall-clock budgets with no unbounded path; exhaustion halts to `needs-rescue` with a traced summary and never a false `done`; the loop never crosses the governed boundary autonomously; cost-per-accepted-change and accept rate are recorded and surfaced; suite green; a non-author reviewer has signed off; SPEC-039 landed (verifier dependency).

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Budgets/stop-conditions are the leading requirement, not a later add | A loop that fails quietly and expensively is the central risk of the pattern; the guardrails must be structural or the feature is a liability |
| 2 | Completion = checklist AND independent verify, not checklist alone | SPEC-028's oracle trusts the maker's self-report; the loop's whole value is an independent gate, so the terminal condition must change |
| 3 | Reuse SPEC-039's check as the gate, targeted at the worktree diff | One verifier serves both triggers — drift after delivery (SPEC-039) and the gate during delivery (here); no second checker to build or keep consistent |
| 4 | Maker ≠ checker via SPEC-007 distinctness + SPEC-005 tiers | The model that wrote the code grades itself too generously; a distinct, optionally-stronger checker is most of the quality, and the tiering lets a cheap maker pair with a strict checker to bound cost |
| 5 | Exhaustion → `needs-rescue`, never a silent `error` or a false `done` | The "Ralph Wiggum" failure is a loop that exits early or spins while spending; the only safe halt is one that reports what still fails and hands to a human |
| 6 | Autonomy bounded to the worktree; the human keeps the irreversible step | This is the reconciliation with propose·decide·execute — the gate/budget bound the work, the human bounds the act; without it the loop violates the wager |
| 7 | Arke governs loops, it does not reimplement loop plumbing | `/loop`, `/goal`, hooks, cron are harness features; Arke's altitude is the gate, budget, state, and boundary the harness loop lacks — reimplementing the primitive would compete with the harness instead of orchestrating it |
| 8 | Re-verify affected + previously-failing criteria, not the whole spec each pass | Full re-verification every iteration multiplies the checker's cost without proportional signal; scoping keeps the maker-checker bill bounded while still catching regressions |

## Open questions
- **Steering vs. autonomy:** SPEC-028 already lets a human steer a delivery mid-flight via the task composer. Should the loop pause for optional human steering between iterations (semi-autonomous), or only surface at verify-pass / budget-exhaustion (fully autonomous within budget)? (Lean: default fully-autonomous-within-budget, with an opt-in "review each iteration" mode for high-stakes specs.)
- **Wall-clock vs. token budget precedence:** when both are near their limit, is there a preferred dimension to report as *the* halt reason, or is first-crossed sufficient? (Lean: first-crossed, recorded precisely.)
- **Partial acceptance:** if a human accepts a `needs-rescue` diff after taking it over manually, how is cost-per-accepted-change attributed between the loop's spend and the human's rescue effort? (Defer; record both, attribute later.)
- **Flaky verify:** a non-deterministic Tier-2 panel could pass on iteration N and fail on N+1 for the same code. Does the loop need a stability check (verify twice, or require the same verdict across the panel) before declaring `done`? (Relates to SPEC-039's agreement bar; likely reuse it.)
- **Acceptable default budgets:** what are the conservative built-in caps (R1) — e.g. 5 iterations, a per-delivery token ceiling, a wall-clock in minutes — and should they scale with the spec's task count?
