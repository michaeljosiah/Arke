# Portable agent capabilities — declarative tools, MCP servers & skills, materialised per harness, edited in the UI

## Why
SPEC-016 made the agent image the portable, parseable unit and this project then adopted Omnigent's
declarative `executor` (harness + model + provider) 100%. But an agent is defined as much by **what it
can do** as by which model it runs — its **MCP servers, code/function tools, sub-agents, and skills**.
Today Arke's image records those only as a thin `ToolDecl[] = {name, kind}` and the adapter **drops
them entirely** when it materialises the agent, so a declared MCP server or tool never reaches the
harness. Two further things are missing: Arke has no **source of truth for what each harness natively
supports** (the adapter exposes only coarse feature flags, so "materialise, else degrade" has nothing
to check against), and there is **no way to author or edit an agent's capabilities from the UI** — only
its model can be changed today (SPEC-016 revised). This spec closes all three: the image carries the
full Omnigent-shaped capability declaration, each adapter declares a **capability manifest** and
materialises the declaration into its native config, and the client gains a **rich, capability-aware
agent editor** to create and edit agents (model, permissions, tools, MCP, skills).

## What changes
- ADDED agent-capabilities — the agent image gains a **rich, Omnigent-shaped `tools` map** (keyed by
  name): an **MCP server** (local `command` array or remote `url`/`headers`, an optional exposed-tool
  whitelist, and host-side `environment`), a **function tool** (`callable` + JSON-Schema `parameters`,
  optional sandbox container), or a **sub-agent** (its own `executor`). Replaces the thin `ToolDecl[]`.
  (breaking: yes — `AgentImage.tools` changes shape; see Decision log #1)
- ADDED harness-integration — a **per-adapter `HarnessCapabilities` manifest** (versioned to the
  harness) declaring what the harness natively supports: MCP (local/remote), skills (+ discovery
  locations), function tools, the tool-gating mechanism, and the built-in tool names. It is the source
  of truth materialisation and the editor validate against. (breaking: no)
- ADDED agent-capabilities — an adapter step **`materializeCapabilities`**: each adapter translates the
  normalised tools/MCP/skills into the harness's native configuration, validated against its manifest;
  an unsupported capability is **skipped with a recorded warning**, never silently claimed. (breaking: no)
- ADDED agent-editor — the client can **create a new agent and edit an existing agent's capabilities**
  from the UI — model (exists), per-tool permissions, enabling/adding tools and MCP servers, and adding
  skills — the editor offering only what the connected harness's manifest supports. (breaking: no)
- MODIFIED agent-images — **skills** remain the `skills/<name>/SKILL.md` convention (matching Omnigent,
  Claude Code, and OpenCode) but are now **materialised** to harnesses that support them (for OpenCode,
  discovered directly from `.opencode/skills/` or `.claude/skills/`). (breaking: no)
- MODIFIED human-in-the-loop — Arke's `permission: {read|edit|bash|webfetch|<tool>: allow|ask|deny}`
  remains the **portable gate** (mapped to SPEC-012, and to OpenCode's `permission` field including
  `mymcp_*` wildcards); Omnigent's code-handler `policies` are carried as an **opaque passthrough**
  honoured only by the Omnigent harness, never required of a native harness. (breaking: no)

## Requirements

### Requirement: The agent image declares capabilities as a rich, keyed tools map
`capability: agent-capabilities` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL parse an agent image's `tools:` as a **keyed map** (Omnigent-shaped, not an array),
where each entry is one of: an **MCP server** (`type: mcp` with either a local `command` + optional
`args`/`environment` or a remote `url` + `headers`, and an optional `tools:` whitelist of exposed tool
names); a **function tool** (`type: function` with a `callable` reference and optional JSON-Schema
`parameters`, `runtime`, and sandbox `container_image`); or a **sub-agent** (`type: agent` carrying its
own `executor`). The loader SHALL retain enough of each entry to reconstruct a working configuration
for a harness, and SHALL reject a malformed entry with a clear `AgentImageError` rather than silently
dropping it.

#### Scenario: An MCP server declaration round-trips with its spawn wiring
- **WHEN** an image declares `tools.github: { type: mcp, command: [uv, run, python, -m, pkg.github_mcp], tools: [search_issues] }`
- **THEN** the loaded `AgentImage` carries the MCP entry with its `command`, `environment`, and exposed-tool whitelist intact
- **AND** a harness adapter can spawn that MCP server from the parsed entry alone.

#### Scenario: A function tool retains its callable and parameter schema
- **WHEN** an image declares `tools.summarize: { type: function, callable: pkg.tools.summarize, parameters: {...} }`
- **THEN** the loaded image carries the `callable` and the JSON-Schema `parameters` for that tool.

#### Scenario: A malformed tool entry fails loudly
- **WHEN** an image declares a `tools.x` with `type: mcp` but neither a `command` nor a `url`
- **THEN** loading the image raises an `AgentImageError` naming the offending tool.

### Requirement: Credentials for tools and MCP servers stay host-side
`capability: agent-capabilities` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL keep every credential a tool or MCP server needs on the host, never inline in the
committed image (NFR-1, extending SPEC-016). A committed image MAY reference a secret only by
**environment interpolation** (`${VAR}`) or a host-side profile/credentials reference; an inline
literal secret (e.g. a bearer token or api-key value in `headers`/`environment`) SHALL be rejected by
the loader. Interpolation is resolved on the host at materialisation time and the resolved value SHALL
never be sent to the client.

#### Scenario: An inline secret in an MCP header is rejected
- **WHEN** an image declares `tools.docs: { type: mcp, url: ..., headers: { Authorization: "Bearer sk-LITERAL" } }`
- **THEN** loading the image raises an `AgentImageError` directing the author to use `${VAR}` or a host-side profile.

#### Scenario: An interpolated secret resolves only on the host
- **WHEN** the same header is written as `Authorization: "Bearer ${DOCS_TOKEN}"`
- **THEN** the image loads
- **AND** the token is resolved from the host environment at materialisation
- **AND** neither the reference nor the resolved value appears in any client-facing projection.

### Requirement: Each adapter declares a versioned HarnessCapabilities manifest
`capability: harness-integration` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL expose, per harness adapter, a **`HarnessCapabilities` manifest** that is the source
of truth for what that harness natively supports, versioned to the harness release. The manifest SHALL
declare at minimum: whether **MCP** is supported and in which forms (local / remote) and its config
shape; whether **skills** are supported and their discovery locations; whether **function tools** are
supported (and sandboxing); the **tool-gating mechanism** (e.g. OpenCode's `permission` field with
`<mcp>_*` wildcards); and the harness's **built-in tool names**. The manifest is authored from the
harness's documentation and MAY be augmented at runtime where the harness exposes a live listing, but
SHALL be usable without the harness running. `materializeCapabilities` and the agent editor SHALL both
validate against it.

#### Scenario: The OpenCode manifest reflects the real harness
- **WHEN** the coordinator loads the OpenCode adapter's `HarnessCapabilities`
- **THEN** it reports MCP `local` + `remote` supported, skills supported (discovered from `.opencode/skills/` and `.claude/skills/`), tool-gating via `permission` wildcards, and the built-in tool set (`bash, edit, write, read, grep, glob, lsp, apply_patch, skill, todowrite, webfetch, websearch, question`).

#### Scenario: The manifest is available without a live harness
- **WHEN** the harness process is not running
- **THEN** the manifest still resolves from the adapter's static declaration so the editor can offer accurate options offline.

### Requirement: Each adapter materialises capabilities into its native config
`capability: harness-integration` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL translate the normalised tools/MCP/skills of an agent image into the connected
harness's **native configuration** when the agent is materialised, validated against that harness's
`HarnessCapabilities`. For the OpenCode adapter this SHALL: write each MCP server into `opencode.json`'s
`mcp` block as `{ type: "local", command: [...], environment: {...}, enabled: true }` (local) or
`{ type: "remote", url, headers, enabled: true }` (remote); express per-agent tool enablement through
the agent's **`permission`** field (using `<mcp>_*` wildcards for a server's tools — the per-agent
`tools` map is deprecated); and rely on OpenCode's native skill discovery (place `SKILL.md` under a
discovered path) rather than a config entry. The Omnigent adapter SHALL pass the Omnigent-shaped
declaration through near-verbatim. A capability a harness does not support SHALL be **skipped with a
recorded `capability.unsupported` warning**, never silently presented as supported.

#### Scenario: An OpenCode agent's MCP server lands in opencode.json
- **WHEN** an image with `tools.github: { type: mcp, command: [...] }` is materialised against the OpenCode adapter
- **THEN** `opencode.json` gains an `mcp.github` entry of `type: local` with that `command` array and `enabled: true`
- **AND** the agent's `permission` enables (or gates) `github_*` per the image.

#### Scenario: An unsupported capability degrades gracefully
- **WHEN** an image declares a capability the connected harness's manifest does not list (e.g. a function tool with a `container_image` the harness does not sandbox)
- **THEN** materialisation completes for everything else
- **AND** a `capability.unsupported` warning is recorded naming the tool and the harness
- **AND** the projection never claims the unsupported capability is active.

### Requirement: Skills are the SKILL.md convention and materialise where supported
`capability: agent-images` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

The system SHALL discover an agent's skills from `skills/<name>/SKILL.md` (each with `name` +
`description` frontmatter and a progressive-disclosure body), matching Omnigent, Claude Code, and
OpenCode. On a harness that supports skills the adapter SHALL make them discoverable to the agent —
for OpenCode, by ensuring the `SKILL.md` folders sit under a location OpenCode already searches
(`.opencode/skills/`, `.claude/skills/`, `.agents/skills/`, project or global); on a harness with no
skills mechanism the skills SHALL remain metadata and the loader SHALL NOT fail. Skills are never
invented in YAML — the directory is the source of truth.

#### Scenario: A skill is discovered and materialised for OpenCode
- **WHEN** an agent directory contains `skills/debate/SKILL.md` with `name: debate`
- **THEN** the loaded image lists the `debate` skill with its description
- **AND** materialising against OpenCode leaves the `SKILL.md` in a discovered path so OpenCode's `skill` tool can load it.

#### Scenario: A skill-less harness does not fail on skills
- **WHEN** an image with skills is materialised against a harness that has no skills mechanism
- **THEN** materialisation succeeds and a warning records that skills were not projected to that harness.

### Requirement: Arke's permission block is the portable gate; Omnigent policies are opaque passthrough
`capability: human-in-the-loop` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

The system SHALL treat the image's `permission: {read|edit|bash|webfetch|<tool>: allow|ask|deny}` as
the **portable, harness-agnostic** authorisation gate, mapped to the SPEC-012 human-in-the-loop flow on
every harness and to OpenCode's native `permission` field (including `<mcp>_*` wildcards). Omnigent's
code-handler `policies` (function `handler` on `[request|response|tool_call|tool_result]`) SHALL be
carried on the image as an **opaque passthrough** honoured only by the Omnigent harness; a native
harness SHALL NOT be required to execute them and SHALL ignore them with a recorded note. Arke SHALL NOT
execute arbitrary policy handler code itself.

#### Scenario: Permission gates a tool on a native harness
- **WHEN** an agent with `permission: { bash: ask }` runs a shell tool on the OpenCode harness
- **THEN** the action routes through the SPEC-012 permission flow (once/always/reject) exactly as today.

#### Scenario: Omnigent policies pass through untouched
- **WHEN** an image carries `policies.pii_guard: { type: function, handler: ..., on: [response] }` and runs on the Omnigent harness
- **THEN** the policy declaration reaches Omnigent verbatim
- **AND** on a native harness the same declaration is ignored with a recorded note, and the image still loads and runs.

### Requirement: An operator can create a new agent from the UI
`capability: agent-editor` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL let an operator create a new agent from the client. Creation SHALL write a valid
`agents/<name>/config.yaml` under the project (name validated as a safe slug, confined to the project
root), seeded with an `executor` (harness + a chosen model, per SPEC-016 revised), an interaction mode,
and a default `permission` posture; it MAY scaffold an empty `skills/` directory. The new agent SHALL
appear in the roster immediately (the registry reloads and the projection refreshes), and its harness
SHALL be one the coordinator has a `HarnessCapabilities` manifest for.

#### Scenario: Creating an agent adds it to the roster
- **WHEN** an operator creates an agent `researcher-2` on the `opencode` harness with model `github-copilot/gpt-5.5`
- **THEN** `agents/researcher-2/config.yaml` is written with that executor and a default permission block
- **AND** the roster lists `researcher-2` without a reload.

#### Scenario: An unsafe or duplicate name is refused
- **WHEN** an operator tries to create an agent whose name is not a safe slug, or that already exists
- **THEN** creation is refused with a clear reason and nothing is written.

### Requirement: An operator can edit an agent's capabilities from the UI, offered only what the harness supports
`capability: agent-editor` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL let an operator edit an existing agent's capabilities from the client: its **model**
(SPEC-016 revised, existing), its **per-tool permissions** (allow / ask / deny), which **tools** are
enabled, its **MCP servers** (add / remove a local or remote server), and its **skills** (add or
reference a `SKILL.md`). The editor SHALL be **capability-aware** — it offers only the tool kinds, MCP
forms, and skill support that the connected harness's `HarnessCapabilities` manifest declares, and it
SHALL surface built-in tool names from the manifest for the permission controls. All edits SHALL be
persisted to the agent's `config.yaml` (host-side), validated (NFR-1: an MCP credential is captured as
a `${VAR}` reference or host profile, never a literal secret), and reflected in the roster live.

#### Scenario: Adding an MCP server through the editor
- **WHEN** an operator adds a local MCP server `github` (command + a `${GITHUB_TOKEN}` env reference) to an agent on the OpenCode harness
- **THEN** the agent's `config.yaml` gains the `tools.github` MCP entry with the `${GITHUB_TOKEN}` reference (not a literal)
- **AND** on next materialisation the server lands in `opencode.json` and the roster shows `github (mcp)`.

#### Scenario: The editor hides options the harness cannot express
- **WHEN** the connected harness's manifest does not support remote MCP servers
- **THEN** the editor does not offer a "remote MCP" option for an agent on that harness.

#### Scenario: A literal secret is refused at edit time
- **WHEN** an operator pastes a literal token into an MCP header field
- **THEN** the edit is refused with guidance to use a `${VAR}` reference or a host profile, and nothing is written.

### Requirement: The client surfaces an agent's declared capabilities without leaking secrets
`capability: agent-capabilities` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL show, in the agent roster/editor, each agent's declared capabilities — tool names and
kinds (mcp / function / agent), MCP endpoints by name, and skills by name — so an operator can see what
an agent can do. The projection SHALL carry no credential value, no `${VAR}` resolution, and no
credentials reference; it is names and kinds only.

#### Scenario: The roster lists an agent's tools and skills
- **WHEN** an operator opens the roster for an agent with a `github` MCP tool and a `debate` skill
- **THEN** the roster shows `github (mcp)` and the `debate` skill
- **AND** the response contains no token, header value, or credentials reference.

## Design

### Architectural decision
The agent image is the **single normalised, Omnigent-shaped description** of an agent's capabilities;
each harness adapter (a) publishes a **`HarnessCapabilities` manifest** of what it natively supports and
(b) is the **materialiser** that translates the declaration into the harness's native dialect. The
Omnigent adapter is near pass-through. Arke keeps its own concise `permission` block as the portable
authorisation gate (it maps cleanly to SPEC-012 and to OpenCode's `permission` field), and treats
Omnigent's code-handler `policies` as an Omnigent-only opaque passthrough — Arke never runs arbitrary
handler code. The UI agent editor is **driven by the manifest**, so it can only ever offer capabilities
the connected harness can actually deliver. Rationale: adopting Omnigent's structure 100% keeps the
image portable; the manifest gives materialisation and the editor a single, offline-usable source of
truth; the permission/policies split preserves NFR-1 and avoids coupling native harnesses to Python
policy code.

### Target architecture
`@arke/agent-image` parses `tools` (keyed map), `skills` (directory), `policies` (opaque), `os_env`,
`params`, and `terminals` into a typed `AgentImage`, and gains a **config writer** (generalising the
SPEC-016-revised `setAgentModel`) that edits `config.yaml` surgically. `@arke/contracts` defines the
tool union (`McpTool | FunctionTool | AgentTool`), the passthrough `Policy`, and the
**`HarnessCapabilities`** type. Each `HarnessAdapter` exposes `capabilitiesManifest(): HarnessCapabilities`
and a `materializeCapabilities(image)` step invoked by `materializeAgent`: the OpenCode adapter writes an
`mcp` block into `opencode.json`, expresses tool gating through the agent's `permission` field, and
relies on native skill discovery; the Omnigent adapter emits the tools map verbatim. The coordinator
adds ops: `harness.capabilities` (return the manifest), `agent.create` (write a new image), and an
extended `agent.configure` (edit tools/permissions/skills/mcp, not only the model). The client's agent
editor (extending the SPEC-016-revised model chip) reads the manifest to render capability-aware
controls. The dispatch path (SPEC-016 model override) is unchanged.

### Data model
- `McpTool { type:"mcp", command?: string[], args?, url?, headers?, environment?, tools?: string[], enabled?, description? }`.
- `FunctionTool { type:"function", callable?, runtime?, parameters?, containerImage?, description? }`.
- `AgentTool { type:"agent", executor, prompt?, osEnv?, passHistory?, maxSessions? }` — `subAgents`
  (recursive `agents/<name>/`) remains the canonical source.
- `Tools = Record<string, McpTool | FunctionTool | AgentTool>` on `AgentImage`, replacing `ToolDecl[]`.
- `Skill { name, description?, path }` (existing `SkillRef`, from `skills/<name>/SKILL.md`).
- `Policy { name, type, handler, on: (...)[], … }` — carried opaque; not executed by Arke.
- `HarnessCapabilities { harness, version?, mcp: { local: boolean, remote: boolean }, skills: { supported: boolean, locations: string[] }, functionTools: boolean, sandbox: boolean, toolGating: "permission" | "tools-map" | "none", builtinTools: string[] }`.

### Interfaces and contracts
- `AgentImage.tools: Tools` (keyed map) — the breaking shape change from `ToolDecl[]`.
- `HarnessAdapter.capabilitiesManifest(): HarnessCapabilities` and
  `HarnessAdapter.materializeCapabilities?(image): Promise<{ registered: string[]; unsupported: { name, reason }[] }>`.
- OpenCode `opencode.json` `mcp` schema: `{ [name]: { type:"local", command: string[], environment?, enabled? } | { type:"remote", url, headers?, enabled? } }`; per-agent tool gating via the agent's `permission` field (incl. `<mcp>_*` wildcards).
- Coordinator ops: `harness.capabilities` → `HarnessCapabilities`; `agent.create { name, harness, model, mode? }`; `agent.configure` extended to `{ name, model?, permission?, tools?, skills? }`.
- Trace records: `capability.materialised { agent, harness, registered }` and `capability.unsupported { agent, harness, capability, reason }`.

### Cross-cutting
- **Security / NFR-1:** tool and MCP credentials are host-side only; the loader and the editor reject
  inline literal secrets and resolve `${VAR}` on the host at materialisation; MCP servers spawn
  processes, so they run under the same `os_env` sandbox / `permission` posture as the agent.
- **Observability:** every capability registration and every `capability.unsupported` skip is written to
  the trace (SPEC-015).
- **Design template:** the agent editor UI follows the `arke-design` skill (`.claude/skills/arke-design/`)
  — it extends the SPEC-016-revised model editor into a capability-aware panel (permissions, tools, MCP,
  skills), rendering only what the connected harness's manifest supports.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Replace the thin `ToolDecl[]` with Omnigent's **keyed `tools` map** (mcp/function/agent) carrying full wiring | The array captured only name+kind, so nothing could be materialised; adopting Omnigent's structure 100% keeps the image portable and makes tools actually work (breaking, but the surface is new/unused) |
| 2 | Keep Arke's `permission` block as the portable gate; carry Omnigent `policies` as **opaque passthrough** | `permission` maps cleanly to SPEC-012 **and to OpenCode's native `permission` field (incl. `<mcp>_*` wildcards)**; Arke cannot/should not execute arbitrary Python policy handlers, so `policies` only mean something on Omnigent |
| 3 | Skills stay the `skills/<name>/SKILL.md` **directory convention** | Verified against the live Omnigent repo AND the OpenCode docs — both auto-discover `SKILL.md` (OpenCode reads `.opencode/skills/` and `.claude/skills/`); materialising to OpenCode needs no config entry |
| 4 | Tool/MCP credentials are **host-side only** (NFR-1), via `${VAR}` interpolation or a host profile | Extends the SPEC-016 credential boundary to tools; an inline literal secret in a committed image (or an editor field) is a hard error |
| 5 | An unsupported capability **degrades with a recorded warning**, never silently | A harness that cannot express a capability must not present it as active — the projection stays honest |
| 6 | Each adapter owns a **`HarnessCapabilities` manifest** (docs-derived, versioned, offline-usable) as the source of truth | Arke has no generic way to enumerate a harness's native tools; a static, versioned manifest lets materialisation validate and the editor offer only real options without the harness running |
| 7 | Per-agent tool gating on OpenCode uses the **`permission` field**, not the deprecated per-agent `tools` map | The OpenCode docs mark per-agent `tools: {name: bool}` deprecated in favour of `permission`; Arke's existing `permission` block maps directly onto it |
| 8 | The UI agent editor is **manifest-driven** (capability-aware) | The editor must never offer a capability the connected harness cannot deliver; reading the manifest guarantees the options match reality |

## Open questions
- Manifest freshness: purely **static (docs-derived, versioned)**, or augmented at runtime where a
  harness exposes a live tool listing (OpenCode's server API — to confirm)? Start static, augment later?
- `container_image` / `sandbox.type` — wire to a real sandbox now, or accept-and-no-op initially (as we did for `os_env.sandbox`)?
- Adopt Omnigent's `self` / `inherit` tool semantics in this spec, or defer to a follow-up?
- `terminals` and `params` — carry them on the image now (passthrough) or defer until a harness consumes them?
- Editor scope: full CRUD on sub-agents (`type: agent`) in v1, or only mcp/function tools + skills + permissions first?
- Where does the agent editor live — the (currently hidden) roster screen promoted for this, or an overlay from the cockpit model chip?
