# Portable agent capabilities — declarative tools, MCP servers & skills, materialised per harness

## Why
SPEC-016 made the agent image the portable, parseable unit and this project then adopted Omnigent's
declarative `executor` (harness + model + provider) 100%. But an agent is defined as much by **what it
can do** as by which model it runs — its **MCP servers, code/function tools, sub-agents, and skills**.
Today Arke's image records those only as a thin `ToolDecl[] = {name, kind}` and the adapter **drops
them entirely** when it materialises the agent, so a declared MCP server or tool never reaches the
harness. To be a genuine light abstraction over Omnigent — and to work across native harnesses
(OpenCode, Claude SDK, Codex, …) — the image must carry the **full, Omnigent-shaped capability
declaration**, and each adapter must **materialise it into that harness's native config**. This closes
the last structural gap between an Arke agent image and an Omnigent agent, and makes tools/MCP/skills
actually functional rather than decorative.

## What changes
- ADDED agent-capabilities — the agent image gains a **rich, Omnigent-shaped `tools` map** (keyed by
  name) that fully describes each capability: an **MCP server** (local `command`/`args` or remote
  `url`/`headers`, with an optional exposed-tool whitelist), a **function tool** (`callable` +
  JSON-Schema `parameters`, optional sandbox container), or a **sub-agent** (its own `executor`).
  Replaces the thin `ToolDecl[]`. (breaking: yes — the `AgentImage.tools` shape changes; see Decision log #1)
- ADDED agent-capabilities — an adapter capability **`materializeCapabilities`**: each harness adapter
  translates the normalised tools/MCP/skills into that harness's native configuration (OpenCode's
  `opencode.json` `mcp` block + per-agent tool enablement; the Omnigent adapter passes the shape
  through near-verbatim). (breaking: no)
- MODIFIED agent-images — **skills** remain the `skills/<name>/SKILL.md` convention (already matching
  Omnigent and Claude Code) but are now **materialised** to harnesses that support them rather than
  parsed and dropped. (breaking: no)
- MODIFIED human-in-the-loop — Arke's `permission: {read|edit|bash|webfetch: allow|ask|deny}` remains
  the **portable, harness-agnostic gate** (mapped to the SPEC-012 permission flow); Omnigent's
  code-handler `policies` are carried as an **opaque passthrough** honoured only by the Omnigent
  harness, never required of a native harness. (breaking: no)
- ADDED agent-capabilities — the client agent roster/editor surfaces each agent's declared tools, MCP
  servers, and skills (names + kinds only; never a secret). (breaking: no)

## Requirements

### Requirement: The agent image declares capabilities as a rich, keyed tools map
`capability: agent-capabilities` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL parse an agent image's `tools:` as a **keyed map** (Omnigent-shaped, not an array),
where each entry is one of: an **MCP server** (`type: mcp` with either a local `command` + `args` or a
remote `url` + `headers`, and an optional `tools:` whitelist of exposed tool names); a **function
tool** (`type: function` with a `callable` reference and optional JSON-Schema `parameters`, `runtime`,
and sandbox `container_image`); or a **sub-agent** (`type: agent` carrying its own `executor`). The
loader SHALL retain enough of each entry to reconstruct a working configuration for a harness, and
SHALL reject a malformed entry with a clear `AgentImageError` rather than silently dropping it.

#### Scenario: An MCP server declaration round-trips with its spawn wiring
- **WHEN** an image declares `tools.github: { type: mcp, command: uv, args: [run, python, -m, pkg.github_mcp], tools: [search_issues] }`
- **THEN** the loaded `AgentImage` carries the MCP entry with its `command`, `args`, and exposed-tool whitelist intact
- **AND** a harness adapter can spawn that MCP server from the parsed entry alone.

#### Scenario: A function tool retains its callable and parameter schema
- **WHEN** an image declares `tools.summarize: { type: function, callable: pkg.tools.summarize, parameters: {...} }`
- **THEN** the loaded image carries the `callable` and the JSON-Schema `parameters` for that tool.

#### Scenario: A malformed tool entry fails loudly
- **WHEN** an image declares a `tools.x` with `type: mcp` but neither a `command` nor a `url`
- **THEN** loading the image raises an `AgentImageError` naming the offending tool.

### Requirement: Credentials for tools and MCP servers stay host-side
`capability: agent-capabilities` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL keep every credential a tool or MCP server needs on the host, never inline in the
committed image (NFR-1, extending SPEC-016). A committed image MAY reference a secret only by
**environment interpolation** (`${VAR}`) or a host-side profile/credentials reference; an inline
literal secret (e.g. a bearer token or api key value in `headers`/`env`) SHALL be rejected by the
loader. Interpolation is resolved on the host at materialisation time and the resolved value SHALL
never be sent to the client.

#### Scenario: An inline secret in an MCP header is rejected
- **WHEN** an image declares `tools.docs: { type: mcp, url: ..., headers: { Authorization: "Bearer sk-LITERAL" } }`
- **THEN** loading the image raises an `AgentImageError` directing the author to use `${VAR}` or a host-side profile.

#### Scenario: An interpolated secret resolves only on the host
- **WHEN** the same header is written as `Authorization: "Bearer ${DOCS_TOKEN}"`
- **THEN** the image loads
- **AND** the token is resolved from the host environment at materialisation
- **AND** neither the reference nor the resolved value appears in any client-facing projection.

### Requirement: Each harness adapter materialises capabilities into its native config
`capability: harness-integration` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL translate the normalised tools/MCP/skills of an agent image into the connected
harness's **native configuration** when the agent is materialised. For the OpenCode adapter this
SHALL write the MCP servers into `opencode.json`'s `mcp` block (local `{ type: local, command }` /
remote `{ type: remote, url }`) and enable the agent's tools in the agent's own materialised file; for
the Omnigent adapter it SHALL pass the Omnigent-shaped declaration through near-verbatim. A capability
a harness does not support SHALL be **skipped with a recorded warning**, never silently presented as
supported.

#### Scenario: An OpenCode agent's MCP server lands in opencode.json
- **WHEN** an image with `tools.github: { type: mcp, command: ..., args: [...] }` is materialised against the OpenCode adapter
- **THEN** `opencode.json` gains an `mcp.github` entry of `type: local` with that command
- **AND** the agent's materialised markdown enables the `github` tool for that agent.

#### Scenario: An unsupported capability degrades gracefully
- **WHEN** an image declares a capability the connected harness cannot express (e.g. a function tool with a `container_image` the harness does not sandbox)
- **THEN** materialisation completes for everything else
- **AND** a `capability.unsupported` warning is recorded naming the tool and the harness
- **AND** the projection never claims the unsupported capability is active.

### Requirement: Skills are the SKILL.md convention and materialise where supported
`capability: agent-images` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

The system SHALL discover an agent's skills from `skills/<name>/SKILL.md` (each with `name` +
`description` frontmatter and a progressive-disclosure body), matching Omnigent and Claude Code. On a
harness that supports skills the adapter SHALL make them available to the agent (e.g. materialised into
the harness's skills location); on a harness that does not, the skills SHALL remain discoverable
metadata and the loader SHALL NOT fail. Skills are never invented in YAML — the directory is the source
of truth.

#### Scenario: A skill is discovered and surfaced
- **WHEN** an agent directory contains `skills/debate/SKILL.md` with `name: debate`
- **THEN** the loaded image lists the `debate` skill with its description
- **AND** the roster surfaces it.

#### Scenario: A skill-less harness does not fail on skills
- **WHEN** an image with skills is materialised against a harness that has no skills mechanism
- **THEN** materialisation succeeds and a warning records that skills were not projected to that harness.

### Requirement: Arke's permission block is the portable gate; Omnigent policies are opaque passthrough
`capability: human-in-the-loop` · `delta: MODIFIED (feat/spec-021-agent-capabilities)`

The system SHALL treat the image's `permission: {read|edit|bash|webfetch: allow|ask|deny}` as the
**portable, harness-agnostic** authorisation gate, mapped to the SPEC-012 human-in-the-loop flow on
every harness. Omnigent's code-handler `policies` (function `handler` on `[request|response|tool_call|
tool_result]`) SHALL be carried on the image as an **opaque passthrough** honoured only by the Omnigent
harness; a native harness SHALL NOT be required to execute them and SHALL ignore them with a recorded
note. Arke SHALL NOT execute arbitrary policy handler code itself.

#### Scenario: Permission gates a tool on a native harness
- **WHEN** an agent with `permission: { bash: ask }` runs a shell tool on the OpenCode harness
- **THEN** the action routes through the SPEC-012 permission flow (once/always/reject) exactly as today.

#### Scenario: Omnigent policies pass through untouched
- **WHEN** an image carries `policies.pii_guard: { type: function, handler: ..., on: [response] }` and runs on the Omnigent harness
- **THEN** the policy declaration reaches Omnigent verbatim
- **AND** on a native harness the same declaration is ignored with a recorded note, and the image still loads and runs.

### Requirement: The client surfaces an agent's declared capabilities without leaking secrets
`capability: agent-capabilities` · `delta: ADDED (feat/spec-021-agent-capabilities)`

The system SHALL show, in the agent roster/editor, each agent's declared capabilities — tool names and
kinds (mcp / function / agent), MCP endpoints by name, and skills by name — so an operator can see what
an agent can do. The projection SHALL carry no credential value, no `${VAR}` resolution, and no
credentials reference; it is names and kinds only.

#### Scenario: The roster lists an agent's tools and skills
- **WHEN** an operator opens the roster for an agent with a `github` MCP tool and a `debate` skill
- **THEN** the roster shows `github (mcp)` and the `debate` skill
- **AND** the response contains no token, header value, or credentials reference.

## Design

### Architectural decision
The agent image is the **single normalised, Omnigent-shaped description** of an agent's capabilities;
each harness adapter is a **materialiser** that translates that description into the harness's native
dialect; the Omnigent adapter is near pass-through. Arke keeps its own concise `permission` block as the
portable authorisation gate (it maps cleanly to SPEC-012 and every harness), and treats Omnigent's
code-handler `policies` as an Omnigent-only opaque passthrough — Arke never runs arbitrary handler code.
Rationale: adopting Omnigent's structure 100% keeps the image portable and future-proof, while the
per-adapter materialiser is the only place that must understand each harness's config, and the
permission/policies split preserves NFR-1 and avoids coupling native harnesses to Python policy code.

### Target architecture
`@arke/agent-image` parses `tools` (keyed map), `skills` (directory), `policies` (opaque), `os_env`,
`params`, and `terminals` into a typed `AgentImage`. `@arke/contracts` defines the tool union
(`McpTool | FunctionTool | AgentTool`) and the passthrough `Policy`. The coordinator's `AgentRegistry`
indexes images unchanged. The `HarnessAdapter` gains a `materializeCapabilities(image)` step invoked by
`materializeAgent`: the OpenCode adapter writes an `mcp` block into `opencode.json` and per-agent tool
enablement into the agent's `.opencode/agents/<name>.md`; the Omnigent adapter emits the tools map
verbatim; a harness with no mechanism for a capability records a `capability.unsupported` warning. The
dispatch path (SPEC-016 model override) is unchanged.

### Data model
- `McpTool { type: "mcp", command?, args?, url?, headers?, env?, tools?: string[], description? }` — a
  local (command/args) or remote (url/headers) MCP server, with an optional exposed-tool whitelist.
- `FunctionTool { type: "function", callable?, runtime?, parameters?, containerImage?, description? }`.
- `AgentTool { type: "agent", executor, prompt?, osEnv?, passHistory?, maxSessions? }` — a sub-agent
  (its own executor); `subAgents` (recursive `agents/<name>/`) remains the canonical source.
- `Tools = Record<string, McpTool | FunctionTool | AgentTool>` on `AgentImage`, replacing `ToolDecl[]`.
- `Skill { name, description?, path }` (existing `SkillRef`, from `skills/<name>/SKILL.md`).
- `Policy { name, type, handler, on: ("request"|"response"|"tool_call"|"tool_result")[], … }` — carried
  opaque; not executed by Arke.
- `osEnv` (existing, SPEC-016 adoption): `{ type, cwd?, sandbox?: { type, writePaths?, allowNetwork? } }`.

### Interfaces and contracts
- `AgentImage.tools: Tools` (keyed map) — the breaking shape change from `ToolDecl[]`.
- `HarnessAdapter.materializeCapabilities?(image): Promise<CapabilityMaterialisation>` where the result
  reports `{ registered: string[]; unsupported: { name, reason }[] }`, folded into the trace.
- OpenCode `opencode.json` `mcp` schema: `{ [name]: { type: "local", command: string[] } | { type: "remote", url: string } }`, plus per-agent `tools: { [name]: boolean }` in the agent file.
- A `capability.unsupported` trace record `{ agent, harness, capability, reason }`.

### Cross-cutting
- **Security / NFR-1:** tool and MCP credentials are host-side only; the loader rejects inline literal
  secrets and resolves `${VAR}` on the host at materialisation; MCP servers spawn processes, so they run
  under the same `os_env` sandbox / `permission` posture as the agent.
- **Observability:** every capability registration and every `capability.unsupported` skip is written to
  the trace (SPEC-015), so an operator can see exactly what materialised on each harness.
- **Design template:** the roster/editor UI follows the `arke-design` skill (`.claude/skills/arke-design/`)
  — it extends the SPEC-016-revised agent editor with a read-only capabilities list.

### Testing
- Unit (loader): mcp/function/agent entries round-trip with full wiring; inline-secret and malformed
  entries are rejected; `${VAR}` is preserved unresolved in the image; skills discovered from `skills/`.
- Unit (adapter): materialising an image with an MCP tool writes the expected `opencode.json` `mcp`
  entry + per-agent enablement; an unsupported capability yields a `capability.unsupported` record and
  does not abort the rest.
- Integration: an agent with a real (local, trivial) MCP server materialises and the server is
  reachable from the harness; the roster projection carries names/kinds and no secret.
- Verify: end-to-end against a running OpenCode + a small MCP server — the agent can call an MCP tool
  driven through the coordinator.

### Definition of done
- All scenarios for the requirements above pass under review.
- `AgentImage.tools` is the keyed Omnigent-shaped map; the OpenCode adapter materialises MCP + tools +
  skills into native config and records unsupported capabilities; the Omnigent adapter passes them
  through; credentials never leave the host and never reach the client.
- Full workspace typecheck + tests green; a reviewer confirms (i) NFR-1 holds for tool/MCP credentials
  and (ii) the tools shape matches the live Omnigent `AGENT_YAML_SPEC.md`.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Replace the thin `ToolDecl[]` with Omnigent's **keyed `tools` map** (mcp/function/agent) carrying full wiring | The array captured only name+kind, so nothing could be materialised; adopting Omnigent's structure 100% keeps the image portable and makes tools actually work (breaking, but the surface is new/unused) |
| 2 | Keep Arke's `permission` block as the portable gate; carry Omnigent `policies` as **opaque passthrough** | `permission` maps cleanly to SPEC-012 on every harness; Arke cannot (and should not) execute arbitrary Python policy handlers, so `policies` only mean something on the Omnigent harness |
| 3 | Skills stay the `skills/<name>/SKILL.md` **directory convention** | Verified against the live Omnigent repo (`examples/debby/skills/debate/SKILL.md`) — it matches Claude Code and Arke's existing discovery; no YAML field needed |
| 4 | Tool/MCP credentials are **host-side only** (NFR-1), via `${VAR}` interpolation or a host profile | Extends the SPEC-016 credential boundary to tools; an inline literal secret in a committed image is a hard error |
| 5 | An unsupported capability **degrades with a recorded warning**, never silently | A harness that cannot express a capability must not present it as active — the projection stays honest |

## Open questions
