# Cross-repo specifications — canonical spec, ripple linkage & deterministic pointer projection

> **Sketch.** This is the first draft of the mechanism decided in
> [ADR 0005](../decisions/0005-multi-codebase-spec-storage.md): a specification that touches
> multiple codebases has **one canonical authored copy** in the repo that owns the capability;
> every other affected repo carries either a thin locally-authored **ripple spec** or a
> **generated read-only pointer** — never a copy. This spec makes that convention machine-readable
> and gives the coordinator the behaviour to enforce and visualise it.

## Why

A spec sometimes drives work in several repositories (a contract repo plus its consumers, a
protocol change spanning client and server). Today Arke has no first-class shape for this: each
project context (SPEC-018) has its own isolated spec library, so a multi-repo change is either
duplicated (drift), informal (a prose mention), or invisible (the affected repo has no trace of
the driver). ADR 0005 fixes the convention; this spec fixes the tooling — linkage in frontmatter,
validation and staleness signalling in the coordinator, pointer generation as a deterministic
projection, and linkage rendered in the library and board.

## What changes

- ADDED cross-repo-specs — canonical specs MAY declare `ripples:` and ripple specs MUST declare `canonical:` in frontmatter; the coordinator parses, validates, and exposes the linkage
- ADDED ripple-projection — a deterministic, logged projection generates read-only **pointer stubs** into affected repos that have no local contract change (per AGENTS.md rule 4, in the style of SPEC-026's generated indexes)
- MODIFIED spec-lifecycle — a material change to a canonical spec marks its ripples **stale**, surfaced in each affected project's library; staleness never resolves silently (breaking: no — specs without linkage frontmatter behave exactly as today) (cross-ref SPEC-008, SPEC-024)
- MODIFIED library/board — the spec library and the board card surface cross-repo linkage for the active project (canonical ⇄ ripples, with per-ripple status); a full cross-project board remains deferred (cross-ref SPEC-010, SPEC-018)

## Requirements

### Requirement: Cross-repo linkage is declared in frontmatter, both directions
`capability: cross-repo-specs` · `delta: ADDED (claude/multi-codebase-spec-storage-c9viul)`

A canonical specification MAY declare the repositories it ripples to, and every ripple
specification MUST declare its canonical, using frontmatter of the shape:

```yaml
# on the canonical spec
ripples:
  - repo: <org>/<repo>          # or a registered projectId (SPEC-018)
    spec: <spec_id | generated> # the ripple spec's id, or `generated` for a pointer stub
    kind: delta | pointer

# on a ripple spec
canonical:
  repo: <org>/<repo>
  spec: <spec_id>
```

The coordinator SHALL parse this linkage when loading a project's spec library and SHALL treat a
`kind: delta` ripple as locally authored contract and a `kind: pointer` ripple as a generated
projection. A spec with neither field is a plain single-repo spec and SHALL behave exactly as
today.

#### Scenario: Linkage is parsed and exposed
- **WHEN** a project's library contains a canonical spec with two declared ripples
- **THEN** the coordinator's spec read model records the linkage (repo, spec, kind) on the canonical spec
- **AND** a library query for that spec returns its ripples

#### Scenario: A dangling back-reference is reported, not trusted
- **WHEN** a ripple spec's `canonical:` names a repo/spec the coordinator cannot resolve among registered projects
- **THEN** the library marks the ripple `unresolved` with the reason
- **AND** nothing is silently dropped or auto-corrected

### Requirement: One authored copy — pointer stubs are generated, read-only projections
`capability: ripple-projection` · `delta: ADDED (claude/multi-codebase-spec-storage-c9viul)`

For an affected repo with no local contract change, the system SHALL generate a **pointer stub**
into that repo's `docs/specifications/` as a deterministic projection of the canonical spec's
frontmatter and summary: a short read-only markdown file carrying `canonical:` frontmatter, the
canonical title/status/capabilities, and a "generated — do not hand-edit" marker (the SPEC-026
posture). Every stub write SHALL be logged to the writing project's trace with its trigger, and
regeneration SHALL be idempotent. The projection SHALL never copy requirement bodies — a stub is
a pointer, not a mirror — and stub content SHALL never flow back into the canonical spec.

#### Scenario: A stub is generated, logged, and idempotent
- **WHEN** the projection runs for a canonical spec that declares a `kind: pointer` ripple to project B
- **THEN** project B's library gains a stub file with the canonical reference and current status
- **AND** the write is recorded in B's trace with the canonical spec as trigger
- **AND** re-running the projection with no upstream change rewrites nothing

#### Scenario: A hand-edited stub is regenerated, loudly
- **WHEN** a generated stub has been hand-edited and the projection next runs
- **THEN** the stub is regenerated from the canonical spec and the overwrite is recorded
- **AND** no hand-written content is treated as contract

### Requirement: Canonical changes surface on ripples — staleness is never silent
`capability: spec-lifecycle` · `delta: MODIFIED (claude/multi-codebase-spec-storage-c9viul)`

The system SHALL extend the spec lifecycle (SPEC-008, SPEC-024) so that a material change to a
canonical specification — a status transition, or a commit touching its Requirements — marks each
of its ripples **stale** in the affected project's library, with the canonical change (commit /
status) that caused it. For `kind: pointer` ripples, regeneration clears staleness. For
`kind: delta` ripples, staleness SHALL persist until a human acknowledges it in that project
(re-review or an explicit "no local impact" decision), and that acknowledgement SHALL be recorded
in the affected project's trace.

#### Scenario: A canonical revision marks delta ripples stale
- **WHEN** a canonical spec drops from approved back to in-review with a requirement change
- **THEN** each linked `kind: delta` ripple shows stale in its project's library, citing the canonical change
- **AND** the staleness persists until acknowledged by a human in that project

#### Scenario: Acknowledgement is a recorded decision
- **WHEN** an engineer acknowledges a stale ripple as "no local impact"
- **THEN** the ripple returns to its prior status
- **AND** the acknowledgement (who, when, canonical trigger) is appended to that project's trace

### Requirement: Linkage is visible in the library and on the board
`capability: cross-repo-specs` · `delta: ADDED (claude/multi-codebase-spec-storage-c9viul)`

For the **active project** (SPEC-018), the spec library and the spec's board card (SPEC-023)
SHALL surface cross-repo linkage: a canonical spec lists its ripples with each ripple's repo,
kind, status, and staleness; a ripple spec links back to its canonical. Repos not registered as
projects SHALL render as inert references (no status). A cross-project board remains out of
scope (deferred per SPEC-010/SPEC-018); this requirement is linkage *on the active project's
surfaces only*.

#### Scenario: The canonical card shows ripple health
- **WHEN** the board renders a canonical spec's card and one of its delta ripples is stale
- **THEN** the card shows the ripple set with the stale ripple distinguished
- **AND** following the ripple opens it in its own project context (or renders inert if unregistered)

## Design

### Architectural decision
Linkage lives in **spec frontmatter** (git-versioned, reviewable, harness-agnostic) rather than in
coordinator state; the coordinator only *reads, validates, projects, and renders* it. This keeps
the specification the source of truth (rule 1) and makes the whole mechanism survive outside Arke
— the frontmatter is meaningful to a human with no coordinator running.

### Target architecture
- `packages/contracts` — zod schemas for `ripples` / `canonical` frontmatter and the linkage
  entries in the spec read model.
- `packages/coordinator` — linkage resolution across registered project contexts (SPEC-018's
  `ProjectRegistry` maps `repo` → `projectId` where possible); the pointer-stub projection as a
  deterministic projection module (SPEC-014 pattern); staleness tracking + acknowledgement op.
- `packages/client` — library rows and board-card affordances for ripple sets and staleness.

### Interfaces and contracts (sketch)
```typescript
{ type: 'request', op: 'spec.links',        args: { specId } }              // → linkage + per-ripple status
{ type: 'request', op: 'spec.ripple.ack',   args: { specId, reason } }      // acknowledge staleness (recorded)
{ type: 'request', op: 'spec.ripple.project', args: { specId } }           // regenerate pointer stubs (logged)
```

### Cross-cutting
- **Governance (rule 3):** stub generation into another repo is a projection write — proposed,
  decided, executed, and logged like any SPEC-014 projection; it never bypasses review in the
  target repo (it lands as a change to commit there, not a silent write to a system of record).
- **Isolation (SPEC-018 / NFR-1):** resolution never reads another project's files directly; it
  goes through that project's context, and unregistered repos degrade to inert references.
- **Design template:** the UI follows the `arke-design` skill (`.claude/skills/arke-design/`).

## Tasks
- [ ] Contracts: zod schemas for `ripples:` / `canonical:` frontmatter + linkage in the spec read model
- [ ] Coordinator: parse + validate linkage on library load; resolve repos against the project registry; `spec.links` op
- [ ] Coordinator: pointer-stub projection (deterministic, idempotent, trace-logged; SPEC-026-style generated marker)
- [ ] Coordinator: staleness on material canonical change; `spec.ripple.ack` with trace record
- [ ] Client: ripple set + staleness on library rows and the board card (active project only)
- [ ] Docs: worked example under `docs/specifications/examples/` (one canonical + one delta ripple + one pointer stub)

### Testing
- Unit: frontmatter schemas (valid, dangling, malformed); stub idempotency; staleness transitions.
- Integration: two registered projects — canonical change in A marks B's delta ripple stale; ack clears it and is traced; pointer stub regenerates and logs in B.
- Manual: unregistered repo renders inert; hand-edited stub is regenerated loudly.

### Definition of done
All scenarios pass; linkage renders in the library and on cards for the active project; stub
generation and staleness acknowledgement both appear in the correct project's trace; `typecheck`
and `build` green; a reviewer has signed off.

## Decision log
| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Linkage in frontmatter, not coordinator state | Spec stays the source of truth; reviewable in the same PR; meaningful without Arke running |
| 2 | Two ripple kinds only — authored `delta` or generated `pointer` | Matches ADR 0005; anything in between is a disguised copy |
| 3 | Staleness on delta ripples requires human acknowledgement | Propose · decide · execute (rule 3); a cross-repo contract change must never be absorbed silently |
| 4 | Cross-project board stays deferred | Linkage on the active project's surfaces covers the need SPEC-030 introduces; a full board is its own spec (SPEC-010/018 open question) |

## Open questions
- `repo` identity: git remote URL, `org/repo` slug, or SPEC-018 `projectId` — and how to
  canonicalise across the three (registry-assisted, with slug as the portable form?)
- Should the pointer-stub projection run automatically on canonical merge (webhook, SPEC-008) or
  only on explicit `spec.ripple.project`?
- Does a canonical spec's **approval** gate on its delta ripples reaching in-review (a lifecycle
  coupling, SPEC-024), or is staleness signalling enough?
- How does linkage flatten on merge — do `ripples:` entries persist as settled metadata, or move
  to the change history once delivered?
- Repo-less specifications (org-wide policy; ADR 0005 decision 4): in scope here as a canonical
  with only ripples and no local code, or a separate convention?
