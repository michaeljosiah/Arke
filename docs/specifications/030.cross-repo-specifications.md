# Cross-repo specifications — canonical spec, ripple linkage & deterministic pointer projection

The mechanism decided in [ADR 0005](../decisions/0005-multi-codebase-spec-storage.md): a specification that
touches multiple codebases has **one canonical authored copy** in the repo that owns the capability; every
other affected repo carries either a thin locally-authored **ripple spec** or a **generated read-only
pointer** — never a copy. This spec makes that convention machine-readable and gives the coordinator the
behaviour to resolve, project, keep honest, and visualise it.

## Why

A spec sometimes drives work in several repositories (a contract repo plus its consumers, a protocol change
spanning client and server). Today Arke has no first-class shape for this: each project context (SPEC-018)
has its own isolated spec library, so a multi-repo change is either duplicated (drift), informal (a prose
mention), or invisible (the affected repo has no trace of the driver). ADR 0005 fixes the convention; this
spec fixes the tooling — linkage in frontmatter, resolution across registered projects, deterministic pointer
generation, staleness signalling that never resolves silently, and linkage rendered in the library and board.

## What changes

- ADDED cross-repo-specs — a canonical spec MAY declare `ripples:` and a ripple spec MUST declare
  `canonical:` in frontmatter; the coordinator parses the (nested) linkage, resolves each `repo` against the
  registered projects, and exposes it on the spec read model. Linkage is a **standing relationship** — it
  persists across delivery (it does not flatten like a `delta:` tag).
- ADDED ripple-projection — a deterministic, idempotent, trace-logged projection generates read-only
  **pointer stubs** into affected repos that have no local contract change, in the style of SPEC-026's
  generated indexes. The stub write is **supervisor-mediated** through the target project's own context so
  SPEC-018 isolation holds; it lands as an uncommitted working-tree change to review + commit there, never
  an auto-commit/push.
- MODIFIED spec-lifecycle — a material change to a canonical spec (its normative hash changes, or it
  regresses status) marks each of its ripples **stale** in the affected project's library, citing the
  canonical change; a `kind: pointer` ripple clears on regeneration, a `kind: delta` ripple stays stale until
  a human acknowledges it in that project. Staleness never resolves silently. *(breaking: no — a spec with no
  linkage frontmatter behaves exactly as today.)* (cross-ref SPEC-008, SPEC-024)
- MODIFIED library/board — the spec library and the board card surface cross-repo linkage for the **active
  project** (canonical ⇄ ripples, per-ripple resolution + staleness); a full cross-project board stays
  deferred (cross-ref SPEC-010, SPEC-018).

**Depends on:** SPEC-018 (multi-project workspaces + registry), SPEC-025 (repo identity — the git remote), SPEC-026
(generated-projection precedent), SPEC-008/024 (lifecycle + material-change detection). Grounded in ADR 0005.

## Requirements

### Requirement: Cross-repo linkage is declared in frontmatter, both directions
`capability: cross-repo-specs` · `delta: ADDED (feat/spec-030-cross-repo-specs)`

A canonical specification MAY declare the repositories it ripples to, and every ripple specification MUST
declare its canonical, using frontmatter of the shape:

```yaml
# on the canonical spec
ripples:
  - repo: <org>/<repo>          # portable git-remote slug (see resolution below)
    spec: <spec_id | generated> # the ripple spec's id, or `generated` for a pointer stub
    kind: delta | pointer

# on a ripple spec
canonical:
  repo: <org>/<repo>
  spec: <spec_id>
```

Because the existing `parseFrontmatter` is a FLAT scalar parser and `SpecFrontmatter` (zod) drops unknown
keys, the coordinator SHALL add a dedicated, side-effect-free linkage parser that reads these two nested
blocks and validates them against new zod schemas (`RippleLink`, `CanonicalLink`), leaving the flat
frontmatter path untouched. A `kind: delta` ripple SHALL be treated as locally-authored contract; a
`kind: pointer` ripple as a generated projection. A spec with neither field is a plain single-repo spec and
SHALL behave exactly as today. Malformed linkage (missing `repo`/`spec`, unknown `kind`) SHALL be surfaced as
a parse warning on the spec's library record, never silently dropped and never fatal to loading the library.

#### Scenario: Linkage is parsed and exposed
- **WHEN** a project's library contains a canonical spec with two declared ripples
- **THEN** the coordinator's spec read model records the linkage (`repo`, `spec`, `kind`) on the canonical spec
- **AND** a `spec.links` query for that spec returns its ripples

#### Scenario: Malformed linkage is reported, not fatal
- **WHEN** a spec declares a `ripples:` entry missing its `spec` field, or an unknown `kind`
- **THEN** the library loads normally and that spec's record carries a linkage-parse warning naming the defect
- **AND** no other spec is affected and nothing is silently dropped

#### Scenario: A plain spec is unchanged
- **WHEN** a spec has neither `ripples:` nor `canonical:`
- **THEN** it parses, lists, and lifecycles exactly as before this spec

### Requirement: A repo is resolved by its portable git-remote slug
`capability: cross-repo-specs` · `delta: ADDED (feat/spec-030-cross-repo-specs)`

Linkage `repo` values SHALL be portable **`org/repo` slugs** (the human-readable, git-remote-derived form —
meaningful without Arke running, per ADR 0005), not opaque `projectId` hashes. The coordinator SHALL maintain
a supervisor-level index from `org/repo` slug → registered `projectId`, derived from each open project's git
remote (SPEC-025 `repo.identity`), and refreshed when a project opens or its remote changes. A ripple whose
`repo` slug resolves to a registered project SHALL carry that `projectId` (and become actionable — projectable,
navigable); a ripple whose slug does not resolve SHALL be marked **`unresolved`** and render as an inert
reference (no status, no cross-context action), with the reason recorded. Resolution SHALL never read another
project's files directly — it consults only the supervisor's slug index (SPEC-018 / NFR-1).

#### Scenario: A registered ripple target resolves
- **WHEN** a ripple names `repo: acme/widgets` and a project with git remote `github.com/acme/widgets` is registered
- **THEN** the ripple record carries that project's `projectId` and is actionable

#### Scenario: An unregistered repo is inert, not an error
- **WHEN** a ripple names a repo with no matching registered project
- **THEN** the ripple renders as an inert reference marked `unresolved` with the reason
- **AND** no cross-context action is attempted against it

### Requirement: One authored copy — pointer stubs are generated, read-only, supervisor-mediated projections
`capability: ripple-projection` · `delta: ADDED (feat/spec-030-cross-repo-specs)`

For an affected repo with no local contract change, the system SHALL generate a **pointer stub** into that
repo's `docs/specifications/` as a deterministic projection of the canonical spec's frontmatter and summary:
a short read-only markdown file carrying `canonical:` frontmatter, the canonical title/status/capabilities, and
a "generated — do not hand-edit" marker (the SPEC-026 posture). The projection SHALL run **through the target
project's own `ProjectContext`** — the owning (canonical) context never writes another repo's files; a
supervisor-mediated call asks the resolved target context to write/refresh the stub and log it to **that
project's** trace. Regeneration SHALL be idempotent (rewrite nothing when the canonical is unchanged) and
SHALL never copy requirement bodies — a stub is a pointer, not a mirror — and stub content SHALL never flow
back into the canonical. The stub SHALL land as an uncommitted working-tree change in the target repo (to be
reviewed and committed there), never an auto-commit or push. A `kind: pointer` ripple with no registered target
SHALL be a no-op (inert), logged as skipped.

#### Scenario: A stub is generated through the target context, logged, and idempotent
- **WHEN** `spec.ripple.project` runs for a canonical spec that declares a `kind: pointer` ripple to registered project B
- **THEN** project B's `docs/specifications/` gains (or refreshes) a generated stub with the canonical reference and current status
- **AND** the write is recorded in **B's** trace with the canonical spec + trigger
- **AND** re-running with no upstream change rewrites nothing

#### Scenario: A hand-edited stub is regenerated, loudly
- **WHEN** a generated stub has been hand-edited and the projection next runs
- **THEN** the stub is regenerated from the canonical spec and the overwrite is recorded in B's trace
- **AND** no hand-written content is treated as contract

#### Scenario: The owning context never touches the peer's files
- **WHEN** the projection writes into project B
- **THEN** the write is performed by B's own `ProjectContext`, not by the canonical's context reaching across
- **AND** an unregistered pointer target is skipped (logged), not written

### Requirement: Canonical changes surface on ripples — staleness is never silent
`capability: spec-lifecycle` · `delta: MODIFIED (feat/spec-030-cross-repo-specs)`

The system SHALL extend the spec lifecycle (SPEC-008, SPEC-024) so that a **material change** to a canonical
specification — detected by the existing `isMaterialChange`/`normativeHash` on its Requirements + Design, or a
status regression — marks each of its ripples **stale** in the affected project's library, citing the canonical
change (the normative-hash delta and/or status transition) that caused it, via a `spec.ripple-stale` event and
a trace record in the affected project. For `kind: pointer` ripples, a subsequent `spec.ripple.project`
regeneration clears staleness. For `kind: delta` ripples, staleness SHALL persist until a human acknowledges
it in that project. The cascade SHALL be supervisor-mediated and SHALL degrade gracefully — an unresolved
ripple target cannot be marked (it is inert), and the canonical's own transition SHALL NOT fail because a
ripple could not be reached (best-effort cascade, logged).

#### Scenario: A canonical revision marks delta ripples stale
- **WHEN** a canonical spec's Requirements are materially edited (its normative hash changes)
- **THEN** each linked, resolved `kind: delta` ripple shows stale in its project's library, citing the canonical change
- **AND** the staleness persists until acknowledged by a human in that project

#### Scenario: A pointer ripple's staleness clears on regeneration
- **WHEN** a `kind: pointer` ripple is stale and `spec.ripple.project` regenerates its stub from the current canonical
- **THEN** the stub is refreshed and the ripple is no longer stale

#### Scenario: The cascade never breaks the canonical's own lifecycle
- **WHEN** a canonical materially changes but one ripple target is unregistered/unreachable
- **THEN** the reachable ripples are marked stale, the unreachable one is logged as skipped
- **AND** the canonical's own status transition completes normally

### Requirement: Ripple acknowledgement is a recorded decision
`capability: spec-lifecycle` · `delta: MODIFIED (feat/spec-030-cross-repo-specs)`

Acknowledging a stale `kind: delta` ripple SHALL be an explicit, recorded human decision in the **affected**
project (re-review, or an explicit "no local impact"): `spec.ripple.ack { specId, reason, actor? }` clears the
ripple's staleness in that project and appends the acknowledgement (who, when, canonical trigger, reason) to
that project's trace. Acknowledgement SHALL be idempotent and SHALL refuse a spec that is not a currently-stale
ripple (named error, no state change).

#### Scenario: Acknowledgement clears staleness and is traced
- **WHEN** an engineer acknowledges a stale delta ripple as "no local impact" in its project
- **THEN** the ripple returns to its prior (non-stale) status
- **AND** the acknowledgement — actor, timestamp, canonical trigger, reason — is appended to that project's trace

#### Scenario: Acknowledging a non-stale spec is refused
- **WHEN** `spec.ripple.ack` targets a spec that is not a currently-stale ripple
- **THEN** it is rejected with a named error and no trace record or state change is written

### Requirement: Linkage is visible in the library and on the board (active project)
`capability: cross-repo-specs` · `delta: ADDED (feat/spec-030-cross-repo-specs)`

For the **active project** (SPEC-018), the spec library and the spec's board card (SPEC-023) SHALL surface
cross-repo linkage: a canonical spec lists its ripples with each ripple's repo, kind, resolution, status, and
staleness; a ripple spec links back to its canonical and shows its own staleness. Unregistered repos SHALL
render as inert references (no status, not navigable). Following a resolved ripple SHALL open it in its own
project context. A cross-project board stays out of scope (deferred per SPEC-010/SPEC-018); this is linkage on
the active project's surfaces only.

#### Scenario: The canonical card shows ripple health
- **WHEN** the board renders a canonical spec's card and one of its resolved delta ripples is stale
- **THEN** the card shows the ripple set with the stale ripple distinguished
- **AND** following the ripple opens it in its own project context, or renders inert if unresolved

#### Scenario: A ripple links back and shows its own staleness
- **WHEN** the library renders a `kind: delta` ripple that is currently stale
- **THEN** its row links to the canonical (repo + spec) and is marked stale with the canonical trigger

## Design

### Architectural decision

Linkage lives in **spec frontmatter** — git-versioned, reviewable in the same PR as the change, and meaningful
to a human with no coordinator running (ADR 0005, rule 1). The coordinator only *reads, resolves, projects,
keeps honest, and renders* it; it holds no authoritative linkage state of its own. This is the first feature
that requires **supervisor-mediated cross-context interaction**: SPEC-018 keeps project contexts isolated, so
every cross-repo action (resolve a target, write a stub into it, mark its ripple stale, acknowledge) is
brokered by the `Coordinator` (the supervisor that owns `contexts: Map<projectId, ProjectContext>`) and
executed **by the target context on its own files/trace** — a context never reaches into a peer's filesystem.

### Target architecture

- **`packages/contracts`** (`spec.ts`, `events.ts`): `RippleLink { repo, spec, kind }` and `CanonicalLink {
  repo, spec }` zod schemas; linkage fields on the spec-library record; `spec.ripple-stale` / `spec.ripple-acked`
  events. `SpecFrontmatter` stays scalar-only — linkage is parsed separately.
- **`packages/coordinator`**:
  - **Linkage parser** — a dedicated `parseLinkage(frontmatterBlock)` (the flat `parseFrontmatter` cannot read
    the nested `ripples:` list / `canonical:` map). Pure + unit-tested; returns `{ ripples[], canonical?,
    warnings[] }`.
  - **Read model** — `specLibrary()` attaches parsed + resolved linkage to each `SpecLibraryRecord`
    (`ripples?: ResolvedRipple[]`, `canonical?: ResolvedCanonical`, `linkageWarnings?`, `rippleStale?`).
  - **`CrossRepoLinker` (supervisor)** — owned by `Coordinator`; maintains the `slug → projectId` index from
    each context's `repo.identity` (SPEC-025 `gitRepoIdentity`), and brokers the three cross-context calls to
    narrow, whitelisted methods on the target `ProjectContext`: `writePointerStub(canonicalRef)`,
    `markRipplesStale(canonicalRef, trigger)`, `ackRipple(specId, …)`. Resolution + brokering only — no file IO
    of its own.
  - **`ProjectContext`** — new ops in `dispatch()`: `spec.links` (resolve + return linkage for a spec in this
    project), `spec.ripple.project` (ask the linker to (re)generate each pointer stub — the canonical side),
    `spec.ripple.ack` (clear + trace a stale ripple — the affected side). Stub generation follows
    `regenerateBundleIndex`'s idempotent write-if-changed + trace posture; the staleness cascade hooks the
    existing `isMaterialChange(rec.normativeHash, text)` check in `applyTransition`/the webhook path.
- **`packages/client`** (`live.ts`, library rows, `board-*` card): ripple sets, resolution/inert state, and
  staleness on the active project's surfaces; a "regenerate stubs" affordance on a canonical; an
  "acknowledge" affordance on a stale delta ripple.

### Interfaces and contracts

**New ops (client → coordinator):**
```typescript
{ op: "spec.links",         args: { specId } }            // → { canonical?, ripples: ResolvedRipple[], warnings[] }
{ op: "spec.ripple.project", args: { specId } }           // (canonical side) regenerate pointer stubs → per-target result
{ op: "spec.ripple.ack",    args: { specId, reason, actor? } } // (affected side) clear + trace staleness
```

**New events (coordinator → client):**
```typescript
{ type: "spec.ripple-stale",  specId, canonicalRepo, canonicalSpec, kind, trigger }   // a ripple went stale
{ type: "spec.ripple-acked",  specId, actor, reason }                                 // staleness acknowledged
```

**Resolved linkage on the read model:**
```typescript
type ResolvedRipple = { repo: string; spec: string; kind: "delta" | "pointer";
  projectId?: string; status: "resolved" | "unresolved"; stale?: boolean; reason?: string };
type ResolvedCanonical = { repo: string; spec: string; projectId?: string; status: "resolved" | "unresolved" };
```

### Cross-cutting

- **Governance (rule 3):** a pointer stub is a projection write — deterministic, logged, and landing as a
  change to commit in the target repo, never a silent write to a system of record and never bypassing review
  there. Delta-ripple staleness requires an explicit, recorded acknowledgement — a cross-repo contract change
  is never absorbed silently.
- **Isolation (SPEC-018 / NFR-1):** all cross-context work is supervisor-brokered and executed by the target
  context on its own files/trace; unregistered repos degrade to inert references. No context reads a peer's
  files.
- **Lifecycle (SPEC-024):** the staleness cascade is best-effort — it never fails the canonical's own
  transition, and linkage frontmatter persists across delivery (a standing relationship, not a `delta:` tag,
  so `flattenDeltaTags` leaves it untouched).
- **Design template:** the ripple/staleness UI follows the `arke-design` skill (`.claude/skills/arke-design/`).
- **Multi-project scoping (SPEC-018):** every op resolves against the caller's **active project**; cross-repo
  reach is only ever to *registered* peers via the supervisor.

  generated pointer stub).

### Testing
- **Unit:** `parseLinkage` (valid nested ripples/canonical; malformed → warning, not throw; a plain spec →
  empty); the `slug → projectId` index + `resolve` (registered vs unresolved); pointer-stub content is
  deterministic + idempotent (same canonical → byte-identical); staleness transition on `isMaterialChange`;
  `ackRipple` refuses a non-stale spec.
- **Integration (two registered project contexts via the supervisor):** a canonical change in A marks B's
  resolved delta ripple stale (event + B-trace); `spec.ripple.ack` in B clears it and is traced in B;
  `spec.ripple.project` writes/refreshes a pointer stub into B (B-trace) and is idempotent; an unresolved
  ripple is inert (no write, no cascade) and the canonical transition still completes.
- **Manual:** hand-edited stub regenerated loudly; unregistered repo renders inert in the library/board.

### Definition of done
All scenarios pass; linkage parses (nested), resolves via the git-remote slug index, and renders in the library
and on cards for the active project; stub generation and staleness acknowledgement each appear in the **correct
(target/affected) project's** trace; the canonical's own lifecycle never breaks on an unreachable ripple;
linkage persists across delivery; `typecheck` + `build` green; a non-author reviewer has signed off.

## Decision log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Linkage in frontmatter, not coordinator state | Spec stays the source of truth; reviewable in the same PR; meaningful without Arke running (ADR 0005) |
| 2 | Two ripple kinds only — authored `delta` or generated `pointer` | Matches ADR 0005; anything in between is a disguised copy |
| 3 | `repo` is a portable `org/repo` **git-remote slug**, resolved to a `projectId` via a supervisor index | The slug is human-readable and stable across machines; `projectId = hash(root)` is opaque and machine-local. Resolves OQ1 |
| 4 | Pointer projection is **explicit** (`spec.ripple.project`) for v1; a material canonical change marks pointer ripples stale to signal a refresh is due | Keeps the cross-repo write human-triggered/governed; auto-on-merge (webhook) is a later enhancement. Resolves OQ2 |
| 5 | Canonical approval does **not** hard-gate on ripple status; staleness/unresolved surface at approval | Hard cross-repo gates are brittle (peer may be unregistered/lagging); surfacing meets the ADR obligation without coupling two repos' lifecycles. Resolves OQ3 |
| 6 | Linkage frontmatter **persists** across delivery (does not flatten like a `delta:` tag) | `ripples:`/`canonical:` are standing relationships, true after delivery — not per-branch deltas. Resolves OQ4 |
| 7 | Cross-context work is **supervisor-mediated**, executed by the target context on its own files/trace | SPEC-018 isolation: a context never reaches into a peer's filesystem; the supervisor brokers, the peer acts |
| 8 | The staleness cascade is **best-effort** — it never fails the canonical's own transition | A cross-repo signal must not make a single repo's governed lifecycle brittle |

## Open questions (deferred)
- **Auto-projection on canonical merge** (webhook-triggered stub refresh) — deferred to a follow-up; v1 is
  explicit `spec.ripple.project` with staleness as the signal (Decision #4).
- **Hard lifecycle coupling** (canonical approval blocked until delta ripples reach in-review) — deferred as a
  stronger, team-tier governance mode (Decision #5).
- **Repo-less / org-wide canonical** (a canonical owned by no implementation repo, ADR 0005 decision 4) — out
  of scope for v1; a separate convention.
- **`org/repo` slug canonicalisation** across remote forms (SSH vs HTTPS, `.git` suffix, host variations) — v1
  normalises to `host/org/repo` lowercased without `.git`; edge remotes may need a registry-assisted alias map.
